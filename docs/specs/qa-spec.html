Section 01

Overview & Quality Philosophy

1.1 Why Quality Is Non-Negotiable

Finance Bag manages its users' most sensitive personal data: income, debts, savings, financial goals, and spending habits. A single bug that miscalculates a debt payoff projection, corrupts a monthly archive, or silently fails to encrypt a backup does not merely frustrate a user — it destroys trust in an application that must be as reliable as a bank statement.

Quality in Finance Bag is therefore a product requirement with the same priority as features. It is designed in from the first line of development, measured continuously, and enforced as a hard release gate. It is never a final verification step.

1.2 Core Quality Values

ValueDefinitionPrimary Test Enforcement
ReliableThe app behaves correctly under all documented conditions. No silent failures, no data loss.Unit tests, integration tests, E2E critical path tests
PredictableThe same action always produces the same result. Calculations are deterministic. UI states are consistent.Business rule tests, regression suite
SecureFinancial data is protected at rest and in transit. No unauthorized access is possible.Security testing, encryption verification, penetration testing
ConsistentUI, formatting, language, and behavior are consistent across all modules and both platforms.Manual visual regression, localization tests
RecoverableEvery failure mode has a recovery path. No operation leaves data in an unresovlable corrupt state.Edge case tests, chaos scenarios, backup/restore tests

MaintainableThe test suite is as maintainable as the production code. Flaky tests are treated as bugs.Code quality gates, test coverage thresholds

1.3 Scope

This specification covers the complete quality assurance strategy for Finance Bag v1.0 across all 15 modules. It defines:

  • The testing architecture and pyramid
  • Per-module quality objectives and test requirements
  • Business rule validation strategies
  • Edge case, security, performance, and usability testing
  • Automation versus manual testing strategy
  • Release readiness criteria and checklist
  • Quality metrics, bug management, and documentation standards
  • Future CI/CD and device farm integration path
Out of scope: This document does not specify test implementation code, test framework configuration files, or CI pipeline YAML. Those are implementation artifacts. This spec defines what must be tested, why, and to what standard — not how it is implemented.

2.3 Test Data Strategy

Seeded Test Datasets:
Finance Bag uses deterministic seeded test data — never random, never real user data in test environments. Four standard datasets are defined:

DS-EMPTY: Fresh install, no data. Tests onboarding, empty states, and first-time flows.
DS-MINIMAL: 1 budget, 3 transactions, 1 goal, no debt. Tests basic flows without complexity.
DS-STANDARD: 3 budgets, 12+ categories, 60+ transactions, 2 goals, 1 debt. Representative of a 3-month active user.
DS-HEAVY: 10+ budgets, 500+ transactions, 5 goals, 3 debts, 24 months of history. Stress-tests performance, reports, and archive navigation.
DS-EDGE: Boundary values, zero balances, maximum amounts, all-categories-at-once, multi-currency, near-full storage. Tests edge cases and limits.

Data isolation: Every test run starts with a clean database state from the appropriate dataset. Tests must never depend on state left by a prior test. Cross-test contamination is a test defect.

Section 03

Static Analysis & Code Quality

Static analysis is the cheapest quality layer — it catches defects before any code runs. All static analysis gates are enforced in pre-commit hooks and CI. A failing static analysis gate blocks the entire pipeline.

3.1 TypeScript Strict Mode

Required TypeScript compiler flags (all must be enabled):
strict: true (enables all strict checks as a group)
noUncheckedIndexedAccess: true — prevents silent undefined from array/object access
exactOptionalPropertyTypes: true — distinguishes undefined from absent property
noImplicitOverride: true — requires explicit override keyword
noPropertyAccessFromIndexSignature: true — prevents silent any from index access

Zero tolerance: @ts-ignore and @ts-expect-error are forbidden except in explicitly documented compatibility shims. Each exception requires a comment explaining the specific library constraint and a ticket to resolve it.

3.2 Linting Rules

3.4 Dependency Audit

  • Every third-party dependency is scanned for known CVEs on every CI run
  • High-severity CVEs block the pipeline immediately; medium-severity CVEs block the next scheduled release if unpatched
  • Dependency licenses are audited: GPL-licensed packages are prohibited in the commercial build; MIT, Apache 2.0, and BSD are permitted
  • No dependency may be added without a corresponding entry in the dependency rationale log (why this package, what it replaces, maintenance status)
  • Packages with zero commits in the past 24 months are flagged for replacement review

3.5 Secret Scanning

Every commit is scanned for accidentally committed secrets (API keys, tokens, passwords, private keys). The scan pattern library covers:

  • Generic API key patterns (high-entropy strings in key/token/secret variable names)
  • Common service-specific patterns (AWS, Google Cloud, Stripe, OpenAI, etc.)
  • Private key headers (-----BEGIN RSA PRIVATE KEY-----, etc.)
  • Connection strings with embedded credentials
Zero tolerance: Any committed secret, even in a feature branch, triggers immediate pipeline failure, secret rotation, and a security incident report. "It was just a test key" is not an acceptable justification — test environments use environment variables, never committed values.
Section 04

Unit & Component Testing

4.1 Unit Testing Scope

Unit tests verify isolated business logic with no external dependencies. Every unit test is synchronous, deterministic, and requires no device, network, or database. The unit test suite is the primary quality assurance mechanism for financial calculation correctness.

What must have unit tests (mandatory):
• All financial calculation functions (budget remaining, debt payoff projection, savings rate, goal progress, FHS score, emergency fund coverage)
• All business rule enforcement functions (allocation validation, duplicate detection, constraint checking)
• All data transformation functions (formatters, parsers, serializers, normalizers)
• All sorting and filtering logic
• All date/time utility functions
• All sync conflict resolution algorithms (all 7 conflict types from SPEC-OFL-001)
• All AI rule-based recommendation logic (Hybrid and Rule-Based modes from SPEC-AIC-001)
• All encryption utility functions (wrap/unwrap operations, not the crypto primitives themselves)
• All state reducers and selectors (Zustand stores)

What does NOT need unit tests:
• Third-party library internals
• Configuration files
• Purely declarative JSX with no logic
• Database schema definitions (tested by integration tests)

4.2 Unit Test Anatomy

Every unit test follows the Arrange-Act-Assert (AAA) pattern. Test names use the format: "[functionName] [scenario description] [expected outcome]".

Test Name PatternExample
[fn] when [condition] returns [result]"calculateBudgetRemaining when spent exceeds limit returns negative value"
[fn] with [input] throws [error type]"parseCurrencyAmount with null input throws InvalidAmountError"
[fn] with [boundary value] handles correctly"applyDebtPayment with zero payment handles correctly"
[fn] given [state] produces [output]"resolveSyncConflict given LWW strategy produces server-side value"

4.3 Financial Calculation Test Requirements

Financial calculation tests must cover the following scenario categories for every calculation function:

Snapshot testing policy: Snapshot tests are used only for leaf-level presentational components with no interactive logic. Snapshots are reviewed on every change — "update snapshot blindly" is forbidden. Every snapshot update requires a visual diff review comment in the PR.

Section 05

Integration Testing

Integration tests verify that multiple subsystems work correctly together. They operate on an in-process SQLite database (using the same schema as production) and do not require a running device or network.

5.1 Integration Test Scope

Integration SurfaceWhat Is Tested
Business Logic ↔ DatabaseCRUD operations produce correct database state; reads return correct calculated values; soft deletes work correctly; ULID ordering is preserved
State Management ↔ DatabaseZustand store actions result in correct DB writes; DB reads populate store state correctly; optimistic updates reconcile correctly
Sync Queue ↔ DatabaseOperations are enqueued correctly; conflict resolution produces correct merged state; retry logic advances correctly; dead operations are flagged
Monthly Archive ↔ Live DataArchive generation captures correct snapshot; post-archive live data is isolated; archive retrieval returns frozen data correctly
Encryption ↔ DatabaseEncrypted fields are unreadable without key; decrypted fields match original values; key rotation produces correct results
Notification Scheduler ↔ Business RulesNotifications are scheduled at correct times; trigger conditions produce correct notification content; dismissed notifications respect cooling period
AI Layer ↔ Financial ContextFinancialContextBuilder produces correctly anonymized payload; rule-based recommendations use correct input data; AI memory reads and writes correctly

5.2 Database Integration Requirements

Every database integration test must verify:
1. Schema integrity: All required columns exist; constraints are enforced (NOT NULL, FK, CHECK)
2. ULID ordering: Records inserted in sequence have monotonically increasing ULIDs
3. Soft delete isolation: Soft-deleted records do not appear in standard queries
4. Integer arithmetic: All monetary fields store and retrieve centimes without precision loss
5. Vector clock: Sync operations correctly increment and compare vector clocks
6. Transaction rollback: Failed multi-step operations leave the database in its pre-operation state
7. Index performance: Common query patterns use indexes (verified by query plan analysis)

5.3 Sync Integration Testing

The sync system (SPEC-OFL-001) has the highest integration complexity. The following scenarios must be covered by dedicated integration tests:

  • Create operation enqueued while offline → processed when online → remote reflects change
  • Update on device A and device B for same record → conflict detected → LWW resolution applies correct winner
  • Delete on device A + Edit on device B for same record → Delete-Wins resolution → record is archived
  • Sync interrupted mid-flight → retry from IN_FLIGHT → correct completion without duplication
  • 5 retry attempts exhausted → operation marked DEAD → correct error state surfaced to user
  • Full epoch sync → all local data replaced with server state → local-only records are preserved
  • Phase 1 preference sync → only app preferences transferred → no financial data in payload

8.5 Financial Health Score Rules

FHS validation approach:
The Financial Health Score is composed of 8 dimensions (per SPEC-AIC-001). Each dimension contributes a weighted score component. The following validations are required:

1. Score range: FHS must always produce a value 0–100. No input combination can produce a value outside this range.
2. Weight sum: The sum of all 8 dimension weights = 1.000 (verified as a constant, not computed at runtime).
3. Dimension independence: Changing one dimension's input only affects that dimension's score component, not others.
4. Perfect score conditions: A synthetic DS-PERFECT dataset produces exactly 100; validate this is achievable.
5. Zero-data behavior: DS-EMPTY produces "Insufficient data" state, not a score of 0 (which would be misleading).
6. Score monotonicity: Improving a dimension (e.g., increasing savings rate) never decreases the overall FHS.

11.3 Battery Impact Testing

Battery impact methodology:
Battery testing uses a standardized 30-minute usage session on a device at 80% charge, with screen at 50% brightness, in a controlled temperature environment (22°C). The session follows a scripted pattern representing a realistic power user session.

Battery consumption targets:
• Active 30-minute session: <5% battery drain (reference: YouTube streaming ≈ 8–12%)
• Background sync (10 operations, Wi-Fi): <0.5% battery drain
• Background sync (10 operations, cellular): <1.0% battery drain
• App at rest for 1 hour (locked): <0.2% battery drain (negligible background activity)

Battery drain red flags:
• Any background location access (Finance Bag must never request location)
• Continuous background network polling (must use push-triggered or scheduled sync only)
• Retained high-frequency timers after app background

11.5 Performance Testing Approach

  • All benchmarks are run on the minimum-spec supported device (iPhone SE / Galaxy A15) — if it meets targets there, it will exceed them on higher-end devices
  • Performance tests run with all standard developer optimizations enabled (production build, not debug build) — debug builds are not valid performance proxies
  • Each metric is measured 5 times; the median value is the reported figure; the 95th percentile must also meet the hard limit
  • Performance regression: any metric that degrades more than 20% from the prior release baseline is treated as a P2 defect and blocks release unless justified
  • Flamegraph profiling is performed for any metric that exceeds its target during testing — the root cause must be identified before shipping

Section 13

Automation Strategy

Automation decisions are made on a cost-benefit basis. Tests that are high-value, stable, and fast gain the most from automation. Tests that require visual judgment, emotional response, or contextual interpretation must remain manual.

13.1 Automation Decision Framework

A test should be automated when:
• It verifies logic that can be expressed as deterministic input → output
• It would need to run on every PR (too expensive to run manually at that cadence)
• It tests a regression that has occurred before (every past bug earns an automated regression test)
• It tests a business rule that must remain invariant regardless of other code changes
• Its failure mode is binary (pass/fail) and human judgment is not needed to interpret the result

A test must remain manual when:
• It requires visual judgment (chart alignment, animation smoothness, color accuracy)
• It tests emotional/experiential quality (onboarding feels welcoming, AI coach feels helpful)
• It requires physical device-specific behavior (biometric sensor, haptic feedback quality)
• It validates legal or compliance language that must be reviewed by a human
• Its maintenance cost exceeds its defect-detection value (rare, complex E2E paths)

13.4 Flaky Test Policy

Definition: A flaky test is one that produces different results on the same code without any code change. Flaky tests are a quality liability — they train developers to ignore red builds, masking real failures.

Policy:
• Any test that fails intermittently more than 1 time in 10 runs is classified as flaky
• Flaky tests are immediately quarantined (removed from the required pass gate) and filed as P2 defects
• The root cause must be identified within 2 sprint cycles: either fix or delete
• A test that is permanently flaky due to timing/environment issues and cannot be made deterministic must be removed and replaced with a more focused unit test
• The flaky test backlog is reviewed in every sprint retrospective

16.4 Required Bug Report Fields

Every bug report must include:
1. Title: Clear, specific description (not "App crashes" — "App crashes when entering €0 transaction amount in Budget module")
2. Severity: S1–S4 (initial reporter assignment; revised by QA Lead in triage)
3. Environment: Device model, OS version, app version, locale, dataset state
4. Reproduction steps: Numbered, minimal steps from a clean state
5. Expected behavior: What should happen
6. Actual behavior: What actually happens
7. Frequency: Always / Sometimes / Rarely — and conditions observed
8. Attachments: Screen recording (strongly preferred over screenshots); crash log if available
9. Regression: Was this working in a prior version? Which version?

16.5 Root Cause Analysis (RCA)

Every S1 bug and every regression (a bug that was previously fixed and reoccurred) requires a written Root Cause Analysis before closure. The RCA answers:

  1. What happened? — Technical description of the defect
  2. Why did it happen? — The root cause (not the symptom)
  3. How did it escape testing? — Gap in test coverage or process
  4. What prevents recurrence? — Automated test added, process change, code review rule added
  5. Could similar bugs exist elsewhere? — Horizontal search for the same pattern in other modules
Section 17

Documentation Standards

Quality without documentation is not quality — it is luck. Documentation ensures that quality practices are repeatable, transferable, and improvable across team changes and release cycles.

17.1 Test Plan

Test Plan — required sections:
1. Scope: What features/modules are being tested in this plan
2. Out of scope: What is explicitly excluded and why
3. Test approach: Which layers of the pyramid are active for this plan (unit, integration, E2E, manual)
4. Entry criteria: Conditions that must be true before testing begins (build available, test data seeded, environment verified)
5. Exit criteria: Conditions that define test completion (all cases run, coverage target met, no open S1 bugs)
6. Resource requirements: Devices, team members, estimated time
7. Risk assessment: High-risk areas with rationale; mitigation approach
8. Defect management: How bugs found in this plan will be triaged and tracked

17.2 Test Case Format

Standard test case fields:
• TC ID: Unique identifier (e.g., TC-BUD-042)
• Module: Module being tested
• Title: What is being validated, in one sentence
• Preconditions: Dataset, device state, user state before test begins
• Steps: Numbered, specific, reproducible steps (no ambiguity)
• Expected result: What must be true after the last step
• Priority: Must-run / Should-run / Nice-to-run
• Automation status: Automated / Manual / To-be-automated
• Last run date and result: Pass / Fail / Blocked / Skip
• Notes: Platform-specific behavior, known workarounds, related bugs

17.3 Release Notes

Release notes structure (user-facing):
• Version number and release date
• "What's New" — new features or capabilities (user-language, not technical)
• "Improvements" — performance, usability, or reliability improvements users will notice
• "Bug Fixes" — list of fixed issues that users were likely to have encountered (no internal IDs; plain language)
• "Known Limitations" — honest disclosure of known issues in this release with workarounds where available

Release notes structure (internal, engineering):
• All public sections above
• Complete list of merged PRs with ticket references
• Database schema changes (migrations applied)
• API contract changes (sync API version, if changed)
• Test coverage delta from previous release
• Performance benchmark comparison table (current vs prior release)

Section 18

Future Scalability & Business Rules

The QA framework is designed to accommodate the full maturity path from manual-first v1.0 testing to a fully automated, continuous delivery pipeline. No redesign of the quality framework should be required to adopt any of the following capabilities.

18.1 Continuous Integration (Ready in v1.0)

The CI pipeline (already designed for v1.0) runs on every PR:
1. Secret scan + dependency audit (L1 — ~15s)
2. TypeScript compilation (L1 — ~30s)
3. ESLint (L1 — ~20s)
4. Unit tests + coverage gate (L2 — ~60s)
5. Component tests + snapshot review (L3 — ~2min)
6. Integration tests (L4 — ~8min)
7. Coverage report published to PR
8. Gate: all must pass; any failure blocks merge

Total CI time target: <12 minutes
CI must never become a bottleneck on developer velocity. If it exceeds 15 minutes, parallelization or pruning is required.

18.2 Continuous Delivery (Planned v1.5)

  • Release candidate builds automatically generated on merge to release branch
  • E2E test suite runs automatically on every RC build in the staging environment
  • Performance benchmarks run automatically and compared to baseline; regression alerts sent
  • Successful E2E + performance run automatically submits to TestFlight / Google Play Internal Testing
  • Final human approval gate required before any production deployment — CD automates, humans approve

18.3 Device Farm Integration (Planned v1.5)

The E2E test suite is designed to run on physical device farms without modification. The device farm adds:

CapabilityValueRequirement
Parallel execution on 6+ devices simultaneouslyE2E suite time reduced from 90min to ~15minE2E tests must be stateless and parallelizable (they are, by design)
Real device coverage (20+ device models)OEM-specific rendering bugs caughtDS-STANDARD dataset deployable to all farm devices
Network condition simulationOffline, 2G, 3G, 4G, packet loss scenarios testedNetwork simulation API integration in test harness
Video recording of every runFailure evidence without reproducing manuallyTest runner must support video artifact capture

18.4 Beta Testing Framework (Planned v1.0 launch)

Structured beta program:
• Internal beta: All team members; immediate on every RC build via TestFlight / Play Internal
• Closed beta (50 users): Recruited from target user profiles (young Algerian professionals); 4-week program; structured feedback sessions
• Open beta (App Store / Play Store): Available 2 weeks before general release; crash reports monitored in real-time

Beta feedback process:
1. In-app feedback button available in beta builds (sends structured report: screen + user-entered description)
2. Weekly beta feedback review session: categorize by module, severity, frequency
3. All S1/S2 issues from beta must be resolved before general availability

18.5 Crash Analytics Integration (v1.0)

  • Crash reporting integrated from day 1 — not retroactively after a crash occurs
  • Crash reports are symbolicated (stack traces reference source lines, not minified bundle addresses)
  • Crash grouping: crashes are grouped by root cause, not by individual occurrence, to surface the most impactful issues first
  • Breadcrumb logging: the last 20 user actions before a crash are captured to aid reproduction (financial values are never in breadcrumbs — only action types and screen names)
  • Alert threshold: PagerDuty (or equivalent) alert triggered if crash rate exceeds 0.5% in any 15-minute window

18.6 Feature Flags (Planned v1.5)

Feature flags allow new features to be deployed to production without being activated, enabling controlled rollouts and instant rollback without an app release.

Feature flag requirements for QA:
• Every feature flag must have a test that verifies behavior in both the enabled and disabled states
• Feature flags that gate financial calculations must have integration tests for both states
• No feature flag can disable a security, encryption, or authentication feature — those are always-on
• Feature flags are evaluated at startup and cached for the session — no mid-session flag changes
• The QA release checklist includes verification that all planned-off flags are correctly off in production

18.7 A/B Testing Considerations (Planned v2.0)

  • A/B testing applies only to UX and onboarding flows — never to financial calculation logic
  • Test groups must be stable (same user always in same group for the duration of the experiment)
  • A/B test variants must each pass all accessibility requirements independently
  • Statistical significance threshold: 95% confidence; minimum sample size calculated before experiment launch
  • A/B test results reviewed by Product and QA before any variant is promoted to default
