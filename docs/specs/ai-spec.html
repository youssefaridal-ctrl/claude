1. Overview & Philosophy

1.1 Role of the AI Layer

The AI Financial Coach is an independent intelligence layer layered on top of Finance Bag's financial data. It reads, analyzes, and interprets financial state to generate insights, predictions, and personalized guidance. It is never a replacement for the user's own judgment — it is a thinking partner that helps users understand their financial situation more deeply and act on it more confidently.

The AI layer is a consumer of financial data, not a producer of it. It never writes to the financial database. Every action it proposes must be explicitly approved by the user and executed through the standard business layer. This separation is fundamental to correctness, trust, and auditability.

2.3 Data Flow

Every AI interaction follows this sequence:

  1. User triggers AI — via NL query, dashboard insight tap, coaching session start, or background schedule.
  2. Intent classification — NL layer routes the request to the appropriate engine (coaching, recommendation, prediction, simulation, explanation).
  3. Context assembly — Data Layer (FinancialContextBuilder) assembles the minimum financial context required for this intent type.
  4. Memory retrieval — Memory Layer supplies relevant user preferences, coaching history, and recent interactions.
  5. Engine processing — Rule engine and/or LLM generates raw output.
  6. Explainability attachment — ExplainabilityContext is assembled and attached to every output object before delivery.
  7. Recommendation lifecycle — If output contains recommendations, they pass through the Recommendation Layer (ranking, deduplication, expiry check).
  8. Presentation formatting — Presentation Layer formats the output for the target UI component.
  9. Memory update — Session context is updated; if interaction contains feedback signal (accept/dismiss), Memory Layer records it.

3.2 Context Payload Specification

For remote AI calls (v2.0+), the FinancialContextBuilder produces a FinancialContext payload with the following constraints:

  • Maximum payload size: 32KB. Any context exceeding 32KB triggers automatic summarization (older periods summarized, recent periods kept in detail).
  • Data freshness: All context reflects the state of the financial database as of the moment the AI request is initiated. Stale context from cache is never used for recommendations.
  • Anonymization transforms: Before any remote AI call — amount rounding to nearest currency unit (no centimes in prompts), goal names replaced with sequential labels ("Goal 1", "Goal 2"), no user-entered text fields, no personal identifiers (no name, email, device_id).
  • Context versioning: The payload includes a context_version field. Prompt templates are versioned to match. A mismatch causes the AI call to abort (use rule-based fallback).
  • Selective assembly: Each AI operation type specifies a ContextRequirement declaration. The FinancialContextBuilder only assembles the declared fields. An expense-category query does not include debt data.

3.3 Data Access Permission Model

AI data access is controlled by the same permission system as the rest of the application:

  • The AI layer is authenticated as a P1 (standard access) internal component. It cannot trigger P2 (re-auth) operations.
  • If the user has set AI to disabled (aic.enabled = false), the FinancialContextBuilder returns an empty context and all AI methods return empty results immediately.
  • If the user has set remote AI to disabled (aic.remote_enabled = false), the Provider Layer routes all calls to the local rule-based provider. The LLM provider is never called.
  • Data access for AI follows the same soft-delete rules as the rest of the app: deleted records (deleted_at IS NOT NULL) are excluded from AI context unless the user explicitly asks about historical deleted data.

4.2 Monthly Coaching Session Flow

The primary coaching interaction is the Monthly Financial Review, triggered automatically at period end or manually from the dashboard. It follows a structured 7-step flow that adapts to the user's financial situation:

  1. Opening assessment: Compare this period's Financial Health Score to last period. Lead with the most significant change (positive or negative). If FHS improved: celebrate specifically ("Your emergency fund grew from 1.2 to 1.6 months of coverage — great progress"). If FHS declined: name the cause without blame ("Your budget utilization rose to 118% this period — let's look at where").
  2. Budget debrief: Review each category: over-budget (explain what the variance was, ask if it was expected or unexpected), under-budget (celebrate and suggest redirection), on-target (brief acknowledgment). Focus on the 2 largest variances, not all categories.
  3. Cash flow summary: Show the period's income vs. total expenses, residual, savings amount. Compare to the previous 3 periods. Name the trend direction.
  4. Debt status update: If user has debt — progress since last period, interest paid vs. principal paid, months remaining at current pace. Name the single most impactful action available.
  5. Goal progress check: For each active goal, report % complete and projected completion date. Flag goals that are off schedule. Prioritize goals with upcoming deadlines.
  6. Recommendation delivery: Present the top 3 ranked recommendations for the upcoming period. Each includes reason, expected benefit, trade-off, and a single action to take. Do not present more than 3 recommendations in a single coaching session — information overload reduces action rate.
  7. Closing commitment: Ask the user to commit to one specific action from the recommendations. Record their choice as a coaching_commitment in the AI memory. Follow up next period on whether it was completed.

4.4 Coaching Tone Rules

The following tone rules are enforced across all coaching output, regardless of operating mode. In Rule-Based mode, template selection enforces these rules. In LLM mode, these rules are included in the system prompt and validated post-generation.

  • Never shame: Phrases like "you failed to", "you didn't manage to", "you wasted", "you should have" are prohibited.
  • Always contextualize setbacks: Every negative observation pairs with a cause ("Your spending rose because of the holiday period — this is common") and a path forward ("Here's how to prepare next time").
  • Celebrate specifically: Generic praise ("Good job!") is less effective than specific praise ("You kept food spending 8% under budget for 3 consecutive periods — that's meaningful consistency").
  • Use "we" language for challenges, "you" for achievements: "Let's look at where we can reduce" vs. "You grew your emergency fund by 40% this year".
  • No comparisons to others: "Most people save X%" is prohibited. The only relevant benchmark is the user's own history.
  • Acknowledge constraint: If the user has limited income or high fixed expenses, acknowledge the constraint before recommending ("With your current fixed costs at 78% of income, there's limited room — here's how to maximize what's available").

5. Recommendation Engine

5.1 Recommendation Lifecycle

Recommendations pass through five stages. A recommendation that skips any stage is invalid.

  1. Detect: The AI engine identifies a financial pattern, gap, or opportunity in the user's data. Triggered by: period-end analysis, real-time threshold breach (e.g., budget category hits 90%), scheduled review, user NL query, or new data event (new debt added, goal created).
  2. Generate: The engine produces a Recommendation object with all required fields (§5.2). In Rule-Based mode, templates are selected and parameterized with the user's actual data. In LLM mode, the template is the starting point and LLM adds nuanced phrasing.
  3. Rank: The Recommendation Layer assigns a display rank based on the priority × confidence matrix (§5.4). Up to 3 recommendations are surfaced at once. The rest wait in queue.
  4. Present: Presentation Layer renders the recommendation with all ExplainabilityContext fields accessible (collapsed by default, expandable on tap).
  5. Track: User interaction is recorded: accepted (tapped the CTA), dismissed (swiped away), snoozed (reminded later), ignored (no interaction for 7 days). Outcome feeds the Memory Layer and future ranking.

5.5 Deduplication and Freshness

  • Deduplication: If a recommendation with the same category + target entity + action is already ACTIVE (not yet expired, accepted, or dismissed), no duplicate is generated. The existing recommendation may be refreshed with updated numbers.
  • Acceptance tracking: If a recommendation is accepted but the underlying condition persists after one period, the recommendation may be re-generated. It is not re-generated if the user has acted on it (e.g., actually redirected the budget).
  • Dismissal cooling: If a recommendation is dismissed, it is suppressed for 14 days before being considered again. A second dismissal suppresses it for 30 days. A third dismissal marks it PERMANENTLY_DISMISSED for this user.
  • Expiry: Recommendations have a hard expiry (expires_at field). Expired recommendations are archived to ai_recommendations with status EXPIRED, not shown to the user. They are used as training signal (user didn't act before it was irrelevant).

  • A9: No large one-time expenses or income events occur.

6.4 Prediction Accuracy Feedback Loop

The system compares past predictions to actual outcomes to improve confidence calibration:

  • After each period closes, the AI compares its 1-period-ahead prediction to actual results (e.g., predicted cash flow residual vs. actual).
  • Prediction error (absolute and directional) is stored in ai_memory with type PREDICTION_ACCURACY.
  • If the rule-based model has consistently overestimated savings for 3+ periods, confidence is automatically downgraded from High to Medium for savings predictions.
  • In v2.0+, this feedback is available as a signal to the LLM prompt ("The rule-based model has underestimated food spending by 15% on average — consider adjusting").

7. What-If Simulation Engine

7.1 Simulation Architecture

What-If simulations are non-destructive projections. They take a snapshot of the current financial state, apply a hypothetical change (the delta), recalculate predictions under the modified scenario, and compare results to the baseline (current trajectory). The simulation never writes to the financial database.

The simulation flow is:

  1. Baseline snapshot: Capture the current prediction outputs (savings trajectory, debt payoff dates, goal completion dates, FHS forecast) as the comparison baseline.
  2. Delta application: Apply the scenario change to the snapshot (e.g., increase salary by 10%, add a $200/month extra debt payment).
  3. Re-projection: Run all relevant prediction models against the modified snapshot. Use the same algorithms as the standard prediction engine — simulations are not approximations.
  4. Delta computation: For each projection dimension, compute: (simulated value) − (baseline value). Express as both absolute amount and percentage change.
  5. Impact narrative: Generate a plain-language summary of the most significant changes: "A 10% salary increase shortens your debt payoff by 14 months and adds $4,200 to annual savings."
  6. Result presentation: Show baseline vs. simulated side by side with a "What changes" list highlighting the most impactful deltas.

7.3 Simulation Constraints

  • Maximum active simulations: 5 simultaneously. When a 6th is requested, the oldest is discarded. Simulations are session-level by default (not persisted between sessions) — users can save up to 3 named simulations to app_state.saved_simulations_json.
  • Scenario combination: Multiple scenario changes can be combined in one simulation (e.g., salary +10% AND extra $200/month debt payment). There is no limit on the number of changes within a single simulation run.
  • Non-destructive guarantee: The simulation uses an in-memory copy of the financial snapshot. The original database is never modified. All simulation data is discarded when the simulation view is closed.
  • Recalculation target: All projections must recalculate within <500ms of the user adjusting a simulation parameter. This target applies in Rule-Based mode. LLM-enhanced narrative generation may take longer but projections are shown immediately with narrative following.
  • Assumption transparency: The same assumption catalog (§6.3) applies to simulations. The scenario delta replaces the relevant assumption (e.g., scenario "Salary +10%" replaces A1 and A7 with the new salary value).

8.2 Query Processing Pipeline

  1. Input normalization: Lowercase, remove punctuation artifacts, handle common misspellings. Max query length: 500 characters. Truncate beyond 500 with user notification.
  2. Intent classification: Rule-Based mode uses keyword matching and pattern templates. LLM mode uses classifyIntent() method. Confidence threshold for classification: 0.7. Below 0.7: prompt for clarification.
  3. Entity extraction: Identify referenced entities (specific goal by name, specific debt, specific budget category, specific time period). Link to actual database records.
  4. Context assembly: FinancialContextBuilder assembles context specific to the detected intent and entities.
  5. Response generation: Route to appropriate engine. Generate response following the response format spec (§8.3).
  6. Conversation history update: Add the query and response to session-level conversation history (max 20 turns, not persisted beyond the session unless user explicitly saves the conversation).

8.3 Response Format Specification

Every NL response must contain all three components. Partial responses are not acceptable:

  • Direct answer: The specific answer to the question, in the first sentence. Never bury the answer after a preamble. Bad: "That's a great question! Let's look at your finances…" Good: "You saved $1,240 last month — 18.5% of your income."
  • Supporting data: 2–3 data points that substantiate the answer, drawn from the user's actual financial records. Cited by category and period. No vague references ("recently", "sometimes") — always specific ("in the last 3 periods", "in October 2025").
  • Suggested follow-up: 1–2 suggested next questions or actions the user might find useful given their query. These are short (tap-able chips in the UI) and contextually relevant. Do not suggest more than 2 — choice overload reduces engagement.

8.5 Conversation Context

The NL interface maintains a session-level conversation history to support multi-turn queries:

  • Context window: Last 20 turns (query + response pairs). Older turns are summarized, not discarded — a 2-sentence summary of earlier context is prepended to the LLM prompt.
  • Reference resolution: "What about my car loan?" after a general debt query resolves "car loan" against the previously discussed debt entities.
  • Pronoun resolution: "How close is it to completion?" after asking about a goal resolves "it" to the last mentioned goal.
  • In Rule-Based mode, conversation context is limited to the current query (no multi-turn resolution). A "Tell me more" follow-up repeats the previous query's topic but does not chain context.
  • Conversation history is session-scoped — it is not persisted to the AI memory table unless the user explicitly saves the conversation.

9.3 Prohibited Patterns (Anti-Explainability)

The following patterns undermine explainability and are prohibited in all AI output:

  • Vague triggers: "Based on your spending patterns" without citing which specific pattern. Required: "Because your dining spending has exceeded budget in 4 of the last 6 months."
  • Unsourced claims: "Most people in your situation save more." Prohibited — no peer comparison, no unsourced benchmarks.
  • Confidence washing: Presenting a LOW confidence prediction with the same visual treatment as a VERY_HIGH confidence one. Confidence must be visually distinct (color, label, range vs. exact date).
  • Hidden assumptions: Making a projection that assumes salary continuity without disclosing it. All A1–A10 assumptions used in a prediction must appear in the output's ExplainabilityContext.assumptions field.
  • Magic recommendations: "This is what you should do" with no explanation. Every recommendation must include reason + expected_benefit + trade_off at minimum.
  • Overconfident language: "You will be debt-free in March 2028." Required: "At your current payment rate, you're on track to be debt-free around March 2028 (HIGH confidence, ±2 months)."

9.4 AI Label Visibility

Users must always know when content is AI-generated. The following labeling rules apply:

  • Every AI-generated card, insight, or message carries a subtle "AI insight" or "AI Coach" label. This label cannot be hidden by user preferences.
  • Rule-based insights are labeled "AI analysis" (to distinguish from LLM-generated content in future versions).
  • In Hybrid or Full AI mode, LLM-generated content is labeled "AI Coach" and includes the confidence indicator.
  • The label must persist even if the user customizes the dashboard — it cannot be lost through widget rearrangement or theme changes.

10.3 Non-Judgmental Feedback Model

Behavioral coaching is the highest-risk area for judgmental tone. The following model governs all behavioral feedback:

  • Separate behavior from identity: "Your spending in Dining Out exceeded budget" not "You overspend on dining". The behavior is what changed; the user is not defined by it.
  • Contextualize before coaching: Before any corrective coaching, acknowledge what went well that period. Even in a poor-performing period, find one positive signal to lead with.
  • Make setbacks informative: "Your food spending rose 34% this period — this often happens during holiday months. Next period you can prepare by setting a slightly higher food budget in advance."
  • Streaks are recognized, not weaponized: "You've saved consistently for 5 months — keep it going!" never becomes "You broke your 5-month saving streak this period." Loss framing is prohibited.
  • Celebrate progress at every scale: A 1% improvement in budget discipline is worth acknowledging if the user has struggled with it. The size of progress matters less than its direction.

12.2 Anonymization Transforms

Before any FinancialContext payload is transmitted to a remote AI provider, the following transforms are applied by the FinancialContextBuilder. These are mandatory — no remote AI call may bypass them:

  • Amount rounding: All monetary amounts are rounded to the nearest base currency unit (e.g., $1,234.56 → $1,235; $78.34 → $78). Centimes/cents are stripped from remote context.
  • Goal name replacement: Goal names are replaced with sequential labels: "Goal 1", "Goal 2", etc. The mapping is maintained in-memory for the duration of the AI call to allow response parsing. The mapping is never persisted.
  • Category name pass-through: Budget category names (Food, Transport, etc.) are transmitted as-is — they are system-defined, not user-entered. User-customized category names are replaced with the parent category name (e.g., "Mom's Birthday Dining" → "Dining Out").
  • Debt name anonymization: Debt names (e.g., "Chase Visa") are replaced with type-based labels ("Credit Card 1", "Personal Loan 1").
  • Date range generalization: Specific dates (salary dates, expense dates) are expressed as offsets within the period ("day 3 of period", "12 days before period end") not as calendar dates.

12.3 User Controls

The following AI privacy controls are available to users in Settings → AI Coach → Privacy:

  • Disable AI entirely (aic.enabled = false): No AI insights, recommendations, coaching, or NL queries. The AI Coach tab and all AI elements are hidden from the UI. Financial data is unaffected.
  • Disable remote AI (aic.remote_enabled = false): All AI operations use Rule-Based mode only. No data leaves the device for AI processing. LLM-specific features are disabled. Default: disabled until user opts in.
  • Disable behavioral tracking (aic.behavioral_tracking = false): Behavioral signals are not computed or stored. Behavioral coaching domain is disabled. Behavioral score component is removed from FHS calculation.
  • Disable AI memory (aic.memory_enabled = false): No Long-Term Memory is stored. AI operates stateless (no coaching commitments, no recommendation outcome tracking, no pattern personalization). Profile Memory (preferences explicitly set by user) is still stored.
  • Export AI data: Available at any time. Produces a JSON file of all ai_memory rows and AI-related app_state fields.
  • Delete all AI data: Full reset of all AI memory, preferences, and behavioral signals. Requires P2 authentication.

12.4 Provider Data Retention

When using a remote AI provider (v2.0+), the following data retention requirements apply to provider selection:

  • Finance Bag will only integrate providers that offer a zero-data-retention mode (no training on user data, no logs retained beyond the request duration).
  • Provider API calls are made with opt-out-of-training headers where available (e.g., OpenAI's training=false flag equivalent).
  • Provider selection criteria include: GDPR compliance, SOC 2 certification, data residency options, zero-log mode availability.
  • The user-facing Privacy Notice must disclose which provider is active when remote AI is enabled.
  • Provider changes require re-notification to users who have enabled remote AI.

12.5 On-Device AI Path (v3.0)

When on-device AI becomes available, it provides the same features as remote LLM without any data transmission:

  • On-device model selection criteria: maximum 2GB model size; inference latency <3s on a mid-range device for a typical query; quantized (INT4 or INT8) to reduce memory footprint.
  • The on-device model is downloaded once over Wi-Fi and stored in the app's document directory (excluded from iCloud backup to avoid backup quota impact).
  • Model updates are delivered via a background download, not bundled with app updates. The current model version is displayed in Settings → AI Coach → About.
  • On-device inference uses the same AIProvider interface as remote providers — the calling code is identical; only the Provider Layer implementation differs.

14. Future AI Compatibility

14.1 Provider Migration Path

The Provider Layer abstraction is the key architectural decision enabling provider portability. Migrating from one AI provider to another requires only a new Provider implementation — zero changes to the AI Layer, Prompt Layer, or any layer above.

The migration checklist for adding a new provider:

  1. Implement the AIProvider interface for the new provider (8 methods, §2.4).
  2. Map the provider's response format to Finance Bag's output types (AIInsight, Recommendation, AIExplanation, Prediction, SimulationResult, NLResponse, CoachingSession, IntentClassification).

  4. Register the new provider in the Provider Registry with a unique provider_id.
  5. Update the Prompt Layer with any provider-specific prompt formatting requirements (e.g., different system prompt structure, different tool-calling format).
  6. Run the AI provider test suite against the new implementation — a standard set of 50 canonical queries with expected output types and quality criteria.

14.3 Voice Assistant Integration (v3.0)

Voice input allows users to interact with the AI Coach using speech. The voice interface uses the same NL pipeline as text queries — only the input modality changes:

  • Speech-to-text: On-device (Apple Speech Recognition / Android SpeechRecognizer) converts voice to text. The text is then processed by the standard NL query pipeline.
  • Text-to-speech: AI Coach responses are read back using on-device TTS with a calm, professional voice profile. Financial numbers are formatted for speech ("twelve hundred dollars" not "1,200").
  • Wake word: Optional "Hey Finance Bag" wake word, implemented using on-device keyword detection (no audio data leaves the device).
  • Voice privacy: Audio is transcribed on-device and immediately discarded. Transcribed text follows the same privacy rules as typed queries.
  • Voice-specific adaptations: Responses are shorter (max 3 sentences before offering to continue); no markdown; no tables; numbers are spoken, not displayed.

14.4 Multimodal AI (v3.0)

Multimodal capabilities allow the AI to process images (primarily receipts and financial documents):

  • Receipt scanning: User photographs a receipt; the on-device model extracts amount, merchant, date, and category suggestion. This pre-fills the expense entry form — the user reviews and confirms before saving. Zero remote transmission unless user explicitly chooses to use a remote model for this.
  • Per-use consent: Before any image is processed, the user is shown exactly what data will be extracted and where it will be sent (on-device vs. remote). Consent is per-image, not per-session.
  • No persistent image storage: The image is discarded immediately after extraction. It is not stored in the AI context or AI memory.

14.5 Agentic Workflows (v3.0)

Agentic AI can propose and execute multi-step financial workflows on behalf of the user. This is the highest-risk AI capability and requires the most rigorous human-in-the-loop design:

  • Human approval required for every action: The agent may propose actions (create a savings goal, adjust a budget category, apply extra debt payment) but may not execute any of them without explicit user confirmation. The agent presents a "plan" view — a list of proposed actions — and waits for user approval on each individually or as a batch.
  • No irreversible actions without double confirmation: Actions that cannot be easily undone (closing a debt account, deleting a goal, factory reset) require a second confirmation step even in an agentic flow.
  • Scope limiting: An agent session is scoped to a user-defined task ("help me plan for buying a car"). The agent cannot take actions outside the declared scope without asking for scope expansion.
  • Audit log: Every agent-proposed action (whether approved or rejected) is written to the audit_log with event type AI_AGENT_ACTION_PROPOSED and AI_AGENT_ACTION_EXECUTED respectively.
  • Abort at any time: A persistent "Stop AI" button is visible during any agentic session. Stopping immediately cancels any pending (not yet executed) actions. Already-executed actions must be manually reversed — the agent cannot roll them back automatically.

14.6 Scalability Considerations

  • Rule-based engine scales linearly with data volume. Up to 10 years of financial history (the expected maximum for a long-term user) completes all analysis operations within the stated latency targets on a mid-range device.
  • LLM token costs grow with context size. The Prompt Layer's context compression strategy (summarizing older periods) caps effective context growth even as the user's financial history grows. A 5-year user sends roughly the same token volume as a 1-year user for most query types.
  • ai_memory table grows at approximately 500 rows/month for an active user. At 10 years, this is ~60,000 rows. Indexed on memory_type + created_at; queries remain under 10ms at this scale.
  • ai_recommendations table is bounded by the deduplication and expiry rules — maximum ~50 ACTIVE recommendations at any time, regardless of history length.
  • Behavioral score computation is O(n) in the number of complete periods. At 120 periods (10 years), computation takes <50ms on indexed queries.

Scenario: User is new — fewer than 3 complete salary periods. Predictions require historical data the system doesn't yet have.

  • All predictions requiring <3 periods show UNCERTAIN confidence with the message: "You've completed [N] of the 3 months of tracking needed for reliable projections. Keep going — your first projection will be ready in [3−N] months."
  • Rule-based recommendations based on current-period data (budget overspend, unused budget) remain available regardless of history length — they require only the current period's data.
  • Coaching sessions are simplified for new users: focus on setup quality (budget set? goals defined? emergency fund started?) rather than trend analysis.

15.2 Conflicting Financial Information (EC-AI-02)

Scenario: User's budget allocations total more than their salary. Total budget exceeds 100% of income.

  • The AI detects the over-allocation and makes it the top-priority recommendation: "Your total budget allocations exceed your income by [amount]. This will result in a negative end-of-period balance. Here's how to rebalance."
  • Cash flow predictions note the over-allocation as the primary driver of negative projection and surface it prominently in the ExplainabilityContext.limitations.
  • Other recommendations are suppressed until the over-allocation is resolved — lower-priority insights are irrelevant when the budget is structurally impossible.

15.3 Missing Salary Record (EC-AI-03)

Scenario: A salary period has no salary record (user forgot to enter salary or had an irregular income month).

  • The missing period is excluded from salary-dependent calculations. A note is added to any prediction using salary averages: "One period (Month X) is excluded due to no salary record — this may affect accuracy."
  • Cash flow prediction for a period with no salary record uses the average of adjacent periods as a placeholder — clearly labeled as an estimate.
  • The AI Coach proactively surfaces a prompt: "You haven't recorded a salary for [period]. Would you like to add it now?" (soft nudge, not a blocking prompt).

15.4 Large Unexpected Financial Event (EC-AI-04)

Scenario: User records an unusually large expense (e.g., 5× their typical monthly spending in one entry — medical emergency, car repair).

  • Anomaly detection: If a single expense exceeds 50% of the user's average monthly residual, the AI flags it as an anomaly in the behavioral intelligence layer (not a mistake — an anomaly).
  • The anomaly is excluded from trend calculations by default (with disclosure: "The [amount] [category] expense in [month] is excluded from trend calculations as an outlier — including it would distort averages"). Users can override this in Settings → AI Coach → Anomaly Handling.
  • The AI proactively generates a specific recommendation: "Your emergency fund would have covered this expense [if yes: with X months remaining / if no: and then required X months to replenish]. Consider increasing EMF contributions."

15.5 AI Provider Unavailable (EC-AI-05)

Scenario: In Hybrid mode, the remote AI provider returns an error or times out.

  • The Provider Layer catches the error and immediately routes to the Rule-Based provider as fallback. The user sees the rule-based response.
  • A subtle notice is shown: "Using offline analysis — some details may be less specific than usual." This notice is dismissable and not shown for more than 3 consecutive degraded interactions (to avoid alarm fatigue).
  • The Provider Layer retries the remote provider after 30 minutes. If available, the next interaction uses the remote provider again without user action.
  • Provider outages are tracked in a provider_health table. If the provider has been unavailable for >24 hours, the user is notified in Settings → AI Coach → Status.

15.6 Low-Confidence Prediction (EC-AI-06)

Scenario: A user asks for a debt payoff date, but their payment amounts vary wildly each period (coefficient of variation >50%).

  • Confidence is set to LOW. Prediction is expressed as a range: "At your current average payment rate, you're likely to be debt-free between [earliest date] and [latest date] — a wide range because your payment amounts have varied significantly."
  • The AI offers a simulation: "Want to see how consistent [amount]/month would change this? [Run simulation]."
  • The prediction is not suppressed — a low-confidence range is more useful than silence.

15.7 User Asks Out-of-Scope Question (EC-AI-07)

Scenario: User asks "What crypto should I buy?" or "What's my credit score?"

  • Intent classified as OUT_OF_SCOPE. The AI does not speculate, deflect, or invent an answer.
  • Response: "I'm focused on the finances you're tracking in Finance Bag and can't answer that. I can help you with [3 contextually relevant alternatives, e.g., "plan your monthly savings", "project your debt payoff", "review your budget"]."
  • Investment advice and credit scoring are explicitly prohibited topics — the AI names this explicitly if asked directly: "I'm not able to give investment advice or access external credit data. For those questions, consider speaking with a licensed financial advisor."

15.8 Outdated Historical Data (EC-AI-08)

Scenario: User has not opened the app for 3 months. Historical data is now 3 months stale for prediction purposes.

  • On first open after 3+ months, the AI Coach runs a "re-entry check": compares the last known financial state to what has changed (new period opened, no expenses recorded, budget not updated).
  • Predictions and recommendations generated immediately after re-entry are labeled with: "Based on data last updated [date] — update your records for more accurate insights."
  • The AI does not suppress recommendations, but ranks a "catch up your records" prompt above all others until the user records at least one expense in the new period.

15.9 User Rejects All Recommendations (EC-AI-09)

Scenario: User consistently dismisses every recommendation over multiple periods.

  • After 5 PERMANENTLY_DISMISSED recommendations in the same category, that category's recommendations are temporarily suppressed (30 days) with a notice: "You've dismissed several [category] suggestions — I'll give you a break from those for a while."
  • The Memory Layer records the dismissal pattern. In Hybrid mode, the LLM is informed of the pattern and adjusts framing (different angle, different benefit emphasis) before the category resumes.
  • A "Why do you keep suggesting this?" option on every recommendation allows the user to understand the trigger condition — this often resolves the dismissal pattern without requiring changes to the engine.

15.10 Negative Financial Health Score Trend (EC-AI-10)

Scenario: User's Financial Health Score has declined for 3 consecutive periods — a significant downward trend.

  • The AI Coach elevates this to a CRITICAL priority coaching trigger, regardless of schedule. The next app open after the third decline triggers a coaching session prompt (soft — not a blocking modal).
  • The coaching session focuses exclusively on identifying the primary driver of the decline (which FHS component declined most?) and the single most impactful action to reverse it.
  • Tone is especially important here: the session leads with acknowledgment ("Your finances have been under pressure lately — let's figure out what's going on and find one thing to improve"), not with a list of failures.
  • If the user declines the coaching session, the dashboard shows a persistent (but dismissable) "Your financial health needs attention" card with a single recommendation — not a full session.

15.11 Goal Conflict (EC-AI-11)

Scenario: User's goals collectively require more monthly contribution than their available residual. Goals are mathematically impossible to all achieve simultaneously.

  • The AI detects the over-commitment and generates a CRITICAL GOALS recommendation: "Your goals require [total required]/month but you have [residual]/month available after expenses. Here's a prioritization plan."
  • The prioritization plan is presented as options, not directives: "Option A: Pause Goal 3 and 4 — Goal 1 and 2 complete by [date]. Option B: Extend all goal timelines by [N] months. Option C: Reduce your savings rate — not recommended given your EMF gap."
  • If the user has set explicit goal priorities (dependency graph), the AI uses those to order the options. If priorities are not set, the AI uses deadline proximity (soonest deadline = highest priority).

15.12 AI Memory Corruption (EC-AI-12)

Scenario: An ai_memory row has a corrupted value_json field (fails JSON parsing).

  • The corrupted row is skipped during memory retrieval. A DEAD_MEMORY_ROW event is logged to the audit_log.
  • The AI operates without that memory signal. This may cause a slightly less personalized response (e.g., defaults to Intermediate sophistication if the sophistication preference row is corrupted).
  • The corrupted row is queued for deletion in the next nightly maintenance cycle. It is not exposed to the user as an error — the degradation is silent and graceful.
  • If >10% of ai_memory rows in a category are corrupted (detected by nightly quick_check), the entire category is cleared and the user is notified: "AI memory was partially reset due to a storage issue. Your coaching preferences may need to be re-set."

16. Business Rules

16.1 Core AI Guarantees

Rule IDRuleRationale
BR-AIC-01 AI Never Writes Financial Data: The AI layer has no write access to the financial database. It may read any authorized data, but all state changes are proposed to the user and executed exclusively through the Business Layer with explicit user confirmation. User trust and data integrity require a hard boundary between AI intelligence and financial data mutation. The AI is an advisor, never an executor.
BR-AIC-02 ExplainabilityContext Is Mandatory: Every AI output object delivered to the user must carry a fully populated ExplainabilityContext. An AI output missing any required ExplainabilityContext field is invalid and must not be presented to the user. Trust is built through transparency. Users must always understand why they are seeing an AI insight, recommendation, or prediction. Unexplained AI output is indistinguishable from black-box manipulation.
BR-AIC-03 Rule-Based Fallback Is Always Available: The AI system must operate in Rule-Based mode even when all network connectivity is absent, all AI providers are unavailable, and the user has disabled remote AI. Rule-Based mode may never be disabled by configuration. Offline-first architecture extends to AI. Users should not lose coaching and recommendations because they have no internet connection. Reliability is a core principle.
BR-AIC-04 Maximum 3 Recommendations Simultaneously: The Recommendation Layer may not present more than 3 active, non-dismissed recommendations at any time. Higher-priority recommendations replace lower-priority ones when the queue is full. Recommendation overload reduces action rates. Three actionable recommendations yield more user behavior change than ten ignored ones. This constraint is behavioral psychology, not a technical limitation.
BR-AIC-05 No Investment Advice: The AI may never suggest buying or selling specific securities, cryptocurrencies, or other investment instruments. It may discuss savings rates, emergency fund adequacy, and general financial health — not specific investment products. Investment advice requires licensing. Exceeding this boundary exposes Finance Bag to regulatory risk and harms users who rely on unlicensed advice.
BR-AIC-06 No Personal Identifiers in Remote Context: FinancialContextBuilder must strip all personal identifiers (name, email, phone, device_id, goal names, debt names) before any remote AI provider call. Anonymization transforms are applied unconditionally — they cannot be disabled by configuration. User privacy is non-negotiable. Remote AI providers should never be able to identify the user or build a personal profile from Finance Bag's context payloads.
BR-AIC-07 Remote AI Is Opt-In: Remote AI features are disabled by default. The first time a user would benefit from a remote AI feature, an opt-in prompt is shown. If declined, the app continues in Rule-Based mode silently — no repeated prompting (max 1 opt-in prompt per 30 days). Data privacy requires informed consent. Remote AI sends data to external services — users must actively choose this. Defaulting to remote AI would violate the Privacy-Conscious principle.
BR-AIC-08 AI Label Always Visible: Every AI-generated card, insight, message, or recommendation must carry a visible "AI analysis" or "AI Coach" label. This label cannot be hidden by user settings, themes, or dashboard customization. Users must always know they are receiving AI-generated content, not manually verified data. This is an honesty requirement, not a UX choice.
BR-AIC-09 Coaching Tone Rules Are Non-Negotiable: The non-judgmental, educational tone rules (§4.4) apply to all AI output in all operating modes. In LLM mode, generated output must be validated against these rules post-generation. Output that violates tone rules must be replaced with the rule-based fallback before presentation. Financial coaching that shames or judges drives users away from their finances at exactly the moment they need engagement. Behavioral economics shows that non-judgmental framing produces better financial outcomes.
BR-AIC-10 Predictions Include Confidence and Assumptions: No prediction is delivered without both a confidence level (VERY_HIGH through UNCERTAIN) and the list of A1–A10 assumptions it relies on. Predictions without these fields must not be presented to the user. An overconfident prediction that doesn't materialize destroys trust more than no prediction at all. Transparent uncertainty helps users make better-informed decisions than false precision.
BR-AIC-11 Simulations Are Non-Destructive: What-If simulations operate on in-memory snapshots only. No simulation operation may write to the financial database, modify app_state, or affect any recommendation that has not been confirmed by the user. Simulations are a safe space for exploration. Users must be able to model extreme scenarios (income loss, new debt) without triggering real-world changes to their financial plan.
BR-AIC-12 Memory Deletion Is Immediate: When a user deletes AI memory (by category or in full), the deletion takes effect within the current database transaction. The next AI interaction must operate without the deleted memory. Delayed or deferred memory deletion is prohibited. Users must be able to trust that privacy controls work immediately. A deleted memory that influences the next AI response — even once — is a privacy violation that damages trust.
BR-AIC-13 Agentic Actions Require Explicit Confirmation: In Full AI / agentic mode, every proposed action requires individual user confirmation. Batch approval ("approve all") is allowed only for actions with identical risk profile. Irreversible actions always require individual confirmation regardless of batch context. Agentic AI that takes unconfirmed actions on users' financial data is a critical safety risk. Human approval is the primary safety mechanism for all agentic workflows.
BR-AIC-14 Financial Health Score AI Component Is Bounded: The AI behavioral score contributes at most 20% to the overall Financial Health Score. Objective financial metrics (debt ratio, savings rate, EMF coverage, goal progress) constitute at least 80% of the FHS. The AI behavioral dimension cannot dominate the overall score. The FHS must be grounded in objective financial facts. A user with excellent financial habits but a low behavioral score (because they haven't engaged with the AI Coach) should not receive a misleadingly low FHS. AI engagement is a bonus dimension, not a gating factor.
BR-AIC-15 User Always Has a Path to Disable AI: Settings → AI Coach → Disable AI must always be accessible from any AI interaction (recommendation card, coaching session, NL query interface). The path to disable AI must never be more than 3 taps from any AI-generated content. User autonomy is a foundational design principle. A user who chooses to manage their finances without AI assistance must be able to do so completely and without friction. Making AI opt-out difficult is a trust violation.
