1. Overview & Design Philosophy

1.1 Design Values

Every visual and interaction decision in Finance Bag must reinforce the following eight values. These values are not aesthetic preferences — they are functional requirements that translate directly into design decisions.

1.3 What This Spec Governs

  • Governs: Color token system; typography scale and rules; spacing grid; component anatomy, variants, and states; navigation patterns; form guidelines; motion principles; accessibility requirements; localization rules.
  • Does not govern: Specific implementation library choices (React Native, Expo); code architecture for components; animation library selection; specific icon SVG files (icon style is governed; specific artwork is not).
  • Authority: This spec takes precedence over individual module design decisions in all matters of visual consistency, accessibility, and platform convention. Module-specific adaptations (accent color, module-specific empty state illustration style) are permitted within the bounds defined here.

2. Visual Identity & Color System

2.1 Color Philosophy

Finance Bag's color language is restrained and purposeful. A dark, neutral base creates a calm, focused environment where financial data can breathe. Module accent colors provide orientation and identity within each domain. Status colors communicate system state — they are functional tools, not decoration.

The guiding rule: color should answer "what does this mean?", not "doesn't this look nice?". Every color that appears on screen must communicate something to the user. A decorative color that carries no semantic meaning is a design debt.

2.2 Four-Layer Token Architecture

Finance Bag's color system is organized in four layers. Each higher layer builds on the layer below. Design decisions use the highest applicable layer — never raw values in a component definition.

2.5 Status Color Usage Rules

  • Success (green): Income amounts; completed goals; positive FHS change; "saved successfully" confirmations; EMF growth. Never use for neutral positive events (e.g., "loading complete" — that's not a success, it's expected behavior).
  • Warning (amber): Budget at 80–99% utilization; goal slightly behind schedule; sync degraded; EMF below recommended. Warning means "attention needed, not yet critical".
  • Error (red): Budget over 100%; form validation failure; sync failure; destructive action confirmation; negative financial events. Error means "action required".
  • Information (blue): Sync status; tips and educational notes; neutral system messages. Information is the default for "here's something to know".
  • Never use status colors for decoration: A green border on a card that has nothing to do with success is prohibited. Color must mean something.
  • Never rely on color alone: Every status must also be communicated with an icon, label, or pattern. Color-blind users must receive the same information.

3.2 Font Family Rules

  • Primary typeface: System UI font stack — SF Pro Display/Text (iOS), Roboto (Android). This ensures: native-quality rendering; OS-level accessibility (Dynamic Type on iOS, Font Scale on Android); no custom font download weight.
  • Monospace (financial values): SF Mono (iOS), Roboto Mono (Android), with system-ui-monospace as fallback. All financial amounts use this typeface with font-variant-numeric: tabular-nums — amounts column-align perfectly at any size.
  • No decorative typefaces: Finance Bag does not use display or handwriting fonts. Trust requires legibility, not personality.
  • Font weight guidelines: 400 (Regular) for body and supporting text; 500 (Medium) for interactive labels and financial values; 600 (Semibold) for titles and card headers; 700 (Bold) for primary headings and large financial values; 800 (ExtraBold) for Display scale only.

3.3 Financial Value Formatting Rules

  • Currency symbol always present: Never show "1,200" — always "€ 1,200.00" or "1 200,00 €" per locale rules. The symbol is part of the data, not decoration.
  • Decimal places: Always 2 decimal places for displayed amounts. Never round to whole numbers in the UI, even when space is tight (use a smaller type size instead).
  • Thousands separator: Per locale — comma for en-US, period for fr-FR, space for ar-DZ.
  • Negative amounts: Displayed with leading minus sign AND in --clr-status-error color. Double encoding for accessibility.
  • Positive amounts: No leading plus sign by default. Leading "+" only when the context explicitly contrasts positive vs. negative (e.g., a cash flow delta showing "+€120.00" vs "−€45.00").
  • Large amounts: Never abbreviate financial values in the app (no "€12K" or "€1.2M"). Abbreviation risks trust-damaging precision errors. Use smaller type size to fit large numbers.
  • Amount color coding: Income, surplus, and credit amounts → --clr-status-success. Expense, deficit, and debit amounts → --clr-txt-primary (neutral, not red — spending is normal). Over-budget amounts → --clr-status-error. Interest costs → --clr-status-warning.

3.4 Dynamic Type & Text Scaling

  • All type sizes are specified in scalable units (sp on Android, pt on iOS). Hard-coded pixel sizes are prohibited.
  • iOS: Honor Dynamic Type accessibility categories from xSmall through AX5. The layout must remain usable at AX3 minimum; AX4/AX5 may truncate with ellipsis on secondary text but primary financial values must always be fully visible.
  • Android: Honor user font scale (0.85× – 2.0×). Test at 1.5× and 2.0× font scale; these are common accessibility settings.
  • Line height scales with font size (always specified as a unitless multiplier, never a fixed px value).
  • Minimum touch target size (44pt/48dp) does not scale with text — it remains fixed regardless of font scale setting.

3.5 RTL Typography Rules

  • Arabic text uses a system Arabic typeface (San Francisco Arabic on iOS, Noto Naskh Arabic on Android) at the same scale as the primary typeface.
  • Arabic script requires minimum 16sp for body text (legibility at smaller sizes is significantly reduced compared to Latin).
  • Mixed Arabic/number strings: currency amounts are LTR even in RTL contexts (€ 1,200.00 reads left-to-right). Text direction markers (U+200F) are used where bidi algorithm needs assistance.
  • Line height for Arabic must be 1.6× minimum (Arabic script has taller ascenders/descenders than Latin).

4. Spacing System

4.1 Base Grid: 4px

All spacing values in Finance Bag are multiples of 4px. This creates the invisible grid that makes layouts feel precise and intentional. A component's padding, margin, gap, border-radius, icon size, and touch target — all are 4px multiples. No 5px, no 7px, no 13px. If the design requires exactly 5px, the answer is 4px or 8px.

4.5 Safe Area Handling

  • iOS safe areas: Dynamic Island / notch top inset and home indicator bottom inset are respected by all full-screen views. Content never starts above the safe area top. Bottom navigation sits above the home indicator.
  • Android edge-to-edge: API 35+ enforces edge-to-edge by default. Status bar and navigation bar are transparent; content extends behind them. Padding is applied programmatically via WindowInsets.
  • Bottom sheet safe area: Bottom sheets always add bottom safe area inset to their handle-to-content padding. A bottom sheet that ignores the home indicator overlaps critical content on iPhone 14/15/16 Pro models.
  • Keyboard avoidance: All screens with inputs use KeyboardAvoidingView (iOS) / adjustPan (Android) to keep the focused input visible. The active input is never hidden behind the keyboard.

5. Iconography

5.1 Icon Style

Finance Bag uses a line icon style (outline strokes, not filled silhouettes) for navigation, actions, and informational icons. The line style conveys precision, professionalism, and technical clarity — aligned with the app's financial character. Filled variants are used exclusively for active/selected states, not as a general style.

  • Stroke weight: 1.5px at 24px base size (scaled proportionally at other sizes). Heavier strokes at smaller sizes to maintain legibility.
  • Corner style: Rounded corners (2px radius on line joints). No sharp, hard-angled icon corners — too aggressive for a calm financial app.
  • Grid: 24×24px artboard. 2px safe area inset (optical area is 20×20px). Icon optical center at artboard center.
  • Pixel-fit: All lines sit on full or half-pixel boundaries to avoid sub-pixel blur on non-retina displays.
  • Consistent metaphor: Icons across the app use a consistent level of detail. No ultra-detailed icons next to minimal flat icons in the same context.

5.5 Icon Accessibility Rules

  • No icon-only interactive elements: Every icon button must have an accessible label (accessibilityLabel on React Native) even if the label is not visually rendered. Screen readers announce the label.
  • Color-independent icons: All icons must be legible in single-color (e.g., when the OS is in grayscale mode or for color-blind users). The icon shape must carry the meaning, not the color alone.
  • Minimum size for touch targets: Icon buttons have a minimum hit area of 44×44pt regardless of icon display size. A 20px icon with 12px padding on all sides satisfies both the visual and touch requirements.
  • Loading state for icon buttons: When an icon button triggers an async operation, the icon is replaced with a spinner and the button is disabled until the operation completes.

7. Overlay & Input Components

7.1 Dialog

Dialogs (also called Alerts on iOS) interrupt the user's flow. They are reserved for situations that genuinely require a decision before the user can continue. Dialogs should be rare — most information can be conveyed in a Toast, Bottom Sheet, or inline.

Dialog Anatomy
  • Overlay: Full-screen scrim, --clr-overlay (50–70% dark). Tapping the scrim does NOT dismiss destructive dialogs — user must choose an action.

Section 11

Forms & Input Guidelines

Finance Bag forms handle sensitive financial data. Every input must be precise, validated, and forgiving of correction. The form experience must never frustrate the user into abandoning data entry.

11.1 Form Layout Principles

  • Single-column layout only — no multi-column forms on mobile

Section 13

Motion & Animation

Motion in Finance Bag serves communication, not decoration. Every animation conveys a relationship, a transition, or a state change. Gratuitous motion is avoided — a financial app must feel stable and trustworthy, not playful.

13.1 Motion Principles

  • Purposeful: Every animated element communicates something — hierarchy, relationship, completion, or feedback. Idle animations and ambient loops are prohibited.
  • Swift: UI transitions complete within 350ms. The app must never feel laggy. Longer animations only for celebratory moments (goal achieved).
  • Natural: All easing curves mimic physical motion — objects accelerate and decelerate; nothing snaps linearly.
  • Contextual: Navigation transitions reflect spatial relationships (push = slide; modal = rise; tab switch = cross-fade).
  • Accessible: All motion respects prefers-reduced-motion. Reduced motion alternatives must be defined for every animated component.

16.2 Error Handling Hierarchy

Errors are handled at the closest-possible scope. Global errors are the last resort.

  1. Silent recovery — retry transparently (e.g., failed background sync retries automatically). No user notification.
  2. Inline error — error shown in the affected component only. Rest of UI remains functional.
  3. Alert banner — for recoverable issues requiring user awareness (sync failed, backup overdue).
  4. Full-screen error — for critical, unrecoverable situations only (data corruption, app crash recovery).
  5. Dialog — for errors requiring an explicit user decision (e.g., "Restore from backup?" after failed migration).

16.3 Confirmation Dialogs

Confirmation dialogs are required before any action that:

  • Permanently deletes data (even with soft-delete, the confirmation explains "This will be hidden from your records")
  • Resets significant configuration (e.g., "Clear all budgets for this month")
  • Irreversibly sends or exports data
  • Cancels a form with unsaved changes
Confirmation Dialog standards:
• Use the Destructive dialog variant for deletes and resets (red primary button)
• Use the Confirmation dialog variant for data exports (standard accent primary button)
• The default-focused button is always CANCEL (never the destructive action)
• Title states the action: "Delete this transaction?" not "Are you sure?"
• Body clarifies consequences: "This transaction will be removed from your records. This cannot be undone."
• Destructive button label repeats the action: "Delete" not "Yes" or "OK"
• Cancel button: always present, labeled "Cancel"
