§ 01

Vue d'ensemble

Finance Bag est architecturée selon le modèle Clean Architecture combiné à une organisation Feature-Driven. Chaque couche a une responsabilité unique. Le domaine métier est pur — aucune dépendance sur React Native. L'infrastructure est interchangeable.

◆
Règle d'or : Les dépendances ne pointent que vers l'intérieur. La couche Domaine ne dépend de rien. L'Infrastructure dépend du Domaine, jamais l'inverse. La Présentation ne touche jamais la base de données directement.
OBJECTIF PRINCIPAL
Application premium fonctionnant hors-ligne, fluide à 60 fps, sécurisée, maintenable sur 5+ ans
CONTRAINTES CLÉS
Offline-first · 60 fps · <1s démarrage à froid · Support 100K+ enregistrements
ÉVOLUTIVITÉ
Open Banking · IA · OCR · Wear OS · Apple Watch · Multi-utilisateurs — sans refactoring majeur

Responsabilités par couche

PRÉSENTATION
Affichage et interactions. Appelle les Use Cases via les stores. Ne contient aucune logique métier. Ne touche jamais la base de données. Gère les états de chargement et d'erreur.
APPLICATION
Orchestration des Use Cases. Gère l'état global (Zustand). Coordonne plusieurs repositories. Publie des Domain Events. Aucune dépendance sur React Native.
DOMAINE ★
Cœur de l'application. Entités métier pures (Transaction, Goal, Credit). Règles invariantes. Interfaces des repositories. Zéro import React Native ou framework.
INFRASTRUCTURE
Implémentations concrètes. SQLite, SecureStore, API Cloud. Interchangeable sans toucher au Domaine. En test : remplacé par des mocks mémoire.

Pattern Result<T, E>

Toutes les opérations fallibles retournent Result<T, AppError> — jamais de throw non contrôlé dans le domaine.

type Result<T, E = AppError> =
  | { ok: true; value: T }
  | { ok: false; error: E };

const ok  = <T>(value: T): Result<T> => ({ ok: true, value });
const err = <E>(error: E): Result<never, E> => ({ ok: false, error });

// Usage dans un Use Case
async function addTransaction(dto: CreateTransactionDTO): Promise<Result<Transaction>> {
  const validated = Transaction.create(dto);
  if (!validated.ok) return err(validated.error);

  const saved = await this.repo.save(validated.value);
  return saved.ok ? ok(saved.value) : err(saved.error);
}

CREATE TABLE schema_migrations (
  version     INTEGER PRIMARY KEY,
  applied_at  INTEGER NOT NULL,
  description TEXT    NOT NULL
);

-- Table sync_metadata (prête pour cloud sync futur)
CREATE TABLE sync_metadata (
  table_name   TEXT    NOT NULL,
  record_id    TEXT    NOT NULL,
  last_modified INTEGER NOT NULL,
  sync_status  TEXT    NOT NULL DEFAULT 'pending',
  device_id    TEXT    NOT NULL,
  PRIMARY KEY (table_name, record_id)
);

Stratégie de Migration

PRINCIPE
  • Chaque migration a un numéro séquentiel
  • Migrations idempotentes (vérification avant exécution)
  • Rollback conservatif : jamais de DROP COLUMN
  • Runner exécuté au démarrage avant toute requête
  • Backup automatique avant migration majeure
PROTECTION
  • Soft deletes uniquement (jamais de DELETE physique)
  • Colonnes toujours ajoutées, jamais supprimées
  • Export auto JSON chiffré hebdomadaire
  • Validation de l'intégrité référentielle au démarrage
  • Snapshot mensuel immuable

Architecture de Synchronisation

Offline-first par design. La DB locale est la source de vérité. Le cloud est une projection secondaire — il n'est jamais requis pour le fonctionnement de l'app.

Réplication

Stratégie Offline-First

1. Local First
Toute écriture va d'abord en SQLite local. Retour immédiat à l'utilisateur. Pas d'attente réseau.
2. Sync Queue
La table sync_metadata enregistre chaque modification avec timestamp et statut. Le SyncEngine les traite quand le réseau est disponible.
3. Résolution Conflits
Last-write-wins sur les champs simples. Merge intelligent sur les listes. Version vector (device_id + timestamp) pour détecter les divergences.
4. Delta Sync
Seules les modifications depuis le dernier sync sont envoyées. Pas de full-sync à chaque connexion. Efficace sur mobile data.
✓
Architecture-ready : La table sync_metadata et les interfaces SyncEngine + ConflictResolver sont définies dès V1. L'implémentation Supabase s'y branche sans modifier le schéma ni les repositories existants.
§ 08

Sécurité

Défense en profondeur : chiffrement à repos, stockage matériel, authentification biométrique, et protection contre la falsification.

Modèle de Menaces

MENACE 1
Accès physique au téléphone déverrouillé → verrou biométrique + auto-lock
MENACE 2
Extraction APK + lecture base SQLite → chiffrement AES-256-GCM à repos
MENACE 3

Stratégies par Domaine

RENDU (60 fps)
  • React.memo + useCallback sur tous les composants lourds

  • FlashList au lieu de FlatList (Shopify)
  • Lazy loading des features par onglet
  • Skeleton loaders — jamais de spinner bloquant

  • Pagination curseur (pas offset) pour les listes

  • Journalisation WAL pour écritures concurrentes
  • Requêtes en arrière-plan (non bloquantes)
MÉMOIRE
  • TanStack Query cache LRU (50 queries max)
  • Images optimisées + cache expo-image
  • Nettoyage store onUnmount des features
  • Éviter les closures et les fuites de refs
  • Hermes GC optimisé (activé par défaut Expo 52+)
