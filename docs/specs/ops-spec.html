SPEC-OPS-001 v1.0.0 — Finance Bag
Section 1
Scope & Core Philosophy
The operational mandate, delivery principles, and architectural boundaries governing every pipeline, release, and production operation for Finance Bag.

Document Purpose

This specification defines the complete continuous integration, continuous delivery, production infrastructure, mobile release engineering, and long-term operational strategy for Finance Bag — a premium offline-first personal finance application built on React Native 0.76 / Expo SDK 52 targeting Android and iOS.

Every process defined here is designed to be automated, auditable, reproducible, and rollback-capable. Manual steps are exceptions that require explicit documentation and a named owner.

Delivery Mandate

Automatically Validated
Every commit triggers validation. No code reaches a shared environment without passing the full CI gate. Validation includes static analysis, unit tests, integration tests, and security scanning.
Automatically Tested
Test suites are mandatory gates, not optional checks. A failing test blocks promotion to the next stage. No human overrides the test gate without a documented incident decision.
Secure by Default
Secrets are never in source code. Signing certificates are hardware-protected where possible. All artifact transfers occur over encrypted channels. SAST and dependency scans run on every build.
Reproducible
Given the same source commit and pipeline version, the build output is byte-for-byte identical. Build environments are pinned and containerized. No side-channel toolchain modifications.
Traceable
Every artifact is tagged with its source commit SHA, build number, timestamp, and pipeline run ID. The lineage from deployed binary back to source line is unbroken and queryable.
Rollback-Capable
Every production release has a documented rollback path. For stores, phased rollout halts are prepared before submission. Emergency hotfix pipelines are tested quarterly, not discovered during incidents.

Guiding Principles

#PrincipleImplication
P-1Pipeline as CodeAll CI/CD configuration lives in version control alongside the application code. Pipeline changes follow the same PR/review process as application changes.
P-2Fail FastCheap checks (lint, format, types) run first. Expensive checks (integration tests, builds) run only after cheap checks pass. This minimises compute waste and developer wait time.
P-3Single Source of TruthOne canonical artifact is built once and promoted through environments. The same binary that passed QA is the binary submitted to the stores.
P-4Defense in DepthSecurity is enforced at every layer: SAST in CI, secret scanning in pre-commit, dependency CVE scanning on every build, binary signing at packaging, certificate pinning in app configuration.
P-5Deployment RingsProduction changes are progressively exposed: internal → closed beta → open beta → phased production rollout. No feature reaches 100% of users without passing through each ring.
P-6Immutable ArtifactsBuilt artifacts are never modified after creation. Promotion is a tagging and distribution operation, never a rebuild. Production artifacts are retained for a minimum of 24 months.
P-7Blameless OperationsIncidents are diagnosed through postmortem, not blame assignment. Systems are assumed to fail; operations procedures assume failure and design recovery paths before they are needed.
P-8Documentation as Deployment GateA release without complete release notes, changelog, and privacy label review is incomplete. Documentation is a release requirement, not an afterthought.

Technology Boundary

CI/CD Platform: GitHub Actions (primary). All pipelines are YAML-defined in .github/workflows/. Expo Application Services (EAS) handles mobile build orchestration. Google Play Console and Apple App Store Connect are the production distribution channels. No third-party CI vendor lock-in is acceptable.

Pull Request Workflow

PR Creation
PRs reference the issue or task ID. Title follows Conventional Commits format. PR body includes: motivation, change summary, testing performed, screenshots for UI changes, and a self-review checklist. Draft PRs allowed for early feedback; must be converted to Ready before CI gate applies.
Review Requirements
Minimum 1 approval for develop. 2 approvals (including Release Manager) for main. Domain-specific changes (schema, security, AI integration) require the named domain owner as one approver. Automated review assignments via CODEOWNERS file.
PR Size Policy
Maximum 400 lines changed per PR (per SPEC-ARC-001). PRs exceeding this must be split unless a single atomic migration or schema change requires more. Mechanical PRs (dependency bumps, generated code) are exempt with a waiver comment.
Merge Policy
Squash merge into develop to maintain clean history. Each squash commit represents one logical change. The squash message is the PR title in Conventional Commits format. No merge commits in develop or main.

Commit Conventions

All commits follow the Conventional Commits 1.0.0 specification. Commit message format: type(scope): description. Enforced by commitlint in the CI pipeline and a local git commit-msg hook.

Version Tagging

Git tags are created on main only by the Release Manager. Tags follow semantic versioning: v{MAJOR}.{MINOR}.{PATCH}. Release candidates are tagged v1.0.0-rc.1. All tags are signed GPG commits. Automated changelog generation reads from Conventional Commits since the previous tag.

AI integration (src/ai/) requires the AI specialist. Pipeline files (.github/workflows/) require both Tech Lead and DevOps.

Stage S-6: Quality Gate Evaluation

The Quality Gate aggregates all prior stage results into a pass/fail decision. It also computes trend metrics and posts a summary comment to the PR.

Hard Blockers
Any single hard-fail from S-1 through S-5 results in a Quality Gate FAIL. The PR is blocked from merge. The engineer must fix the issue, push a new commit, and the full pipeline re-runs from S-1.
Warning Accumulation
Warnings from any stage are recorded and aggregated. If warning count exceeds the sprint warning budget (tracked in the operations dashboard), a WARN gate fires and requires Tech Lead acknowledgement before merge.
Trend Reporting
The gate posts: test coverage delta, bundle size delta, CVE count, warning count, and pipeline duration to the PR as a structured comment. All metrics are persisted to the pipeline telemetry store for dashboard display.

Stage S-7: Build Verification

Runs only on develop branch merges and release/hotfix branches. Not required for every PR to reduce queue time.

CI Target SLO: Full pipeline (S-1 through S-6) must complete in under 18 minutes for PRs. S-7 (build verify) adds up to 12 minutes for branch builds. Pipeline duration exceeding these targets for two consecutive runs triggers a performance investigation task.

Automatic Rollout Halt

If any health gate threshold is breached, the automated CD system halts the staged rollout immediately. The breach is logged to the operations dashboard, the on-call engineer is paged, and the rollout percentage is frozen at its current level. Rollback is not automatic — it requires an engineer decision — but the halt is.

Emergency Release Process

Hotfix Trigger
A severity P0 bug in production (crash affecting >1% of users, security vulnerability, data integrity failure) triggers the hotfix pipeline. All regular releases are frozen while the hotfix is in flight.
Hotfix Branch
Branched from the last release tag on main. Fix is applied and reviewed with 2 approvers (including Release Manager). CI full pipeline runs. No steps are skipped — speed is achieved through prioritisation, not bypass.
Expedited Review
Both stores offer expedited review for critical security fixes. The Release Manager submits with the expedited review flag and a clear description of the security/safety issue. Target: 24–48h store review.
Merge Strategy
Hotfix is merged to main (for release), tagged with a patch version, and immediately cherry-picked to develop to avoid regression in future releases. Both merges are documented in the incident postmortem.

Section 10
Feature Flag Architecture
Gradual rollout, emergency kill switches, regional targeting, and A/B experimentation framework using a local-first feature flag system.

Feature Flag Approach

Finance Bag is an offline-first application. Feature flags must therefore function without network connectivity. The primary flag evaluation engine is local — flags are bundled with the app build and evaluated at runtime without a network call. A remote configuration layer (fetched on app launch when online) can override local defaults, but the app functions correctly with local defaults when offline.

Local-First Flag Evaluation: All feature flags have a hardcoded local default that is the safe/stable behavior. Remote flag values are cached after fetch and used for the session. If no remote fetch has occurred (fresh install, offline), local defaults apply. A flag cannot make a feature unavailable for an offline user who previously had it enabled — deactivation only takes effect on the next successful remote fetch.

Section 12
Incident Response
Operational procedures for critical bugs, production outages, security incidents, store rejections, and the postmortem process that drives systemic improvement.

Incident Classification

INC-TYPE-01 Critical Production Bug P0
Definition: Crash affecting >1% of daily active users, or any crash that results in data loss. Response: On-call engineer paged within 5 minutes via automated alert. Rollout halted immediately. Root cause investigation begins. Hotfix pipeline activated if fix is identified. If no fix within 2 hours, full rollback initiated. Communication: Status update in internal Slack every 30 minutes during active incident. PM notified immediately.
INC-TYPE-02 Security Incident P0
Definition: Any confirmed or suspected breach of user data, credential exposure, or vulnerability that could lead to unauthorized access. Response: Immediate notification to Tech Lead and Release Manager. App taken offline if data breach is confirmed (emergency update submitted to stores). Legal/privacy counsel notified within 2 hours. Regulatory notification initiated within 72 hours per GDPR Article 33. No public communication without legal review. Forensics: All logs preserved immediately; no system modifications until forensic snapshot is captured.
INC-TYPE-03 Store Rejection P1
Definition: App Review rejection from Apple or Google Play preventing the current release from reaching users. Response: Release Manager reviews rejection reason within 4 hours. If metadata/policy issue: resolve and resubmit within 24 hours. If code change required: hotfix pipeline or next release depending on severity. If rejection is disputed: App Review Appeal initiated with detailed explanation and evidence. Communication: PM notified; planned release date updated; no external communication about delay unless explicitly requested.
INC-TYPE-04 Broken Release (Non-Critical) P1
Definition: A released version contains a bug that significantly degrades the experience for a specific flow or user segment but does not cause data loss or crashes above P0 threshold. Response: Assessment within 2 hours of detection. Decision: fix in next scheduled release (if minor, workaround available) or expedited patch release (if impactful). Feature kill switch activated if the broken feature can be disabled safely. Users affected >10%: patch release initiated within 5 business days.
INC-TYPE-05 Third-Party Service Outage P1/P2
Definition: Anthropic API unavailability, or any external dependency that degrades Finance Bag's functionality. Response: AI features degrade gracefully to manual mode (per SPEC-ARC-001 offline design). User communication within the app (subtle indicator that AI is temporarily unavailable). No code change required for temporary outages. If outage exceeds 24 hours: assess impact and communicate via in-app notice. Monitor Anthropic status page; resume when restored.

Postmortem Requirements

All P0 incidents and selected P1 incidents require a written blameless postmortem. The postmortem document includes: incident timeline, root cause analysis, impact measurement, contributing factors, corrective actions (with owners and deadlines), and process improvements. Postmortems are stored in the team wiki and reviewed in the next retrospective.

Blameless Culture: Postmortems identify systemic failure points, not individual errors. The question is always "why did the system allow this to happen?" not "who made this mistake?" Action items target process, tooling, and automation improvements that prevent recurrence — not disciplinary measures.

Database Schema Versioning

SQLite schema version is independent of application version but coupled to it. Each schema migration is numbered (migration_001, migration_002, ...) and run sequentially on app upgrade. Drizzle ORM manages migration generation and execution. Rules: migrations are append-only (never modify historical migrations); every migration has a corresponding test; migrations are verified in the integration test suite before release.

Irreversible Constraint: Database migrations are one-directional. There is no rollback migration. If a released schema change causes issues, the fix is a new forward migration, not a reversal. This is enforced by the soft-delete-only design — data is never physically removed, making forward migration always possible without data loss.

API Versioning (Future)

Finance Bag v1.0 has no backend API. When cloud sync is introduced in v2.0, the API will follow versioned URL paths (/api/v1/, /api/v2/). The mobile client will explicitly version its API requests. A minimum of two API versions will be supported simultaneously during transition periods. This architecture is defined in SPEC-ARC-001 §7 (Scalability) and will be specified fully in the v2.0 architecture addendum.

Export Compliance

The declaration is reviewed at each major version release and whenever the encryption implementation changes.

Multi-Region Infrastructure (v2.0+)

When a backend is introduced in v2.0, the infrastructure pipeline supports multi-region deployment from the start. The CD pipeline will include a region selection matrix, region-specific environment secrets, and health gates per region before cross-region promotion. The mobile app pipeline is unaffected by backend regionalization — it targets an API endpoint that resolves regionally at the DNS level.

Pipeline Versioning

The CI/CD pipeline configuration itself is versioned and change-controlled. Pipeline changes require a PR reviewed by both the Tech Lead and the assigned DevOps owner. Pipeline changes are not exempt from the quality gate — a broken pipeline workflow is treated as a P1 operational incident. Quarterly pipeline audits review for deprecated actions, outdated runners, and security advisories.

Architectural Stability Guarantee

Invariant for Future Expansion: The following architectural decisions are locked for all future applications and expansions built on this pipeline: (1) GitHub Actions as the CI orchestrator, (2) EAS as the mobile build platform, (3) single-artifact promotion model (no rebuilds for environment promotion), (4) dual-approval for production releases, (5) phased rollout with automated health gates, (6) zero-secret-in-code policy, (7) EAS Managed Credentials for signing. These may only be changed by a formal Architecture Decision Record with sign-off from the Tech Lead and Release Manager.

Business Rules

BR-OPS-01 Every production release artifact must be built exactly once from a tagged commit on the release branch or main branch and promoted through all environments unchanged. No environment-specific rebuild of a production artifact is permitted.
BR-OPS-02 No code may be merged to develop or main without passing all mandatory CI quality gates (S-1 through S-6). No human override of a failing quality gate is permitted — the gate must be fixed and the pipeline re-run in its entirety.
BR-OPS-03 Production deployment requires dual approval from the Release Manager and the Product Manager. Neither may approve their own submission. This rule applies to every production promotion including hotfixes, with no exception.
BR-OPS-04 Staged rollout must proceed in rings (5% → 20% → 50% → 100%) with a minimum 24-hour health gate between each ring. Skipping a ring or shortening a gate requires a formal exception documented by the Release Manager with stated justification.
BR-OPS-05 Any breach of a health gate metric during staged rollout immediately and automatically halts the rollout at its current percentage. Rollout expansion may not resume until the root cause is identified and documented, and the Release Manager approves continuation.
BR-OPS-06 No secret — API key, certificate, password, token, or encryption key — may appear in source code, CI logs, build artifacts, or any version-controlled file. Detection of any secret in any of these locations triggers an immediate security incident and mandatory rotation regardless of whether the secret is "real" or a placeholder.
BR-OPS-07 Android App Signing must remain enrolled in Google Play App Signing. The upload key and app signing key are different keys. The app signing key is managed by Google. This enrollment may not be revoked. Alternatives requiring a new package name are not acceptable.
BR-OPS-08 No production data may flow into any environment below STAGING. Any environment below STAGING that receives production data must be immediately isolated, quarantined, wiped, and reported as a security incident within 30 minutes of detection.
BR-OPS-09 All P0 incidents require a written blameless postmortem completed within 5 business days. All P1 incidents require a written postmortem within 14 days. Postmortems must include a timeline, root cause, impact measurement, and at least one actionable process improvement with a named owner and deadline.
BR-OPS-10 All feature flags must have a named owner, an expiry target, and a documented kill switch authority. Flags with no active rollout purpose must be removed (hardcoded to their final state) within one sprint of their rollout completion. Flag accumulation is treated as technical debt.
BR-OPS-11 The hotfix pipeline may not bypass any CI quality gate. Speed in a hotfix is achieved through prioritisation (immediate reviewer availability, expedited store review submission) — not through skipping validation. A hotfix with a failing CI gate is not deployable regardless of business urgency.
BR-OPS-12 Production release artifacts must be retained for a minimum of 24 months with their associated build metadata (commit SHA, pipeline run ID, signing certificate used, EAS build number). Retention shorter than 24 months requires a documented regulatory review justifying the reduction.
BR-OPS-13 The Apple Developer Program and Google Play Developer Account must each have at least two named organization owners at all times. Single-owner accounts represent a business continuity risk and are not acceptable. Ownership transfers are documented and tested annually.
BR-OPS-14 Emergency DR drills must be conducted at minimum annually and must include: signing key recovery simulation, artifact retrieval from archive, environment rebuild from infrastructure-as-code, and rollback execution from the previous production version. All drill outcomes are documented.
BR-OPS-15 Changes to the CI/CD pipeline configuration require PR review by both the Tech Lead and the DevOps-responsible engineer, with the same quality gate applied to pipeline changes as to application changes. Pipeline-as-code is not exempt from the review and quality standards applied to application code.
