Overview & Database Philosophy

The database is the single source of truth for Finance Bag. Every feature module reads from and writes to this shared foundation through its own domain functions — no module may access another module's tables directly. The data model is designed to remain correct, auditable, and performant across 10+ years of financial history without redesign.

Foundational Invariants. These rules apply to every entity in the database without exception: (1) All monetary values stored as integer centimes (×100) — no floats, ever. (2) Deleted records use soft delete only — deleted_at timestamp, no hard deletes on financial data. (3) Computed fields are never stored — all derived values calculated at read time. (4) The salary period is the fundamental unit of financial time — not the calendar month.

1.1 Four Design Pillars

🔒
Integrity First
Referential integrity, validation constraints, and audit trails take precedence over query simplicity. A write that would corrupt data must fail, not silently succeed.
📴
Offline-First
The database is the entire persistence layer. No feature requires a network call. SQLite with WAL mode provides ACID compliance and concurrent read access without a server.
📸
Snapshot Immutability
Closed periods are sealed. Historical data is append-only. Editing a current record never modifies the archived record that captured its prior state.
🔭
Future-Proof Schema
Every table carries a schema_version in the migrations registry. New columns are additive and nullable. Breaking changes require a versioned migration with rollback support.

1.2 Hot vs Cold Data Model

The database maintains a deliberate separation between operational (hot) data and historical (cold) data. This distinction governs access patterns, retention, and indexing strategy.

DimensionHot Data (Operational)Cold Data (Historical)
DefinitionCurrent period records, active entitiesSealed monthly archives, snapshot tables
Access patternFrequent reads & writesInfrequent reads, write-once
MutabilityFully mutable (within business rules)Immutable after sealing
VolumeSmall and boundedGrows linearly over time
Index densityHigh — optimized for dashboard speedLower — optimized for report queries
Examplessalary_periods, expenses, debtsmonthly_archives, fhs_history

1.3 Ownership Rules

  • Each table is owned by exactly one module. Only the owning module's functions may write to that table.
  • Cross-module reads are permitted (e.g., Dashboard reads from SAL, BUD, DBT, EMF, GOL tables) but cross-module writes are prohibited.
  • The EVT module's event_log is readable by all modules for diagnostic purposes.
  • Archive tables (monthly_archives and all snapshot tables) are written by the EVT automation engine and read by RPT.
  • The audit_log is written by a shared audit service and read by no module directly (diagnostic/support tool only).

2.3 ID Strategy

All primary keys use ULID (Universally Unique Lexicographically Sortable Identifier). ULIDs are preferable to UUID v4 for database performance because they are monotonically increasing — new rows sort after existing rows naturally, reducing B-tree page splits and improving insert performance in SQLite.

// ULID format: 26-character base32 string // First 10 chars = timestamp (ms precision) — ensures chronological sort // Last 16 chars = random — ensures uniqueness // Example: 01HZQBN7V3K5XW2PM4RNDE8FYA // All PKs: TEXT NOT NULL PRIMARY KEY — stored as string, never integer autoincrement // Exception: system domain tables may use INTEGER AUTOINCREMENT for migration counters

2.4 Referential Integrity Model

  • FOREIGN KEY constraints enabled — SQLite requires PRAGMA foreign_keys = ON per connection. This must be set at connection initialization, not once globally.
  • Cascade DELETE is prohibited on financial data tables. Deleting a parent record never silently removes children. Instead, the owning module must explicitly soft-delete children first.
  • Cascade UPDATE is only used for surrogate key changes during migrations, never during normal operation.
  • NULL FK is allowed only where the relationship is optional (e.g., source_entity_id on events, category_id on uncategorized expenses).

Entity Relationships

4.1 Relationship Catalog

1:1
users → profiles
Each user has exactly one profile. Shared primary key — profiles.id = users.id. No join needed; the PK is the FK.
1:1
users → settings
Singleton row in settings with a fixed key. Logically 1:1 though not enforced by FK (singleton pattern).
1:N
salary_periods → salary_records
One period can have multiple salary records (initial entry + corrections). The active total is the SUM of non-deleted records.
1:N
salary_periods → budget_allocations
One allocation row per (period, category) pair. Allocations are created fresh each period, not carried over automatically.
1:N
salary_periods → expenses
All expenses belong to the period in which they were incurred. Cross-period expense correction is not permitted — instead, soft-delete and re-enter.
1:N
salary_periods → debt_payments
Payments are anchored to the period in which they were recorded, enabling per-period debt analysis in Reports.
1:N
salary_periods → emf_contributions
Each contribution belongs to a period. Multiple contributions per period are permitted (lump sums allowed).
1:N
salary_periods → goal_contributions
Same as EMF — each contribution anchored to a period.
1:1
salary_periods → monthly_archives
One archive per period, created at period close. UNIQUE constraint on period_id in monthly_archives. Archive is immutable once sealed.
1:N
budget_categories → budget_allocations
A category can have allocations in many periods. Deleting a category (soft) does not affect historical allocations.
1:N
budget_categories → expenses
A category groups many expenses. FK is nullable — uncategorized expenses have category_id = NULL.
M:N
expenses ↔ tags (via expense_tags)
An expense can have many tags; a tag can apply to many expenses. Junction table with composite PK. Deleting a tag soft-deletes the tag row; the junction rows are also soft-deleted (set deleted_at via trigger).
1:N
debts → debt_payments
Each debt has a payment history. Payments are never moved between debts. Cascade rule: soft-deleting a debt does NOT cascade to payments (audit integrity).
1:N
emergency_fund → emf_contributions
The singleton EMF entity owns all contributions. The FK always resolves to 'emf-singleton'.
1:N
financial_goals → goal_contributions
Each goal owns its contribution history. Completing a goal (status=COMPLETED) does not cascade-delete contributions.
M:N
financial_goals ↔ financial_goals (via goal_dependencies)
Self-referential many-to-many relationship. Encodes the goal DAG. Application layer enforces acyclicity using Kahn's algorithm before any edge insertion.
1:1
financial_goals → roadmap_nodes
A goal may optionally be linked to a roadmap node via roadmap_node_id. Not all goals are on the roadmap; not all roadmap nodes are goals.
M:N
roadmap_nodes ↔ roadmap_nodes (via roadmap_edges)
Self-referential DAG for the financial roadmap. BFS propagation runs from completed nodes to unlock dependents.
1:N
monthly_archives → archive_category_snapshots
One snapshot row per category per archive. All archive child tables are immutable after parent.sealed_at is set.
1:N
monthly_archives → archive_debt_snapshots
One row per active debt at period close. Fully paid debts are still captured for historical completeness.
1:N
monthly_archives → archive_goal_snapshots
One row per active or recently completed goal at period close.
1:1
monthly_archives → archive_emf_snapshot
One EMF snapshot per archive (shared PK pattern — archive_emf_snapshot.archive_id = monthly_archives.id).
1:N
expenses → attachments
An expense can have one attachment (receipt photo). Future: multiple attachments per expense via a junction table.

4.2 Polymorphic Relationships

The roadmap_nodes.linked_entity_id field is a polymorphic FK — it may reference a row in debts, emergency_fund, or financial_goals depending on the value of linked_entity_type. SQLite cannot enforce a polymorphic FK at the database level; integrity is enforced at the application layer.

Similarly, event_log.source_entity_id (from the EVT spec) is polymorphic — it references different entity types depending on source_module. The application resolves the reference using the module identifier.

5

Monthly Snapshot Model

At the end of each salary period, the system creates an immutable archive snapshot that permanently records the period's financial state. Once sealed, no record in the archive tables may ever be modified or deleted. The snapshot model provides trustworthy historical reporting even after categories are renamed, debts are paid off, or goals are deleted.

Sealing Immutability Guarantee. A monthly archive is sealed by setting sealed_at to a non-null timestamp. After that point, any write attempt to that archive row or its child snapshot rows is rejected at the application layer. The schema_version field records the spec version at sealing time so future migrations can interpret the data correctly.

5.1 Sealing Trigger

Sealing is triggered by the BUDGET_PERIOD_ADVANCED system event. The EVT module publishes this event; the DB layer handles the SEAL_MONTHLY_ARCHIVE automation. The sealing process is transactional — all or nothing. A partial seal is treated as a failure and retried.

5.2 Sealing Process (6 Steps)

  • Verify period is CLOSED. The salary_periods.status must equal 'CLOSED' before archiving may begin. An ACTIVE period cannot be sealed.
  • Create monthly_archives row. Aggregate all financial totals for the period: total_income, total_allocated, total_spent, total_debt_payments, total_goal_contribs, total_emf_contribs, total_saved. Read FHS at open (from prior period's archive or fhs_history) and FHS at close (from current fhs_history row). Copy denormalized period_label, start_date, end_date.
  • Create archive_category_snapshots. For each category that had a budget allocation in this period, insert one row. Capture category_name at this moment (denormalized) so future renames do not alter historical records.
  • Create archive_debt_snapshots. For each active or newly-paid debt, insert one row capturing balance_at_open, balance_at_close, total paid, principal vs interest split, and status_at_close. Creditor_name is denormalized.
  • Create archive_goal_snapshots. For each goal that received a contribution or changed status this period, insert one row. goal_name and target_amount are denormalized. completion_pct_at_close is stored in basis points (0–10000).
  • Create archive_emf_snapshot. Single row sharing the archive_id as PK. Captures EMF balance movement, contribution total, milestone level, and completion percentage in basis points. Then set sealed_at = NOW() on the monthly_archives row to finalize the seal.

5.3 Archive Integrity Verification

After sealing, the system verifies: (1) total_income − total_allocated − total_saved does not produce a negative unallocated remainder without explanation, (2) each snapshot row's FK matches the archive_id, (3) sealed_at IS NOT NULL. If any check fails, the archive is flagged as INTEGRITY_ERROR and an alert is raised — the data is retained for manual inspection, not deleted.

5.4 Entity Not Present in a Period

If a debt or goal had no activity in a period but was active, it still receives a snapshot row so the archive is a complete cross-section of financial state. Goals and debts with deleted_at IS NOT NULL at period start are excluded unless they had activity before deletion.

5.5 Re-Sealing Prohibited

Once sealed_at is set, re-sealing (overwriting or amending the archive) is explicitly prohibited. If a data error is discovered in a sealed archive, a correction_log entry is appended — the original archive record is never altered. Corrections are annotated but do not modify historical totals.

Data Versioning Strategy

The schema_migrations table records every applied migration in sequence. The version field is a monotonically increasing integer. No migration may be applied out of order, and no migration may be rolled back once applied to production data without explicit operator intervention.

6.1 Migration Table Structure

FieldTypeDescription
versionINTEGER PKMonotonically increasing migration sequence number
nameTEXT NOT NULLHuman-readable migration name (e.g. add_expense_notes_column)
checksumTEXT NOT NULLSHA-256 of the migration SQL — prevents silent modification of applied migrations
applied_atINTEGER NOT NULLUnix ms timestamp when migration completed
rollback_sqlTEXT NULLABLEReverse migration SQL; null means irreversible

6.2 Migration Rules

  • Migrations run in strict ascending version order on app startup before any reads or writes.
  • If the current schema checksum does not match the recorded checksum, the app refuses to start and surfaces a data integrity error to the user.
  • Additive changes (new columns with DEFAULT, new tables) are always safe. Destructive changes require a multi-step migration: add new, backfill, verify, remove old.
  • Column renames require creating a new column, backfilling, then dropping the old — never renaming directly in SQLite (no ALTER COLUMN support).
  • Archive tables (monthly_archives, archive_*) store schema_version at sealing time so the application knows which version's logic to use when reading historical rows.

6.3 app_state Version Tracking

The app_state table stores a db_schema_version key that is updated after each successful migration batch. On startup, the app reads this key to determine the current schema version before attempting to run migrations. This provides a fast pre-check without scanning the migrations table.

6.4 Entity-Level schema_version

Archive tables include a schema_version TEXT field (e.g. '1.0', '2.3') captured at seal time. This allows the reporting layer to apply version-specific parsing rules when reading archived data — essential for long-lived archives that predate schema changes. The format is MAJOR.MINOR where MAJOR increments on breaking changes.

Search & Query Model

Finance Bag's search is entirely local. All queries execute against the SQLite database without network calls. The query model balances completeness (returning correct results across soft-deleted or archived data) with performance (sub-100ms response on 5+ years of data).

7.1 Expense Search

The primary search surface is expense search, accessed from the Reports and Budget modules. Expense search supports the following filter dimensions, all combinable:

DimensionFilter TypeSource Field(s)

Soft-deleted expenses (deleted_at IS NOT NULL) are always excluded from search results unless the query explicitly requests deleted records (admin/debug context only).

7.2 Saved Report Filters

Users may save up to 10 active search filter combinations as named saved_report_filters. Each filter stores a filter_json blob containing the full filter state. Saved filters are not versioned — they serialize the current filter UI state at save time. A hard limit of 10 active (non-deleted) rows is enforced at the application layer before insert.

7.3 Cross-Period Aggregation Queries

Reports module queries aggregate across multiple periods. Common patterns:

  • Spending by category over N periods — GROUP BY category_id, period_id with SUM(amount) where deleted_at IS NULL.
  • FHS trend — SELECT from fhs_history ordered by date with a 365-day window; no joins required.
  • Net savings trend — JOIN salary_records and expenses by period_id, aggregate per period.
  • Debt paydown curve — SELECT balance_at_close from archive_debt_snapshots ordered by archive.end_date for a specific debt_id.
  • Goal progress timeline — SELECT balance_at_close from archive_goal_snapshots ordered by archive.end_date for a specific goal_id.

7.4 Query Scope Rules

  • All operational queries must include deleted_at IS NULL unless archive/history is explicitly requested.
  • Archived data queries operate on the archive_* tables, never join back to operational tables to fill gaps (historical data must be self-contained in the archive).
  • The fhs_history table is append-only; queries always read with ORDER BY date DESC LIMIT N.
  • Aggregate queries on expenses must always group by period first to avoid cross-period contamination in paginated results.

Indexing Strategy

Indexes are chosen based on actual query patterns derived from the feature specifications. No speculative indexes are created. Each index is named with a consistent convention: idx_{table}_{columns}. Composite indexes list columns in selectivity order (highest cardinality first). Covering indexes are used where the query can be satisfied entirely from the index without a table scan.

SQLite B-tree note. ULID primary keys provide naturally ordered B-tree insertions (monotonically increasing prefix). UUID v4 would cause random page splits; ULIDs avoid this entirely, keeping the primary index hot and compact.

8.2 Partial Index Pattern

Where SQLite supports it, partial indexes are used on soft-deleted tables to index only active records: WHERE deleted_at IS NULL. This keeps the index compact when historical data accumulates. The expenses table especially benefits — over years of data, most rows will be from prior periods.

8.3 Index Anti-Patterns to Avoid

  • Do not index notes or description columns with a standard B-tree index — full text search uses LIKE patterns which cannot use these indexes anyway.
  • Do not add covering indexes for singleton tables (users, settings, emergency_fund) — they are one-row tables and any index overhead exceeds the benefit.
  • Do not create indexes on the composite-PK junction tables (expense_tags, goal_dependencies, roadmap_edges) — the composite PK already provides efficient lookup in both directions for small datasets.

Archiving Strategy

Archiving is the process of permanently sealing a closed period's financial state into the archive tables while the operational tables continue to hold current-period live data. Archiving is not the same as backup — it is a business process that produces an immutable historical record.

9.1 Two-Tier Data Lifecycle

TierTablesAccess PatternMutabilityRetention
Hot (Operational)expenses, salary_records, debt_payments, goal_contributions, emf_contributions, debts, financial_goals, budget_allocationsHigh read + write, current periodFull CRUD (soft delete)Active until period closed; soft-deleted rows retained indefinitely
Cold (Archive)monthly_archives, archive_category_snapshots, archive_debt_snapshots, archive_goal_snapshots, archive_emf_snapshotRead-only after sealing; write once at seal timeImmutable after sealed_at IS NOT NULLIndefinite — financial history must never expire
Analyticsfhs_history, audit_log, event_logAppend-only; queried for trend displayAppend only; no updatesfhs_history: 365 days; audit_log: 365 days; event_log: 90 days

9.2 Period Lifecycle States

  • ACTIVE — the current open period. Only one period may be ACTIVE at a time. All new transactions are associated with this period.
  • CLOSED — the period's end date has passed. No new transactions may be attached. The period is eligible for archiving (sealing). The salary_periods row is not yet archived.
  • ARCHIVED — the period has been sealed into monthly_archives. archived_at is set. The salary_periods row is updated to ARCHIVED status. Operational rows for this period remain in hot tables (soft-deleted ones included) for potential audit or re-aggregation, but are excluded from all active-period UI.

9.3 Retention Policy for Operational Tables

Operational tables do not auto-purge financial transaction rows. The following time-bounded tables have explicit retention limits enforced by the CLEANUP_OLD_EVENTS automation:

  • event_log — rows with created_at older than 90 days are hard-deleted (events are non-financial system data).
  • fhs_history — rows with date older than 365 days are hard-deleted (trend display only requires the last year; full history lives in archive FHS fields).
  • audit_log — rows with created_at older than 365 days are hard-deleted (compliance window). If a future version requires longer retention, this limit is configurable via app_state.
  • dead_letter_queue — rows older than 30 days that have been resolved are hard-deleted.
Financial data rows (expenses, debt_payments, salary_records, goal_contributions, emf_contributions) are never hard-deleted, even after their period is ARCHIVED. They remain in the operational tables in perpetuity for potential re-aggregation, audit, or data export. Soft-delete (deleted_at) is the only removal mechanism.

9.4 Large Attachment Management

The attachments table stores only metadata. Actual file bytes are stored in the device's local file system at local_uri. The thumbnail_uri points to a compressed preview. When an expense is soft-deleted, its attachment record is soft-deleted but the file is retained for a configurable grace period (default 30 days) before the file system entry is cleaned up. The file cleanup is handled by the app, not by a SQLite trigger.

10.2 Application-Layer Validation Rules

  • Period must be ACTIVE before writes. Any mutation to expenses, salary_records, debt_payments, goal_contributions, emf_contributions must check that the target period_id maps to an ACTIVE salary period.
  • UNIQUE constraint on budget_allocations. (period_id, category_id) is UNIQUE. Attempting to create a second allocation for the same category in the same period is rejected with a meaningful error, not silently overwritten.
  • Debt current_balance must not go negative. Enforced at application layer rather than a CHECK constraint to provide a user-friendly error message when an over-payment is attempted.
  • Goal contributions must not exceed target_amount − current_balance. Over-contributions are rejected; the goal enters COMPLETED state exactly when current_balance reaches target_amount.
  • salary_periods UNIQUE on period_label. Period labels follow the format YYYY-MM (e.g. 2025-03). Only one period per label is allowed.
  • Max 10 saved_report_filters. Enforced before INSERT; if the user has 10 active filters, they must delete one before creating a new one.
  • DAG integrity on goal_dependencies. Before inserting a dependency row, the application checks that the new edge does not create a cycle. Kahn's algorithm is run on the full dependency graph. If a cycle would result, the insert is rejected.
  • DAG integrity on roadmap_edges. Same cycle-prevention logic as goal_dependencies — BFS/DFS from the proposed to_node_id must not reach from_node_id before insertion is permitted.

10.3 Cross-Entity Consistency Rules

  • When a debt is marked PAID_OFF, current_balance must be ≤ 0 (or exactly 0 after rounding). Any outstanding balance is flagged as a consistency warning, not silently zeroed.
  • When a goal is marked COMPLETED, current_balance must equal target_amount. A goal with remaining balance cannot self-complete.
  • A salary period cannot be CLOSED if it is currently the only ACTIVE period and no new period has been opened yet.
  • The EMF singleton row (id = 'emf-singleton') must always exist. If not found, it is created lazily on first access with zero balances.
11

Security Model

Finance Bag stores sensitive personal financial data on-device. The security model prioritizes local encryption, access control at the OS level, and auditability without requiring any server-side authentication infrastructure.

11.1 Encryption at Rest

The SQLite database file is encrypted using SQLCipher (or expo-sqlite's built-in encryption API). The encryption key is derived from the user's device biometric/PIN authentication secret via the platform Keychain (iOS) or Keystore (Android). The key is never stored in plaintext. The database cannot be opened without the derived key — raw file access yields ciphertext.

11.2 Biometric Lock

When settings.biometric_lock = TRUE, the app re-challenges biometric authentication after a configurable inactivity timeout (default 5 minutes). The database connection is closed on lock and re-opened only after successful re-authentication. The settings table itself stores only the preference flag — the biometric challenge is handled at the OS platform layer.

11.3 Obscure Amounts

When settings.obscure_amounts = TRUE, all monetary values in the UI are replaced with placeholder characters (e.g. ••••). This is a UI-layer feature only — amounts are stored and computed normally in the database. Obscuring affects: dashboard totals, expense amounts, debt balances, goal amounts, EMF balances.

11.4 Audit Log

The audit_log table records all data mutations at the row level. Every INSERT, UPDATE, and soft-delete operation on financial tables produces an audit row. The audit log is:

  • Append-only — no UPDATE or DELETE is permitted on audit_log rows by the application.
  • Immutable in the sense that the application has no delete path for audit rows within the 365-day retention window.
  • Stored locally on-device — not synced to any external service in v1.
  • Scoped per session — session_id identifies the app session (generated at launch) so sequences of operations can be correlated.
  • triggered_by identifies the module or automation that caused the change (e.g. 'BUD', 'EVT:AUTOMATION', 'USER').

11.5 Data Export Security

When the user requests a data export (SEC.DATA_EXPORT_REQUESTED event), the following security controls apply:

  • Re-authentication is required (biometric or PIN) before export begins, regardless of the current session lock state.
  • The export is written to a temporary file in the app's private sandboxed storage first. The user must explicitly choose a destination via the OS share sheet.
  • The export file name includes a timestamp to prevent silent overwriting of prior exports.
  • The audit log records the export event including timestamp and what data was exported.

11.6 FK Enforcement

PRAGMA foreign_keys = ON must be set for every SQLite connection before any read or write. This is non-negotiable — SQLite disables FK enforcement by default. The connection initialization sequence must include this pragma as step one. Failure to set it means child rows can exist without valid parent rows, violating referential integrity silently.

12.2 WAL Mode

SQLite is configured in WAL (Write-Ahead Log) mode via PRAGMA journal_mode = WAL. WAL mode provides concurrent readers during writes and dramatically improves write throughput for the event-heavy patterns in Finance Bag (EVT module publishes frequently). WAL checkpoint is set to auto-checkpoint at 1000 pages to prevent unbounded WAL file growth.

12.3 Dashboard Snapshot Cache

The dashboard snapshot is the most performance-critical path in the app. Rather than recomputing it on every navigation to the Dashboard screen, the REBUILD_DASHBOARD_SNAPSHOT automation pre-computes the full dashboard state after any financial mutation and stores the result as JSON in app_state (key: dashboard_snapshot). The Dashboard screen reads this key on mount — no aggregation queries run at render time.

The snapshot is invalidated (and scheduled for rebuild) whenever any of the following events fire: SALARY_RECORDED, EXPENSE_CREATED/UPDATED/DELETED, DEBT_PAYMENT_RECORDED, GOAL_CONTRIBUTION_RECORDED, EMF_CONTRIBUTION_RECORDED, FHS_SIGNIFICANT_CHANGE.

12.4 Query Optimization Rules

  • Never use SELECT * in production queries — select only the columns needed to reduce data transferred from storage layer.
  • Aggregate queries (SUM, COUNT, AVG) on large tables must always use indexed columns in the WHERE clause to enable index-only scans.
  • LIKE queries with a leading wildcard ('%text%') cannot use a B-tree index and will full-scan the expenses table. This is acceptable as a user-initiated search, not a background query. For >10,000 expense rows, this may require progressive result delivery.
  • All writes to the database are serialized through a single connection (SQLite single-writer model). Concurrent writes from different modules must go through the same connection instance or queue.
  • Use PRAGMA cache_size = -8000 (8MB page cache) for the primary connection to keep hot B-tree pages in memory across queries within a session.

Backup & Recovery

Finance Bag is an offline-first app. There is no cloud sync in v1. Backup is the user's responsibility, but the app provides structured export tools to facilitate it. Recovery is the process of restoring a previously exported backup to a new or reset device.

13.1 Export Formats

  • Manual export — User-initiated from Settings. Requires re-authentication. Produces a file shared via OS share sheet.
  • iCloud / Google Drive auto-backup (v2) — Not in v1. Placeholder in spec for future cloud sync module. The database encryption key must be derivable from cloud-stored credentials in that scenario, not the device-local biometric key.
  • Onboarding import — At fresh install, the user may import a full DB backup file to restore their financial history. Import validates schema_version compatibility before applying.

13.3 Recovery Process

  • User initiates restore from Settings → Import Backup.
  • User selects a .sqlite backup file via OS file picker.
  • App reads the app_state key db_schema_version from the backup file to check compatibility.
  • If schema version is compatible (same MAJOR version), the app replaces the current database file with the backup.
  • If schema version is older (lower MAJOR or MINOR), the app runs forward migrations after restoring.
  • If schema version is newer than the app version, restore is rejected with an error prompting the user to update the app first.
  • After restore, the app rebuilds the dashboard snapshot and re-indexes any tables that need it.

13.4 Data Loss Prevention

  • Before a restore, the app creates a backup of the current database to a temp location. If the restore fails, the prior database is reinstated.
  • Partial writes during the sealing process are protected by SQLite transaction ACID guarantees — a failed seal leaves no partial archive rows.
  • The app detects database corruption on startup via PRAGMA integrity_check (quick mode). If corruption is detected, the user is prompted to restore from backup rather than attempting to repair.

Future Compatibility

The database schema is designed to evolve without requiring full data migrations for minor additions. The following patterns ensure long-term maintainability.

14.1 Additive-Only Schema Evolution Principle

New features add new columns (with DEFAULT values) or new tables. They do not rename existing columns, change column types, or remove columns without a multi-step migration. The only destructive schema changes permitted are removing columns that have been deprecated for at least two major app versions and confirmed to have zero usage via migration-time inspection.

Several tables include a JSON blob field that provides an extensibility escape hatch without requiring schema migrations for minor additions:

14.3 AI Module Readiness

The data model is designed to be queryable by a future AI module without schema changes:

  • fhs_history provides a complete time-series of financial health for ML model training.
  • archive_*_snapshots provide period-level aggregates that form natural training features.
  • expense.description and notes fields are free text that can be used for category suggestion ML models.
  • audit_log provides behavioral patterns (which modules users interact with most, at what times).
  • The app_state table can hold AI model configuration, inference cache, and recommendation history without schema changes.
  • The event bus (EVT module) is already instrumented to emit AI-readable events (AI.* event type category) when the AI module is enabled.

14.4 Multi-Currency Future State

The currencies reference table and profiles.currency_code FK are designed to support future multi-currency operation. In v1, all amounts are in a single currency (the user's selected currency). The currencies.decimal_places field supports non-centimal currencies (JPY = 0 decimal places). A future migration would add a currency_code column to expenses and other monetary tables, defaulting to the user's primary currency, enabling per-transaction currency tracking.

14.5 Cloud Sync Future State

ULID primary keys are ideal for multi-device sync scenarios because they are generated client-side and are globally unique without coordination. If cloud sync is added in a future version, the ULID scheme requires no PK changes. The updated_at timestamps on mutable tables support conflict resolution via last-write-wins or merge strategies. The audit_log provides a complete change history that a sync server could use for conflict resolution.

Business Rules

Business rules at the database layer enforce invariants that must hold regardless of which UI path or automation triggered the write. These are distinct from UI validation (which provides user-friendly errors) and from event automation (which responds to data changes). DB business rules are the last line of defense.

BR-DB-01
Day-of-Month Cap at 28
Any field representing a day-of-month (salary_day, payment_due_day, contribution_day) must be capped at 28. This prevents issues with months that have fewer than 31 days. CHECK constraints enforce 1–28. Values 29, 30, 31 are rejected at application layer with an explicit error message.
BR-DB-02
One Active Period at a Time
The salary_periods table may have at most one row with status = 'ACTIVE'. Enforced by a partial unique index: CREATE UNIQUE INDEX idx_one_active_period ON salary_periods (status) WHERE status = 'ACTIVE'. Attempting to create a second ACTIVE period raises a UNIQUE constraint violation.
BR-DB-03
No Hard Deletes on Financial Data
The application must never issue a DELETE statement on financial transaction tables (expenses, salary_records, debt_payments, goal_contributions, emf_contributions, debts, financial_goals, emergency_fund). Only soft-delete via UPDATE SET deleted_at = NOW() is permitted. The audit_log records this operation as SOFT_DELETE.
BR-DB-04
Singleton Table Integrity
Tables with singleton semantics (users, settings, emergency_fund) must have exactly one row. emergency_fund uses id = 'emf-singleton'; settings uses id = 'app-settings'. These IDs are hardcoded string constants in the application. Inserting a second row to these tables raises a PK conflict. If the singleton row does not exist, it is created lazily on first access.
BR-DB-05
Shared PK for 1:1 Relationships
The profiles table uses id as both primary key and a FK to users.id. This shared-PK pattern means a profile can only exist if the user exists, and exactly one profile per user is guaranteed by the PK constraint. The same pattern applies to archive_emf_snapshot (shared PK with monthly_archives).
BR-DB-06
Money Arithmetic Invariant
All arithmetic on monetary amounts uses integer centimes only. Division operations that would produce fractional centimes must round using ROUND_HALF_UP. The result of interest_portion + principal_portion must equal the total payment amount exactly (no rounding discrepancy tolerated). Rounding discrepancies are assigned to the principal_portion.
BR-DB-07
Archive Immutability After Sealing
Once monthly_archives.sealed_at IS NOT NULL, no UPDATE to that row or any of its child snapshot rows is permitted. The application enforces this by checking sealed_at before any write to archive tables. A sealed archive may never be re-sealed, amended, or deleted by normal application paths.
BR-DB-08
Cascade DELETE Prohibited
No FK relationship in the database may use ON DELETE CASCADE. Referential actions on financial data are handled explicitly by the application layer. When a parent entity is soft-deleted, the application decides which child entities to also soft-delete (and records each in audit_log). Silent cascade deletion is incompatible with the auditability requirement.
BR-DB-09
ULID Format Enforcement
All primary keys must be ULIDs: 26-character base32 strings, first 10 characters encoding a millisecond-precision timestamp. UUID v4 keys are prohibited in financial tables. UUID v4 may only be used as idempotency keys in the EVT module's event_log — and only temporarily, as the specification prohibits UUID v4 idempotency keys (see BR-EVT-09 in SPEC-EVT-001).
BR-DB-10
Foreign Key Pragma Per Connection
PRAGMA foreign_keys = ON must be the first statement executed after opening any SQLite connection. No exceptions. FK enforcement is off by default in SQLite and will not persist across connections. The DB initialization layer must set this pragma before returning the connection to any module.
16

Edge Cases

These edge cases represent scenarios that are difficult to handle correctly but likely to occur in real usage. Each has a specified correct behavior that the application must implement.

16.1 Period Boundary Edge Cases

EC-DB-01
Expense Entered After Period Closed
If a user records an expense after the period has been CLOSED (e.g. forgot to enter a receipt), the application must allow back-dating the expense to the prior period — but only if that period has not yet been ARCHIVED (sealed). Once a period is sealed, no expense may be added to it. The UI must surface a clear warning when editing a closed-but-not-sealed period.
EC-DB-02
Debt Payment Exceeds Outstanding Balance
If a debt_payment.amount > debts.current_balance (e.g. the user made a final overpayment), the system accepts the payment but caps balance_after = 0, automatically marks debts.status = 'PAID_OFF', and publishes DEBT_PAID_OFF event. The overpayment amount is not tracked as a credit — it is treated as rounding/escrow and the difference is discarded.
EC-DB-03
Goal Contribution Overshoots Target
If a goal_contribution.amount would cause current_balance to exceed target_amount, the contribution is silently capped at (target_amount − current_balance). The recorded amount is the capped value, not the entered value. The UI must show the user the capped amount before confirming. After the contribution, the goal transitions to COMPLETED status automatically.
EC-DB-04
Salary Day 29–31 in User Profile (Legacy Migration)
If a user migrated from a version that allowed salary_day up to 31, their profile may contain a value > 28. On read, the application clamps the value to 28 for all business logic purposes. A one-time migration sets the stored value to 28. No functional regression — Feb 28 is always used for salary_day = 29/30/31 in practice.
EC-DB-05
Category Deleted Mid-Period
If a budget_category is soft-deleted (deleted_at IS NOT NULL) while expenses referencing it exist in the current period, those expenses retain their category_id FK (no cascade). The budget view shows the category as "Deleted" in the expense list. When the period is sealed, the archive_category_snapshots row includes the category even if deleted, so historical reports remain accurate. The deleted category is not available for new expense assignment.
EC-DB-06
Uncategorized Expenses
expenses.category_id is nullable. An expense with category_id = NULL is treated as "Uncategorized". Uncategorized expenses contribute to period total spending but do not reduce any category's allocated amount. The FHS budget score treats uncategorized spend as untracked allocation, penalizing the score proportionally. Users are prompted to categorize expenses but are not blocked from saving uncategorized ones.
EC-DB-07
No Salary Recorded for a Period
A salary period with no associated salary_records is valid (e.g. the user had no income that period). In this case, total_income = 0 in the archive snapshot. The FHS income stability component handles this gracefully — consecutive zero-income periods reduce the stability score. The budget view shows ₹0 income with a prompt to add salary rather than an error state.
EC-DB-08
Circular Dependency in goal_dependencies
The application must prevent circular dependencies in the goal_dependencies DAG. Before inserting a new dependency row, it runs a DFS from the proposed dependent_goal_id to verify it cannot reach prerequisite_goal_id through existing edges. If a cycle would result, the insert is rejected with a user-visible error: "This dependency would create a circular chain." The check runs in O(V + E) time on the in-memory adjacency list.
EC-DB-09
Archive Sealing Interrupted Mid-Transaction
If the device loses power or the app crashes mid-seal, SQLite's WAL mode ensures the transaction is rolled back atomically. The monthly_archives row will have sealed_at = NULL (or will not exist). On next startup, the system detects the orphaned CLOSED period (status = 'CLOSED', no sealed archive) and re-triggers the sealing process. The incomplete partial archive rows (if any) are detected by the absence of sealed_at and are cleaned up before a fresh seal attempt.
EC-DB-10
First-Time Launch with No Data
On first launch, the app runs all migrations against a fresh empty database, inserts the singleton rows (users, profiles, settings with defaults, emergency_fund with zero balances), creates the first salary period with ACTIVE status, and inserts the system budget categories (ESSENTIAL, FLEXIBLE, SAVINGS, DEBT, EMF, GOAL). No FHS row is created yet — FHS computation requires at least one salary record. The app_state key onboarding_complete is set to false until the user completes the onboarding flow.
