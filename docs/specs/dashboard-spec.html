01

Overview & Module Identity

Depends on SPEC-BUD-001 SPEC-DBT-001 SPEC-EMF-001 SPEC-GOL-001 SPEC-RMP-001

The Dashboard is the single entry point for Finance Bag. It is a read-only aggregation surface — it owns no data, persists no computed state, and writes nothing to the database. Every figure it shows is derived in real time from the five upstream modules. Its purpose is to answer six questions within one glance:

How much is available?Available Money — net disposable after all allocations, debts, and contributions
How much is allocated?Sum of all active budget category allocations for the current salary period
What is the debt status?Total outstanding balance, next due payment, Debt-to-Income ratio
How is the emergency fund?Current milestone level, completion percentage toward next milestone
How are goals progressing?Active goal count, aggregate completion %, roadmap on-track status
What needs attention?Prioritized alerts ordered by urgency and financial impact

Design Principle: 5-Second Rule

The user must be able to answer all six questions above within 5–10 seconds of opening the app, without scrolling. This is a hard constraint governing which widgets appear above the fold, what information density the layout uses, and how much cognitive parsing the UI demands. All decisions in this spec are filtered through this constraint.

Module Scope

  • Financial Health Score (FHS) computation — 6-component formula, grades, and trend deltas
  • Available Money Engine — the canonical financial position calculation
  • Configurable widget system — 15 widget types, ordered and hideable
  • Smart Insights engine — contextual, actionable, non-repetitive financial nudges
  • Alert Center — prioritized notification surface aggregated from all modules
  • Quick Actions — 10 one-tap shortcuts to high-frequency operations
  • 10 chart types for financial trend visualization
  • Dashboard personalization and 3 layout presets
  • Global search across all financial entities
  • Performance targets: critical path < 200 ms
ℹ️
No writes from the dashboard. The dashboard never modifies module data. Quick Actions navigate to the correct module screen to complete the action. The sole exception is alert dismissal, which updates a local UI-state store only — never the module databases.

Data Architecture & Schema

The dashboard maintains no persistent database tables. It operates through two layers: a computed snapshot assembled at mount and refreshed on a defined schedule, and a UI state store for alert dismissal and personalization preferences.

Information Hierarchy

The dashboard is structured in three tiers. Content at a higher tier is always visible without interaction. Content at lower tiers requires scrolling or a tap.

Tier 1 — Immediate View (above the fold, visible on open)

These are non-negotiable above-the-fold positions. No layout preset may move them below the fold.

  • Available Money — large typographic treatment, the first thing eyes land on
  • Financial Health Score — displayed as a score badge and grade label directly below Available Money
  • Budget ring / period bar — compact visual showing allocated vs. spent vs. remaining for the current period
  • Critical alert count — if criticalAlertCount > 0, a red banner appears immediately below the FHS badge

Tier 2 — Primary Context (visible with minimal scroll)

  • Debt summary card — total balance, DTI label, next payment
  • Emergency fund progress bar — current level, completion %, months-to-next
  • Goals summary card — active count, aggregate progress, roadmap status chip
  • Top 3 alerts from Alert Center

Tier 3 — Detail & Exploration (full scroll or dedicated screen)

  • Smart Insights carousel (up to 3 insights)
  • Quick Actions row
  • Individual goal cards (if Goals widget is expanded)
  • Charts (accessed via widget expand or dedicated chart screen)
  • Full alert list

Financial Health Score (FHS)

The Financial Health Score is a composite 0–100 index representing the user's overall financial wellness at a given moment. It aggregates the six core dimensions of personal finance into a single, instantly readable number. The score is computed on every snapshot rebuild and is never stored in the database.

ℹ️
Total: 100 points across 6 components. Each component score is floored to 0 — negative values are not possible. The total is also clamped to [0, 100].

4.1 Component 1 — Savings Rate (0–20 pts)

Definition: The fraction of gross income being saved or invested each period, including goal contributions and EMF contributions but excluding debt repayment.

savingsAmount = totalGoalContribs + totalEMFContribs savingsRatePct = savingsAmount / grossIncome × 100 savingsRatePts = savingsRatePct >= 20 → 20 savingsRatePct >= 15 → 16 savingsRatePct >= 10 → 12 savingsRatePct >= 5 → 8 savingsRatePct >= 1 → 4 savingsRatePct == 0 → 0 // If grossIncome == 0: savingsRatePts = 0

4.2 Component 2 — Debt Burden (0–20 pts)

Definition: The Debt-to-Income ratio (DTI) — monthly debt payments as a percentage of gross monthly income. Uses the same DTI definition as SPEC-DBT-001.

dtiPct = (totalDebtPayments / grossIncome) × 100 debtBurdenPts = dtiPct < 15 → 20 // HEALTHY dtiPct < 20 → 17 dtiPct < 28 → 13 // MODERATE dtiPct < 36 → 8 // ELEVATED dtiPct < 44 → 4 // HIGH dtiPct >= 44 → 0 // If grossIncome == 0 and totalDebtPayments == 0: debtBurdenPts = 20 // If grossIncome == 0 and totalDebtPayments > 0: debtBurdenPts = 0

4.3 Component 3 — EMF Readiness (0–20 pts)

Definition: Emergency Fund milestone level from SPEC-EMF-001. Rewards having a meaningful financial safety net.

emfReadinessPts = emfMilestoneLevel == LEVEL_3 (6 months) → 20 emfMilestoneLevel == LEVEL_2 (3 months) → 15 emfMilestoneLevel == LEVEL_1 (1 month) → 9 emfMilestoneLevel == LEVEL_0 (started) → 3 no EMF record exists → 0 // LEVEL_4 (custom) uses the emfHealthScore component instead: // emfReadinessPts = ROUND(emfHealthScore / 100 × 20)

4.4 Component 4 — Budget Balance (0–15 pts)

Definition: How well actual spending aligns with the budget plan. Rewards staying within budget; penalizes overruns; also penalizes significantly under-spending (plan accuracy).

utilizationPct = totalSpent / totalAllocated × 100 budgetBalancePts = utilizationPct == 0 → 0 // No allocations or no spending data utilizationPct <= 80 → 12 // Under-utilizing budget (plan inaccurate) utilizationPct <= 95 → 15 // Optimal zone: 80–95% utilizationPct <= 100 → 11 // 96–100%: technically in budget utilizationPct <= 110 → 5 // 101–110%: moderate overrun utilizationPct > 110 → 0 // >110%: significant overrun // Additional penalty: if overspentCategories > 0, subtract MIN(overspentCategories, 3) // Final: budgetBalancePts = MAX(0, budgetBalancePts − overspentCategories penalty)

4.5 Component 5 — Goal Progress (0–15 pts)

Definition: Composite goal health, weighted by roadmap dependency leverage from SPEC-RMP-001.

avgGoalHealth = mean of goalHealthScore across all ACTIVE goals // from SPEC-GOL-001 §13 goalProgressBase = ROUND(avgGoalHealth / 100 × 12) // Dependency Leverage Bonus (0–3 pts) blockedGoalCount = count of goals with roadmapStatus == BLOCKED onTrackCount = count of goals with roadmapStatus ∈ {IN_PROGRESS, RECOMMENDED_NEXT} leverageBonus = blockedGoalCount == 0 AND onTrackCount >= 2 → 3 blockedGoalCount == 0 AND onTrackCount == 1 → 2 blockedGoalCount == 0 → 1 blockedGoalCount >= 1 → 0 goalProgressPts = MIN(15, goalProgressBase + leverageBonus) // If no ACTIVE goals: goalProgressPts = 0

4.6 Component 6 — Monthly Stability (0–10 pts)

Definition: Behavioural consistency signals from the current period: salary recorded on time, no category overruns, contributions made.

stabilityPts = 0 // Sub-component A: Salary recorded on time (0–4 pts) IF currentPeriod.salaryRecordedAt IS NOT NULL: salaryDelay = salaryRecordedAt − periodStart (in days) stabilityPts += salaryDelay <= 2 → 4 | salaryDelay <= 5 → 2 | ELSE → 1 // Sub-component B: No budget overruns (0–3 pts) IF overspentCategories == 0: stabilityPts += 3 IF overspentCategories == 1: stabilityPts += 1 // Sub-component C: Contributions made (0–3 pts) IF totalGoalContribs > 0 OR totalEMFContribs > 0: stabilityPts += 3 monthlyStabilityPts = MIN(10, stabilityPts)

4.7 Total Score & Grade Labels

fhsTotal = savingsRatePts + debtBurdenPts + emfReadinessPts + budgetBalancePts + goalProgressPts + monthlyStabilityPts fhsTotal = CLAMP(fhsTotal, 0, 100)

Available Money Engine

Available Money is the single most important number in the app. It answers "how much can I actually spend right now?" — accounting for every financial commitment. It must be computed consistently, transparently, and displayed prominently.

5.1 Core Formula

availableMoney = grossIncome − totalAllocated // sum of PeriodCategoryAllocation.allocatedAmount (SPEC-BUD-001) − totalDebtPayments // sum of scheduled Credit.minimumPayment for this period (SPEC-DBT-001) − totalGoalContribs // sum of Goal.monthlyContribution for ACTIVE goals (SPEC-GOL-001) − totalEMFContribs // EmergencyFund.monthlyContribution if fund is ACTIVE (SPEC-EMF-001) // All terms are in integer centimes. Result may be negative. // Negative availableMoney is displayed in red with a warning icon.
⚠️
Budget allocations vs. spending. totalAllocated uses the planned allocation for the period, not actual spending. This reflects commitments, not reality. Actual spending is shown separately as totalSpent. The Available Money number intentionally represents the plan so users can evaluate budget discipline.

5.2 Allocation Waterfall Breakdown

Below the Available Money figure, the dashboard displays a breakdown showing how gross income is consumed. These are always displayed as centimes amounts, not percentages, so users see exact figures.

Line ItemSourceDisplay Label
Gross IncomecurrentPeriod.totalIncome"This period's income"
− Budget AllocationsSum of PeriodCategoryAllocation.allocatedAmount"Budgeted spending"
− Debt PaymentsSum of active Credit.minimumPayment"Debt payments"
− Goal ContributionsSum of active Goal.monthlyContribution"Goal savings"
− EMF ContributionsEmergencyFund.monthlyContribution"Emergency fund"
= Available MoneyComputed result"Available to spend"

5.3 Spending Remaining

A secondary figure, distinct from Available Money, shows how much of the current budget allocations has not yet been spent:

remainingBudget = totalAllocated − totalSpent // If remainingBudget < 0: user has overspent their budget plan. // Displayed in amber (0 to -10%) or red (< -10%).

5.4 Edge Cases

ConditionBehavior
grossIncome == 0 (no salary recorded yet)Show "— Income not recorded yet" placeholder; all derived figures are "—"
availableMoney < 0Display in red; show "Over-committed by X" below the figure; trigger ALERT-007
totalAllocated == 0 (no budget set up)Show "No budget plan" chip; Available Money = grossIncome; trigger ALERT-009
All contributions = 0No warning here — the FHS Savings Rate component will penalise this naturally

Smart Insights Engine

Insights are short, contextual, and actionable messages surfaced on the dashboard to help users improve their financial position. The engine evaluates a set of rules against the current snapshot and selects the highest-priority insights that have not been recently shown.

7.1 Insight Structure

type Insight = { id: string // deterministic: e.g. 'INS-003-2026-07' code: InsightCode priority: number // 1 (highest) – 100 (lowest) title: string // max 48 chars body: string // max 120 chars ctaLabel: string // e.g. "Adjust budget", "View debt plan" ctaRoute: string // Expo Router path suppressedUntil: number // Unix ms — do not show before this time }

7.2 Insight Selection Algorithm

  1. Evaluate all 30 insight rules against the current DashboardSnapshot
  2. Filter out any insight whose suppressedUntil > now
  3. Sort remaining candidates by priority ascending (lower = higher priority)
  4. Select top 3; if fewer than 3 qualify, show fewer (never show a placeholder)
  5. After display: set suppressedUntil = now + suppressionPeriod for each shown insight

Alert Center

Alerts are time-sensitive notifications that require user awareness or action. Unlike Insights (which are nudges), alerts are triggered by specific threshold violations or system events across all modules. They are aggregated onto the dashboard and ordered by a computed urgency score.

8.1 Alert Structure

type DashboardAlert = { id: string // deterministic: source module + event key code: AlertCode severity: AlertSeverity // 'CRITICAL' | 'WARNING' | 'INFO' title: string // max 60 chars body: string // max 140 chars sourceModule: string // 'BUD' | 'DBT' | 'EMF' | 'GOL' | 'RMP' ctaRoute: string urgencyScore: number // 0–100; used for sort order generatedAt: number // Unix ms dismissable: boolean }

8.2 Urgency Score Formula

urgencyScore = (severityWeight × 50) // CRITICAL=50, WARNING=30, INFO=10 + (timelinessWeight × 30) // daysUntil==0 → 30, ==1 → 25, ==2 → 20, >7 → 0 + (financialImpactWeight × 20) // fraction of grossIncome affected × 20, capped at 20 // Alerts with urgencyScore >= 70 are CRITICAL and trigger the red banner (Tier 1)

8.4 Alert Dismissal Rules

  • Dismissed alert IDs are stored in DashboardUIState.dismissedAlerts (cleared on app restart, not persisted across sessions)
  • Snoozing: WARNING alerts can be snoozed for 24 hours; they re-appear automatically after the snooze expires
  • An alert re-appears on the next snapshot rebuild if the triggering condition still holds, even if previously dismissed

Global Search & Overview

Global Search allows users to find any financial entity across all modules from a single search bar accessible from the dashboard header. It does not query any external service — all search is local, against the SQLite database.

12.2 Search Algorithm

  • Minimum query length: 2 characters
  • Case-insensitive substring match across all indexed fields
  • Results are grouped by entity type with a section header per group
  • Maximum 5 results per entity type (20 total); a "View all [N]" link navigates to a filtered module screen
  • Search executes on every keystroke after 300 ms debounce; runs on a background thread to avoid blocking the UI
  • Soft-deleted records (deleted_at IS NOT NULL) are excluded from all search results
  • Recently viewed entities are shown as suggestions before the user types

Performance Architecture

13.1 Performance Targets

Partial snapshot rebuild (single module)< 100 msModule write → affected widget re-renders

App cold start to Tier 1 visible< 800 msJS bundle ready → WIDGET-AM and WIDGET-FHS populated

13.2 Caching Strategy

  • Critical path pre-computation: On every budget period write, pre-compute and cache the Available Money and FHS totals in Zustand. Dashboard reads from cache, not from DB, for these two values
  • Snapshot fields are computed in parallel where queries have no dependency on each other (budget summary, debt summary, EMF summary, goals summary are independent — run concurrently)
  • FHS ring buffer (Section 4.8) is read from AsyncStorage on mount; never requires a DB query for trend delta computation
  • Stale-while-revalidate: Dashboard shows the previous snapshot immediately on mount, then silently rebuilds in the background; updated values replace stale ones without a loading spinner
  • Module partial invalidation: Each module's Zustand slice tracks a lastModifiedAt timestamp; dashboard compares this against snapshot's generatedAt to determine which module summaries are stale

13.3 Database Query Optimization

  • All aggregate queries use SQLite SUM(), COUNT(), and MAX() — no in-JS aggregation of raw rows
  • Dashboard queries filter by deleted_at IS NULL and period_id = ? as the first two WHERE conditions — these columns must be indexed
  • The budget summary query joins categories with allocations and expenses in a single query, not three separate queries
  • Debt summary uses a single query with a sub-select for next-due payment rather than loading all debt records
  • No N+1 queries: goal health scores are not computed on the dashboard — only the avgGoalCompletionPct aggregate is fetched

Edge Cases

EC-DSH-01
First App Open — No Data
When no budget period, no salary, no goals, no debts, and no EMF exist: display a welcoming onboarding state, not a dashboard full of zeros. Each widget shows its own empty state with a "Get started" CTA. FHS is not computed or shown. Available Money widget shows "Set up your budget to get started." ALERT-009 is the only active alert.
EC-DSH-02
No Salary Recorded for Current Period
grossIncome = 0. Available Money = 0. Do not attempt to compute FHS Savings Rate or Debt Burden components — they become 0 pts. Display "Income not recorded" placeholder in WIDGET-AM. Trigger ALERT-028 (from INS-028 equivalent). FHS is computed with 0 pts for those two components; all other components use available data.
EC-DSH-03
Negative Available Money
Show the negative amount in red with a "−" prefix and a warning icon. ALERT-003 fires. The FHS Monthly Stability component's Sub-component B is penalised. The insight INS-011 fires. The allocation waterfall breakdown remains visible so the user can identify which commitment is causing the over-commitment.
EC-DSH-04
All Goals Completed or Archived
WIDGET-GS shows "All goals completed 🎉" with activeGoalCount = 0. goalProgressPts = 0 (no active goals to score). INS-012 triggers to encourage creating a new goal. WIDGET-GL shows an empty state. roadmapStatus = NOT_STARTED.
EC-DSH-05
Snapshot Build Failure (Partial Data)
If any module's DB query throws an error during snapshot build: that module's summary fields are set to null; the affected widgets render in the ERROR state (Section 6.2). The remaining modules' widgets render normally. The error is logged with the module name and query. A retry button appears on each errored widget; the global pull-to-refresh re-triggers the full snapshot build.
EC-DSH-06
Budget Period Rollover During Session
If the current period's end date passes while the app is in the foreground: detect this on the 15-minute auto-refresh tick, trigger a full snapshot rebuild, and display ALERT-012 (period rollover). The new period's allocations may be 0 until the user sets up the new budget — ALERT-009 fires to prompt action.
EC-DSH-07
FHS History Gap
If the FHS ring buffer has no entry for 7 or 30 days ago (app was not opened those days): fhsDelta7d and fhsDelta30d are set to null and the trend indicator is hidden rather than showing a misleading 0. "Trend data unavailable" tooltip is shown on tap.
EC-DSH-08
Very Large Numbers
For grossIncome or totalDebtBalance above 1 000 000 centimes (10 000 in currency units): compactNumbers mode is automatically enabled for those specific values regardless of user setting. The full number remains accessible via tap-to-expand tooltip. This prevents layout overflow in the hero widget.
EC-DSH-09
All Debts Paid Off
totalDebtBalance = 0, debtCount = 0. WIDGET-DS shows "Debt free 🎉" state. debtBurdenPts = 20 (maximum). DTI label = HEALTHY. INS-030 fires. nextDueDebt = null.
EC-DSH-10
Insight Engine Returns Zero Insights
When all 30 insight rules fail their trigger conditions (or all are suppressed): WIDGET-IN is not shown (it does not render a placeholder). This prevents an empty carousel from appearing. The widget slot is collapsed and the next widget moves up.

Business Rules

BR-DSH-01
Dashboard Owns No Data
The dashboard module may only READ from other modules' tables. No INSERT, UPDATE, or DELETE may originate from any dashboard code path. The only exception is writing to the DashboardUIState in AsyncStorage (alert dismissals, layout preferences). This is enforced architecturally — dashboard Zustand slices have no write methods for module data.
BR-DSH-02
Computed Fields Never Stored
availableMoney, fhsTotal, fhsComponents, budgetUtilizationPct, dtiRatio, emfCompletionPct, avgGoalCompletionPct — and all other fields in DashboardSnapshot — are never written to the database. Every snapshot rebuild re-derives all values from stored primitives. Consistency is guaranteed by this invariant.
BR-DSH-03
Centimes Throughout
All monetary values in DashboardSnapshot are stored and computed as integer centimes. Division is performed only at display time, using ROUND(centimes / 100, showCents ? 2 : 0). No floating-point arithmetic is performed on monetary values during computation.
BR-DSH-04
Soft Deletes Always Excluded
Any record with deleted_at IS NOT NULL is excluded from all dashboard computations, regardless of module. This applies to categories, debts, goals, contributions, and expenses. A soft-deleted goal's contributions do not count toward totalGoalContribs.
BR-DSH-05
FHS Ring Buffer Limit
The FHS history ring buffer holds exactly 31 entries (one per day). When a 32nd entry would be written, the oldest is evicted first. The ring buffer is keyed by calendar date (ISO string), not by period — it accumulates daily even within a single salary period. Writing occurs at most once per calendar day, on the first snapshot build of each day.
BR-DSH-06
Alert Priority Ordering
Alerts on the dashboard are always sorted by urgencyScore descending. CRITICAL alerts (ALERT-001 through ALERT-004) must always appear before WARNING alerts, regardless of their urgencyScore numeric value. In case of a tie in urgencyScore, sort by generatedAt descending (most recent first).
BR-DSH-07
Insight Suppression Persistence
Insight suppressedUntil timestamps survive app restarts — they are persisted in AsyncStorage alongside DashboardUIState. The exception is "Never again" insights (INS-024, INS-029, INS-030) — their seen status is stored as a permanent boolean flag, not a timestamp.
BR-DSH-08
Maximum 3 Insights Displayed
Even if more than 3 insights qualify simultaneously, only the top 3 by priority are displayed. There is no "Show more insights" affordance on the dashboard widget — the full insights list is accessible via a dedicated screen in the future AI compatibility layer.
BR-DSH-09
Quick Action Navigation Is Stateless
Quick Actions navigate to module screens using Expo Router's push() — they do not pass pre-filled form state. The target screen is responsible for determining sensible defaults (e.g., QA-003 opens the payment screen; the debt screen selects the next-due debt itself, not the dashboard).
BR-DSH-10
Period Alignment
All "current period" computations use the salary-period boundaries from SPEC-BUD-001 BR-01, not calendar month boundaries. If a calendar month contains two partial salary periods, only the active (current) period's data is shown in Tier 1. Prior period data is accessible through charts and the budget history screen.

Future Scalability & AI Compatibility

The dashboard architecture is designed to accommodate the following future capabilities without requiring schema changes or breaking existing snapshot contracts.

16.1 AI Insights Layer

  • The Insight structure (Section 7.1) is already AI-ready: code, priority, title, body, and ctaRoute can all be generated by an LLM using DashboardSnapshot as the input context
  • Future: a background AI agent receives the snapshot as a JSON payload and returns a ranked list of Insight objects — these are merged with the rule-based insights list and deduplicated by code
  • The suppression system (suppressedUntil) applies equally to AI-generated and rule-based insights

16.2 Multi-Currency Support

  • The centimes representation is currency-agnostic — all arithmetic is correct regardless of currency
  • The currencySymbol display setting is the only currency-aware field today
  • Future: add a currencyCode field (ISO 4217) and an exchange rate store for multi-currency goal tracking — DashboardSnapshot gains a baseCurrencyCode field and all amounts are normalized to base currency at read time

16.3 Widget Ecosystem

  • The widget catalogue (Section 6.1) uses a plugin architecture: each widget is a self-contained component that receives only the DashboardSnapshot slice it needs
  • Future third-party or user-created widgets receive only a typed read-only snapshot slice — they cannot access the database or other module stores directly
  • Widget size classes (Section 6.3) are fixed — new widgets must declare one of the four existing size classes

16.4 Predictive Analytics Hooks

  • The FHS ring buffer (Section 4.8) is the foundation for trend prediction — 31 data points support short-term linear extrapolation
  • Future: a fhsForecast30d field is added to DashboardSnapshot, computed by a simple linear regression over the ring buffer
  • The Available Money Engine formula (Section 5.1) is suitable for "what if my salary changes" simulations — same architecture as SPEC-RMP-001 What-If engine

16.5 Cloud Sync Readiness

  • DashboardUIState (layout, widget order, alert dismissals) is the only dashboard-owned data that would need cloud sync — it is already isolated in AsyncStorage
  • All financial data is owned by module stores — dashboard never duplicates data, so no sync conflicts can arise from dashboard state
  • FHS ring buffer should be included in cloud backup as it contains irreplaceable historical trend data

16.6 Notification System Integration

  • CRITICAL alerts (Section 8.3, ALERT-001 through ALERT-004) are candidates for push notifications when the app is backgrounded
  • The DashboardAlert structure maps 1:1 to a push notification payload — title, body, and ctaRoute translate directly
  • Future: a background task (Expo TaskManager) checks for critical alerts every 4 hours and delivers push notifications for any unread CRITICAL alerts
