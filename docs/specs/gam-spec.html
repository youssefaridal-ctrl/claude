§1 — Overview & Philosophy

The Finance Bag Gamification, Achievements & User Motivation Engine (GAM Engine) is a behavioral reinforcement system designed to encourage sustainable financial habits through positive recognition, meaningful milestones, and adaptive encouragement. It is not a game layer. It is a behavioral design layer grounded in evidence-based motivation science.

1.1 The Fundamental Distinction

Core Principle: The GAM Engine rewards financial reality, not app engagement. A user who enters fewer transactions because they have fewer expenses is doing well — they should not be penalized. A user who enters many transactions because they are overspending should not be rewarded for their input volume. Recognition is always tied to healthy financial behavior, never to raw activity metrics.

1.2 Design Pillars

Pillar I — Authenticity

Every achievement reflects a genuine financial accomplishment. Badges are earned, not collected. The system celebrates what happened in a user's actual financial life, not their use of app features.

Pillar II — Sustainability

Mechanics are designed for long-term engagement across years of use, not for short spikes in session frequency. Streaks have grace periods. Challenges are optional. No achievement expires.

Pillar III — Safety

The system never applies pressure, shame, or urgency. It is entirely opt-out-able, never compares users to each other, and surfaces no negative rankings. Users who disengage lose nothing except optional recognition.

Pillar IV — Meaning

Rewards carry semantic weight — a badge for paying off a debt means something because the underlying financial event is significant, not because a task counter reached a threshold.

Pillar V — Adaptability

The motivation engine adapts to user profile and financial context. Encouragement for a user in debt reduction mode is different from encouragement for a user building long-term savings.

Pillar VI — Privacy

Achievement data is private by default. No achievement detail, streak count, or financial milestone is ever shared with other users or surfaced in any social or comparative context.

1.3 Behavioral Science Foundation

The GAM Engine draws from three well-validated behavioral frameworks:

FrameworkApplication in GAM Engine
Self-Determination Theory (SDT)Achievement system supports autonomy (user chooses challenges), competence (progressive difficulty with mastery achievements), and relatedness (personal history and journey, not social ranking). Extrinsic rewards (badges) are designed to support, not undermine, intrinsic financial motivation.
Operant Conditioning — Variable Ratio + Fixed RatioMilestone achievements use fixed-ratio reinforcement (known targets). Hidden achievements use variable-ratio (surprise). The ratio is kept healthy: no slot-machine-style randomness on frequency; surprises are rare and meaningful.
Implementation IntentionsChallenges translate vague goals ("save more") into specific behavioral commitments ("contribute to savings every month for 3 consecutive months"). The specificity increases follow-through rate.
Loss Aversion (managed)Streaks are designed to be encouraging to maintain, but their loss causes no penalty, only the absence of ongoing recognition. Grace periods and recovery mechanics prevent loss aversion from becoming anxiety.
Progress PrincipleVisible progress toward meaningful goals is a primary intrinsic motivator (Amabile & Kramer). The progress visualization system (§7) is the primary delivery mechanism for this effect.

1.4 What the GAM Engine Is Not

  • Not a points economy — there is no currency to earn, spend, or lose.
  • Not a leaderboard — users are never ranked against each other.
  • Not a daily-check-in loop — the app does not require daily engagement to maintain status.
  • Not a notification machine — gamification events generate at most one notification per significant achievement, with full user control over frequency.
  • Not a substitute for financial advice — motivational messages are positive reinforcement only; they never constitute financial guidance.

1.5 Scope

The GAM Engine covers: behavioral event detection, achievement evaluation and unlock, streak tracking, milestone recognition, progress visualization, adaptive motivational messaging, optional challenges, reward assignment, personalization, and the data model supporting all of the above. Integration with the Financial Health Score (FHS), sync engine, AI coach, and backup system is defined in §17.

2.3 Non-Recognized Behaviors

Prohibited from triggering gamification: Transaction volume (number of entries), session length, time spent in app, number of screens visited, notification interaction rate, feature discovery, social sharing, referrals, in-app feedback submission. These metrics measure engagement with the app, not financial health. Including them would misalign the reward system with the user's actual financial well-being.

2.4 Behavior Detection Rules

  • Idempotency: Each behavior evaluation for a given time period produces at most one positive recognition event. BHV-D-01 fires at most once per month, regardless of how many times the budget is checked.
  • Retroactive evaluation: If a user enters historical data (past months), past behavior evaluations are re-run. Achievements unlocked retroactively are delivered as a summary notification, not as individual pop-ups.
  • Minimum thresholds: Growth behaviors (BHV-G-03, BHV-G-06) require a minimum absolute delta in addition to a percentage change, to prevent micro-fluctuations from generating recognition. Minimum delta is 1% of average monthly income or 100 centimes, whichever is larger.
  • Time window definitions: "Month" = calendar month. "Week" = ISO week (Monday–Sunday). All time window evaluations use the device's configured locale for week start, and UTC dates for month boundaries.
  • Deleted data handling: If a transaction triggering a past behavior is deleted, the achievement or streak credit for that period is revoked silently. No in-app notification for revocation (§18 edge cases).

§3 — Achievement Architecture

3.1 Achievement Type Taxonomy

One-Time Achievements

Unlocked exactly once. Celebrate a first meaningful event: first budget, first debt repaid, first goal achieved. Cannot be re-earned. Always displayed as permanently unlocked in the achievement collection.

Progressive Achievements

Multi-tier achievements that advance through levels (Bronze → Silver → Gold → Platinum). Each tier has a higher threshold. The user sees their current tier and progress toward the next. E.g., "Debt Fighter" at 1 / 3 / 6 / 12 debt payments on schedule.

Milestone Achievements

Celebrate crossing a specific quantitative threshold: FHS = 90, emergency fund = 6 months, first full year of planning. Predefined milestones listed in §6. These are the most emotionally significant achievements in the system.

Consistency Achievements

Tied to the streak system (§5). Awarded at streak milestone counts (3, 6, 12, 24, 36 months). Celebrate sustained habit formation over extended periods.

Mastery Achievements

Awarded when a user demonstrates expert-level financial management across multiple dimensions simultaneously: budget discipline + savings growth + FHS improvement in the same month.

Hidden Achievements

Not shown in the achievement collection until unlocked. Users discover them through natural financial behavior. Unlock message reveals what was achieved and why it was hidden. Examples: logging 100 total transactions (all categories), reaching FHS 90 within 12 months of first use.

Educational Achievements

Awarded for engaging with informational features: reading the monthly report, consulting the AI coach 10 times, reviewing the budget summary for 6 consecutive months. Encourage awareness without requiring financial improvement.

Recovery Achievements

Awarded for returning after a setback. Celebrate resilience, not perfection. E.g., "Back on Track" for resuming budgets after a missed month; "Phoenix" for restarting after 90+ days of inactivity.

Seasonal Achievements (Future)

Time-limited achievements unlocked during specific calendar periods (New Year planning, year-end review). Not implemented in v1; system architecture supports addition without model changes.

Long-Term Achievements

Require years of sustained financial management: 1 year of planning, 3 years of data, 5 years of financial history. These are the system's most prestigious recognitions.

3.4 Achievement Evaluation Engine

  • Trigger points: Achievement conditions are evaluated on: (1) every behavior event (BHV-*) fired, (2) month-end evaluation pass, (3) week-end evaluation pass, (4) FHS recalculation, (5) app launch (deferred evaluation for any pending events while offline).
  • Evaluation order: ONE_TIME → MILESTONE → RECOVERY → PROGRESSIVE → CONSISTENCY → MASTERY → EDUCATIONAL → HIDDEN. This order ensures single-session unlocks are processed in a meaningful narrative sequence.
  • Batch presentation: If multiple achievements unlock in the same evaluation pass, they are queued and presented to the user one at a time via the celebration modal, with a max of 3 per session. Overflow is delivered as a summary notification.
  • Deduplication: Each achievement_id can appear at most once in UNLOCKED state per tier. Duplicate evaluation results are silently discarded.
  • Offline evaluation: All evaluation runs locally. When the app is offline, achievement evaluations queue and fire on next app launch. No evaluation is blocked by connectivity state.

5.3 Grace Period Rules

Grace Period Design Principles
  • Each streak allows exactly one grace period per 6-period window. Using two grace periods within 6 months resets the streak.
  • Grace periods are applied automatically — the user does not need to invoke them or explain themselves.
  • A grace period is shown differently in the streak history (the "~" dot above) — not hidden, not treated as a hit. Honest representation of the history.
  • Grace periods do not reset the streak count. A streak of 5 with one grace used shows as a 5-streak, not 4.
  • Grace periods cannot be stacked. If a second consecutive period is missed, the streak resets regardless of grace availability.
  • After a streak resets, grace periods refresh on the new streak. The 6-period window starts fresh.
  • STK-07 (weekly) has the same grace rules but measured in weeks — one missed week per 6-week window.

5.4 Streak Reset Rules

  • Two consecutive misses: Streak resets to 0. Grace cannot be applied to the second consecutive miss.
  • Second grace within 6 periods: The second grace attempt is treated as a miss. Streak resets.
  • Reset is silent: No negative notification, no shame message. The streak counter quietly returns to 0. The next qualifying period starts a new streak from 1.
  • Reset is recorded: Streak history is retained (the ✕ dot persists in the visual history) so the user can see their long-term pattern honestly.
  • No penalty: A reset streak has no impact on any achievement progress. Consistency achievements (STK-01 at 12 months) require 12 consecutive qualifying periods — a reset simply means starting again, with no other consequence.

5.6 Streak Anti-Patterns Prohibited

  • No "streak freeze" purchasable or earnable items — they encourage app engagement over financial behavior.
  • No notifications that create urgency ("Your streak ends in 2 hours!").
  • No visual degradation (fire dying, meter depleting) as a period approaches without the behavior — negative pressure mechanics.
  • No negative messaging on streak reset.
  • No comparison of streak counts between users.
  • No streak leaderboard.

7.2 Progress System Design Rules

  • Always show the destination: Every progress element shows both the current state and the target. A progress bar with no endpoint teaches nothing about goals.
  • Upward-only framing: Visualizations frame history as accumulation (what has been built) not depletion (what's missing). The emergency fund ring shows "months covered" not "months to go."
  • Personal records: The system tracks personal bests for key metrics (highest savings rate in a month, longest streak, highest FHS) and highlights them in the visualizations as motivational reference points.
  • No comparative baselines: No visualization compares the user to "other users," "people like you," or any external cohort. All progress is measured against the user's own history and stated goals.
  • Sparse is better than dense: The main dashboard shows at most 3 progress indicators. Full collection and detailed progress accessible via deliberate navigation (Settings → Achievements, or dedicated screen). No unsolicited progress push.

  • FHS trend is shown as a sparkline alongside the timeline, keyed to months.
  • Net worth trend (if sufficient data) shown as an area below the timeline.
  • Achievement unlocks are layered as visual markers on the timeline — the user can see exactly when each achievement was earned relative to their financial trajectory.
  • A "beginning" marker shows the user's first recorded month, giving a sense of how far they have traveled.
  • This view is read-only and does not surface any underlying transaction values.

§9 — Challenge Framework

Challenges are optional, time-bounded behavioral commitments that the user explicitly opts into. They are entirely voluntary — declining, abandoning, or never starting a challenge has no negative consequence. Challenges translate good intentions into specific behavioral targets.

9.1 Challenge Design Principles

Opt-in only: No challenge is ever started automatically. No challenge is ever suggested with urgency framing. Challenges are discoverable from a dedicated "Challenges" section, never pushed via notification without permission.
  • Each challenge has a clear behavioral target, duration, and success criterion defined upfront.
  • Progress is visible to the user at any time during the challenge.
  • Abandoning a challenge silently removes it — no negative feedback, no "failed" state shown.
  • Challenges never require spending money, increasing debt, or any financially harmful action.
  • Challenges may adapt to the user's scale (e.g., "Save X% of income" not "Save €500").

9.4 Challenge Restart & Repeat Rules

§11 — Motivational Feedback & Messaging

Motivational messages are the primary voice of the GAM Engine. They appear at achievement unlocks, month-end summaries, challenge completions, streak milestones, and contextual encouragement moments. All messages are written to strict guidelines and localized for fr/en/ar.

11.1 Message Writing Guidelines

Mandatory Rules for All Messages
  • No financial amounts: Messages never state or imply specific amounts, percentages, or balances. "Your savings grew" is correct; "You saved €250" is prohibited.
  • No comparisons to others: No "most people don't…", no "better than average," no cohort framing.
  • No urgency or FOMO: No "Don't miss out on…", no countdown framing, no "before it's too late."
  • No shame or guilt: Even in recovery contexts, messages celebrate the return, never reference the absence.
  • Active voice: "You built security" not "Security was built."
  • Present tense for achievement: Describe what the user has now accomplished, not what they did.
  • Under 160 characters per message: Enforced at the localization layer. Messages must be concise enough to read in a glance.
  • Culturally neutral: No idioms, sports metaphors, or culturally specific references that may not translate. Reviewed by native speakers for each locale.

13.2 Active Safety Design Decisions

  • Grace periods as default: The grace period system (§5.3) is not a concession to imperfection — it is an active signal that financial life is not always consistent, and the app respects that.
  • Recovery achievements as first-class citizens: ACH-070 and ACH-071 are not consolation prizes — they are genuine recognition that returning after a setback is harder and more meaningful than uninterrupted streaks.
  • No achievement for high transaction volume: A user who enters 200 transactions in a month may be overspending. Rewarding transaction volume would reward potentially harmful financial behavior. This is explicitly excluded (§2.3).
  • Quiet Mode as a dignified exit: Users who feel overwhelmed by motivational features can exit cleanly and completely. The option is presented without question and without consequences (§12.3).
  • Messages reviewed by behavioral psychologists: All achievement and motivational messages are reviewed against the message guidelines (§11.1) by at least one person trained in behavioral health before publication.
  • No engagement metrics in the GAM Engine's own success criteria: The GAM Engine's success is measured by behavioral improvement indicators (savings rate trends, FHS improvement, debt reduction rates) — not by session frequency, achievement collection rate, or notification open rate.
  • Debt framing is never punishing: For PROF-DBT users, messaging always frames debt management as progress and autonomy ("you are choosing to reduce this"), never as deficiency or failure.

13.3 Distress Signal Handling

The GAM Engine is not a mental health system, but it operates in a domain (personal finances) that can be a source of significant stress. The following design decisions acknowledge this:

  • If a user has not interacted with the app for 90+ days and then returns, the recovery flow (BHV-R-01) fires without any reference to the gap duration or what was missed.
  • Month-end summaries for months with no budgets and no recorded transactions are not generated — there is nothing to summarize, and generating an empty summary would function as a reminder of absence.
  • The AI coach is the appropriate place for users to discuss financial stress or difficulty. The GAM Engine does not attempt to handle emotional content — it routes to encouragement, not advice.

§15 — Performance & Offline Behavior

The GAM Engine is a local-first subsystem. It must operate fully offline, consume minimal resources compared to the core financial data layer, and scale gracefully to years of achievement history and thousands of evaluations.

15.2 Offline Operation

  • All achievement evaluation logic operates on data stored locally in SQLite — no network request is required for any gamification function.
  • Behavior events generated offline are queued in the GAM event queue and processed at next app launch (or immediately if the app is running and the queue is processed).
  • Celebration animations and achievement displays do not require network access — all assets (icons, animation definitions) are bundled with the app.
  • Certificate and card exports work offline — the export is generated from local data and local assets only.
  • The Achievement Collection is fully available offline — no online check for achievement state.

15.3 Synchronization

Achievement state is part of the user's data and must be synchronized correctly across devices when multi-device support is added in future versions. Design decisions for sync-readiness:

  • Each achievement unlock event is stored as an immutable record with a ULID, a timestamp, the achievement_id, and the device_id that generated the unlock. This enables conflict-free merging (last-write-wins per achievement_id is inappropriate — earliest-unlock-wins is the correct policy).
  • Streak state is derived from behavior event history, not stored as a mutable counter. If behavior events sync correctly, streak state is automatically consistent across devices.
  • The GAM Engine's SQLite tables are included in the app's standard backup and restore process (§17.2).
  • In the event of a conflict (same achievement unlocked on two devices at different times), the earliest unlock timestamp is canonical.

15.4 Scalability to Long-Term Use

  • Achievement history: The achievement catalog is designed to grow — new achievements can be added in future versions. The evaluation engine processes only the active catalog for each evaluation pass; deprecated achievements are excluded from live evaluation but preserved in unlock history.
  • Streak history pagination: Streak dot timelines for users with 5+ years of data are paginated. Default view shows last 12 periods; full history accessible via scroll with virtualized rendering.
  • Behavior event queue: The GAM event queue is bounded — processed events are archived after the evaluation pass. The archive is compacted monthly (events summarized by month, raw events discarded after 90 days). This prevents unbounded growth in long-lived installations.
  • Month-end evaluation chunking: For retroactive evaluation (e.g., after re-enabling gamification), the engine processes months in reverse-chronological chunks of 6 months, yielding between chunks to prevent blocking the app for long-history users.
  • Achievement catalog upper bound: The v1 catalog contains ~70 achievements. The data model and evaluation engine are designed to handle up to 1,000 achievement definitions without schema changes.

15.5 Resource Consumption Targets

  • Memory: GAM Engine in-memory state ≤5MB during normal operation (active streak states, current evaluation context). Achievement collection loaded on demand, not permanently cached.
  • Storage: GAM Engine SQLite tables target ≤10MB for a 5-year user with full history. Event archive compaction ensures this bound is maintained.
  • CPU: Month-end evaluation pass must not consume more than 500ms of background CPU time. All GAM Engine processing is classified as P3 Normal priority in the background task queue (SPEC-PMO-001 §3.4).
  • Network: Zero network consumption for GAM Engine in v1. Analytics events for aggregate product insights (total achievement unlocks per type) use the opt-in anonymous business analytics pipeline defined in SPEC-PMO-001 §9.

16.2 GAM Settings Schema

All personalization settings from §12 are stored in the existing app settings table (SQLite) under the namespace "gam.*". No new table is required. Key names follow the pattern: gam.enabled, gam.celebration_intensity, gam.quiet_mode, etc. All settings are included in backup/restore.

16.3 Data Isolation

All GAM Engine tables are stored in the main app SQLite database alongside financial data, sharing the same AES-256-CBC encryption and WAL mode configuration. Achievement data is user data — it deserves the same protection as financial records. No financial values are stored in any GAM Engine table. The source_entity_id in the behavior event queue is a ULID reference, not a financial value or description.

§17 — Integration Points

The GAM Engine integrates with the other Finance Bag subsystems as a consumer of their events. It never modifies financial data; it only reads and reacts to financial state changes.

17.1 Financial Health Score (FHS) Integration

  • The GAM Engine subscribes to FHS recalculation events. On each FHS update, it checks whether any BHV-G-09 (FHS improved) or BHV-G-10 (FHS milestone) conditions are met.
  • The FHS value used for gamification is the same value displayed to the user — no separate calculation.
  • FHS improvements during gamification-disabled periods are evaluated retroactively when gamification is re-enabled, using the stored FHS history.
  • The GAM Engine reads FHS history for the motivation engine profile classification (§8.1) — PROF-ADV requires FHS >75 sustained over 24+ months.

17.2 Backup & Restore Integration

  • All GAM Engine tables are included in the standard app backup. A restore includes full achievement history, streak state, challenge history, and milestone history.
  • After a restore, the GAM Engine performs a consistency check: it re-derives streak states from the restored gam_streak_history table and compares to the restored gam_streak_state. Any discrepancy is resolved in favor of the history (the history is the source of truth).
  • Achievement states are not re-evaluated after restore — the restored states are trusted. A full re-evaluation is available as a manual developer action but not triggered automatically.
  • If the backup was created on a different app version with a different achievement catalog, the restore process checks for new achievements added since the backup date and evaluates them retroactively.

17.3 AI Coach Integration

  • The AI coach has read access to the user's achievement collection and streak states to provide contextual coaching. For example: if the user has STK-06 (Budget Discipline) at streak 5, the AI coach can acknowledge this when discussing budget performance.
  • The AI coach can suggest challenges (CHG-01 through CHG-10) when the setting "Challenge Suggestions" is enabled (§12.1). Suggestions are framed as offers, not commands: "Would a 30-Day Savings Sprint be useful right now?"
  • AI-generated personalized challenges (future) will use the same challenge schema and the same challenge lifecycle as catalog challenges (§9.3).
  • Achievement unlocks are never surfaced in the AI coach interface — the coach conversation is a separate context from the celebration flow.

17.4 Sync Engine Integration

  • GAM Engine tables are synced as part of the standard sync operation. Achievement state changes (unlocks, streak updates, challenge completions) are included in the sync payload.
  • Sync conflicts in GAM Engine data are resolved by the earliest-wins policy for achievement unlocks (the device that first achieved the unlock is canonical) and by history-merge policy for streak history (all period records from all devices are merged; the streak state is then re-derived from the merged history).
  • Behavior events that were queued while offline are evaluated when the app comes online, but the evaluation is based on the offline timestamp, not the sync timestamp — ensuring achievements are credited to the correct period.

17.5 Monitoring & Analytics Integration (SPEC-PMO-001)

  • GAM Engine operations are instrumented with performance traces (§5.3 of SPEC-PMO-001). Key traced operations: behavior event evaluation, month-end evaluation pass, retroactive evaluation, certificate generation.
  • Anonymous business analytics (opt-in) include: achievement unlock count by type (no user ID, no achievement name — category only), challenge start and completion rates, gamification feature enable/disable rate. No specific achievement identity is reported.
  • GAM Engine health is one of the optional health indicator subsystems in the Health Dashboard (SPEC-PMO-001 §8). GAM Engine DEGRADED state = evaluation queue stuck for >24 hours with processed events pending.

17.6 Notification System Integration

  • Gamification push notifications use the same notification infrastructure as budget alerts and reminders, governed by the same user notification settings.
  • Gamification notifications are a separate notification category — users can disable them independently of financial alert notifications.
  • The 1-per-day maximum for gamification notifications (§11.5) is enforced in the notification scheduler, not in the GAM Engine itself. The GAM Engine signals "a notable gamification event occurred" and the notification scheduler decides whether and when to surface it.

§18 — Edge Cases & Business Rules

18.1 Edge Case: Deleted Financial Records

Finance Bag uses soft deletes for financial records. A soft-deleted record is not included in calculations but is retained in the database. A hard delete (via data export + account deletion) permanently removes records.

  • Soft delete of a transaction that triggered BHV-G-01 (emergency fund contribution): The behavior event is considered retroactively invalid for the affected period. If the streak was maintained solely by that event, the period is reclassified as MISS. Streak counts are recalculated. If this causes an achievement unlock to be invalidated, the achievement state transitions to REVOKED silently.
  • Soft delete of a budget that triggered BHV-D-01 (budget respected): Same policy — the month's BHV-D-01 credit is removed. Streak and achievement states recalculated.
  • Hard delete (account deletion): All GAM Engine data is deleted along with all financial data. No achievement history survives account deletion.
  • User notification of revocation: Achievement revocations are silent — no "Your achievement was removed" message. The achievement collection simply reflects the current state. This avoids the distressing experience of receiving a negative notification about a past achievement.

18.2 Edge Case: Archived Months

  • When a month is archived, its financial data is read-only. Behavior evaluations for archived months are finalized and locked — no re-evaluation occurs unless the data is un-archived and modified.
  • Streak history for archived months reflects the state at archive time. If the month was qualifying, it shows as HIT. If not, MISS. Archive does not alter streak history.
  • Achievement progress counts from archived months remain credited. Un-archiving a month and deleting records triggers a retroactive re-evaluation only for the affected month.

18.3 Edge Case: Goal Cancellation

  • If a user cancels a financial goal, any BHV-G-04 (goal contribution) events tied to that goal are retained in achievement progress history — contributions were made, regardless of the goal outcome.
  • If the goal is archived as CANCELLED (not COMPLETED), ACH-023 (Dream Achieved) does not fire for that goal. Only COMPLETED goals count toward ACH-023.
  • ACH-043 (All Goals Achieved) requires all goals in ACHIEVED or ARCHIVED:COMPLETED state. A cancelled goal does not satisfy this condition.
  • CHG-06 (Goal Completion Push) that targets a cancelled goal transitions to ABANDONED state automatically when the goal is cancelled.

18.4 Edge Case: Debt Restructuring

  • When a debt is restructured (balance changed, schedule changed, existing debt archived and replaced with a new debt record), the streak for STK-02 (Debt Payment) is evaluated against the new schedule from the restructuring date.
  • Past payment streak history is preserved as-is for periods before restructuring. The new schedule defines qualifying behavior going forward.
  • If restructuring results in no outstanding debt (debt forgiven or paid off in restructuring), BHV-G-07 fires and the debt-free check runs.

18.5 Edge Case: Duplicate Achievements

  • The evaluation engine includes a deduplication check before writing any UNLOCKED state: if gam_achievement_state already contains an UNLOCKED record for the same achievement_id + tier pair, the duplicate evaluation result is discarded.
  • This prevents race conditions where the same behavior event triggers two evaluation passes simultaneously (e.g., two sync operations completing at the same time).
  • The deduplication check is enforced at the database layer via a UNIQUE constraint on (achievement_id, tier), not only in application logic.

18.6 Edge Case: Long Inactivity & Returning Users

  • A user returning after ≥30 days of inactivity: BHV-R-01 fires. The recovery motivation profile (PROF-RCV) activates. The welcome back message is shown on first session. No mention of absence duration or streak loss.
  • A user returning after 90+ days: BHV-R-01 fires + the "Phoenix" hidden achievement evaluates (ACH-071).
  • Streaks during inactivity: each month/week without a qualifying behavior during the inactive period is treated as MISS in the streak history. If consecutive misses exceed one, the streak resets. This is recorded in gam_streak_history but never surfaced to the returning user as a negative notification.
  • If gamification was enabled at departure and the user returns, the GAM Engine runs a catch-up evaluation for all periods during inactivity. Any achievements that would have been earned during inactivity (e.g., a long-term achievement based on account age, not behavior) are awarded in a silent batch on return.

18.7 Edge Case: Backup Restoration

  • Restoring from a backup resets all GAM Engine tables to the state at backup time. Any achievements unlocked between backup date and restore date are lost.
  • After restoration, the engine runs a forward evaluation pass from the backup date to the current date using the restored financial data. Achievements that should have been earned in the gap period are awarded retroactively in a silent batch.
  • If the restored backup is from a different app version, new achievements in the current catalog that postdate the backup are evaluated against all available historical data.
  • Certificate files (PNG/PDF) are not stored in the SQLite backup — they are regenerable on demand from the achievement record. No certificate data is lost in a restore; certificates can be regenerated from any UNLOCKED achievement.

18.8 Edge Case: Data Migration

  • When a user imports financial history from another app or from a previous version of Finance Bag, the GAM Engine evaluates all imported historical months in a background evaluation pass.
  • Achievements unlocked via imported data are delivered as a summary notification ("You've earned N achievements based on your imported history") rather than individual celebrations — the celebration moment is only meaningful for real-time events.
  • Streaks calculated from imported data use the same rules as live data. If the imported history shows continuous budgets for 14 months, STK-01 begins at 14.
  • The migration evaluation pass is the lowest priority background task (P4) and runs over multiple sessions if needed, to avoid impacting app performance during initial data import.

18.9 Business Rules — SPEC-GAM-001

BR-GAM-01 through BR-GAM-05
  • BR-GAM-01: No gamification event may fire in response to transaction volume (count of transactions entered). Only behavioral quality metrics (budgets respected, savings contributed, debts paid) may trigger recognition. This is structurally enforced by the behavior catalog (§2.3).
  • BR-GAM-02: All achievement unlock conditions must be evaluable using only locally available financial data. No achievement requires a server round-trip to evaluate. Gamification must be fully offline-capable.
  • BR-GAM-03: Achievement progress may never decrease while financial records are unchanged. If a data modification causes a decrease (e.g., record deletion), the decrease is applied silently with no negative notification to the user.
  • BR-GAM-04: No financial amount, balance, or transaction value may appear in any motivational message, achievement description, certificate, or celebration animation. Messages reference behavior and progress, never specific values.
  • BR-GAM-05: Streak grace periods are applied automatically, without user action or awareness in the moment. A grace period is not a "skip" that the user manages — it is an inherent feature of healthy streak design. Users see grace periods in their historical dot timeline, but no in-the-moment notification informs them that a grace is being applied.
BR-GAM-06 through BR-GAM-10
  • BR-GAM-06: The gamification system must be fully opt-out-able. Disabling gamification must have zero impact on all financial tracking features, budgets, reports, FHS calculation, AI coach, backup/restore, or sync. Gamification is additive recognition, never a core dependency.
  • BR-GAM-07: No challenge may be started automatically by the system. Challenges are always user-initiated. The AI coach may suggest a challenge in conversation (if "Challenge Suggestions" is enabled), but the user must explicitly tap "Start Challenge" in the Challenge Catalog — a coach suggestion cannot start a challenge.
  • BR-GAM-08: A maximum of 3 challenges may be active simultaneously. This limit is enforced at the data layer (the "Start Challenge" action is rejected if 3 ACTIVE challenges already exist) and confirmed in the UI before the limit is reached ("You can run up to 3 challenges at once — you have 1 slot remaining").
  • BR-GAM-09: No achievement may expire or become inaccessible after being unlocked. All earned achievements, titles, and certificates are permanently available in the user's collection for the lifetime of the account. A deprecated achievement is removed from the catalog (no new users can earn it) but remains visible to users who already earned it.
  • BR-GAM-10: The motivational message system must have one code path per profile-message category, reviewed and approved by a behavioral health consultant before shipping to production. No message may be shipped that was not included in this review. Ad hoc message additions in code are prohibited.
BR-GAM-11 through BR-GAM-15
  • BR-GAM-11: The GAM Engine may not compare any user's financial data, achievement count, streak length, or milestone status to any other user's. No inter-user data access is permitted in the GAM Engine's read paths. This constraint is structural: the GAM Engine reads only from the current user's local SQLite database.
  • BR-GAM-12: Recovery achievements (ACH-070, ACH-071) are held to the same quality standard as all other achievements. They are not consolation prizes — their motivational message must celebrate the act of returning with equal sincerity to any growth achievement's message.
  • BR-GAM-13: When the gamification system is re-enabled after being disabled, the retroactive evaluation pass must complete silently (no ceremony for past achievements). Only achievements earned in real time (after re-enabling) generate in-app celebrations. This prevents an overwhelming flood of celebration popups on re-enable.
  • BR-GAM-14: The evaluation engine must be idempotent: running the same evaluation pass twice on the same data must produce the same result and must not double-award any achievement or streak credit. This is enforced by the UNIQUE constraint (§18.5) and by checking existing state before writing new state.
  • BR-GAM-15: No gamification feature may create a notification that implies urgency, pending loss, or a deadline. Push notifications for gamification events communicate what was earned (positive), never what is at risk (negative). All notification copy must pass the message guidelines review (§11.1) before publication.
