§1 — Architectural Principles

Every significant architectural decision in Finance Bag flows from a small set of first-order principles. These principles are not aspirational statements — they are operative constraints that govern every design choice.

1.1 Core Principles

PrincipleOperative DefinitionArchitectural Impact
Offline-FirstThe application delivers 100% of its core functionality without a network connection. Connectivity enhances, never enables.All data stored locally in SQLite. Sync is background, additive. No screen requires a network call to render. Error states for network failure never block the user.
Privacy by DesignSensitive financial data never exits the device unencrypted. Telemetry is structurally incapable of carrying financial values. Consent is granular and revocable.AES-256-CBC encryption at rest (SQLCipher). Financial values excluded from monitoring API surface. Separate encrypted log DB. No financial content in push notification payloads.
Security by DesignSecurity is a structural property of the architecture, not a layer added afterward. Every boundary has a defined trust model.Biometric + PIN auth before any DB access. Keychain-stored encryption keys. No plaintext financial data in memory beyond the active session scope. Certificate pinning for sync API. Auto-lock on background.
Data Integrity Above AllIncorrect financial data is worse than no data. The system prefers failing safely over producing wrong results. Zero tolerance for duplicate financial records.All money as integer centimes (no floating-point arithmetic). Transactional writes with rollback. PRAGMA foreign_key enforcement. FHS invariant checks before every calculation. Sync conflict types A–G with deterministic resolution rules.
Clean ArchitectureBusiness logic is independent of frameworks, databases, and UI. Domain rules can be reasoned about, tested, and modified without touching infrastructure code.Strict layer boundaries: Domain has zero dependencies on React Native, SQLite, or Expo. Application layer orchestrates; Domain layer decides. Infrastructure adapters implement domain interfaces.
Separation of ConcernsEach module has one reason to change. The sync engine changes when sync protocol changes; the budget domain changes when budget rules change; they never change for each other's reasons.22 distinct modules (§4). Each owns its data, its business logic, and its public interface. No module directly reads another module's database tables.
Dependency InversionHigh-level policy (domain) never depends on low-level mechanism (SQLite, network, native APIs). Both depend on abstractions defined by the domain.Repository interfaces defined in Domain; implemented in Data. AI provider interface in Domain; Claude adapter in Infrastructure. Sync interface in Domain; CRDT implementation in Infrastructure.
TestabilityEvery business rule must be exercisable in a unit test without a device, a database, or a network. Test coverage is a first-class design constraint.Pure functions for all domain calculations. Repository interfaces allow mock injection. No business logic in React components (only UI state). 90% unit coverage target on domain layer (SPEC-QA-001).
Explicit Over ImplicitSystem behavior is determined by explicit configuration and code paths, never by convention magic, framework defaults, or environment inference.TypeScript strict mode with noUncheckedIndexedAccess, exactOptionalPropertyTypes. No implicit any. No optional chaining as error suppression. All nullable values handled explicitly.
ReversibilityArchitecture decisions that are hard to reverse require proportionally more justification. Prefer architectures that keep future options open over those that optimize for one predicted future.ULID primary keys (globally unique; no auto-increment coupling). Soft deletes only. Additive schema migrations. Feature flags for unreleased features. Layer interfaces allow swapping implementations.
Minimal FootprintThe application occupies the smallest reasonable amount of device resources (memory, CPU, storage, battery) at all times. Resource use is monitored and governed.Hermes JIT engine. Background task APIs (not continuous processes). 3-tier cache with bounded limits. Main thread prohibition list (SPEC-PMO-001 §3). WAL mode + mmap for DB efficiency.

1.2 Principle Hierarchy

When principles conflict, the following priority order governs. A lower-priority principle may never override a higher-priority one without an explicit ADR justifying the exception:

  1. Data Integrity (no financial data loss or corruption is acceptable under any circumstance)
  2. Security & Privacy (encrypted, consented, never exposed)
  3. Offline-First (full function without network)
  4. Clean Architecture (domain independence)
  5. Testability
  6. All other principles (Separation of Concerns, Reversibility, Minimal Footprint, Explicit Over Implicit)

§3 — High-Level Architecture

3.1 Layer Stack

Presentation Layer
React Native screens and components. Expo Router navigation. Zustand store subscriptions. No business logic. No direct DB access. Reads from store; dispatches actions. SPEC-DSN-001 governs all visual and interaction rules.
Application Layer
Use-case orchestrators. Coordinates between domain services and infrastructure. Manages transactions across repository boundaries. Emits domain events after successful operations. One use-case class per user action (CreateTransaction, CloseBudgetMonth, etc.).
Domain Layer
Pure TypeScript business logic. Entities, value objects, aggregates, domain services, repository interfaces. No imports from React Native, Expo, SQLite, or any infrastructure package. The Financial Hierarchy System (FHS) and all 6 invariants live here. FHS, budget calculation, debt amortization, goal projection, emergency fund coverage — all pure functions.
Data Layer
Repository implementations using drizzle-orm + SQLCipher SQLite. Schema definitions (drizzle tables). Migration runner. Materialized view refresh. Query builders. Prepared statement management. The data layer implements domain interfaces — it imports from Domain, never the reverse.
Infrastructure Layer
Platform adapters: Expo SecureStore (key management), Expo Notifications, Expo FileSystem, Expo Updates, NetInfo, expo-local-authentication. Sync engine CRDT implementation. AI provider adapter (Anthropic Claude). Monitoring signal emitters. Backup/restore file I/O. These are all replaceable without touching Domain or Application.
AI Layer
Standalone bounded layer. AI Provider interface (Domain-defined). Prompt composition. Context assembly (financial summary — no raw values). Response parsing and validation. Rate limiting and retry logic. Cache management. On-device model fallback interface (future). See SPEC-AI-001.
Cross-Cutting Layer
Logging (structured, 6 levels), caching (3-tier), localization (fr/en/ar + RTL), validation (Zod schemas), configuration (feature flags, env), monitoring (SPEC-PMO-001), security services, error boundary coordination, accessibility utilities. Consumed by all other layers; depends on nothing above Infrastructure.

3.3 Supplemental Subsystem Layers

Synchronization Layer

Offline-first CRDT sync engine. Queue management, conflict resolution (types A–G), retry with exponential backoff, connectivity state machine. Lives in Infrastructure; exposes a domain-level SyncRepository interface. SPEC-OFF-001.

Security Layer

Authentication (biometric + PIN), session management, encryption key lifecycle, auto-lock, export encryption, certificate pinning. Spans Infrastructure and Cross-Cutting. Every DB operation requires an active authenticated session. SPEC-SEC-001.

Notification Layer

Budget alert generation, scheduled reminders, gamification notifications, achievement alerts. Uses Expo Notifications (APNs/FCM). Governed by user consent and priority rules. Bounded at 1 gamification notification per day (SPEC-GAM-001 §11.5).

Analytics Layer

Anonymous, opt-in business metrics. 18 event types. No financial values. Structurally separated from technical monitoring. Batched transmission when online. SPEC-PMO-001 §9.

Gamification Layer

GAM Engine: behavior event detection, achievement evaluation, streak tracking, milestone engine, challenge framework. Reads financial domain events; writes only to gam_* tables. Full opt-out available. SPEC-GAM-001.

Monitoring Layer

4 signal types: metrics, logs, traces, health indicators. Device-local encrypted log DB. Financial values structurally excluded. Developer diagnostic tools. SPEC-PMO-001.

§4 — Module Map

Finance Bag is organized into 22 modules. Each module owns its domain entities, its application services, its repository interface, and its UI screens. Modules communicate only through domain events and well-defined public interfaces — never through direct cross-module table reads.

4.1 Core Financial Modules

MOD-01
Authentication & Session
Biometric + PIN auth, session tokens, auto-lock timer, failed attempt tracking, export PIN management. Gate for all other module access. Events emitted: SESSION_STARTED, SESSION_LOCKED, SESSION_EXPIRED. Dependencies: None (bootstraps before all others).
MOD-02
Financial Hierarchy System (FHS)
Core domain module. Defines the 5-level entity tree (Account → Period → Category → SubCategory → Transaction). Enforces 6 invariants. Owns entity definitions used by all financial modules. Events emitted: FHS_INVARIANT_CHECKED, FHS_VIOLATION_DETECTED. Dependencies: None (used by all financial modules).
MOD-03
Transaction Management
CRUD for income, expense, and transfer transactions. Centimes validation, category assignment, date entry, recurring transaction scheduling. Events emitted: TRANSACTION_CREATED, TRANSACTION_UPDATED, TRANSACTION_DELETED. Reads from: MOD-02 (FHS), MOD-06 (budget category validation).
MOD-04
Salary & Income
Salary entry, income tracking, monthly income baseline, variable income support. Events emitted: SALARY_ENTERED, INCOME_UPDATED. Consumed by: MOD-06 (budget baseline), MOD-10 (FHS calculation), MOD-21 (GAM behavior BHV-P-04).
MOD-05
Budget Engine
Monthly budget creation, category allocation, spending vs. budget tracking, budget rollover rules, month closing. Events emitted: BUDGET_CREATED, BUDGET_UPDATED, MONTH_CLOSED, BUDGET_LIMIT_APPROACHING, BUDGET_LIMIT_EXCEEDED. Reads from: MOD-03, MOD-04. Consumed by: MOD-10, MOD-12, MOD-21.
MOD-06
Category & SubCategory
Category hierarchy management, custom categories, system categories, icon and color assignment, category archiving. Events emitted: CATEGORY_CREATED, CATEGORY_ARCHIVED. Consumed by: All financial modules (category foreign keys).
MOD-07
Debt Management
Debt account creation, payment tracking, balance calculation, amortization schedule, debt payoff projection. Events emitted: DEBT_PAYMENT_RECORDED, DEBT_BALANCE_UPDATED, DEBT_FULLY_REPAID. Consumed by: MOD-10, MOD-12, MOD-21 (BHV-D-02, BHV-G-07).
MOD-08
Emergency Fund
Emergency fund balance tracking, coverage calculation (months of expenses), contribution recording, threshold alerts (1/3/6 months). Events emitted: EMERGENCY_CONTRIBUTION_RECORDED, EMERGENCY_FUND_MILESTONE_REACHED. Consumed by: MOD-10, MOD-21 (BHV-G-01, BHV-G-02).
MOD-09
Financial Goals
Goal creation (name, target amount, target date), goal contribution, goal progress tracking, goal completion, goal cancellation, goal dependencies (goal requires other goal as prerequisite). Events emitted: GOAL_CREATED, GOAL_CONTRIBUTION_MADE, GOAL_ACHIEVED, GOAL_CANCELLED. Consumed by: MOD-10, MOD-21.
MOD-10
Financial Health Score (FHS Calc)
FHS calculation engine consuming inputs from MOD-04–09. Weighted scoring across 6 dimensions. Monthly recalculation. Historical FHS storage. FHS trend analysis. Events emitted: FHS_RECALCULATED, FHS_MILESTONE_REACHED, FHS_IMPROVED. Consumed by: MOD-12 (dashboard), MOD-17 (AI), MOD-21 (GAM).

4.2 Presentation & Analysis Modules

MOD-11
Archive Engine
Month archiving, archive browsing, archive restoration, archive deletion. Immutable archive constraint enforcement. Events emitted: MONTH_ARCHIVED, ARCHIVE_RESTORED. Reads: All financial modules for month data. Archive tables are read-only after creation.
MOD-12
Dashboard
Aggregated summary view. Reads from Zustand store (denormalized from MOD-03–10). Never queries DB directly in render. Dashboard refresh triggered by domain events. Materialized view pattern for performance. No events emitted. Pure read module.
MOD-13
Reports & Analytics
Monthly report, annual report, category analysis, savings trend, debt reduction trend, net worth trend. All reports generated in background tasks. Paginated dataset processing. Events emitted: REPORT_GENERATED. Reads: All financial modules (read-only).
MOD-14

Full-text search across transactions (description, category, amount range, date range). SQLite FTS5. Search history (last 20 queries). No financial data in search index metadata. No events emitted.
MOD-15

CSV and PDF export generation, export encryption (optional), export file management. Background generation. Progress observable. Events emitted: EXPORT_COMPLETED, EXPORT_FAILED. Reads: All financial modules.

4.3 Infrastructure & Platform Modules

MOD-16
Synchronization Engine
CRDT-based offline-first sync. Operation queue management, conflict resolution (7 types A–G), connectivity state machine (ONLINE/OFFLINE/DEGRADED), exponential backoff retry, sync cycle metrics. Events emitted: SYNC_CYCLE_COMPLETED, SYNC_CONFLICT_RESOLVED, SYNC_ERROR. SPEC-OFF-001.
MOD-17
AI Coach Platform
Conversational AI coaching. Prompt composition (financial context without raw values), Claude API adapter, response streaming, conversation history, coaching session management, rate limiting, fallback responses. Events emitted: AI_COACH_CONSULTED, AI_COACH_ERROR. SPEC-AI-001.
MOD-18
Backup & Restore
Encrypted backup creation (AES-256-CBC, export PIN), backup scheduling, backup verification, restore from backup, cloud backup storage (Expo FileSystem + cloud adapter). Events emitted: BACKUP_CREATED, BACKUP_RESTORED, BACKUP_FAILED. SPEC-SEC-001.
MOD-19
Notifications
Budget alert generation, scheduled reminders, achievement notifications, permission management, notification preferences, notification history. Expo Notifications / APNs / FCM. SPEC-PMO-001 §11.
MOD-20
Monitoring & Diagnostics
4-signal observability (metrics, logs, traces, health indicators). Encrypted log DB. Performance profiler. DB inspector. Sync diagnostics. Diagnostic bundle export. Health dashboard. Alert engine (26 alerts ALT-001–026). SPEC-PMO-001.
MOD-21
Gamification Engine
Behavior event detection, achievement evaluation (30+ achievements), streak tracking (7 streaks), milestone engine (15 milestones), challenge framework (10 challenges), reward assignment. Fully opt-out-able. SPEC-GAM-001.
MOD-22
Settings & Configuration
User preferences, localization settings, security settings, notification preferences, gamification settings, privacy settings, theme selection, currency settings, feature flags. Settings stored in SQLite under namespaced keys. SPEC-SET-001.

5.5 FHS Invariants (Domain-Level)

These 6 invariants are checked by FHSCalculationService before every calculation. Any violation is an EMER alert (ALT-021) and halts all writes:

INV-1: Budget totals ≤ income INV-2: No negative emergency fund balance INV-3: Goal dependencies form a DAG (no cycles) INV-4: Debt balance = initial − Σ payments INV-5: Category totals = Σ transactions in category INV-6: FHS components sum to defined weight total

6.2 Money Representation Flow

User input (string "12.50") → Presentation: parse → 1250 centimes (int) → Domain: stored as int64 centimes → DB: INTEGER column, never REAL → Sync wire: integer JSON field → Display: centimes → locale string (presentation only)

Floating-point arithmetic on monetary values is prohibited at every layer. The ESLint rule no-floating-point-money enforces this at compile time.

§7 — Event Flow

7.1 Domain Event Bus

Finance Bag uses a synchronous, in-process domain event bus. Events are not persisted (except in the monitoring log). They are fire-and-forget within the same application operation cycle. Side-effect handlers (sync queue, GAM engine, monitoring) subscribe to events and execute asynchronously in background tasks.

Design decision: Synchronous event dispatch within the Application layer's transaction scope ensures that event handlers see the committed state. Side-effect handlers (sync, GAM, notifications) are scheduled as background tasks after the transaction commits — they never run in the write transaction scope.

7.3 Event Ordering Guarantees

  • Domain events are dispatched after their triggering write transaction commits. An event never describes data that might roll back.
  • Multiple events from a single use case are dispatched in declaration order. Handlers see a consistent state for all events in the same use case.
  • Background handlers are idempotent — if an event is replayed (e.g., after a crash during handling), the second execution produces the same result.
  • Events are not persisted (no event store in v1). If the app crashes between event dispatch and background handler execution, the handler is replayed on next launch via the pending evaluation queue in the GAM Engine and monitoring subsystems.

8.2 Dependency Injection Architecture

Finance Bag uses manual DI (not a DI container framework) for maximum transparency and testability. Dependencies are injected at module initialization time and resolved at application startup.

DI Wiring Pattern

Application startup creates a single CompositionRoot that instantiates all repositories (data layer implementations), all infrastructure adapters, and all application services, wiring them together explicitly. The CompositionRoot is the only place where concrete implementations are referenced. All other code depends on interfaces.

  • Repository interfaces → defined in Domain layer
  • Repository implementations → created in CompositionRoot using Data layer
  • Application services → created in CompositionRoot, receiving repository interfaces
  • Infrastructure adapters → created in CompositionRoot, passed to services that need them
  • Tests → create their own CompositionRoot with mock/in-memory implementations

8.4 Plugin Architecture for Future Extensions

Future modules (bank integrations, investment module, tax module) attach to the system via a defined plugin interface:

  • A plugin registers its bounded context with the CompositionRoot.
  • A plugin may subscribe to existing domain events from the event bus.
  • A plugin may expose new domain events to the bus.
  • A plugin owns its own SQLite tables (namespaced with the plugin prefix).
  • A plugin never modifies existing domain tables; it extends the model by addition.
  • A plugin is independently removable: its tables can be dropped, its event subscriptions removed, and the core system continues unchanged.

9.2 Error Boundary Architecture

Three-Level Error Boundary Strategy
  1. Screen-level React Error Boundary: Wraps each major screen. On error: logs to monitoring, shows screen-level error state ("Something went wrong on this screen") with a retry button. App navigation remains functional.

12.3 Security Cross-Cutting

Input Validation

All data entering the domain layer is validated by schema validators at the application service boundary. Raw UI input never reaches domain entities without validation. Validation errors are ERR-VAL class and surfaced to the user as field-level messages.

API Key Management

The Anthropic API key is stored in Expo SecureStore (iOS Keychain / Android Keystore), never in AsyncStorage, never logged, never included in error reports. The key is read once at startup and held in memory for the session duration only.

Biometric Gate

Biometric authentication (face ID / fingerprint) re-challenge fires on app foreground after 5+ minutes backgrounded. The SQLCipher key derivation is tied to the biometric-unlocked credential chain. Failed biometric attempts increment a counter; 5 consecutive failures trigger a forced re-auth flow.

Content Security

AI-generated text is treated as untrusted content: rendered as plain text, never evaluated, never injected into DOM as HTML. User-entered category names and note fields are sanitized of control characters before storage. No XSS vectors exist in a React Native context, but injection into SQLite is prevented by parameterized queries exclusively.

§13 Scalability Strategy

Finance Bag must remain performant across the full user lifecycle: from a new user with 10 transactions to a power user with 5+ years of financial history across multiple accounts. Every architectural choice must be validated against the long-horizon data scale.

13.1 Transaction Volume Scalability

Target scale

10,000+ transactions per user. 5+ years of daily entries = ~1,800 entries/year × 5 = 9,000 minimum. Power users: 20,000+.

SQLite indexing strategy

Composite indexes on (account_id, date DESC), (category_id, date DESC), (date, type). The query planner must use index scans, never full-table scans, for paginated list queries.

Pagination protocol

All list queries use keyset (cursor) pagination: WHERE date < :cursor_date AND id < :cursor_id LIMIT :page_size. Page size: 50 items. Offset pagination is forbidden (degrades with large tables).

Virtual rendering

FlashList with estimatedItemSize handles all transaction lists. The recycler pool is bounded; only visible + 2-screen buffer items are in memory. Smooth scroll to any position in 20,000-item list without jank.

13.3 Cloud Sync Scalability (Future)

When cloud sync is introduced (Phase 4), the following architectural constraints are established now to prevent lock-in:

  • CRDT-ready data model: All entities use ULID primary keys (globally unique, sortable) and updated_at vector clocks from day one. No sequential auto-increment IDs exist that would conflict during merge.
  • Soft deletes only: No hard deletes. Deletions are tombstoned. This enables three-way merge without loss.
  • Delta sync protocol: Sync payloads contain only records modified since the last successful sync timestamp. Full sync is a recovery path only.
  • Conflict resolution policy: Last-write-wins by updated_at for scalar fields. For monetary aggregates, the server holds the authoritative total and clients reconcile.
  • Bandwidth budget: Sync payload max 512KB per sync cycle. Records exceeding this are chunked. Attachments (future: receipt photos) are synced separately on Wi-Fi only.
  • Multi-device registry: Each device registers a UUID. The sync server tracks per-device cursors. Devices can operate fully offline for up to 30 days without losing sync eligibility.

Security price data (daily OHLCV) for potentially 100s of tickers. Requires a time-series optimised table with sliding window aggregation. Portfolio net worth feeds into Financial Health Score — the FHS domain service interface already accepts extension hooks for this.

Tax Module

Tax-year boundaries cross fiscal years in many jurisdictions. The existing fiscal-year configuration supports this without schema changes. Tax rule sets are static per jurisdiction-year; stored as versioned JSON blobs.

Family / Shared Finance

Requires a multi-tenancy concept layered above the current single-user model. The ULID-based data model supports namespace partitioning. The sync engine (Phase 4) is designed for this expansion — each family member is a device participant in a shared sync graph.

Business Finance

Double-entry bookkeeping requires a journal entry model parallel to the current transaction model. The domain layer's bounded context design isolates personal finance from business finance — they share the money value object and reporting infrastructure but have separate aggregate roots.

Desktop (Web / Electron)

The domain and application layers are platform-agnostic TypeScript. A web/desktop presentation layer can be added without modifying domain logic. SQLite via sql.js (WASM) or native better-sqlite3 replaces expo-sqlite at the infrastructure layer.

Wearable (watchOS / Wear OS)

Quick-add transaction via complication. The wearable communicates with the phone app via WatchConnectivity; the phone writes to SQLite and emits events. No direct database access on the wearable; it is a thin input terminal.

14.5 Database Migration Architecture

  • Migrations are managed by drizzle-orm and stored in src/infrastructure/db/migrations/.
  • Each migration file has an up and a down function. Down migrations are required and tested.
  • Migrations run at app startup, before the first database access. A migration lock prevents concurrent runs.
  • The migration version is stored in the app_metadata table and checked on each startup.
  • If a migration fails, the app enters a recovery mode with a user-visible error and instructions to contact support. The database is not partially migrated — all migrations are wrapped in a SQLite transaction.
  • Migration testing in CI: each migration is run against a snapshot of the previous schema to verify forward compatibility; each down migration is then applied to verify rollback.

§15 Risk Analysis

This section catalogues the highest-probability and highest-impact architectural risks, each with a defined probability, impact severity, and active mitigation strategy. Risks are reviewed at each major release milestone.

15.1 Risk Registry

RISK-01 SQLite Performance Degradation at Scale HIGH

Description: Query latency on the transactions table degrades beyond the 50ms budget as users accumulate 10,000+ records without proper indexing or pre-aggregation.

Probability: Medium (likely for power users within 2 years of use).

Impact: High (degraded UX on list screens and reports; user-visible lag).

Mitigations: (1) Composite indexes enforced at schema definition time. (2) Keyset pagination on all list queries. (3) Pre-aggregated monthly_summaries table maintained by domain events. (4) Hot/warm/cold data tiering for records >2 years old. (5) FlashList virtual rendering prevents render-side degradation. (6) CI performance benchmarks run on 10,000-record dataset.

RISK-02 SQLCipher Key Loss / Biometric Failure HIGH

Description: Loss of the SQLCipher encryption key (device reset, Keychain corruption, failed biometric enrollment) results in permanent data loss with no recovery path.

Probability: Low-Medium (device resets are common user behaviour).

Impact: Critical (permanent, irrecoverable data loss).

Mitigations: (1) Export-to-CSV or export-to-JSON available from day one — users can back up before device operations. (2) Cloud sync (Phase 4) provides the primary recovery path once available. (3) Key recovery flow using account password (Phase 4). (4) Clear in-app warnings before operations known to clear Keychain (e.g. full device reset). (5) Onboarding prompts user to export after first week of use.

RISK-03 Anthropic API Dependency Risk HIGH

Description: AI features are unavailable during Anthropic API outages, rate limit exhaustion, or pricing changes that make the feature economically unviable.

Probability: Medium (API outages occur; pricing evolves).

Impact: Medium (AI features degrade; core finance tracking unaffected).

Mitigations: (1) Graceful degradation: all AI features display cached results or helpful static content when API is unavailable. (2) 24-hour response cache reduces API dependency for repeat queries. (3) Rate limiting client-side: maximum 10 AI requests per user per day to control costs. (4) AI layer abstracted behind IAIProvider interface — alternative providers (local LLM, OpenAI) are drop-in replacements without domain changes. (5) AI features are explicitly optional; no core flow depends on AI availability.

RISK-04 React Native / Expo SDK Version Lag MEDIUM

Description: The ecosystem moves fast; delaying RN or Expo SDK upgrades accumulates compatibility debt and eventually requires a high-risk big-bang upgrade.

Probability: High (inevitable without active management).

Impact: Medium (upgrade risk; potential security vulnerabilities in outdated deps).

Mitigations: (1) SDK upgrade tracked on a quarterly cycle (not release-by-release). (2) Dedicated upgrade branch; full E2E test suite run before merge. (3) Expo managed workflow reduces native upgrade complexity. (4) Breaking change monitoring via Expo changelog subscription. (5) Architecture Decision Records document the current version lock-in rationale.

RISK-05 Sync Conflict Complexity (Phase 4) MEDIUM

Description: Multi-device sync introduces conflict scenarios (offline edits to the same transaction on two devices) that are hard to resolve without data loss or user confusion.

Probability: High once multi-device is enabled.

Impact: Medium-High (incorrect financial data if conflicts are silently wrong).

Mitigations: (1) CRDT-ready data model from day one (ULID keys, soft deletes, updated_at). (2) Last-write-wins with explicit conflict log — users can review and resolve. (3) Conflict detection at the aggregate level, not field level, to reduce false positives. (4) Conservative merge: when in doubt, preserve both versions and present to user. (5) Extensive conflict simulation in integration test suite before Phase 4 launch.

RISK-06 Technical Debt Accumulation MEDIUM

Description: Pressure to ship features causes shortcuts in architecture (bypassing domain layer, direct DB access from components, skipping tests) that compound into systemic fragility.

Probability: High without governance.

Impact: Medium (progressively slower velocity; bug surface expands).

Mitigations: (1) Architecture review gates on every PR touching domain or infrastructure layers. (2) Dependency cycle detection in CI (any cycle is a build failure). (3) 20% of each sprint reserved for technical debt reduction. (4) Module ownership matrix ensures clear accountability. (5) Tech debt log maintained in docs/tech-debt.md with severity and owner.

RISK-07 App Store Policy Changes LOW

Description: Apple or Google policy changes could require features to be removed, permissions to be changed, or review processes to be extended.

Probability: Low-Medium (policies evolve annually).

Impact: Medium (forced feature changes; potential rejection).

Mitigations: (1) Privacy-first architecture aligns with evolving App Store privacy requirements. (2) No use of private APIs or undocumented behaviours. (3) Annual review of App Store policy changes against current implementation. (4) Feature flags enable rapid removal of any feature that becomes policy-non-compliant without a full release.

RISK-08 Data Migration Failures LOW

Description: A schema migration that runs incorrectly in production corrupts user data or leaves the database in an inconsistent state.

Probability: Low (with proper CI testing).

Impact: Critical (data corruption is the worst user outcome).

Mitigations: (1) Every migration wrapped in a SQLite transaction — atomicity guaranteed. (2) Down migrations required and CI-tested. (3) Pre-migration backup export offered to users for major schema versions. (4) Migration tested against 10,000-record synthetic dataset in CI. (5) Staged rollout: migrations that have never run in production first deploy to 1% of users for 24 hours before wider rollout.

16.4 Versioning & Deprecation Policy

  • App versioning: Semantic versioning (MAJOR.MINOR.PATCH). MAJOR: breaking schema change or major UX overhaul. MINOR: new feature or bounded context. PATCH: bug fix or OTA-eligible change.

  • Feature deprecation: Features are deprecated via feature flag (set to forced-off), announced in the changelog, and removed after minimum 60 days from deprecation announcement.
  • Spec versioning: Each SPEC-* document has a version field in its header table. Spec amendments require a version bump and a changelog entry in the document itself.

18.2 Architecture Business Rules

BR-ARC-01
All money values throughout the system — in storage, in computation, in inter-module communication — must be represented as integer centimes (smallest unit of the currency). Floating-point arithmetic on monetary values is prohibited at every layer. The Money value object is the single enforcer of this rule; raw numbers may not be passed across bounded context boundaries in place of a Money instance.
BR-ARC-02
Domain entities and domain services must have zero dependency on any infrastructure concern: no SQLite imports, no network calls, no platform APIs (React Native, Expo), no Zustand stores. A domain entity or service that compiles only in a React Native context is an architecture violation. Domain code must be compilable and testable in a plain Node.js environment.
BR-ARC-03
Every public mutation in the system — every command that changes domain state — must be handled by an application service use case. Presentation layer components and Zustand stores must not write directly to the repository layer or domain entities. The application service is the sole orchestrator of: validation, domain operation, repository persistence, and event dispatch.
BR-ARC-04
Primary keys for all aggregate roots and entities must be ULIDs (Universally Unique Lexicographically Sortable Identifiers) generated at the domain layer, not at the database layer. Auto-increment integer IDs are prohibited. Sequential IDs that reveal record counts or creation order are prohibited.
BR-ARC-05
Physical deletion of records is prohibited throughout the system. All deletions must be implemented as soft deletes using a deleted_at timestamp. This applies uniformly to transactions, accounts, budgets, categories, debts, goals, achievements, challenges, and all other domain entities. The prohibition on physical deletion stands even when the user explicitly requests "delete everything" — PII fields are nulled, but the structural record (with ULID and timestamps) remains for sync integrity.
BR-ARC-06
The domain event bus operates synchronously for event dispatch (the handler chain executes before the originating use case returns), but event handlers that perform background work (cache invalidation, aggregate updates in other bounded contexts, gamification processing) must be registered as asynchronous and must not block the originating use case's response. No bounded context handler may fail the originating transaction — failures in event handlers are logged and retried in the background.
BR-ARC-07
No circular dependencies may exist between modules, bounded contexts, or layers. A module in the Gamification bounded context may subscribe to events from the Financial Tracking bounded context, but may not import types or call functions directly from that context's application layer. All cross-context communication is mediated by the domain event bus or explicitly defined anti-corruption layer adapters.
BR-ARC-08
All external dependencies (libraries, frameworks, APIs) are wrapped behind interfaces defined in the domain or application layer. No external library type, class, or function may be imported directly into domain entities, value objects, or application services. Third-party types that must cross this boundary are translated by adapter classes at the infrastructure layer boundary.
BR-ARC-09
Schema migrations are forward-only in production. A destructive migration (removing a column, dropping a table, renaming a column) requires a minimum two-version deprecation cycle: in version N, the column is stopped-being-written; in version N+1 (minimum 30 days after N), the column is physically removed. Every migration must have a functioning down migration that is tested in CI. Migrations that cannot be safely reversed must be explicitly flagged in the ADR as irreversible and require additional architectural review.
BR-ARC-10
The Anthropic API key must never appear in: log output (at any level), error reports (Sentry or otherwise), analytics events, exported data, network requests to any endpoint other than the Anthropic API, or local storage outside of Expo SecureStore. The key is accessed exactly once at application startup from SecureStore and held in the CompositionRoot's scope for the session lifetime only.
BR-ARC-11
Feature flags control feature visibility and rollout, not business logic. A feature flag must never be inside a domain entity or domain service. Feature flags are evaluated at presentation-layer entry points (screen components, navigation guards) or application-layer command handlers. The domain layer is always "on" — it never knows about feature flags. This ensures domain invariants are testable independently of flag state.
BR-ARC-12
All user-visible strings must be externalized to translation key files. Hardcoded English strings in component code are a linting error (CI failure). Translation keys must use the namespaced dot-path convention. ICU Message Format is mandatory for strings containing counts, genders, or conditional content. Missing translation keys fall back through the locale chain to en-US — they never display a raw key string to the user.
BR-ARC-13
All list queries against the SQLite database must use keyset (cursor) pagination. OFFSET-based pagination is prohibited due to performance degradation at scale. The pagination cursor must be based on a sortable field (typically date DESC, id DESC) and must be stable across data mutations (i.e., inserting a new record must not cause a page shift in existing cursors).
BR-ARC-14
The architecture specification (SPEC-ARC-001, this document) is the authoritative source of truth for all architectural decisions. In the event of a conflict between this document and any other specification, this document prevails for structural concerns (layers, modules, communication patterns, error handling, data representation). The domain-specific specification prevails for business logic within its domain. Genuine conflicts between documents must be resolved via the ADR process before implementation — code that implements a conflicting interpretation without an ADR is a technical debt item that must be resolved in the next sprint.
BR-ARC-15
No implementation code (executable TypeScript, JavaScript, SQL, shell scripts) may appear in any SPEC-* specification document. Specifications describe behaviour, constraints, interfaces, data models, and invariants in prose, tables, and diagrams only. Pseudo-code illustrating an algorithm or state machine transition is permitted, clearly labelled as non-executable. Any code found in a specification document must be removed before the specification is merged; this is a CI check on the docs/specs/ directory.

18.3 Architecture Principles Summary (Reference)

The 11 architectural principles (§1) are restated here as a quick reference, in hierarchy order:

  1. Data Integrity Above All — Correctness over convenience; financial data is trusted implicitly
  2. Security by Design — Encryption and access control are not add-ons
  3. Privacy by Design — Minimum data collection; maximum user control
  4. Offline-First — Full functionality without network; connectivity is an enhancement
  5. Clean Architecture — Strict layer boundaries; domain is the centre of gravity
  6. Separation of Concerns — Each module has one clear responsibility
  7. Dependency Inversion — Domain drives the design; infrastructure conforms to domain interfaces
  8. Testability — Every business decision testable in isolation from infrastructure
  9. Explicit Over Implicit — Errors thrown, not swallowed; state typed, not inferred
  10. Reversibility — Prefer decisions that can be undone over ones that cannot
  11. Minimal Footprint — Smallest dependency set, smallest bundle, smallest storage footprint that meets requirements
