Overview & Security Philosophy

The foundational principles that shape every security decision in Finance Bag — non-negotiable, not optional defaults.

1.1 The Core Premise

Financial information is uniquely sensitive. It reveals not just wealth but behaviour: where a person shops, what they owe, who they depend on, how much they earn. A breach of Finance Bag is not a data inconvenience — it is a personal violation. Every architectural decision in this specification begins from that premise.

Non-Negotiable Security Axioms
  • Security must never depend on a single defensive layer. If one layer fails, the next must hold.
  • Usability cannot be sacrificed — a security feature that users disable is worse than none at all.
  • All financial data is encrypted at rest. No unencrypted copy ever touches persistent storage.
  • No financial data leaves the device without explicit user action. Telemetry, analytics, and crash reports contain zero financial data.
  • The encryption key is never stored alongside the data it protects.

4.1 Authentication Model Overview

4.2 Local Biometric Authentication

Biometric Auth Flow
  1. App foreground event triggers auth check. If security.biometric_lock = true AND the last successful auth is older than security.auto_lock_timeout seconds, the auth screen is presented.
  2. The auth screen presents a biometric prompt via expo-local-authentication. The prompt message reads: "Unlock Finance Bag to access your accounts."
  3. On success: the DB encryption key is retrieved from expo-secure-store (TEE-backed) using the biometric auth result as authorization proof. The DB connection is opened with the key. The app proceeds.
  4. On failure: auth.failed_attempt_count (stored in-memory, never persisted) increments. After 3 failures, PIN entry is offered as fallback. After 5 total failures, the PIN entry is locked for a progressively increasing duration (15s → 30s → 60s → 5 min → 15 min → permanent lock requiring email recovery).
  5. On permanent lock: all in-memory data is cleared. DB connection is closed. The user must initiate the Account Recovery flow.

4.3 PIN Fallback

  • PIN is a 6-digit numeric code set during onboarding (required if biometric is enabled).
  • PIN is stored as a salted hash (Argon2id, memory=64MB, iterations=3, parallelism=1) in expo-secure-store — never in finance.db.
  • PIN salt is a random 32-byte value generated at PIN creation time, stored alongside the hash.
  • PIN verification happens in the app process. The hash is fetched from secure storage, the candidate is hashed with the stored salt, and compared in constant time.
  • PIN can only be changed after a successful biometric or current PIN verification.
  • A PIN that has never been set means biometric failure results in a "Contact support" message and no further fallback.

4.5 Future Cloud Authentication

When cloud features are activated, users create an account via email. The authentication model is passwordless by design.

Magic Link Email Flow (Future)
  1. User enters email address.
  2. Server generates a 64-byte random token (CSPRNG), stores a SHA-256 hash of it with 15-minute expiry, and sends the plaintext token as a URL in an email.
  3. User taps the magic link. The app receives the token via deep link.
  4. App sends token to server. Server hashes it and compares to stored hash. On match: issues a short-lived access token (JWT, 15-minute TTL) and a long-lived refresh token (opaque, 30-day TTL, stored in expo-secure-store).
  5. Server marks the magic link token as consumed (one-use only). A reused token returns 401 and triggers a security alert event to the user's email.
  6. Subsequent API calls use the access token in the Authorization header. Silent re-auth via refresh token happens when the access token expires.

5.3 Re-Authentication Gate Design

Re-Auth Gate UX Rules
  • The gate is presented as a modal sheet that temporarily covers the current screen. The user can dismiss it (cancelling the sensitive operation) or authenticate.
  • A 60-second window is granted after successful re-auth during which additional P2 operations in the same screen do not re-challenge. Navigating away resets the window.
  • The gate must clearly state what operation it is protecting: "Authenticate to export your financial data."
  • Failed re-auth closes the modal and cancels the operation. It does not count against the main session failure counter.
  • The gate cannot be bypassed by background/foreground cycling.

5.4 Future Administrative Permissions

When family profiles or business accounts are introduced, an additional P4 (Administrator) permission level will be defined. Administrators can: invite members, set org-level mandatory preferences, view shared categories, and remove members. The P4 gate requires email-based MFA in addition to biometric re-auth. This level is not implemented in v1.0 and this section serves as a reservation in the permission model.

Encryption Architecture

The complete encryption strategy across every storage layer — algorithms, key sizes, derivation methods, rotation procedures, and the hardware root of trust.

6.1 Database Encryption (At-Rest)

SQLCipher Configuration
  • Algorithm: AES-256-CBC (SQLCipher 4 default cipher)
  • PBKDF2 iterations: 256,000 (SQLCipher 4 default; PRAGMA kdf_iter = 256000)
  • HMAC: HMAC-SHA512 per page (page-level integrity)
  • Page size: 4096 bytes (SQLite default; cipher overhead per page is 16 bytes for salt + 32 bytes for HMAC)
  • Key type: Raw 32-byte binary key (not a passphrase). The key is passed as PRAGMA key = "x'<hex>'" using hex encoding.
  • Key source: Randomly generated 32 bytes at first launch, stored in expo-secure-store with requireAuthentication: true and authenticationPrompt set.
  • Both databases: finance.db and search.db use the same encryption key.

6.3 Key Derivation for Backup

The backup encryption key is never stored. It is derived from the DB_KEY at backup creation time using HKDF and a fresh random salt. The salt is stored in the backup file header (in plaintext — its purpose is to make each backup's derived key unique, not to protect the salt itself). Recovering the backup key requires the DB_KEY, which requires biometric auth. An attacker with a backup file but without the device (and thus without the DB_KEY) cannot derive the backup key.

Backup Key Derivation
  • backup_salt = random_bytes(16) — unique per backup, stored in backup header
  • backup_key = HKDF(IKM=DB_KEY, salt=backup_salt, info="finance-bag-backup-v1", length=32)
  • backup_iv = random_bytes(12) — unique per backup, stored in backup header
  • Backup ciphertext: AES-256-GCM(key=backup_key, iv=backup_iv, plaintext=gzip(db_wal_checkpoint))
  • Authentication tag: 16 bytes appended to ciphertext (GCM tag — covers the AAD of the backup header)
  • AAD (Additional Authenticated Data): JSON header bytes including app version, timestamp, schema version — authenticated but not encrypted

6.5 Key Rotation

DB Key Rotation Procedure
  1. Key rotation requires P2 re-authentication.
  2. Generate a new 32-byte random key: new_key.
  3. Open the existing DB with old_key.
  4. Execute SQLCipher's PRAGMA rekey = "x'<new_key_hex>'". This re-encrypts all pages in place without copying the database file.
  5. On PRAGMA rekey success: store new_key in expo-secure-store, replacing old_key.
  6. If any step fails: abort rotation, retain old_key. Log a SECURITY_EVENT to audit_log.
  7. After rotation: invalidate all existing backups (they used a BACKUP_KEY derived from the old DB_KEY and are now unrestorable without re-deriving with the old key, which no longer exists). Display a warning: "Your previous backups cannot be restored with the new key. Create a new backup now."

7.2 iOS Backup Exclusion

All files containing financial data must be excluded from the iOS iCloud backup mechanism. The NSURLIsExcludedFromBackupKey attribute is set to true on finance.db, search.db, the attachments/ directory, and the backups/ directory. The only files permitted in iCloud backups are app preferences that don't contain financial data.

Important: Encrypted backups are the intentional backup path

Finance Bag's .fbk files are the official backup mechanism. iCloud backup is explicitly disabled for financial data. Users who want cloud backup must use Finance Bag's own encrypted export to iCloud Drive or Google Drive (future). This ensures the backup key is always required to restore.

7.4 Clipboard Security

  • When a user copies a financial amount to clipboard, a toast displays: "Amount copied — will clear in 60 seconds."
  • A 60-second timer clears the clipboard using Clipboard.setString(''). If the user navigates away before 60 seconds, the timer continues in the background.
  • On iOS 16+, UIPasteboard.expiration is set to 60 seconds as a native fallback even if the app is killed.
  • The clipboard clear timer is cancelled if the user explicitly taps "Keep" on the toast.

7.5 Attachment Security

Receipts and images attached to expense records are encrypted individually before being written to disk. This approach ensures attachments are protected even if an attacker bypasses SQLCipher but gains raw file system access.

  • Encryption: AES-256-GCM. Key: derived from DB_KEY using HKDF with info="finance-bag-attachment-v1" and salt=expense.id bytes. This makes each attachment's encryption key unique to its associated record.
  • IV: 12 random bytes prepended to the ciphertext in the stored file.
  • File extension: .fbatt (Finance Bag Attachment). Content type not inferrable from extension.
  • Thumbnails: generated in-memory only, never written to disk. Rendered from the decrypted attachment buffer at display time.
  • Temporary decryption: decrypted to an in-memory buffer for display. Never written to /tmp or the OS temp directory.

7.6 Startup Integrity Check

On every cold app launch, before presenting any UI or opening the biometric gate, Finance Bag runs a non-blocking integrity check:

  1. PRAGMA integrity_check on finance.db (run in background thread after biometric auth).
  2. If integrity_check returns errors: present a "Database Integrity Warning" screen offering restore from backup or factory reset. Do not allow further reads from a corrupt DB.
  3. Schema version check: compare app_state.schema_version to the expected version for this app build. If a migration is needed, run it before opening the main app.
  4. Key availability check: confirm expo-secure-store can retrieve the DB key (without actually opening the DB — just checking the key slot exists). If the key is missing: present key recovery flow before biometric prompt.

Backup Architecture

A complete backup system with automatic scheduling, encryption, versioning, integrity verification, and a safe restore flow — all without transmitting unencrypted data outside the device.

9.1 Backup File Format (.fbk)

Finance Bag Backup files use the .fbk extension. The format is: a fixed-length plaintext header (JSON) followed by the AES-256-GCM ciphertext of a gzip-compressed SQLite WAL checkpoint of finance.db.

Backup File Structure
  • Magic bytes: FBKV1\x00 (6 bytes) — identifies Finance Bag Backup format and version
  • Header length: 4-byte little-endian uint32 — length of JSON header in bytes
  • JSON header (plaintext, AAD-authenticated): { "app_version": "1.0.0", "schema_version": 14, "created_at": "2026-07-12T03:00:00Z", "backup_salt_hex": "...", "backup_iv_hex": "...", "finance_db_size_bytes": 2048000, "record_counts": { "expenses": 342, "periods": 6, ... } }
  • GCM auth tag: 16 bytes (covers header as AAD + ciphertext)
  • Ciphertext: AES-256-GCM encrypted gzip of the WAL-checkpointed finance.db SQLite file

9.2 What Is Backed Up

  • All tables in finance.db (all financial data, preferences, audit log, event log)
  • search.db (regenerable, but included for faster restore)
  • Attachment files (individually encrypted .fbatt files)
  • DB encryption key (never leaves the Keychain/Keystore)
  • Device-specific preferences (sync_eligible: false) — biometric settings, auto-lock timeout
  • PIN hash (device-specific; user must re-set PIN after restore)
  • Session tokens (short-lived; invalid on restore)
  • OS-level cache data

9.4 Backup Creation Process

  1. Pre-auth: Backup creation requires P2 re-authentication (a sensitive operation that may produce exportable data).
  2. WAL checkpoint: Execute PRAGMA wal_checkpoint(FULL) to ensure all WAL pages are flushed to the main database file.
  3. File copy: Copy the database file to a temp location within the app sandbox (not /tmp).
  4. Compress: gzip the copied database file at compression level 6.
  5. Derive backup key: Fetch DB_KEY from expo-secure-store (biometric auth was already completed in step 1). Generate random 16-byte salt. Derive BACKUP_KEY via HKDF.
  6. Encrypt: AES-256-GCM encrypt the compressed data. Generate 12-byte random IV. Produce ciphertext + 16-byte GCM tag.
  7. Assemble .fbk: Write magic bytes + header length + JSON header + GCM tag + ciphertext to final backup file path.
  8. Verify: Attempt a test-decrypt of the first 4KB of the backup to confirm the file was written correctly.
  9. Register: Write backup metadata to app_state.backup_manifest_json.
  10. Cleanup: Delete the temp unencrypted copy.
  11. Log: Write BACKUP_CREATED event to audit_log.

9.5 Backup Restoration Process

Restore is destructive — all current data will be replaced

Restore replaces the entire current database with the backup contents. A pre-restore backup is automatically created before proceeding (§9.3 pre-operation type).

  1. P2 re-authentication required.
  2. Compatibility check: Read backup JSON header. Compare schema_version to current app's minimum supported restore schema version. If the backup is older than supported, reject with a clear message. If the backup is newer (from a future app version), reject with upgrade prompt.
  3. Pre-restore backup: Automatically create a pre-operation backup of current data (step 3 in §9.4, abbreviated). If this backup fails, abort the restore.
  4. Derive restore key: Fetch DB_KEY from expo-secure-store. Read backup_salt from .fbk header. Derive BACKUP_KEY via HKDF.
  5. Decrypt and verify: AES-256-GCM decrypt. GCM tag verification is performed by the cipher — any tampering causes decryption to fail with an authentication error. If decryption fails: abort, leave current DB intact, present error.
  6. Decompress: gzip decompress to a temporary SQLite file in app sandbox.
  7. Integrity check: Open the temp SQLite with DB_KEY. Run PRAGMA integrity_check. If it fails: abort, delete temp file, present error.
  8. Migrate: If backup schema_version is older than current schema, run forward migrations on the temp DB.
  9. Replace: Close all current DB connections. Rename temp DB file to finance.db. Reopen DB connection.
  10. Post-restore: Trigger REBUILD_SEARCH_INDEX event (search.db rebuilt from restored finance.db). Display "Restore complete. Your data has been restored to [backup date]." PIN reset prompt if PIN was stored (device-specific, not in backup).
  11. Log: Write BACKUP_RESTORED event to audit_log.

9.6 Incremental Backup (Future)

v1.0 uses full database backup (the entire finance.db file). This is appropriate given typical database sizes at year 1 (≈2–5 MB). When database sizes grow beyond 20 MB (projected at year 3+ for heavy users), incremental backup based on SQLite WAL page tracking or change journal will be introduced. The .fbk format version field accommodates this — version 2 will support incremental payloads with a delta manifest in the header.

Cloud Synchronization

An offline-first synchronization architecture that is CRDT-compatible, privacy-preserving, and conflict-aware — designed for future activation without architectural surgery.

v1.0 Status: Architecture Defined, Not Yet Activated

Cloud synchronization is not active in v1.0. This section specifies the full architecture so that when cloud sync launches, no data model changes are required. All ULIDs, updated_at timestamps, and sync_eligible preference flags are already in place as sync readiness hooks (SPEC-DB-001 §14).

10.1 Synchronization Principles

  • Offline-first: The local database is always the source of truth for the current device. Sync is an eventual consistency mechanism, not a dependency. The app functions identically with or without a network connection.
  • No financial data in transit without user account: Sync requires an explicit cloud account creation. Anonymous users remain fully local.
  • Preference sync separate from data sync: Preferences (sync_eligible=true) are synced as a lightweight JSON document. Financial data sync is a larger, more complex operation introduced in a later phase.
  • Conflict resolution is deterministic: All conflicts resolve by a defined rule — no ambiguous merge states.
  • Zero-knowledge architecture (goal): The server stores only encrypted data. The cloud provider cannot read user financial data. All encryption and decryption happens on-device.

10.2 Synchronization Phases

PhaseWhat syncsWhen activated
Phase 1 — Preference SyncAll preferences with sync_eligible = true. This is a small JSON document (typically <5KB). Does not include financial data.On cloud account creation (future)
Phase 2 — Backup SyncEncrypted .fbk backup files uploaded to user's cloud storage bucket. Server stores opaque ciphertext only.After Phase 1 is stable

10.3 Conflict Detection and Resolution

Conflict Classification
  • Type A — No conflict: Changes to different records on different devices. Resolution: merge both. Winner: all changes applied. No user notification required.
  • Type B — Same record, non-overlapping fields: Device A changes expense.category_id; Device B changes expense.notes. Resolution: field-level merge. Both changes applied. No user notification.
  • Type C — Same record, same field, different values: Device A changes expense.amount_cents to 5000; Device B changes it to 6000. Resolution: last-write-wins on updated_at (device clock skew tolerance: ±60 seconds; ties broken by device_id lexicographic order). User notified via a "Sync merged changes" digest notification (max 1 per day).
  • Type D — Delete vs. update: Device A soft-deletes a record; Device B updates the same record. Resolution: delete wins. The update is discarded. This prevents "ghost resurrection" of deleted data.
  • Type E — Archive conflict: A period is sealed on one device while the other device has unsynced changes to that period. Resolution: the sealed period takes precedence (archives are immutable per SPEC-DB-001 §5). The conflicting changes are surfaced to the user as "Changes that could not be applied."

10.4 Sync Payload Security

  • Preference sync payload: JSON document encrypted with a SYNC_KEY derived from the user's cloud account credentials (via HKDF). The server stores the ciphertext; the plaintext is never on the server.
  • Backup sync payload: .fbk files are already encrypted per §9. Uploaded as-is to cloud storage. No additional encryption layer needed.
  • Live data sync payload (Phase 3): Delta records encrypted per-field or per-record using the DB_KEY-derived SYNC_KEY. Server cannot read individual field values.
  • Sync token: The cloud auth session token (§4.5) authorizes all sync API calls. It is separate from the SYNC_KEY. Compromising the session token does not expose data decryption capability.

12.4 Session Security Hardening

  • No session ID on disk: The local session (P1/P2) is represented only by in-memory flags. It cannot be stolen via file access.
  • JWT claims validation: On every access token use, the app validates: iss (issuer), aud (audience = app's bundle ID), exp (expiry), iat (issued-at, not more than 15 min ago), sub (user ID matches stored user ID). Any claim mismatch triggers immediate session invalidation.
  • Token binding (future): Access tokens will be bound to the device's public key (DPOP — Demonstrating Proof of Possession, RFC 9449). This prevents token replay from a different device even if the token is extracted from memory.
  • Concurrent session limits: Maximum 5 concurrent cloud sessions (one per registered device). A 6th device login invalidates the oldest session.

  • Magic link one-use: As described in §4.5, magic link tokens are marked consumed on first use. A replayed magic link returns 401 and triggers a security alert email.
  • Local event deduplication: EventBus deduplication (idempotency keys per SPEC-EVT-001) prevents replay of automation events within Finance Bag's own event pipeline.

14.4 Anti-Tampering

  • Code signing: iOS: mandatory Xcode signing with Apple Developer certificate; App Store distribution adds additional Apple signature. Android: mandatory APK signing with keystore; Play App Signing adds Google signature layer.
  • No debug builds in production: __DEV__ flag is false in release builds. Developer options require 7-tap unlock (§14.5 SPEC-SET-001). ADB debugging not possible on production iOS.
  • Database integrity check on startup: PRAGMA integrity_check detects page-level corruption or tampering with the SQLite file structure. SQLCipher's HMAC per page also detects bit-flip tampering at the cipher level.
  • Backup HMAC: AES-256-GCM authentication tag covers the entire backup ciphertext. Any byte modification causes decryption to fail with an authentication error.
  • Binary obfuscation (future): JavaScript bundle obfuscation via Metro bundler + Hermes bytecode compilation. Not implemented in v1.0 — noted as a future hardening measure against reverse engineering.

Future Security

Architecture reservations and forward-compatibility slots for the next generation of security capabilities — designed to activate without structural changes to the current model.

18.1 Passkeys / WebAuthn

Passkey Architecture (Future)

Passkeys (FIDO2 WebAuthn resident credentials) will replace the magic link flow for cloud authentication. The user's device generates an asymmetric key pair (P-256 or Ed25519), stores the private key in the Secure Enclave / Android Keystore, and registers the public key with Finance Bag's server.

  • Local biometric auth (Face ID / fingerprint) unlocks the Secure Enclave key to sign the WebAuthn challenge — same hardware path as the current DB key retrieval.
  • The same biometric challenge that unlocks the database can simultaneously sign the cloud auth challenge. Users experience a single "face unlock" that does both.
  • Passkeys are synced cross-device via iCloud Keychain (iOS) and Google Password Manager (Android), providing built-in account recovery without relying on Finance Bag's servers.
  • Backward compatibility: magic link email remains as passkey fallback on devices that do not support FIDO2 (iOS 15 and older, Android without FIDO2 authenticator).

18.2 Hardware Security Modules (HSM) for Cloud

When Finance Bag's cloud infrastructure is established, encryption keys used for server-side operations (sync payload signing, backup integrity verification keys) should be managed by a cloud HSM (AWS CloudHSM, Google Cloud HSM, or Azure Dedicated HSM) rather than software key stores. HSM provides FIPS 140-2 Level 3 or higher assurance. Key operations occur inside the HSM boundary; key material never leaves the HSM in plaintext. This is a server-side concern only — user data encryption keys always remain on-device.

18.3 Certificate Pinning

Before cloud features launch, certificate pinning must be implemented to prevent MITM attacks on the Finance Bag API even if a CA is compromised. Implementation approach:

  • Pin subject public key (SPKI): Pin the SHA-256 hash of the server's public key (not the full certificate). This allows certificate rotation without a client app update, as long as the key pair is retained.
  • Backup pins: Include at least 2 backup pins (for the root CA and an intermediate CA) to prevent an app update being required if the primary pin must be rotated urgently.
  • Pin rotation process: New pin pushed to app 30 days before old pin expires. Old pin and new pin both active during the overlap window. App update enforced when old pin expires.
  • Bypass for debugging: Certificate pinning bypass is available in debug builds only (controlled by build flag). Never in production.

18.4 AI Fraud Detection

A future AI-powered anomaly detection layer will analyze behavioral signals (server-side only — no on-device ML model in v1.0) to identify suspicious account activity. Signals considered:

  • Login location changes (country, timezone)
  • Device change patterns (new device + immediate full export)
  • Bulk data operations (mass expense deletion within minutes of login)
  • Sync payload anomalies (unusual size, unusual entity type distribution)
  • Velocity signals (3+ magic link requests in an hour)

The AI model produces a risk score (0.0–1.0) for each session event. Scores above 0.7 trigger a hold + user verification. Scores above 0.9 trigger an automatic session freeze. All AI decisions are logged and reviewable by the user in an "Account Security" view. No AI decision is irreversible without human confirmation.

18.5 Behavioral Authentication

Passive biometric signals (typing rhythm, swipe pattern, hold angle) can supplement or replace active biometric challenges for low-stakes in-app operations. Architecture slot:

  • A BehavioralAuthProvider interface is reserved in the auth layer. It receives interaction events from the React Native gesture responder and produces a continuous confidence score (0.0–1.0).
  • When confidence drops below a threshold (e.g., 0.6 sustained for 30 seconds), the app re-triggers an active biometric challenge as if the auto-lock had fired.
  • Behavioral auth is always supplementary — it cannot replace biometric hardware for key retrieval (which requires a hardware-verified challenge). It only controls the P1 → P2 escalation timing.
  • All behavioral data is processed on-device in real time. No behavioral signals are transmitted to any server. Feature is off by default; user opts in.

18.6 Secure Cloud Vault

A future Finance Bag premium feature: a zero-knowledge cloud vault where users store financial documents (tax returns, insurance certificates, contracts) with end-to-end encryption. Architecture principles:

  • Zero-knowledge: Files are encrypted on-device before upload. The Finance Bag server stores only ciphertext. Server cannot read vault contents even with full database access.
  • Key hierarchy: Vault encryption key derived from DB_KEY + a vault-specific HKDF derivation. Independent of the backup key derivation path.
  • Sharing: Selective vault item sharing uses envelope encryption — the item is encrypted with a random content key; the content key is encrypted with the recipient's public key (from their passkey). Only the intended recipient can unwrap the content key.
  • Deduplication without knowledge: Server-side deduplication uses deterministic encryption (AES-SIV) to identify duplicate uploads without knowing the plaintext. This is opt-in only (deterministic encryption is less secure than probabilistic but enables storage savings).
