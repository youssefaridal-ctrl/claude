01

Overview & Module Identity

Reads from SPEC-BUD-001 SPEC-DBT-001 SPEC-EMF-001 SPEC-GOL-001 SPEC-RMP-001 SPEC-DSH-001

The Reports & Analytics module is a read-only intelligence layer that answers the questions every financial app must ultimately answer: where is my money going, am I improving, and what should I do next? It operates over the complete historical record written by all other modules and produces structured report objects, analytical metrics, and personalized insights.

Unlike the Dashboard (which shows the current moment), Analytics shows trends across time. Unlike individual module screens (which show a single domain), Reports provide a cross-module picture — income, budget, debt, EMF, and goals in a single view.

Core Questions Answered

Where is money going?Category-level spending breakdown with period-over-period change rates
Are habits improving?Behavioral metrics: savings consistency, budget discipline score, debt repayment reliability
Am I financially healthier?FHS trend over time; component-level drill-down showing which dimension changed
What should I improve?Ranked improvement recommendations derived from the behavioral analytics engine
What trends to watch?Trend indicators with directional arrows and projected trajectories

Module Scope

  • 7 report types spanning daily through lifetime financial history
  • Standardized Financial Summary block included in every report
  • 10 advanced analytics metrics with formulas and interpretations
  • Comparison engine for period-over-period, year-over-year, and custom-range analysis
  • Cash flow analysis with liquidity and forecast readiness
  • Behavioral analytics: 10 habit scores with trend direction
  • AI-ready insights engine with structured Observation / Explanation / Recommendation / Impact format
  • FHS historical record — 12-month rolling store
  • 10 visualization types mapped to specific analytics
  • Export system: PDF, CSV, Excel (future), print-friendly
  • Search & filter system with saved filters
  • Predictive analytics architecture for AI integration
ℹ️
Read-only module. The analytics engine never writes to module tables. All computations are derived from stored primitives at query time. Computed report fields are never persisted. Exception: the FHS historical record (Section 10) is written daily by a background task and stored in a dedicated fhs_history table — this is the only persistent output owned by the RPT module.

Data Architecture

2.1 RPT-Owned Tables

The RPT module owns exactly two persistent tables:

table fhs_history { id: TEXT PRIMARY KEY // UUID v4 date: TEXT NOT NULL UNIQUE // ISO date 'YYYY-MM-DD' fhs_total: INTEGER NOT NULL // 0–100 savings_pts: INTEGER NOT NULL debt_pts: INTEGER NOT NULL emf_pts: INTEGER NOT NULL budget_pts: INTEGER NOT NULL goal_pts: INTEGER NOT NULL stability_pts: INTEGER NOT NULL created_at: INTEGER NOT NULL // Unix ms } // Retention: 365 days. Rows older than 365 days are deleted in background cleanup. // Written once per calendar day by the analytics background task on first app open. table saved_filters { id: TEXT PRIMARY KEY name: TEXT NOT NULL // User-defined label, max 40 chars filter_json: TEXT NOT NULL // JSON-serialized ReportFilter object created_at: INTEGER NOT NULL deleted_at: INTEGER // Soft delete }

2.2 Report Object (In-Memory)

type Report = { id: string // deterministic: 'RPT-MONTHLY-2026-07' type: ReportType generatedAt: number // Unix ms periodStart: string // ISO date periodEnd: string // ISO date summary: FinancialSummary // Section 4 analytics: AnalyticsBlock // Section 5 cashFlow: CashFlowBlock // Section 7 behavioral: BehavioralBlock // Section 8 insights: ReportInsight[] // Section 9 comparisons: ComparisonBlock | null // Section 6 — only when prior period exists charts: ChartDataBlock // Section 11 } type ReportType = 'DAILY' | 'WEEKLY' | 'MONTHLY' | 'QUARTERLY' | 'YEARLY' | 'CUSTOM' | 'LIFETIME' type ReportFilter = { dateRangeStart: string | null dateRangeEnd: string | null categoryIds: string[] goalIds: string[] debtIds: string[] minFhsScore: number | null maxFhsScore: number | null tags: string[] includeArchived: boolean }

2.3 Analytics Query Strategy

  • All aggregate queries run against expo-sqlite using SUM(), AVG(), COUNT(), MIN(), MAX() at the database level — no in-JS row iteration
  • Reports spanning multiple periods use a period table join — not a calendar month grouping — to respect salary-period alignment from SPEC-BUD-001 BR-01
  • Soft-deleted records (deleted_at IS NOT NULL) are excluded from all analytics except the LIFETIME report's "archived items" section
  • Report generation runs on a background worker thread; the UI shows a loading skeleton while the query executes
  • Generated reports for standard types (DAILY, WEEKLY, MONTHLY) are cached in Zustand for the current session; cache is invalidated on any module write
03

Report Types

RPT-DAILY
Daily Report
Covers a single calendar day. Purpose: track what was spent today vs. the daily budget rate. Shows today's expenses by category, running period total, and a simple "on track / off track" indicator based on period pacing. Useful for users who log expenses daily. Comparison: today vs. same weekday last week.
RPT-WEEKLY
Weekly Report
Covers Mon–Sun (or a 7-day rolling window). Purpose: weekly spending rhythm — which categories spiked, what portion of the period budget has been used in the first N days. Week-over-week trend bar for top 5 categories. Reminder to record missing expenses if any day has zero activity.
RPT-MONTHLY
Monthly Report
Covers one calendar month OR one salary period (user chooses; default: salary period). The primary report type. Full Financial Summary, all analytics sections, behavioral scores, and comparison to prior month. Includes FHS component breakdown and goal contribution summary.
RPT-QUARTERLY
Quarterly Report
Covers 3 consecutive months/periods. Purpose: medium-term trend detection. Aggregates monthly data to reveal seasonal patterns. Shows which quarter goals were hit, EMF milestone progression over the quarter, and debt reduction rate. Comparison: current Q vs. prior Q.
RPT-YEARLY
Yearly Report
Covers 12 months. Purpose: annual financial review — savings rate evolution, total debt paid this year, total goal contributions, EMF growth, FHS evolution from Jan to Dec. Full 12-month bar chart for income/spending. Highlights: largest single expense, best savings month, worst budget month.
RPT-CUSTOM
Custom Range Report
User-defined start and end date. Any duration from 1 day to lifetime. All available analytics sections are included if data exists for the range. Required when comparing two specific non-standard periods. Filter presets can save custom ranges.
RPT-LIFETIME
Lifetime Financial Report
Covers all recorded history from the first salary period to today. Purpose: long-term financial biography. Total income ever recorded, total debt ever paid, total saved, net position change, all achieved milestones, all completed goals, FHS high and low points. Export-focused — designed as a shareable PDF summary.

3.1 Report Period Resolution

// For each ReportType, resolve the period boundaries: DAILY: periodStart = today; periodEnd = today WEEKLY: periodStart = startOfCurrentWeek; periodEnd = endOfCurrentWeek MONTHLY: periodStart = currentSalaryPeriod.start; periodEnd = currentSalaryPeriod.end // OR: periodStart = firstDayOfMonth; periodEnd = lastDayOfMonth QUARTERLY: periodStart = firstDayOf(currentQuarter); periodEnd = lastDayOf(currentQuarter) YEARLY: periodStart = Jan 1 of current year; periodEnd = Dec 31 of current year CUSTOM: periodStart = filter.dateRangeStart; periodEnd = filter.dateRangeEnd LIFETIME: periodStart = MIN(salary_period.start_date); periodEnd = today

3.2 Data Availability Guards

  • If the requested period has no recorded income: summary fields that depend on grossIncome are shown as "—" (not 0)
  • If a period spans fewer than 3 salary periods, quarterly trend analytics show available data with a "Limited data" badge
  • LIFETIME report requires at least 1 completed salary period; otherwise a "Not enough data" state is shown
  • DAILY report only shows "today vs. same weekday last week" comparison if same-weekday data exists

Advanced Analytics Engine

The analytics block computes 10 cross-period metrics that reveal financial trajectory, not just point-in-time state. Each metric includes a value, a trend direction, and a plain-language interpretation.

5.1 AnalyticsBlock Type

type AnalyticsBlock = { incomeGrowthRate: AnalyticMetric spendingGrowthRate: AnalyticMetric debtReductionRate: AnalyticMetric emfGrowthRate: AnalyticMetric goalFundingRate: AnalyticMetric savingsRateTrend: AnalyticMetric cashFlowTrend: AnalyticMetric financialStability: AnalyticMetric budgetDisciplineScore: AnalyticMetric behaviorEvolution: AnalyticMetric } type AnalyticMetric = { value: number unit: string // '%', 'centimes', 'pts', etc. trend: Trend // 'UP' | 'DOWN' | 'STABLE' | 'INSUFFICIENT_DATA' trendPct: number | null // % change vs comparison period label: string // metric name interpretation: string // max 120 chars — what this value means }

5.2 Metric Formulas & Interpretations

MetricFormulaPositive Trend Means
Income Growth Rate(avgIncome_current − avgIncome_prior) / avgIncome_prior × 100Earning more per period — income is rising
Spending Growth Rate(totalSpent_current − totalSpent_prior) / totalSpent_prior × 100Spending more — investigate if income grew proportionally
Debt Reduction RatetotalDebtReduced / totalDebtAtStart × 100 (per period)Paying down debt faster — momentum building
EMF Growth Rate(emfEnd − emfStart) / emfStart × 100Emergency fund growing — safety net strengthening
Goal Funding RatetotalGoalContribs / SUM(requiredMonthlyContribution) × 100Contributing as planned or above — goals are funded
Savings Rate TrendsavingsRatePct_current − savingsRatePct_prior (pp change)Saving a larger fraction of income — trajectory improving
Cash Flow Trend(totalIncome − totalSpent − totalDebtPayments) delta ppMore net cash remaining — financial breathing room increasing
Financial StabilitySTDEV(monthlyFHS, last 6 months) — lower = more stableLower standard deviation — consistent financial health
Budget Discipline ScoreperiodsWithinBudget / totalPeriods × 100 (rolling 6)More periods where spending stayed within allocation
Behavior EvolutionComposite: weighted mean of behavioral sub-scores delta vs prior 3 periodsOverall financial behavior improving across multiple dimensions
⚠️
Trend direction thresholds. STABLE is declared when |trendPct| < 2%. INSUFFICIENT_DATA when fewer than 2 comparison periods exist. Do not display a trend arrow in INSUFFICIENT_DATA state — show "—" instead.

Comparison Engine

The Comparison Engine produces a side-by-side analysis of two periods across all financial dimensions. It highlights improvements (green) and regressions (red) so users can immediately see what changed and in which direction.

6.1 ComparisonBlock Type

6.3 Improvement / Regression Logic

// Direction is computed per metric based on whether an increase is good or bad: metrics where HIGHER is BETTER: savingsRate, emfCompletionPct, goalFundingRate, fhsTotal, budgetDisciplineScore, totalIncome, totalSaved, totalDebtReduced metrics where LOWER is BETTER: totalSpent, dtiPct, debtBalance, spendingGrowthRate, budgetOverrunPct direction = IF metric in HIGHER_IS_BETTER: delta > 0 → IMPROVED delta < 0 → REGRESSED ELSE → NEUTRAL IF metric in LOWER_IS_BETTER: delta < 0 → IMPROVED delta > 0 → REGRESSED ELSE → NEUTRAL // NEUTRAL when |delta| / valueB < 2% (noise threshold)

Financial Insights Engine

Report Insights are structured observations generated from the report's data. Every insight must answer four questions: what was observed, why it happened, what to do about it, and what the expected impact is.

9.1 ReportInsight Type

type ReportInsight = { id: string code: InsightCode priority: number // 1 = highest; determines display order category: InsightCategory // 'SPENDING' | 'SAVINGS' | 'DEBT' | 'GOALS' | 'BEHAVIOR' | 'FORECAST' observation: string // max 100 chars: what the data shows explanation: string // max 140 chars: why this is significant recommendation: string // max 140 chars: what action to take expectedImpact: string // max 100 chars: what happens if recommendation is followed sentiment: 'POSITIVE' | 'NEGATIVE' | 'NEUTRAL' dataPoints: InsightDataPoint[] // supporting numbers }

9.2 Insight Template Examples

RINS-001 — Savings Rate Rising
Observation"Your savings rate increased from [X]% to [Y]% compared to last period."
Explanation"You saved [N] more this period. This trend compounds — every extra [Z] saved now reduces the time to your next goal by [M] months."
Recommendation"Maintain or increase your current contribution level to lock in this momentum."
Expected Impact"If maintained, your [goal name] target is now reachable [N] months earlier."
RINS-002 — Debt Burden Decreasing
Observation"Your DTI ratio fell from [X]% to [Y]% this period."
Explanation"You reduced total debt by [N], lowering the share of income committed to repayments."
Recommendation"Redirect the freed-up capacity to your emergency fund or the highest-priority goal."
Expected Impact"Redirecting [N]/period would add [M] months of EMF coverage in [K] periods."
RINS-003 — Category Spending Rising
Observation"[Category] spending increased [X]% compared to last period."
Explanation"This category now accounts for [Y]% of total spending, up from [Z]%."
Recommendation"Review your [category] budget allocation — it may need to be increased or the spending reduced."
Expected Impact"Bringing spending back within allocation frees [N] for savings or debt repayment."

9.3 Insight Selection Rules

  • Maximum 5 insights per report
  • At most 2 insights per category (SPENDING, SAVINGS, DEBT, GOALS, BEHAVIOR, FORECAST)
  • POSITIVE-sentiment insights are included alongside NEGATIVE ones — celebrate wins
  • Insights are sorted: NEGATIVE priority 1–2 first, then POSITIVE, then NEUTRAL
  • Insight body language is always empathetic and action-oriented — never accusatory
  • Data points cited in insights must match the report's period exactly

Financial Health History

The FHS historical record enables trend charts, period comparisons, and year-over-year health evolution. It is the only persistent output produced by the RPT module.

10.1 Write Policy

  • One fhs_history row is written per calendar day, on the first snapshot build of that day
  • If a row already exists for today's date, no write occurs — the day's first snapshot is the canonical reading
  • Rows are retained for 365 days; a background cleanup task (runs on app open, at most once per day) deletes rows older than 365 days
  • If the app is not opened on a given day, no row is written for that day — gaps are tolerated and handled in charts by interpolation or explicit "no data" markers

  • Users can save any ReportFilter combination with a name (max 40 chars)
  • Saved filters are stored in the saved_filters table (Section 2.1)
  • Maximum 10 saved filters; when limit is reached, saving a new one requires deleting an existing one
  • Saved filters are listed in a dropdown on the report screen; selecting one applies all filter dimensions simultaneously
  • Built-in preset filters: "Last 3 Months", "This Year", "All Goals Only", "Debt Overview" — these are not editable

Predictive Analytics Architecture

The predictive analytics layer is designed for future AI integration. The current implementation provides deterministic projections using simple extrapolation; the architecture supports replacement with ML models without changing the data contract.

14.1 PredictiveBlock Type

type PredictiveBlock = { expectedSavingsNextPeriod: Projection debtPayoffDate: ProjectedDate emfCompletionDate: ProjectedDate cashFlowNextPeriod: Projection budgetUtilizationForecast: Projection goalCompletionProbability: GoalProbability[] modelVersion: string // 'RULE_BASED_V1' | future: 'ML_V1' confidenceLevel: 'LOW' | 'MEDIUM' | 'HIGH' } type Projection = { value: number // projected value (centimes or %) lowerBound: number upperBound: number basisPeriods: number // how many historical periods the projection is based on } type ProjectedDate = { date: string | null // null if insufficient data confidence: 'LOW' | 'MEDIUM' | 'HIGH' assumption: string // "Based on last 3 months average contribution" } type GoalProbability = { goalId: string goalName: string probability: number // 0–100 onTimeLabel: 'ON_TRACK' | 'AT_RISK' | 'LIKELY_LATE' }

14.2 Rule-Based Projection Formulas (V1)

// Expected Savings Next Period avgSavings3 = MEAN(totalSaved, last 3 periods) growthRate = linear regression slope over last 3 periods expectedSavingsNextPeriod.value = avgSavings3 + growthRate bounds = ± STDEV(totalSaved, last 3 periods) // Debt Payoff Date avgMonthlyReduction = MEAN(totalDebtReduced, last 3 periods) IF avgMonthlyReduction > 0: periodsToPayoff = CEIL(totalDebtBalance / avgMonthlyReduction) debtPayoffDate = today + periodsToPayoff × avgPeriodLength // Goal Completion Probability FOR each ACTIVE goal: requiredMonthly = goal.requiredMonthlyContribution avgContrib3 = MEAN(goal contributions, last 3 periods) fundingRatio = avgContrib3 / requiredMonthly probability = fundingRatio >= 1.0 → 90 fundingRatio >= 0.8 → 75 fundingRatio >= 0.5 → 50 fundingRatio >= 0.2 → 25 ELSE → 10 // Confidence = LOW when basisPeriods < 3 // Confidence = MEDIUM when basisPeriods 3–5 // Confidence = HIGH when basisPeriods >= 6 (future: ML model)

14.3 AI Integration Readiness

  • The PredictiveBlock type is the stable contract between the RPT module and any future AI model — the AI replaces internal projection functions but the output shape is unchanged
  • The fhs_history table (365 rows) plus all module tables provide sufficient training features for a time-series model when AI integration is built
  • The analytics module can optionally serialize the last 12 months of AnalyticsBlock and BehavioralBlock snapshots as a feature vector for an on-device ML model
  • All projections are clearly labeled as estimates; no UX element implies that predictions are guarantees

Edge Cases

EC-RPT-01
Incomplete Month / Period
When the current period is not yet complete: analytics metrics are computed on partial data. All figures show a "Period in progress" badge. Averages and percentages are computed on actuals to date, not projected to end-of-period. Behavioral scores that count "periods" use only completed periods — the current in-progress period is excluded from denominators.
EC-RPT-02
Missing Salary in Period
grossIncome = 0 for a period. That period is excluded from income-growth-rate calculations (to avoid divide-by-zero and misleading -100% figures). The period is included in behavioral scoring as a missed "income timeliness" period. A "Missing income" note appears in the report's Financial Summary for that period.
EC-RPT-03
Negative Balance or Over-Committed Period
cashFlowBalance < 0 is displayed in red with a "Deficit" badge. The comparison engine counts this as a regression for the cashFlow metric. Behavioral analytics penalises the budget discipline score. The predictive engine treats this as a warning: if 2+ consecutive periods show deficit, the confidence level on all projections is downgraded.
EC-RPT-04
Archived Goals and Debts
By default, archived goals and soft-deleted debts are excluded from analytics. When the "Include Archived" filter is enabled: archived goals are shown in the goals section with an "Archived" label; their contributions are included in totalSaved; their behavioural scores are included in historical computations for periods when they were active.
EC-RPT-05
FHS History Gaps
Days where no fhs_history row exists (app not opened) are displayed as gaps in line charts, not as 0. Gap interpolation is never performed — the chart shows a dashed line between the last known value and the next known value. The gap is explicitly labeled "No data" on tap. Streak calculations exclude gapped days.
EC-RPT-06
Duplicate Records
If duplicate expense records are detected (same amount, same date, same category, within 1 minute of each other): they are flagged with a "Possible duplicate" warning in the report's expense table. They are still included in all totals — the spec does not auto-delete duplicates. The user must manually resolve them in the budget module.
EC-RPT-07
Currency Symbol Change
If the user changes the currencySymbol setting mid-history: historical amounts remain in centimes (currency-agnostic). The new symbol is applied to all displays including historical periods. A note in the LIFETIME report warns: "Currency symbol changed on [date] — all amounts are displayed in the current symbol but were recorded under a different symbol."
EC-RPT-08
Report Generation Timeout
If the analytics query takes longer than 3 seconds: show a partial report with populated sections and a "Loading..." placeholder for slow sections. Log the slow query for diagnostics. At 10 seconds: cancel the query, show an error state with a "Generate simpler report" option that omits behavioral analytics and predictive blocks.
EC-RPT-09
Fewer Than 3 Historical Periods
When fewer than 3 completed salary periods exist: behavioral scores that require "last 6 periods" compute over available periods with a "Based on [N] periods" badge. Comparison blocks that require a prior period show "No comparison available yet — keep recording to unlock". Predictive blocks show with confidenceLevel = LOW and basisPeriods = actual count.
EC-RPT-10
Partial CSV Export
If the CSV export fails mid-write (e.g. device storage full): the partial file is deleted immediately — no corrupted file is left on disk. The user sees "Export failed: device storage full" with a link to storage settings. The export operation is atomic: write to a temp file first, then rename on success.

Business Rules & Performance

BR-RPT-01
Analytics Module Owns No Source Data
The RPT module reads from all other module tables but writes only to fhs_history and saved_filters. Any report computed value that appears to require a new column in a source module's table is a design error — add a computed field to the Report type instead.
BR-RPT-02
Centimes Throughout Analytics
All monetary values in analytics computations are integer centimes. Division to compute percentages or rates produces a floating-point result; this is the only context where floating-point arithmetic is permitted in the RPT module. The result is stored as a float in the Report object but never persisted as a centimes value with fractional cents.
BR-RPT-03
Period Alignment
All period-based analytics use salary-period boundaries from SPEC-BUD-001 BR-01, not calendar months. When a report type requires calendar alignment (e.g. YEARLY uses calendar year Jan–Dec), the data is grouped by salary periods that overlap with the calendar range — a period that straddles Jan 1 is included in the year where its start date falls.
BR-RPT-04
Insight Cap Per Report
Maximum 5 ReportInsights per report, max 2 per category. This prevents insight fatigue. The selection algorithm always prefers insights with lower priority numbers (more critical). If fewer than 5 insights qualify, show fewer — do not pad with lower-quality insights to reach the cap.
BR-RPT-05
No Predictive Values Presented as Certainties
All projected dates and amounts must display a confidence label (LOW / MEDIUM / HIGH) and an assumption sentence. UX copy must never use language implying certainty ("you will save...", "your debt will be paid off on..."). Required framing: "Based on your recent history, you are on track to..." or "At your current pace..."
BR-RPT-06
Saved Filter Limit
Maximum 10 saved filters (excluding built-in presets). Saving a filter when 10 exist returns a validation error: "Filter limit reached — delete an existing saved filter to save a new one." Built-in preset filters do not count toward the limit and cannot be deleted.
BR-RPT-07
FHS History Write Guard
The fhs_history write is guarded by a unique constraint on the date column. If the background task attempts to write for a date that already has a row, the INSERT is silently ignored (ON CONFLICT IGNORE). This prevents duplicate writes on multi-app-open days.
BR-RPT-08
Performance Targets
MONTHLY report generation: < 500 ms. YEARLY report generation: < 1500 ms. LIFETIME report generation: < 3000 ms. Custom range up to 1 year: < 1000 ms. These are measured from query start to Report object fully populated, on a device with 2 years of financial history. Targets assume SQLite indexes on: expenses(date, category_id), salary_periods(start_date), fhs_history(date).
BR-RPT-09
Offline-First Architecture
All analytics computations run locally against the on-device SQLite database. No network request is required to generate any report, export any file, or display any chart. This is a hard requirement — analytics must be available without internet connectivity at all times.
BR-RPT-10
Future Scalability: Large Data Sets
For users with > 3 years of history (> 36 salary periods, > 10,000 expense records): aggregate queries must use indexed GROUP BY operations. Row-by-row JS computation is prohibited for any aggregate that could instead be done in SQL. The fhs_history table's 365-day retention cap ensures this table stays bounded. Category-level expense aggregates are pre-computable as period-end snapshots stored in a future period_summary table (optional optimisation, not required in V1).
