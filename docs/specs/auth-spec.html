Authentication & User Account System
Specification

● Draft 🔐 Security Classification: Internal 📋 Version 1.0.0 🌍 Targets: FR · AR · EN markets
01

Executive Summary

Finance Bag handles sensitive personal financial data — salary figures, credit obligations, savings goals. The authentication system must ensure that users trust the application from their first interaction. Trust is earned through transparency, resilience, and the feeling that their data is protected even if their device is lost.

This specification defines a privacy-first, offline-capable authentication model designed for the francophone and Arabic-speaking markets of the Maghreb and Middle East, where phone-based identity often supersedes email, internet connectivity is inconsistent, and user trust in digital financial products is earned gradually.

✅
Core Recommendation

Launch with Email + Password as the only registration method, with optional biometric unlock for returning users. Add Google Sign-In in v1.1 and phone-based OTP in v1.2. Do not launch with anonymous guest mode — the trust signal from requiring a verified email is more valuable than conversion friction reduction at this stage.

Guiding Principles

  • Offline-first: Once authenticated, users must be able to access all their local financial data without an internet connection.
  • Zero knowledge where possible: Financial data remains encrypted at rest on the device. The server does not need to read it.
  • Friction proportional to risk: Reading data requires less verification than modifying account credentials.
  • Graceful degradation: Authentication failures should never permanently lock a user out of their own financial data.
  • Minimal data collection: Collect only what is needed for authentication and app functionality. Nothing more.

Account Creation

Email Registration

Email registration is the foundation method. It gives users a portable, recoverable identity that is not tied to any third-party platform or telephone carrier.

DimensionDetail
AdvantagesWorks everywhere, no carrier dependency, recoverable, user understands it, audit trail possible, no third-party privacy concern
DisadvantagesRequires email access for recovery, inbox delivery not guaranteed, higher friction than social login
Security ConsiderationsEmail can be compromised; verification step mandatory before full account access. Disposable email domains must be blocked at registration.
UX RecommendationSingle-screen form: email field, password field, confirm password. Inline validation, strength indicator. CTA: "Créer mon compte". No username, no birthday.
Email Registration Flow
  1. 1
    User enters email + password
    Inline validation fires on blur. Email format check. Password strength indicator updates in real time.
  2. 2
    Client-side validation passes
    Email format valid, password meets policy, both password fields match.
  3. 3
    POST /auth/register
    Server normalizes email (lowercase, trim). Checks for existing account. Checks for disposable email domain. Hashes password with Argon2id.
  4. 4
    Server sends verification OTP
    6-digit code, 10-minute TTL, delivered via transactional email. Account created but marked unverified.
  5. 5
    User enters OTP
    Auto-submit on last digit. If incorrect, decrement attempt counter. Account deleted after 5 consecutive failures.
  6. 6
    Account verified → onboarding
    Account status set to active. Server issues refresh token + access token. App transitions to onboarding welcome screen.

Phone Registration (v1.2)

Phone-based registration is a priority for the MENA market, where mobile numbers are the primary digital identity for many users. It is deferred to v1.2 due to the SMS infrastructure cost and SIM-swapping risks that require additional mitigations.

DimensionDetail
AdvantagesHigher trust in MENA context, no email required, fast registration, familiar to WhatsApp / banking app users
DisadvantagesSIM-swapping attacks, SMS delivery failures in some regions, carrier costs, phone number can change
Security ConsiderationsSIM-swap protection: require a 24-hour hold before phone number change takes effect. Always link an email as backup recovery method.
UX RecommendationCountry selector (flag + dial code auto-detected by locale), phone field. OTP sent as SMS. 6-digit, 5-minute TTL.

Social Authentication (v1.1)

🔐
Social Auth Security Rule

Never trust the client-side social auth result. Always validate the provider's token on the server before creating or authenticating a user. A forged client-side result is the most common social auth vulnerability.

Anonymous Guest Mode — Decision

⚠️
Decision: Do Not Launch Guest Mode

Guest mode is not recommended for a financial application at launch. The primary reason is data loss risk: if a user populates the app with financial data as a guest and then loses the device or uninstalls, all data is permanently lost. In a financial context, this creates a traumatic first experience that destroys trust permanently. The secondary reason is that Finance Bag targets users who are already motivated to manage their finances — they will register. Guest mode is more useful for entertainment or utility apps where casual exploration has no real cost.

Alternative: Offer a demo mode with pre-populated fake data that users can explore before registering. This provides the "try before you commit" benefit without the data loss risk. Demo mode data is never stored.

Email Verification

Email verification is mandatory before a user can access full app functionality. An unverified account cannot add financial data. This prevents disposable email abuse and ensures account recovery is possible.

OTP Specification

Format
6-digit numeric
Numeric-only enables keyboardType="numeric" on mobile. 6 digits = 1 million possible values, sufficient for short-TTL codes.
Expiration
10 minutes
Long enough for users to check email on another device. Short enough to limit brute-force windows.
Max attempts per OTP
5 attempts
After 5 wrong entries the OTP is invalidated. The user must request a new one. Prevents brute force (5 × 1,000,000 = very large keyspace in practice).
Resend limit
3 per hour
Prevents using the verification system as a spam vector to send emails to arbitrary addresses.
Generation
CSPRNG
Cryptographically secure pseudorandom number generator. Never use Math.random() for security tokens.
Storage on server
Bcrypt hash only
The OTP is hashed before storage so a database breach cannot expose valid codes. Verified by bcrypt.compare().

Anti-spam Protection

  • Block known disposable email domains (maintained blocklist: mailinator.com, guerrillamail.com, etc.).
  • Rate-limit verification email sends per IP: max 10 per hour per IP address.
  • Rate-limit per email address: max 3 resends per hour.
  • If resend limit is hit, surface a clear countdown timer showing when the next send is available.
  • Unverified accounts older than 24 hours are automatically purged by a background job.

Email Content Requirements

  • Subject line in the user's registration language (FR/AR/EN).
  • Code displayed prominently in a large font — avoid hiding it in a link-only email.
  • Expiration time explicitly stated: "This code expires in 10 minutes."
  • Security notice: "If you did not create a Finance Bag account, ignore this email."
  • No links to click — code-only. This eliminates phishing risk from link-based verification.
ℹ️
OTP vs Magic Link Decision

This spec chooses a 6-digit OTP over a magic link. The reason is mobile UX: on a phone, users often check email on the same device running the app. A magic link causes them to leave the app, tap the link in the email client, and deep-link back — which fails in many email clients. A numeric code is trivially typed and auto-submits, which is a significantly better experience.

05

Login

Login Flow

Email + Password Login
  1. 1
    User enters email + password
    Email normalized to lowercase. No real-time validation to avoid leaking whether an email is registered.
  2. 2
    POST /auth/login
    Rate-limited per IP and per email. Timing-safe comparison to prevent email enumeration via response time.
  3. 3
    Server validates credentials
    Fetch user by email. Compare submitted password against Argon2id hash. If no match: increment lockout counter, return generic error.
  4. 4
    Lockout check
    If 10 consecutive failures: account enters soft lock for 15 minutes. Email sent with unlock link. Counter resets on successful login.
  5. 5
    Session creation
    Server issues access token (JWT, 15-min TTL) and refresh token (opaque, 30-day TTL). Refresh token stored as HttpOnly cookie + in secure device storage.
  6. 6
    Biometric prompt (if enrolled)
    On subsequent logins, skip email/password. Biometric success unlocks the locally cached refresh token. No password required.

Error Messages

Error messages must be generic enough not to reveal whether an email is registered, but specific enough to be actionable:

SituationMessage Shown to UserRationale
Wrong email or password"Email ou mot de passe incorrect."Never distinguish — prevents email enumeration
Account locked"Trop de tentatives. Réessayez dans 15 min ou consultez vos emails."Reveals lock state but not the email registration status
Account not verified"Vérifiez votre email pour activer votre compte. [Renvoyer le code]"Safe to reveal; user already knows they registered
Network error"Connexion impossible. Vérifiez votre réseau."Clear, actionable
Server error"Une erreur est survenue. Réessayez dans quelques instants."Never expose stack traces or internal errors

Automatic Login

On app relaunch, the following sequence applies:

  1. Check if a valid refresh token exists in expo-secure-store.
  2. If yes and not expired: silently exchange for a new access token in the background. User lands directly on the dashboard.
  3. If refresh token is expired or missing: show the login screen.
  4. If biometric is enrolled and refresh token is present but locked: show biometric prompt before unlocking the token.

Suspicious Login Detection

Flag a login as suspicious when: the device fingerprint is new AND the location/timezone differs significantly from the last known login. Action: send a security alert email ("New device sign-in to your Finance Bag account") with device details and a one-click "This was not me" revocation link.

Session Parameters

Access token TTL
15 minutes. Short to limit window if intercepted.
Refresh token TTL
30 days. Extended since it is stored in secure device storage, not in memory.
Refresh rotation
On every use. Old refresh token invalidated immediately. Reuse of old token triggers family revocation (all sessions of that user revoked).
Max concurrent sessions
5 devices. Oldest session revoked when limit exceeded.
Idle timeout
No idle timeout for local biometric-protected sessions. The biometric acts as the idle protection.
06

Password Policy

Minimum Length
8 characters
NIST SP 800-63B recommends 8 as the minimum for user-created passwords. Complexity rules compensate for short passwords.
Maximum Length
128 characters
Argon2id handles any length after hashing. A maximum prevents DoS via extremely long password inputs.
Complexity
1 uppercase + 1 digit
Minimal complexity. Research (NIST SP 800-63B) shows excessive complexity rules lead to predictable patterns (P@ssw0rd). Focus on length and uniqueness instead.
Common password check
Top 10,000 blocked
Blocks "password123", "123456789", etc. Check against an offline blocklist on the client — do not send candidate passwords to a server for checking.
Personal info check
Name/email blocked
If user's email is ali@example.com, block passwords containing "ali" or "example". Prevents obvious guessing.
Breach check
HaveIBeenPwned API
Use k-anonymity: send first 5 chars of SHA-1 hash, receive matching hash suffixes. Never send the full password or hash. Warn user; do not block.

Password Strength Indicator

Display a 4-level strength bar (Faible / Moyen / Fort / Très fort) calculated client-side using the zxcvbn algorithm. The score should reflect real-world crackability, not just character class presence.

Password Visibility Toggle

All password fields must include a visibility toggle (eye icon). This is a usability necessity, not a security risk: users on mobile frequently make typos in hidden fields, which causes unnecessary login failures.

Password Confirmation

Require a confirm password field only on the registration screen. On all other screens (password change, password reset), a single field is sufficient since the user is authenticated and can use the visibility toggle to verify their input.

Password Recovery

Password Reset Flow
  1. 1
    User taps "Mot de passe oublié"
    Shown on the login screen below the password field.
  2. 2
    User enters email address
    Normalize to lowercase. Submit triggers POST /auth/forgot-password.
  3. 3
    Server response: always success
    "Si cet email existe, vous recevrez un code." — Response is identical whether the email is registered or not. Prevents email enumeration.
  4. 4
    Server sends 6-digit reset OTP
    Separate OTP namespace from verification OTP. 15-minute TTL. Max 3 resends per hour. Stored as bcrypt hash.
  5. 5
    User enters OTP
    5 attempts allowed. After 5 failures: OTP invalidated, back to step 2.
  6. 6
    OTP verified → new password screen
    Server returns a short-lived reset token (5 minutes). App shows new password + confirm password fields.
  7. 7
    User submits new password
    Client validates against policy. POST /auth/reset-password with new password + reset token. Server hashes new password, invalidates all existing sessions, sends security email.
  8. 8
    All sessions revoked
    Immediately invalidate all refresh tokens for this user. User is logged out of all devices. This is mandatory after a password reset.
🔐
Lost Email Access

If a user loses access to their email, there is currently no fallback recovery path at v1.0. This is intentional — adding phone recovery as a fallback is the v1.2 phone integration. For v1.0, the account is unrecoverable. This edge case must be disclosed in the account creation screen: "Your email is your account recovery method. Please use a reliable email address."

Security Architecture

Password Hashing

Use Argon2id with the following parameters (OWASP 2023 recommendation for interactive logins):

Algorithm
argon2id — hybrid mode resistant to both GPU and side-channel attacks
Memory
64 MiB (m=65536)
Iterations
3 (t=3)
Parallelism
4 (p=4)
Output length
32 bytes
Salt
16-byte random salt per hash, generated with CSPRNG. Stored alongside hash.
🔐
Why Not bcrypt?

bcrypt is limited to 72-byte passwords, has no memory hardness, and is increasingly fast to crack on GPUs. Argon2id is the winner of the Password Hashing Competition (2015) and is recommended by OWASP, NIST, and the IETF. It's the right choice for new systems in 2026.

Secure Storage on Device

DataStorageWhy
Refresh tokenexpo-secure-storeBacked by iOS Keychain / Android Keystore. Not readable outside the app. Never stored in AsyncStorage.
Biometric keyexpo-secure-store with biometric requirementToken only unlockable after biometric success.
Access tokenIn-memory (Zustand store) onlyShort-lived; no persistence needed. Cleared on app close.
Financial dataSQLite (expo-sqlite)Encrypted at rest by SQLCipher when using expo-sqlite with encryption key.
Database keyexpo-secure-storeThe SQLite encryption key is stored in the secure store, not hardcoded.

Token Architecture

Access Token — JWT signed with RS256. Short-lived (15 min). Contains: userId, sessionId, iat, exp. No sensitive data in the payload — JWTs are only base64-encoded, not encrypted.

Refresh Token — Opaque random string (256-bit, base64url). Stored in the database as a bcrypt hash. Supports rotation on every use. Revocable per-session or per-user.

Reset Token — Opaque random string (256-bit). Single-use. 5-minute TTL. Deleted immediately after use.

⚠️
IP Rate Limiting + VPN / Mobile Networks

Aggressive per-IP rate limiting on mobile can block legitimate users sharing a mobile carrier's NAT IP (very common in Maghreb networks). Use IP-based limits as a secondary defense, not the primary. Email-based rate limiting is the primary control and should be stricter.

Security Event Logging

The following events must be logged with timestamp, user ID (not email), IP, and device fingerprint:

  • Successful login
  • Failed login (increment lockout counter)
  • Account lockout triggered
  • OTP generated, OTP verified, OTP failed
  • Password changed
  • Email changed
  • Session revoked
  • Account deleted

Logs are retained for 90 days. Logs are the primary tool for investigating account compromise claims.

Privacy by Design

  • Data minimization: Only the fields listed above are stored. No analytics trackers, no advertising IDs, no behavioral telemetry.
  • Purpose limitation: Email is used only for authentication and security notifications. Never for marketing without separate explicit consent.
  • Local-first: All financial data lives on the device only (v1.0). The server never sees salary figures, transaction amounts, or credit details.
  • Encryption in transit: All API communication over HTTPS/TLS 1.3 minimum. Certificate pinning recommended for the mobile app.
  • Encryption at rest: SQLite database encrypted with a per-user key stored in the device secure store. Server DB columns containing PII encrypted at the application layer.

Account Deletion Process

Account Deletion Flow
  1. 1
    User initiates deletion in settings
    Warning dialog: "This will permanently delete all your data. This cannot be undone after 30 days."
  2. 2
    Require current password + type "SUPPRIMER"
    Prevents accidental deletion. High-friction is appropriate here.
  3. 3
    Account suspended immediately
    All sessions revoked. Email locked. Account status = pending_deletion. Confirmation email sent with recovery link (valid 30 days).
  4. 4
    30-day grace period
    User can cancel via recovery link in the confirmation email. After 30 days with no cancellation, hard delete is triggered.
  5. 5
    Hard delete
    All server records deleted. Backup purge scheduled within 7 days. Confirmation email sent: "Your account has been deleted."

Data Export (GDPR Article 20)

User can request a machine-readable export of all their data from Settings. The export is:

  • Delivered within 24 hours via a secure download link sent to the verified email.
  • JSON format, UTF-8 encoded.
  • Includes: profile data, all financial records stored on device (if sync is enabled in future versions), security event log, device list.
  • Download link expires after 24 hours.
  • Limited to once per 30 days to prevent abuse.

Consent Management

At registration, users consent to the Privacy Policy and Terms of Service via a checkbox with a link. This is the only consent gate at v1.0. If email marketing is added in future versions, a separate explicit opt-in is mandatory — it must not be pre-ticked.

Offline Behavior

Design Principle

Finance Bag's core value proposition (budgeting, tracking expenses, monitoring credits) must be usable without an internet connection. Authentication should not block access to local data that already exists on the device.

Scenario Behavior Available Features
Previously logged in, offline Biometric or cached session unlocks local SQLite DB. No server call needed. All local features: dashboard, transactions, credits, goals, emergency fund. Full read + write.
Access token expired, offline Biometric succeeds → app works locally. Server sync deferred until connectivity returns. All local features. Sync icon shows pending state.
Never logged in, offline Login screen shown. Cannot authenticate. Cannot create account. None — first authentication requires connectivity.
Auth server unreachable, online If refresh token is valid locally, proceed. If expired, show login with message: "Serveur inaccessible. Réessayez plus tard." Local features only if previously authenticated.
Session revoked server-side (e.g., all devices logout) Next server sync attempt returns 401. App clears local tokens and shows login screen. Data remains in local DB. User must re-authenticate. Local data preserved.

Local Authentication Gates

When the app is backgrounded and reopened, the behavior depends on the time elapsed:

  • Less than 5 minutes: No re-authentication required. App resumes directly.
  • 5 to 30 minutes: Biometric prompt shown if enrolled. Passcode fallback if biometric fails.
  • Over 30 minutes: Biometric prompt required. If biometric fails 3 times, full login (email + password) required.
ℹ️
Local-First Commitment

At v1.0, Finance Bag is fully local. There is no cloud sync of financial data. This means the offline story is simple: if you are authenticated on your device, everything works. Cloud sync in a future version will require careful thinking about conflict resolution and end-to-end encryption to preserve the privacy-first design.

Network interruption after OTP sent No response from verify endpoint OTP still valid on server. User can retry when online. "Connexion perdue. Le code est toujours valide. Réessayez dans quelques instants."

Lost access to email User cannot receive OTP for password reset v1.0: no alternative. Account unrecoverable. v1.2: phone fallback. Documented at registration: "Utilisez un email auquel vous avez accès en permanence."
Multiple rapid login attempts Rate limiter per IP + per email Exponential backoff: 1s, 2s, 4s, 8s delay between attempts. "Trop de tentatives. Attendez X secondes avant de réessayer."
User cancels during registration App navigates away before completion Unverified account purged after 24h by background job. No dangling accounts. None — silent cleanup.
Token refresh race condition Two simultaneous requests with same refresh token First use succeeds, second returns 401. Refresh token rotation detects reuse. All sessions revoked. User redirected to login: "Session expirée. Reconnectez-vous."
Biometric hardware unavailable expo-local-authentication returns unsupported Biometric enrollment option hidden. Password-only mode. No message — option simply not shown.
