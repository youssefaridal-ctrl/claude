01
Overview & Architecture Philosophy

Most personal finance apps treat goals as a flat list of independent items. Finance Bag's Roadmap Engine elevates this into a connected financial plan — a directed graph where goals have relationships, where completing one unlocks others, and where changing any goal cascades intelligently through the entire plan.

Core insight: A person saving for a house, paying off debt, and building an emergency fund is not managing three separate goals — they are executing one coherent financial strategy. The Roadmap Engine makes that strategy explicit, visible, and adaptive.

Architectural Principles

Graph-First Design
Goals and their dependencies form a Directed Acyclic Graph (DAG). All roadmap computations are graph operations: topological sort, reachability, cycle detection, and impact propagation.
Derived State Only
Roadmap status, ordering, feasibility, and impact are never stored — they are computed from the current goal/dependency graph and financial state on every read. This eliminates synchronization bugs.
Non-Destructive Simulation
What-If scenarios run on an in-memory clone of the graph. Real data is never modified by simulations. Results are ephemeral — shown to the user, discarded unless explicitly applied.
Graceful Degradation
The system functions with zero dependencies (flat goal list). Users discover dependency features progressively. No dependency is required to use Finance Bag.

Ten dependency types cover the full range of financial relationships between goals. Each type has defined enforcement behavior and visualization treatment.

Recommended Before RECOMMENDED_BEFORE SOFT System recommends completing target first. Source is NOT blocked — user can proceed but sees advisory banner. Finish personal loan before starting vacation savings ACTIVE (with advisory)

Sequential Goal SEQUENTIAL HARD Target and source form an explicit chain. Parallel Goal PARALLEL INFO Goals are explicitly marked as running simultaneously. System verifies combined required monthly contributions are feasible within disposable income. No blocking; this is budget-awareness metadata. Vacation and Wedding savings run in parallel ACTIVE (feasibility checked)

04
Roadmap Engine

The Roadmap Engine is a pure computation layer that transforms the stored set of Goals and GoalDependency records into a structured, ordered financial plan.

Graph Construction

Build Directed Graph G = (V, E)
V (nodes) = { All Goals (status ≠ ARCHIVED), All active Debts (referenced in dependencies), EmergencyFund (if referenced in any dependency) } E (edges) = { For each non-deleted GoalDependency: directed edge: targetEntity → sourceGoal (reads: "targetEntity must come before sourceGoal") weight(edge) = dependency.strength (HARD=2, SOFT=1, INFO=0) }

Topological Layer Assignment

Kahn's Algorithm (BFS-based Topological Sort)
1. Compute in-degree for every node (count of HARD incoming edges) 2. Initialize queue Q with all nodes having in-degree = 0 (no hard prerequisites) 3. While Q is not empty: a. Dequeue node N → assign to current Layer L b. For each outgoing edge N → M (where M has dependency type HARD): - Decrement in-degree of M - If in-degree of M becomes 0: enqueue M 4. Increment layer counter L after processing all nodes at current level 5. If any nodes remain with in-degree > 0 after exhausting Q: → CIRCULAR_DEPENDENCY conflict detected (Section 08) Output: each node has a LayerIndex (0 = available immediately, N = requires N levels of completion)

Dependency Satisfaction Check

Per-Dependency Condition Evaluation
function isSatisfied(dep: GoalDependency): boolean { target = resolveTarget(dep) // Goal, Credit, or EmergencyFund switch dep.conditionType: FULLY_COMPLETED: return target.status === 'COMPLETED' || target.status === 'PAID' PERCENTAGE_REACHED: return target.completionPct >= dep.conditionValue.pct AMOUNT_REACHED: return target.currentSavedAmount >= dep.conditionValue.minAmount EMF_MILESTONE: emfOrder = { LEVEL_0:0, LEVEL_1:1, LEVEL_2:2, LEVEL_3:3, LEVEL_4:4 } return emfOrder[emf.currentMilestoneLevel] >= emfOrder[dep.conditionValue.level] DEBT_PAID: return credit.status === 'PAID' LIFE_EVENT_OCCURRED: return lifeEvent.status === 'OCCURRED' CUSTOM: return dep.manuallyMarkedSatisfied === true }

06
Impact Analysis Engine

Whenever any goal, debt, or EMF state changes, the engine propagates that change through the dependency graph and reports the downstream effects before the user confirms the change.

Impact Analysis Algorithm

Propagation via BFS from Changed Node
function analyzeImpact(changedNodeId, changeType, changePayload): impactList = [] visited = Set() queue = [changedNodeId] while queue not empty: current = queue.dequeue() if current in visited: continue visited.add(current) for each dep where dep.target = current: affected = dep.sourceGoal impact = computeImpact(affected, changeType, changePayload) if impact is not null: impactList.append({ goal: affected, impact }) queue.enqueue(affected) // propagate transitively return sorted(impactList, by: impactSeverity DESC)

Impact Types Per Change Event

Change on SourceImpact TypeAffected DependentsDisplayed As
targetAmount increased DATE_SHIFT All goals BLOCKED by this goal (completion date shifts later) "[Goal B] unblocks ~3 months later than planned"
targetDate shortened FEASIBILITY_CHANGE + BUDGET_PRESSURE Goals in PARALLEL dependency; goals competing for same budget "Shortening this deadline increases required monthly by [Δ], reducing budget for [Goal C]"
targetDate extended DATE_SHIFT (positive) Blocked goals: unblock date shifts later "[Goal B] won't be available until [new date], [N] months later"
Goal PAUSED INDEFINITE_BLOCK All goals with HARD dependency on this goal "[Goal B] and [Goal C] are now indefinitely blocked. Pause duration affects their timelines."
Goal COMPLETED early DATE_SHIFT (positive) + UNBLOCK All goals BLOCKED by this goal "[Goal B] is now unblocked — [N] months ahead of schedule!"
Goal CANCELLED DEPENDENCY_ORPHANED + STATUS_CHANGE Goals that depended on this goal "[Goal B] was blocked by [cancelled goal]. It can now be started — or choose a new dependency."
Priority changed REORDER Goals competing for same budget allocation "[Goal B] moves down in recommended order. Required monthly for [Goal B] may decrease."
Debt paid off earlier UNBLOCK + BUDGET_FREED Goals with DEBT_PAID condition "[Goal] is now unblocked. [Amount]/mo freed from debt payments available for goals."

Impact Display UX

Pre-commit impact sheet: Before any change that has downstream impact is saved, the system shows a bottom sheet: "This change affects [N] other goals." List each affected goal with its impact in plain language. User sees impact, then taps "Confirm Change" or "Cancel." This is shown for HARD-dependency impacts only; SOFT-dependency impacts are shown as a dismissible info banner after saving.
07
Goal Prioritization Engine

The engine produces a recommended execution order for all ACTIVE and DRAFT goals, accounting for financial health, dependencies, deadlines, and strategic value. It never overrides user-set priorities — it produces a suggested order alongside the user's chosen order.

Prioritization Score Formula

Score per Goal (0–100)
priorityScore(goal) = (deadlineUrgency × 30) + (userPriorityWeight × 25) + (dependencyLeverage × 20) + (feasibilityBonus × 15) + (riskPenalty × 10) ───────────────────────────────────────────────────── deadlineUrgency (0–1): if no targetDate: 0.3 (neutral) if targetDate < today: 1.0 (overdue) daysLeft = targetDate - TODAY urgency = MAX(0, 1 - (daysLeft / 730)) // 730 days = 2 years = zero urgency clamp to [0, 1] userPriorityWeight (0–1): CRITICAL=1.0, HIGH=0.75, MEDIUM=0.5, LOW=0.25, OPTIONAL=0.1 dependencyLeverage (0–1): unlockedGoalCount = count of goals directly or transitively unblocked by THIS goal completing leverage = MIN(1, unlockedGoalCount / 5) // 5+ unlocked = max leverage feasibilityBonus (0–1): FULLY_FEASIBLE=1.0, ACHIEVABLE=0.75, CHALLENGING=0.4, UNREALISTIC=0.0 riskPenalty (0–1, subtracted): if EMF.currentMilestoneLevel = LEVEL_0 AND goal.category ≠ EMF: 0.5 penalty if DTI ≥ 40% AND goal is not DEBT-related: 0.3 penalty if goal.feasibilityScore = UNREALISTIC: 0.5 penalty max cumulative penalty = 1.0

Recommendation Output Format

The engine outputs a ranked list with a natural-language explanation for each position:

RankGoalScoreExplanation
#1Emergency Fund Top-Up88"Completing this unlocks 3 other goals and reduces your financial risk score. Highest leverage move available."
#2Personal Loan Payoff74"Deadline in 14 months. Completion frees [amount]/mo for other goals and unblocks your House Down Payment."
#3Vacation Fund61"High priority, achievable within current income. Completing this while Loan is active is feasible."
#4House Down Payment47"Currently blocked by Loan Payoff. Contributes will be available from March 2026."

Explanation Reasoning Rules

  • Leverage: Always mention how many goals completing this one would unblock.
  • Deadline: If targetDate exists, express urgency in human terms ("in 14 months", "in 3 weeks").
  • Budget freed: If completing this goal frees budget (monthly contribution), state the amount.
  • Risk gate: If risk penalty was applied, explain why ("Your Emergency Fund is at Level 0").
  • Feasibility: If goal is CHALLENGING or UNREALISTIC, note it and suggest the simplest fix.
08
Conflict Detection

The engine detects planning conflicts proactively — both when saving changes and on each roadmap load. Conflicts are classified by severity and presented with specific, actionable resolution options.

Conflict Types

IDConflictSeverityDetection MethodResolution Options
CON-01 Circular Dependency CRITICAL DFS traversal: when adding edge A→B, check if B has path back to A. O(V+E). Block the dependency creation. Show: "This creates a loop: A → B → C → A." Suggest removing one link.
CON-02 Impossible Contribution Plan CRITICAL SUM(requiredMonthly for all ACTIVE + RECOMMENDED_NEXT goals) > disposableIncome × 1.5 Show which goals are causing overflow. Recommend pausing lowest-priority goals or extending deadlines.
CON-03 Timeline Overlap Conflict HIGH Two goals with overlapping deadline windows both marked CRITICAL and requiring >80% disposable income each. "These two goals both need most of your income in the same period. Consider staggering them by [N] months."
CON-04 Unrealistic Deadline HIGH requiredMonthlyContribution > 2.5 × disposableIncome for a single goal. Suggest extending targetDate until feasibilityScore ≥ ACHIEVABLE. Show the minimum viable date.
CON-05 Conflicting Priority Order MEDIUM A CRITICAL goal is BLOCKED by a LOW-priority goal, and the LOW goal has a later deadline than the CRITICAL goal. "Your [LOW] goal is blocking your [CRITICAL] goal. Consider raising [LOW]'s priority or removing the dependency."
CON-06 Orphaned Dependency LOW A dependency references a goal that has been CANCELLED or ARCHIVED. Auto-remove the dependency (with notification). Unblock the source goal.
CON-07 Missing EMF Gate HIGH User has a CRITICAL goal (e.g. Home Purchase) with no dependency on EMF and EMF is at LEVEL_0. Advisory: "Financial planning best practice suggests completing your Emergency Fund first. Add this as a dependency?"
CON-08 Deadline Inversion HIGH Source goal's targetDate is earlier than its blocking dependency's estimated completion date. "[Goal A] is due in March but its prerequisite [Goal B] won't complete until June. Extend [Goal A] or accelerate [Goal B]."

Conflict Severity Display

CRITICAL — Blocked
Red banner. Action required before saving. Cannot save conflicting dependency creation (CON-01 only). Other CRITICAL conflicts are displayed but not blocking.
HIGH — Warning
Amber inline callout. Change is saved but conflict is flagged persistently on the roadmap until resolved.
MEDIUM — Notice
Purple info chip. Shown once, dismissible per conflict instance. Re-evaluates on next relevant change.
LOW — Info
Blue info line. Auto-resolves where possible (CON-06). Shown only in the Conflicts panel, not inline.

Unexpected Income Allocation Algorithm

PRIORITY_ORDER Strategy
remaining = lumpSumAmount for each goal sorted by priorityScore DESC: needed = goal.remainingAmount allocated = MIN(needed, remaining) applyContribution(goal, allocated) remaining -= allocated if remaining ≤ 0: break // Remaining amount (if any) suggested for EMF or savings
LARGEST_IMPACT Strategy
for each goal, compute impactScore: impactScore = (dependencyLeverage × 0.5) + (deadlineUrgency × 0.3) + (pctCompletionGain × 0.2) // how much would this contribution move the needle allocate in descending impactScore order until lumpSum exhausted

The roadmap has two primary views: a Timeline View (time-ordered, easy for non-technical users) and a Graph View (dependency-explicit, for power users). Both display the same underlying data.

Timeline View

ElementDesign
Vertical axisCalendar time (months), scrollable. Today = anchor point with current-position indicator.
Goal cardsPositioned at their estimatedCompletionDate. Width represents duration (createdAt → completion).
Completed goalsGreen filled card with checkmark. Stacked above the "Today" line.
Active goalsIndigo outlined card with animated progress fill.
Blocked goalsDimmed card with lock icon. Positioned at their estimated-start date.
Dependency linesVertical connector between the completion of a prerequisite and the start of a dependent goal. HARD=solid line, SOFT=dashed, OPTIONAL=dotted.
Life eventsDiamond ◆ markers on the timeline axis with event icon and label.
Milestone markersSmall dots on active goal cards at 25/50/75/90% positions along the time axis.
Conflict indicatorsRed ⚡ icon on any card involved in a detected conflict.

Graph View

ElementDesign
Layout algorithmHierarchical (Sugiyama-style): goals sorted by layer from topological sort. Layer 0 at top, highest layer at bottom. Left-to-right within each layer by priorityScore DESC.
Node shapeRounded rectangle. Icon + name + small progress ring + completion %.
Node border colorGreen=COMPLETED, Indigo=IN_PROGRESS, Amber=RECOMMENDED_NEXT, Red=BLOCKED, Grey=UPCOMING, Purple=PAUSED.
Edge linesHARD: solid line with filled arrowhead. SOFT: dashed line with open arrowhead. OPTIONAL: dotted line, lighter opacity.
Edge colorSatisfied dependencies: green. Unsatisfied HARD: red. SOFT: amber. OPTIONAL: grey.
Debt nodesRectangular card with balance amount. Connected to goal nodes via red HARD edges when debt is a prerequisite.
EMF nodeShield icon card showing current milestone level. Connected to goals requiring EMF milestones.
InteractionTap node → goal detail. Long-press node → add/edit dependency. Pinch → zoom. Pan → scroll graph.

Accessibility & Simplicity Requirements

  • Timeline View is the default — it is the simpler, non-technical view. Graph View is accessed via a toggle.
  • All status information must be conveyed via both color AND icon/shape (never color alone).
  • Blocked goals show the prerequisite name in text, not just a lock icon.
  • Dependency lines must remain legible at the default zoom level for up to 10 goals. Above 10, a minimap is shown.
  • Respects prefers-reduced-motion: all animations replaced by instant transitions.

Edge Cases
IDScenarioExpected Behavior
EC-01Circular dependency attemptCON-01 detected before save. Dependency creation rejected with explanation of the cycle. No changes persisted.
EC-02All goals are BLOCKED simultaneouslyAt least one node has no incoming HARD edges (or the graph has a cycle — detected as CON-01). If genuinely all blocked: show "Your roadmap is locked — review your dependencies." List all roots that need attention.
EC-03A dependency target is deleted (CANCELLED/ARCHIVED)CON-06 auto-resolves: dependency soft-deleted, source goal unblocked, notification sent. GoalTimelineEvent: DEPENDENCY_ORPHANED logged.
EC-04A goal has a SEQUENTIAL dependency but the auto-activation budget redirect is declinedSource goal still activates (status → ACTIVE). Budget stays on old allocation. No retry of redirect prompt.
EC-05Life event logged as OCCURRED but income impact is unknownincomeImpact = 0 (neutral). User prompted to update once income is known. Roadmap shown with advisory: "Income impact for [Event] not yet configured."
EC-06User removes a HARD dependency from a previously BLOCKED goalGoal immediately re-evaluates all remaining deps. If now unblocked: roadmapStatus → UPCOMING / RECOMMENDED_NEXT. GoalTimelineEvent: DEPENDENCY_REMOVED logged. No contribution history affected.
EC-07Two goals have a mutual SOFT_DEPENDENCY (A soft-depends on B AND B soft-depends on A)Allowed (SOFT deps don't create hard cycles). Both shown as advisory-linked in roadmap. Prioritization engine computes scores independently.
EC-08A FINANCIAL_REQUIREMENT condition is partially met then the prerequisite goal is deletedDependency becomes orphaned (CON-06). Source goal unblocked. User notified: "Your prerequisite for [Goal] was removed."
EC-09What-If scenario is run but produces no meaningful deltaShow "No significant impact detected" with a brief explanation (e.g. "Adding $50/mo changes completion by less than 1 week"). Still show the comparison table for completeness.
EC-10User has zero dependencies (flat goal list)Roadmap degrades gracefully to standard goal list, sorted by priorityScore. No graph view available (disabled with "Add dependencies to unlock the roadmap view" prompt). All other features work normally.
EC-11A goal targeted by a SEQUENTIAL dependency has its targetDate removedEstimated unblock date for source goal becomes "Unknown". Source remains BLOCKED. Advisory: "Add a target date to [Goal] to estimate when [Source Goal] will activate."
EC-12CUSTOM conditionType — user manually marks a dependency as satisfiedUser taps "Mark as Satisfied" on the dependency. Sets manuallyMarkedSatisfied = true. Source goal re-evaluates. Cannot be undone (immutable). GoalTimelineEvent: DEPENDENCY_SATISFIED logged.

Business Rules
IDRule
BR-RMP-01A dependency between a sourceGoal and itself is prohibited (sourceGoalId ≠ targetGoalId). Enforced at DB constraint and UI validation levels.
BR-RMP-02Circular dependencies are strictly prohibited for HARD dependency types. Circular SOFT dependencies are allowed (no blocking behavior). CON-01 check runs before every HARD dependency insert.
BR-RMP-03A BLOCKED goal may still receive manual contributions. BLOCKED status only prevents auto-contributions (isAutoContribute). The user may contribute manually at any time.
BR-RMP-04Roadmap state (layer assignments, roadmapStatus, priorityScore) is never stored in the database. It is always derived at read time. This is a hard architectural invariant.
BR-RMP-05What-If scenarios are ephemeral. They may not be saved to the database. The only persistence path is "Apply Scenario" which saves the underlying goal/contribution changes, not the scenario itself.
BR-RMP-06GoalDependency records are soft-deleted only. Hard deletion is prohibited. Deleted dependencies are excluded from graph construction but remain in the audit log.
BR-RMP-07A maximum of 20 GoalDependency records per goal (as source or target) is enforced. This prevents pathological graph complexity. v2.0 may raise this limit.
BR-RMP-08SEQUENTIAL auto-activation only fires once. If the source goal is later cancelled and a replacement goal is set up, the SEQUENTIAL dependency must be re-created manually.
BR-RMP-09LifeEvent financial impacts (incomeImpact, expenseImpact) are stored as centimes and treated as monthly changes to disposableIncome. They are applied by the Salary module (SPEC-SAL-001), not by the Roadmap Engine directly.
BR-RMP-10The prioritization engine's recommended order is advisory only. It never overrides the user's manually set priorityOrder. Both orderings are displayed side-by-side in the Roadmap Dashboard.

Scalability Roadmap

v1.1 — Goal Templates
Pre-built dependency bundles (e.g. "Home Purchase Bundle" = EMF LEVEL_2 + Personal Loan Payoff + Down Payment). One-tap roadmap bootstrap.
v2.0 — Shared Family Roadmap
Multi-user ownership of GoalDependency. Goals can be shared; dependencies can be co-created. Roadmap shows combined household financial plan.
v2.0 — Bank Sync Triggers
SEQUENTIAL auto-activation tied to real bank transactions. Goal unlocks automatically when bank account shows required balance.
v2.0 — AI Dependency Engine
ML model trained on aggregate (anonymized) dependency patterns suggests dependencies for new goals based on goal category, amount, and user profile.
v3.0 — Investment Graph
Investment accounts as roadmap nodes. Market-linked goals with return projections. Portfolio rebalancing as a dependency condition.
v3.0 — Natural Language Interface
User describes a goal in natural language; AI parses it, creates the Goal entity, infers likely dependencies, and asks for confirmation before saving.

All roadmap state is derived at read time from GoalDependency + LifeEvent records plus cross-module data from SPEC-GOL-001, SPEC-DBT-001, and SPEC-EMF-001. No roadmap computation results are stored.
