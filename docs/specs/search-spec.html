Overview & Philosophy

The Global Search & Command Center (module: SCH) is the single unified entry point through which users access any data, screen, or action in Finance Bag. It operates as a context-aware overlay that can be invoked from anywhere in the application in under 100ms. Users should never need to remember navigation paths — the search box is the navigation.

Core Principle: Zero-Friction Information Retrieval. A user who wants to find March's salary, check a debt's payment history, jump to goal settings, or create a new expense should be able to do all of these from a single interface without knowing which module owns the data. The search system abstracts away the module hierarchy entirely.

1.1 Four Foundational Pillars

IInstantResults appear within 50ms of first keystroke. No loading spinners. No waiting. The index is always warm.
IIIntelligentTypo-tolerant, synonym-aware, context-sensitive. "salaery march" finds salary records from March. "emargency" finds Emergency Fund.
IIIActionableEvery result exposes relevant quick actions. Users never need to open a detail screen just to perform a common operation.
IVOffline-FirstAll search is local. The full index lives on-device. Network is never required and never queried.

1.2 What Users Can Find

The SCH module indexes data across every Finance Bag module. A non-exhaustive list of searchable entities:

1.3 Relationship to Other Modules

SCH is a read-only consumer of all other modules' data. It does not own financial entities. Its ownership is limited to: the search index tables, search history, command registry, and saved searches. When a user performs an action through the Command Center (e.g. "Create Goal"), the request is delegated to the owning module (GOL) for execution — SCH never writes to other modules' tables.

Search Architecture

The search architecture is a 7-layer stack running entirely on-device. Each layer has a single responsibility and communicates with adjacent layers through well-defined interfaces. No layer bypasses another.

2.1 Architecture Layers

L7Presentation LayerThe search UI overlay. Renders the input bar, result groups, command palette, and quick action menus. Receives SearchResultSet from L6 and renders it. Sends raw query strings to L6.
L6Search OrchestratorThe top-level coordinator. Receives a query from L7, invokes L5 (Query Processor), receives ranked results from L4, applies active filters, and assembles the final SearchResultSet for L7.
L5Query ProcessorTokenizes, sanitizes, classifies, and normalizes the raw query string. Extracts filter intent. Produces a ParsedQuery struct consumed by L4 and L3.
L4Ranking EngineScores each candidate result using the multi-factor ranking formula. Produces an ordered list of RankedResult objects. Has no knowledge of the UI.
L3Index EngineExecutes the parsed query against the search index (SQLite FTS5 virtual table + a supplementary inverted index for structured fields). Returns raw candidate matches.
L2Index ManagerOwns the index lifecycle: build, update, and invalidate. Listens to EVT module events to trigger incremental index updates. Runs index writes on a background queue. Exposes read APIs to L3.
L1Data Source AdaptersOne adapter per module (SAL, BUD, DBT, etc.). Each adapter knows how to read its module's entities and convert them to IndexRecord objects. Adapters are the only layer that reads from other modules' tables.

2.2 Core Components

ComponentLayerResponsibility
SearchOrchestratorL6Entry point for all search queries. Coordinates query processing, index lookup, ranking, and result assembly.
QueryParserL5Tokenizes raw input. Extracts filter tokens (e.g. category:food). Expands synonyms. Returns ParsedQuery.
FuzzyMatcherL5Applies Levenshtein distance (≤ 2) for typo tolerance on tokens not found in the index verbatim.
IndexEngineL3Queries FTS5 virtual table for text matches. Queries structured index for field matches. Returns raw candidates.
IndexManagerL2Manages incremental index updates triggered by EVT events. Batches writes. Maintains index freshness.
RankingEngineL4Computes final score for each candidate result using the multi-factor formula.
CommandRegistryL6In-memory registry of all available commands. Commands are registered by modules at app startup. Queried in parallel with the index during any search.
SearchCacheL6LRU in-memory cache mapping query strings to SearchResultSet. Cache capacity: 50 entries. TTL: 30 seconds (invalidated sooner on index update).
DataSourceAdapter[]L1Per-module adapters that read entities and produce IndexRecord objects for the IndexManager.

2.3 Index Storage

The search index is stored in a separate SQLite database file (search.db) co-located with the main finance.db. Using a separate file provides two advantages: (1) index rebuilds do not compete with hot financial writes, and (2) the index can be deleted and fully rebuilt without touching financial data. search.db uses WAL mode like the main database and is encrypted with the same key.

The index database owns three tables:

  • search_index — FTS5 virtual table for full-text matching.
  • search_index_meta — Structured metadata for each indexed entity (used for filter lookups not suited to FTS5).
  • search_history — User's recent and saved search queries.

3.3 FTS5 Virtual Table Configuration

The search_index FTS5 table indexes searchable_text, display_title, and display_subtitle. FTS5 configuration:

  • tokenizer = unicode61 — supports non-ASCII characters (French accents, Arabic, etc.) for multi-locale support.
  • prefix = '2 3 4' — builds prefix indexes for 2-, 3-, and 4-character prefixes, enabling fast auto-complete for short queries.
  • content table — the FTS5 table is a content table backed by search_index_meta, keeping the text stored once.
  • rank = bm25(10.0, 5.0, 1.0) — title match weight (10x), subtitle match weight (5x), body match weight (1x).

4

Ranking Algorithm

Every candidate result receives a numerical relevance score. Results are presented in descending score order within each group. Ties within a group are broken by recency (last_indexed_at DESC). The ranking algorithm is intentionally transparent — it is a deterministic weighted sum, not a black box.

4.1 Score Formula

score = fts_score × priority_boost // static entity type weight (0.7 – 1.5) × recency_factor // decays from 1.0 toward 0.4 over 90 days × frequency_factor // 1.0 + (user_clicks / max_clicks × 0.5) × context_factor // 1.3 if entity belongs to active period + pin_bonus // flat +5.0 if entity is pinned + favorite_bonus // flat +2.0 if entity is favorited

4.2 Factor Definitions

FactorRangeSourceDescription
fts_score0.0 – ∞FTS5 bm25()BM25 relevance score from SQLite FTS5. Title match weighted 10×, subtitle 5×, body 1×. Negated (FTS5 returns negative values; multiply by -1).
priority_boost0.7 – 1.5Index recordStatic per-entity-type multiplier. Commands (1.5) and active debts/goals (1.4) surface above historical records (0.8).
recency_factor0.4 – 1.0ComputedExponential decay: max(0.4, e^(−age_days / 45)). An entity updated today scores 1.0; one updated 90 days ago scores ~0.45. Archive records have a fixed floor of 0.5.
frequency_factor1.0 – 1.5Click logHow often the user has clicked this result after a search. Tracks up to 30 days of click events per entity. Normalized relative to the most-clicked entity in the session.
context_factor1.0 or 1.3App state1.3 if the entity's period_id matches the currently active salary period. 1.0 otherwise. Surfaces current-period data ahead of historical data when the query is ambiguous.
pin_bonus0 or 5.0User preferenceFlat additive bonus for entities the user has pinned (not a multiplier, so it can surface pinned items regardless of text match quality).
favorite_bonus0 or 2.0User preferenceFlat additive bonus for favorited entities.

4.4 Zero-Query Default State

When the search overlay opens with no query typed, the system renders a curated default screen rather than an empty state. It shows: (1) Recent searches (max 5), (2) Pinned commands (max 3), (3) Suggested commands based on context (e.g. "Add Expense" when in Budget view), and (4) Quick access to the current period's key metrics. The ranking algorithm does not run in zero-query state.

5.1 Step Definitions

StepNameInputOutputNotes
①ReceiveRaw string from UIRaw stringDebounced at 150ms from last keystroke. Queries shorter than 1 character skip to zero-query default state.
②SanitizeRaw stringSanitized stringStrip HTML/SQL injection patterns. Truncate to 200 characters. Trim whitespace. Normalize Unicode (NFC form). No query is ever passed to SQLite unsanitized.

⑥ExecuteExpanded token setRaw candidate listRun FTS5 MATCH query with expanded tokens. Also run CommandRegistry lookup in parallel (separate query path). Merge both candidate lists.

5.2 Query Intent Classification

Advanced Filtering System

Filters can be applied via inline query directives (§5.3), via the filter panel UI (a secondary panel accessible from within the search overlay), or via saved searches that embed pre-configured filter states. All filters are additive (AND logic) by default.

6.1 Filter Dimensions

6.2 Filter Combination Logic

  • Multiple values within the same dimension use OR logic (e.g. Category = Food OR Groceries).
  • Multiple dimensions use AND logic (e.g. Category = Food AND Status = ACTIVE).
  • Negation prefix (-term) uses NOT logic against the text match, not against the metadata filters.
  • Filter state is serialized as a JSON object and stored in the active search session. Navigating away and returning restores the last active filter state for the session.

6.3 Filter Panel UX

  • Accessible via a "Filters" button/chip row below the search input bar.
  • Active filters are shown as dismissible chips in a filter strip above the results.
  • Tapping a chip opens its dimension picker. Tapping the × on a chip removes that filter immediately (live results update).
  • "Clear all filters" resets all dimensions at once.
  • The filter panel does not require a confirmation button — changes apply instantly to results (debounced at 80ms).
  • Active filter count is shown as a badge on the "Filters" button (e.g. "Filters (3)").

6.4 Smart Filter Suggestions

Based on the current query, the system suggests relevant filters. If the user types "grocery", the filter system suggests "Category: Groceries" as a quick-apply chip. If the user types "march", it suggests "Month: March" and "Year: [current year]". Suggestions appear as tappable chips below the input bar and disappear once a filter is applied.

7.4 Quick Preview Card

On long-press (mobile) or hover-with-delay (>500ms, future desktop), a quick preview card expands without navigating away. The card shows the entity's most relevant structured data:

  • expense preview: amount, category, date, notes excerpt, tags
  • debt preview: current balance, creditor, interest rate, next due date, total paid
  • goal preview: progress bar (balance / target), target date, monthly contribution, status
  • monthly_archive preview: income, spending, savings, FHS at close, top category

The preview card does not navigate. It provides a "read snapshot" that lets users confirm they found the right item before opening it.

7.5 Match Highlighting

Matched query tokens are highlighted in result titles and subtitles. Highlighting uses a bold weight and the accent color (#E879F9) for the matching characters. Fuzzy matches (typo-corrected) are highlighted in the correction target — not in the misspelled query token. Highlighting is applied to display strings at render time using the highlight_ranges offsets from the SearchResult object.

7.6 Empty State

When no results match the query: (1) Show the query text echoed back clearly. (2) Show "No results for [query]". (3) Surface up to 3 spelling-corrected suggestions ("Did you mean: [correction]?"). (4) Suggest clearing active filters if any are applied. (5) Offer a "Create [entity type]" command if the query looks like a name (no digits, no operators, no filter directives).

Command Center

The Command Center is the action layer of the search overlay. Every command registered with the CommandRegistry is searchable and executable without leaving the overlay. Commands are first-class search results — they appear at the top of results when query intent is NAVIGATIONAL or TRANSACTIONAL.

Mental model: search IS the navigation. The Command Center replaces traditional tab-bar navigation for power users. Typing "salary" is faster than tapping Budget → Income → Salary. Typing "create goal" is faster than locating the "+" button on the Goals screen.

8.4 Command Execution Flow

  • User selects a command from the result list (tap or keyboard Enter).
  • SCH closes the search overlay with a dismissal animation (100ms).
  • If action_type = NAVIGATE: SCH fires a navigation event to the Expo Router path in navigation_target.
  • If action_type = OPEN_SHEET: SCH fires a bottom-sheet open event for the creation/edit sheet registered by the owning module.
  • If action_type = EXECUTE: SCH calls the module's registered handler function directly.
  • If action_type = TOGGLE: SCH toggles the setting and shows a toast confirmation.
  • The command execution is recorded in the recent commands list (max 10 recent commands).

8.5 Context-Sensitive Command Surfacing

When the user opens search from a specific screen, the Command Center promotes commands relevant to that context:

  • From Budget screen: "Add Expense", "Edit Category", "View Period Summary" appear first.
  • From Debt detail screen: "Record Payment", "Edit Debt", "View Payment History" appear first.
  • From Goal detail screen: "Add Contribution", "Edit Goal", "View Progress" appear first.
  • From Dashboard: "Add Expense", "Add Salary", "View FHS History" appear first.
  • Context is passed as a source_context parameter when the search overlay is opened. The CommandRegistry uses this to re-rank commands before returning them.

9.4 Debounce & Incremental Search

  • Debounce interval: 150ms from last keystroke. The query pipeline does not run on every character — it runs 150ms after the user stops typing. This prevents unnecessary work on fast typists.
  • Minimum query length: 1 character. A single character triggers a search (prefix index covers 2, 3, 4-char prefixes; for 1-char queries, auto-complete suggestions and recent searches are shown).
  • Incremental results. As the user types more characters, results narrow. The result list animates smoothly on update (fade/reorder, not full re-render).
  • Cancel in-flight query. If the user types a new character while a previous search is processing, the previous result is abandoned. Only the most recent query's results are displayed.

9.6 Auto-Complete

As the user types, up to 3 auto-complete suggestions appear below the input bar as a secondary chip row. These are candidate query completions, not results. They are sourced from: (1) the user's own search history matching the prefix, (2) popular query patterns across all entity display titles, (3) known filter directive completions (typing "category:" shows all category names as completions). Tapping a completion chip replaces the current input with the completion and immediately executes the query.

Smart Search makes the search bar behave like a knowledgeable assistant rather than a text matcher. It understands the user's intent in natural language and maps it to structured queries against the index. In v1, these capabilities operate on local heuristics and synonym expansion — no AI models are required. The architecture is explicitly designed to upgrade to true semantic AI search without redesign.

10.3 Typo Tolerance

The FuzzyMatcher applies Levenshtein distance correction for tokens not found in the FTS5 vocabulary:

  • For tokens ≤ 3 characters: no fuzzy expansion (too many false positives).
  • For tokens 4–6 characters: Levenshtein distance ≤ 1 (one character insertion/deletion/substitution).
  • For tokens 7+ characters: Levenshtein distance ≤ 2 (two character edits).
  • Fuzzy candidates are scored lower than exact matches — the FTS5 BM25 score for the exact term is used; fuzzy matches receive a 0.7× penalty.
  • No more than 5 fuzzy expansions per query to prevent result explosion.

10.4 Amount Recognition

The QueryParser detects numeric tokens that look like monetary amounts and converts them to centimes for structured filter matching:

  • "500" → amount filter: approximately 50000 centimes ± 20% range
  • ">500" or "more than 500" → amount filter: > 50000 centimes
  • "500-1000" or "between 500 and 1000" → amount filter: 50000–100000 centimes
  • Currency symbols are recognized: "$500", "€500", "₹500" — the symbol is validated against the user's configured currency.

10.5 Date Recognition

The QueryParser recognizes temporal expressions and resolves them to concrete date ranges:

  • Month names: "january", "jan", "feb", "february"… → month: [1–12], year: [current year or specified]
  • ISO dates: "2025-03", "2025" → YYYY-MM or YYYY year filter
  • Relative: "this month", "last month", "this year", "last year", "last 3 months" → resolved at query time
  • Quarter: "Q1 2025", "first quarter" → date range January–March 2025

10.6 AI Readiness Architecture

The following hooks in the search architecture allow seamless upgrade to semantic AI search without replacing the pipeline:

  • Semantic embedding slot: search_index_meta includes an embedding_json column (null in v1). When an embedding model is available, the IndexManager populates this column. The RankingEngine adds a cosine similarity term to the ranking formula when embeddings are present.
  • QueryParser AI handoff: After heuristic parsing, the QueryParser calls a pluggable NLPInterpreter interface. In v1, the implementation is the heuristic pattern matcher. In future versions, an on-device language model fills this role without changing the interface.
  • Voice entry: Voice input goes through a SpeechToText transcription layer and feeds its transcript directly into the QueryParser at step ④ — the same pipeline handles text and voice without modification.
  • OCR search: An image OCR layer extracts text from receipts and populates the expense.notes field, making them searchable through the existing FTS5 index without any pipeline changes.

Performance Architecture

Search performance is non-negotiable. A slow search is worse than no search — users will not trust or use a search that feels sluggish. Every architectural decision in the SCH module is evaluated against the 50ms end-to-end target for indexed queries.

11.1 Performance Targets

OperationTargetWorst-Case Bound
Search overlay open (time to interactive)< 80ms200ms (cold start, search.db not in page cache)
First result render (indexed query)< 50ms from last keystroke150ms (complex filter + large index)
Auto-complete suggestions< 30ms80ms
Command palette (no text query)< 20ms50ms (CommandRegistry is in-memory)

Full index rebuild (cold)< 3s for 5 years of data10s (background, non-blocking)
Incremental index update (single entity)< 20ms50ms
Free-text LIKE scan (no index)Acceptable up to 500msOnly for fallback non-indexed fields

11.2 Index Freshness Strategy

The search index must always reflect current data. Stale index entries are a correctness bug, not a performance tradeoff. The IndexManager maintains freshness through two mechanisms:

  • Event-driven incremental updates. The IndexManager subscribes to the EVT module's FINANCIAL_STATE_CHANGED, DEBT_BALANCE_CHANGED, GOAL_STATUS_CHANGED, and all SYNC.* events. On each event, it identifies the affected entity and re-indexes only that entity's row (not the full index).
  • Startup consistency check. On app launch, the IndexManager compares the last_indexed_at of the most recently modified entity in each module's primary table against the corresponding index row. Any entity modified after its index row was last written is queued for re-indexing. This catch-all handles cases where events were missed (e.g. app killed during a write).

11.3 Index Size Estimation

ScenarioApprox Entity CountEst. Index Size
1 year of usage~1,200 entities~2 MB
3 years of usage~3,500 entities~5.5 MB
10 years of usage~12,000 entities~18 MB

These estimates include FTS5 prefix indexes (2, 3, 4 chars) which add approximately 2× overhead over raw text storage. Even at 10 years, the index remains well within mobile storage budgets (18 MB).

11.4 SearchCache

An in-memory LRU cache intercepts repeated queries within a session. Cache characteristics:

  • Capacity: 50 query→result mappings.
  • Key: SHA-256 of (sanitized_query + JSON-serialized active filter state).
  • TTL: 30 seconds after last access. Invalidated immediately on any IndexManager write.
  • On cache hit: skip steps 4–7 of the pipeline entirely. Present cached result in <5ms.
  • Cache is not persisted across app sessions — it is warm only for the current session.

11.5 Background Index Operations

All index writes run on a dedicated background serial queue (not the main thread). Reads (during search queries) run on the search query queue (can be concurrent with index writes because WAL mode in search.db allows concurrent readers). The IndexManager ensures writes are batched: if 5 events fire within 200ms of each other, they are coalesced into a single batch index write rather than 5 sequential writes.

12

Security & Privacy Model

The search index contains condensed copies of sensitive financial data. It must be protected with at minimum the same security level as the primary database.

12.1 Index Encryption

search.db is encrypted with the same key as finance.db. Both files are opened with the same derived key (from the platform Keychain/Keystore). The encryption key is never stored in plaintext. Decryption is required to open either database — raw file reads return ciphertext.

12.2 Biometric Lock Integration

When the app is locked (biometric lock triggered), the search overlay cannot be opened. The search entry point (FAB, gesture, header icon) is disabled on the lock screen. Even if the overlay were somehow opened programmatically, the search.db connection is closed at lock time and requires re-authentication to re-open. Search is fully blocked until re-authentication succeeds.

12.3 Obscure Amounts in Search Results

When settings.obscure_amounts = TRUE:

  • All monetary amounts in search result subtitles are replaced with "•••• [currency symbol]".
  • The display_subtitle in SearchResult replaces formatted amounts with the obscured placeholder at render time.
  • Quick preview cards obscure all amount fields.
  • The obscuring is a render-time transformation — stored index data is unmodified. The index itself stores unobscured values (protected by encryption).
  • Amount-based filter directives (e.g. amount:>500) continue to work correctly — the filter operates on centimes in the index, not the display string.

12.4 Search History Privacy

  • Search history is stored in search.db — same encryption applies.
  • History is never sent off-device in v1. No telemetry, no analytics, no crash reporting that includes query strings.
  • Users can clear history per-query or all at once from within the search overlay.
  • Users can disable history recording entirely via Settings → Search → Save Search History (default: enabled).
  • When disabled, no new queries are written to search_history. Existing history is not cleared — the user must clear it manually.

12.5 Index Content Safety

The index does not contain:

  • Full monetary amounts in plaintext in the FTS5 text fields (amounts are in metadata_json only, accessed only by the filter layer, not by FTS5 full-text matching).
  • Authentication credentials, encryption keys, or biometric data.
  • File contents of attachments (only filenames and metadata are indexed).
  • The rollback_sql field from schema_migrations.

12.6 Deleted Entity Handling

When an entity is soft-deleted in the main database, the IndexManager receives the corresponding EVT event and sets search_index_meta.deleted = 1 on that entity's index row. Deleted rows are excluded from all search queries (WHERE deleted = 0). The index row is retained (not hard-deleted) for 30 days, then purged in a nightly maintenance pass. This 30-day window allows the "undo soft delete" feature to restore an entity without requiring a full re-index.

13

Offline Behavior

Finance Bag is an offline-first application. The Global Search & Command Center operates with full fidelity offline — no capability is degraded, no features are hidden, no "search not available" messages are shown. Network connectivity is irrelevant to search.

13.1 Fully Local Architecture

Every component of the search system lives on-device:

  • search.db — The complete search index. Never requires a network call to populate or query.
  • CommandRegistry — In-memory, populated at app startup from statically registered commands. No network dependency.
  • SearchCache — In-memory. No network dependency.
  • Synonym dictionary — Bundled in the app binary. No network dependency.
  • FuzzyMatcher — Pure local computation. No network dependency.

There is no fallback mode. Offline IS the mode. A future cloud-sync version would add cloud results as an additive layer on top of local results, never replacing them.

13.2 Index Consistency Without Network

Because all data lives locally, the index is always consistent with the main database. The only scenario where the index could be temporarily stale is if the IndexManager's event subscription missed an update due to an app crash. The startup consistency check (§11.2) handles this case by re-indexing any entities whose updated_at timestamp is newer than their last_indexed_at in the index.

13.3 No Degraded Features

There are no "requires network" features in v1 search. This table documents that explicitly:

Search History & Persistence

The search history system stores the user's past queries to enable fast repetition of common searches, query auto-complete seeding, and personalized ranking signals.

14.1 search_history Table Schema

FieldTypeDescription
idULIDHistory entry identifier
queryTEXT NOT NULLThe sanitized search query string as entered by the user
filter_state_jsonTEXT NULLSerialized filter state active when this query was run (null if no filters)
result_countINTEGERNumber of results returned (for display in history list)
executed_atINTEGERUnix ms timestamp of query execution

is_savedINTEGER DEFAULT 01 = saved search (user gave it a name)

14.2 History Limits

  • Recent history: Max 50 non-pinned, non-saved rows. When the 51st is inserted, the oldest unpinned+unsaved row is deleted.
  • Pinned searches: Max 10 pinned rows. Pinned searches never auto-expire.
  • Saved searches: Max 10 saved rows (same limit as saved_report_filters). Users must delete one before adding another.
  • Duplicate queries (same query string + filter hash within 1 hour) do not create a new history row — they update the executed_at of the existing row.

14.3 History Display in Zero-Query State

When the search overlay opens with no input, the recent history section shows the last 5 non-pinned queries. Pinned searches are shown in a separate "Pinned" section (max 3 shown, expandable to all 10). Saved searches are shown in a "Saved" section. Tapping any history row immediately executes the query (no typing required).

14.4 History Management UX

  • Swipe-left on a history row reveals: Pin / Unpin, Save, Delete.
  • Long-press on a history row opens the same action sheet.
  • "Clear all history" is accessible from Settings → Search → Search History. It deletes all non-pinned, non-saved rows.
  • Pinned and saved rows survive "Clear all history" — they must be individually deleted.
  • If history recording is disabled (§12.4), the history section in the zero-query state shows only pinned and saved searches.

14.5 Click Signal Logging

When a user selects a search result (navigating to an entity or executing a command), the event is logged to a search_click_log table in search.db. This drives the frequency_factor in the ranking algorithm. The click log stores: entity_id, entity_type, query, clicked_at. Rows older than 30 days are hard-deleted in the nightly maintenance pass. The click log is not exported in any user-facing export — it is internal ranking signal data.

15

Future AI Compatibility

The SCH architecture is explicitly designed to remain architecturally stable as AI capabilities are added. Every AI feature described here is additive — it plugs into existing interfaces without restructuring the core pipeline.

15.1 Semantic Search Upgrade Path

In a future version with an on-device language model, semantic search adds one step to the pipeline and one field to the index, touching nothing else:

  • A background job generates embedding vectors for each entity's searchable_text and stores them in search_index_meta.embedding_json.
  • The QueryParser generates an embedding vector for the user's query using the same model.
  • The IndexEngine performs an approximate nearest-neighbor search across stored embeddings (using SQLite's JSON functions or a compiled extension like sqlite-vss).
  • Semantic match candidates are merged with FTS5 candidates and passed to the RankingEngine, which adds a semantic_similarity term to the scoring formula.

The Presentation layer, SearchOrchestrator, SearchCache, CommandRegistry, and all filter logic remain completely unchanged.

15.2 Voice Search Integration

Voice input is a transport mechanism, not a separate search system. When voice input is activated, the SpeechToText module transcribes speech to text and passes the resulting string into the QueryParser at step ④ of the existing 8-step pipeline. The entire downstream pipeline (expand, execute, rank, filter, present) runs identically for voice and typed queries. The only voice-specific UI consideration: the input bar shows a microphone animation instead of a text cursor while recording, and the transcript appears in the text field progressively as words are recognized.

15.3 OCR Attachment Search

When receipt/document OCR is implemented, extracted text is stored in expense.notes (or a new expense_ocr_text field added via migration). The DataSourceAdapter for the BUD module includes this field in the entity's searchable_text when building the index record. No changes to the search pipeline are required — the OCR text is just additional FTS5-indexed text.

15.4 Predictive Search & Personalized Ranking

A future ML-based ranker replaces the deterministic frequency_factor component with a learned model that predicts which result the user is most likely to select given: query text, time of day, day of week, current screen context, and recent click history. The ranker interface is already abstracted in the RankingEngine (the frequency_factor is computed by a pluggable FrequencySignalProvider). The ML model replaces only this provider — the rest of the scoring formula and all other layers are unchanged.

15.5 Bank Transaction Import Search

When bank transaction import is added (a future module), imported transactions become a new entity type in the index. The DataSourceAdapter for the import module produces IndexRecord objects with entity_type: 'bank_transaction', module: 'BANK'. The index, query pipeline, and presentation layer handle this entity type identically to any other — no special casing required.

15.6 Cross-Device Search (Cloud Sync)

When cloud sync is introduced, the index becomes a derived artifact that can be fully rebuilt from the synced database. Each device maintains its own local index. Cross-device search (searching across data that exists only on another device) requires a cloud-hosted index — this is out of scope for v1 and does not affect the local architecture. The entity_id ULID scheme already supports cross-device identity without coordination.

16

Business Rules

BR-SCH-01
Index Freshness Maximum Lag: 5 Seconds
After any financial entity is created, updated, or soft-deleted, the corresponding index row must be updated within 5 seconds. The IndexManager's event subscription must process index updates asynchronously but promptly. A user who creates an expense and immediately searches for it should find it within one search attempt (one debounce cycle of 150ms + one pipeline execution of ≤ 50ms + the 5s index lag in worst case).
BR-SCH-02
No Deleted Entities in Results
Soft-deleted entities (those with deleted_at IS NOT NULL in the main database, and deleted = 1 in the index) must never appear in search results. This is enforced by a mandatory WHERE deleted = 0 clause in every FTS5 query. There is no "show deleted items" toggle in v1.
BR-SCH-03
Query Sanitization Before Any DB Access
Every query string must pass through the sanitization step (step ②) before any SQLite query is constructed from it. The sanitized string is HTML-stripped, truncated to 200 characters, and Unicode-normalized. SQLite parameterized queries must be used — string interpolation into SQL is prohibited in the search layer as in all other modules.
BR-SCH-04
Command Execution Delegates to Owning Module
The SCH module may never write to another module's tables directly, even during command execution. "Create Goal" from the Command Center calls the GOL module's public creation function. "Add Expense" calls the BUD module's public creation function. SCH is a consumer and delegator — it has no write access to financial tables.
BR-SCH-05
History Disabled = No History Writes
When settings.save_search_history = FALSE (a new settings field owned by SCH), no rows are written to search_history for executed queries. Pinned and saved searches that already exist are preserved. The auto-complete suggestion seeding from history is replaced by vocabulary-only suggestions when history is disabled.
BR-SCH-06
Max 10 Saved Searches
At most 10 rows with is_saved = 1 may exist in search_history. Before saving a new search, the application checks the current count and rejects the save if the limit is reached, surfacing the error: "You've reached the maximum of 10 saved searches. Delete one to save a new one."
BR-SCH-07
Index Rebuild Must Not Block the UI
Full index rebuilds (triggered on first launch, after a database restore, or after index corruption) must run on a background thread. While a rebuild is in progress, the search overlay remains functional — it queries whatever portion of the index has been built so far and shows a subtle "Index updating…" indicator. It does not show a blocking loading screen.
BR-SCH-08
Amounts Never in FTS5 Searchable Text
Monetary amounts (in centimes or formatted display strings) must not be included in the searchable_text column fed to FTS5. Amounts are stored exclusively in metadata_json.amount and accessed only by the filter layer. This rule prevents users from finding expenses by typing raw currency amounts into the text search box — amount-based retrieval goes through the structured filter system exclusively.
BR-SCH-09
Single Entry Point — No Module-Level Search
Individual modules (BUD, DBT, GOL, etc.) must not implement their own search systems. Any search functionality within a module screen (e.g. filtering an expense list) that goes beyond local in-memory array filtering must be delegated to the SCH module via its public query API. This ensures the index stays as the single source of truth for all search operations.
BR-SCH-10
search.db Recoverable Without Data Loss
The search.db file is a derived index — it contains no data that does not already exist in finance.db. If search.db is corrupted or deleted, it can be fully rebuilt from finance.db by triggering a full index rebuild. A "Rebuild Search Index" option must exist in Settings → Advanced. Corruption of search.db must never affect the integrity of finance.db.
17

Edge Cases

EC-SCH-01
Query Containing Only Special Characters or Operators
Queries that consist entirely of special characters (!@#$%^&*()), filter operators without values (category: amount:), or negation only (-) are treated as empty queries after sanitization. The system renders the zero-query default state rather than attempting to execute a malformed FTS5 query. No error is shown — the overlay simply shows the default state.
EC-SCH-02
Query Longer Than 200 Characters
Queries are truncated to 200 characters at step ②. The truncation happens at the last word boundary before 200 characters (no mid-word cuts). A subtle indicator in the input field shows that the query was truncated (e.g. the character count turns amber at 180 characters). This prevents pathologically long queries from causing excessive FTS5 work.
EC-SCH-03
Index Corrupted or Missing on Launch
If search.db fails PRAGMA integrity_check on startup (corruption detected) or the file is missing entirely, the IndexManager creates a fresh empty search.db and triggers a full background rebuild from finance.db. Search is available immediately (returning no results until the rebuild progresses) with a banner notification: "Search is rebuilding your index — results may be incomplete." The banner disappears when the rebuild completes.
EC-SCH-04
Stale Index Entry for a Renamed Entity
When a financial_goal is renamed from "Vacation" to "Holiday Fund", the GoalDataSourceAdapter re-indexes the entity with the new name. The stale "Vacation" entry is replaced (upsert by entity_id). During the brief window between the rename and the re-index (≤ 5 seconds per BR-SCH-01), the old name may appear in search results — this is acceptable. The navigation_target in the result still points to the correct entity, so the user is never misdirected.
EC-SCH-05
User Searches for an Amount While Obscure Mode is On
Amount-based filter directives (amount:>500) continue to work correctly in obscure mode. The filter operates on the raw centimes value in metadata_json.amount — which is unaffected by obscure mode. The results are returned normally. Only the display of amounts in result subtitles and preview cards is obscured. The user can find expenses by amount even when they cannot see the amounts in results.
EC-SCH-06
User with No Financial Data (First Launch)
On first launch, the index is empty. Any query returns zero results. The empty state in this context shows: "Nothing to search yet — start by adding your salary and first expense." The Command Center remains fully functional (commands are registered at startup regardless of data). The user can use the Command Center to navigate to any screen and create their first data.
EC-SCH-07
Two Searches Dispatched Faster Than Debounce
If the user pastes text (triggering an instant query) and then immediately types another character before the first query completes, the second query cancels the first. Only the most-recently-dispatched query's results are displayed. The in-flight first query is aborted at the SearchOrchestrator level before it reaches the IndexEngine. The SearchCache may still populate from the first query's result if it completes before cancellation — this is harmless since cache keys are query-specific.
EC-SCH-08
Command Requiring Context Invoked Without Context
Commands with requires_context = true (e.g. "Record Payment" needs a debt in context, "Add Contribution" needs a goal in context) may be surfaced in global search without any entity in context. When executed from global search without the required context, these commands open the relevant creation sheet but start in "entity selector" mode — the user first chooses which debt or goal the action applies to, then proceeds with the action. No error is thrown; the command always succeeds by asking for the missing context.
EC-SCH-09
Extremely Large Number of Search Results
If a query like "a" matches thousands of expenses (any expense containing the letter "a"), the system caps FTS5 to return at most 500 raw candidates. The RankingEngine scores and sorts these 500 candidates, then applies per-group limits before presentation. The user sees at most 5 expense results (expandable to 50). The "500 candidate" cap is enforced by LIMIT 500 in the FTS5 query — the user never waits for thousands of rows to be processed.
