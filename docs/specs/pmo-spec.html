Section 01

Overview & Philosophy

1.1 Why Performance Is a Product Feature

Finance Bag users open the app in specific, time-pressured moments: at the grocery checkout to check their budget, at the bank to record a payment, at month-end to review spending. An app that takes 4 seconds to start, freezes on navigation, or displays stale data is not a minor inconvenience — it actively fails the user at the moment they need it most.

Performance is therefore a first-class product requirement with the same priority as financial accuracy and security. It is designed and measured from the first day of development, not tuned during a pre-release "performance sprint." An app that was fast at launch and degrades over years of use and data accumulation has failed its users as surely as one that was always slow.

1.2 The Four PMO Pillars

Performance

The app is fast, responsive, and efficient under all conditions — from first launch with empty data to 3 years of financial history.

Monitoring

Problems are detected proactively, before users report them. The system monitors itself and alerts the team to degradations.

Observability

When something goes wrong, the team has enough instrumentation to diagnose the root cause without reproducing it manually.

Reliability

The app recovers gracefully from failures. Users experience continuity even when individual operations fail.

1.3 Core Principles

PrincipleApplication to Finance Bag
Measure everything that mattersEvery user-perceptible operation has a performance counter. Unmeasured operations cannot be improved.
Prioritize the P95 user, not the averagePerformance targets are defined as percentiles (P50, P95, P99). A fast average with a slow tail is not acceptable for a financial app — the tail users matter.
Degrade gracefully, recover automaticallyWhen performance degrades (low memory, slow network, full storage), the app reduces its scope gracefully rather than failing catastrophically.
Observability is for operators, not auditorsLogs, metrics, and traces serve the engineering team's operational needs. They are not retroactive forensics tools — they are continuous operational intelligence.
Privacy is not optional in monitoringFinancial values, user names, and transaction details never appear in any telemetry, log, or metric payload. Observability and privacy are co-requirements, not trade-offs.
Monitoring must survive failuresThe monitoring subsystem must function when the rest of the app is struggling. It is the last thing to degrade, not the first.

1.4 Scope

This specification covers the complete performance, monitoring, and observability architecture for Finance Bag v1.0. It defines what to measure, how to measure it, what to alert on, how to log, how to diagnose failures, and how to scale the observability model as the app matures. It covers both local (on-device) instrumentation and the path to future cloud-based observability.

Out of scope: Implementation code, configuration files, specific SDK integrations, and server-side infrastructure. This spec defines what the system must do and why — not how it is implemented.

Section 03

Performance Architecture

Finance Bag's performance architecture is built around a core principle: keep the main thread as close to idle as possible at all times. Every strategy below serves this principle, directly or indirectly.

3.1 Main Thread Protection

The main thread budget: The main (UI) thread has a 16.67ms frame budget at 60 fps (8.33ms at 120 fps). Any work that exceeds this budget produces dropped frames visible to the user as jank. Finance Bag enforces strict main thread discipline:

Permitted on main thread:
• React component rendering and re-rendering
• User interaction handling (touch events)
• Animation frame callbacks
• Reading from already-computed state

Prohibited on main thread:
• Any database read or write (all DB I/O is async background)
• Any network request
• Any encryption/decryption operation
• Any report or aggregate calculation exceeding 2ms
• JSON serialization of large payloads (>100 fields)
• File I/O (backup, export, log writes)
• Image processing or heavy DOM-equivalent reconciliation

3.2 Multi-Tier Caching Architecture

Finance Bag uses a three-tier caching strategy. Each tier is progressively slower and more persistent. The goal is to serve the most-requested data from the fastest tier.

TierStorageTTL PolicyCapacityWhat Lives Here
L1 — In-MemoryZustand store (JS heap)Session lifetime; invalidated by relevant data events~5MB budgetCurrent month's budget summaries, dashboard aggregates, active module data
L2 — SQLite Materialized ViewsDedicated summary tables in the encrypted SQLite DBEvent-driven invalidation (transaction add/edit/delete triggers recalculation)No limit (DB-backed)Monthly totals per budget, per category; FHS component scores; dashboard snapshot
L3 — Archived DataImmutable archive records in SQLitePermanent (never invalidated — archives are immutable by spec)No limitAll prior-month archives; historical report data
Cache invalidation rules:
• L1 cache is invalidated by Zustand event subscription. When a transaction is added to Budget A, only Budget A's cached summaries are invalidated — not all budgets.
• L2 materialized views are updated synchronously within the same SQLite transaction as the triggering operation. The view is never stale relative to the underlying data.
• L3 archives are never invalidated. Attempting to invalidate an archive is a programming error caught at the business logic layer.
• Cross-tier consistency: L1 is always derived from L2; L2 is always derived from raw transaction data. No cache tier holds data independent of its source.

3.4 Background Processing Architecture

Background Task Queue:
Finance Bag uses a priority-ordered background task queue that runs on a dedicated worker thread (off the main thread). Tasks are classified into four priority levels:

P1 — Critical (runs immediately, blocks UI feedback):
• Transaction save (user is waiting for confirmation)
• Authentication operations
• PIN verification

P2 — High (runs within 500ms of trigger):
• Dashboard aggregate recalculation after data change
• Sync queue enqueue after user action
• Search index update after transaction save

P3 — Normal (runs when CPU idle, within 5s):
• Incremental sync execution
• Report data pre-computation
• AI recommendation recalculation
• Notification scheduling

P4 — Background (runs during OS-granted background time):
• Full-epoch sync
• Nightly database maintenance
• Log compression and rotation
• Backup file verification

3.7 Memory Management

Memory lifecycle rules:
1. Acquisition: Data is loaded into memory only when needed. Archive data for months not currently displayed is not held in memory.
2. Retention: The in-memory (L1) cache has an explicit eviction policy. When the app receives a memory pressure warning (iOS: UIApplicationDidReceiveMemoryWarningNotification; Android: onTrimMemory), L1 cache is cleared aggressively — data will be reloaded from L2 (SQLite) on next access.
3. Release: Module screens release their data subscriptions when unmounted. Navigating away from Reports clears chart data from memory. Navigating back re-fetches from L2.
4. Leak prevention: Every event listener, subscription, and timer registered by a component is stored in a ref and cleared in the cleanup function. No orphaned subscriptions.
5. Large object handling: Export PDF buffers, backup file buffers, and large chart datasets are released immediately after use. They are never held in long-lived component state.
6. Monitoring: Memory usage is sampled every 30 seconds during active sessions. A trend of >2MB/minute growth triggers a memory leak diagnostic report.

4.3 Trace Architecture

Trace coverage — operations that generate traces:
1. App launch sequence (root span → child spans: bundle parse, DB open, auth check, dashboard load)
2. Transaction create (user tap → validation → DB write → cache update → UI refresh)
3. Sync operation (trigger → queue → network → conflict resolution → DB write → UI update)
4. Report generation (trigger → DB aggregate queries → calculation → chart data preparation → render)
5. AI Coach request (query → context build → provider call → response parse → recommendation creation)
6. Backup creation (trigger → DB read → encryption → file write → verification)
7. Restore operation (file read → decryption → DB write → verification → UI refresh)

Trace sampling policy:
• v1.0 (local only): 100% of traces captured locally; stored in rolling trace buffer (last 100 traces)
• v1.5 (cloud): 10% random sampling for normal operations; 100% sampling for errors and slow operations (P99+)
• Error traces: always 100% captured regardless of global sampling rate

4.5 Signal Correlation

The four signal types are correlated through a shared session_id and correlation_id on every telemetry event. This allows any incident to be investigated across all signal types:

Correlation workflow example — "User reported dashboard is slow":
1. Identify the session_id from the user's report (extracted from a diagnostic export)
2. Filter metrics for that session_id: app_launch_duration = 4.2s → above P99
3. Filter traces for session_id, trace_type = "dashboard_load": DB aggregate query = 3.1s → the bottleneck
4. Filter logs for session_id around that timestamp: "materialized_view_invalidated, rebuild_duration=3100ms" → cache miss on cold start
5. Health indicators at that time: DB health = DEGRADED, db_queue_depth = 47 (high)
6. Root cause identified: large sync batch triggered materialized view rebuild during app launch
Section 05

Monitoring Framework

Monitoring translates raw signals (metrics, logs, traces, health indicators) into operational awareness. Where observability answers "what happened?", monitoring answers "is anything wrong right now?"

5.1 Monitoring Architecture

Finance Bag v1.0 — Local Monitoring Architecture:
In v1.0, all monitoring is performed locally on-device. The telemetry pipeline is:

Instrumentation layer (embedded in production code, zero-overhead when disabled)
→ Telemetry collector (in-process service; collects events, batches them, writes to local store)
→ Local telemetry store (dedicated SQLite table separate from app data; rotating 7-day window)
→ Diagnostic exporter (reads telemetry store on demand; generates diagnostic report bundle)
→ Health monitor (reads from telemetry store; evaluates health indicator rules; updates health state)

Finance Bag v1.5 — Cloud Monitoring Integration:
The v1.5 pipeline adds a remote export step between the telemetry collector and local store:
Telemetry collector → Privacy filter → Anonymization layer → Remote export (batched, gzip-compressed) → Cloud observability platform
Local store is retained as fallback; remote export is best-effort (failures do not impact app functionality).

Error Reporting Architecture

Error reporting in Finance Bag distinguishes between five error classes, each with different handling, storage, and escalation behaviors. The framework captures the context needed for root cause analysis while never capturing sensitive financial data.

6.1 Error Classification

ClassDefinitionExamplesUser Experience
CRASHUnrecoverable error that terminates the process. App exits unexpectedly.JS runtime error in critical path; native module crash; OOM killApp closes; relaunches to recovery screen or last stable state
UNHANDLEDUncaught exception that does not crash the process but leaves the app in undefined state.Unhandled Promise rejection; async error without catchFeature may stop working; app may require navigation reset

6.2 Error Report Schema

Every error report contains the following fields:
• error_id: ULID — unique identifier for this error instance
• session_id: Session in which the error occurred
• error_class: CRASH / UNHANDLED / HANDLED / USER_VISIBLE / SILENT
• error_type: Specific error category (DatabaseError, NetworkError, AuthError, etc.)
• message: Error message string (sanitized — no financial values)
• stack_trace: Symbolicated stack trace (for CRASH and UNHANDLED)
• module: Which Finance Bag module the error occurred in
• screen: Which screen was visible when error occurred
• breadcrumbs: Last 20 user actions and system events before the error (action types only — no financial data)
• device_info: OS version, device model, app version, available memory at time of error
• occurred_at: ISO 8601 timestamp
• is_fatal: Boolean — whether the error crashed the app
• recovery_action: What the system did in response (retry, fallback, navigate, none)

6.4 Error Deduplication

The same error occurring repeatedly must not flood the error log with identical entries. Error deduplication rules:

  • Errors are grouped by a fingerprint computed from: error_type + top 3 stack frames + module
  • The first occurrence is always stored in full
  • Subsequent occurrences within the same session increment a occurrence_count counter on the fingerprint group
  • If the same error fingerprint occurs across multiple sessions, it is promoted to a "trending error" status in the health dashboard
  • Deduplication resets across app version boundaries — a new release starts fresh error grouping

6.5 Silent Failure Detection

Silent failures are the most dangerous error class — they allow incorrect state to persist without the user knowing. Finance Bag uses invariant assertions to detect silent failures:

Invariant assertion categories:
• Financial invariants: After every transaction write, assert that the parent budget's materialized total matches the sum of its transactions. Discrepancy logged as HANDLED error.
• Sync invariants: After sync completion, assert that the local operation count matches the server-acknowledged count. Discrepancy logged + sync flagged for review.
• Encryption invariants: After writing encrypted data, immediately re-read and verify the decrypted value matches the original. Mismatch = CRASH-level error (data integrity).
• State invariants: After state transitions (e.g., goal ACTIVE → COMPLETED), assert all required fields are populated and consistent. Invalid state logged as HANDLED error.

7.3 Sensitive Data Filtering Rules

The following data MUST NEVER appear in any log entry:
• Monetary amounts (any currency value, budget limit, transaction amount, balance, salary)
• User-entered text (transaction labels, goal names, notes, budget category names)
• PIN, biometric data, encryption keys, session tokens
• Device identifiers (IDFA, Android Advertising ID, IDFV unless anonymized)
• Names, emails, or any personally identifiable information
• AI-generated recommendations content
• Sync payload content (may contain financial data)

What IS permitted in logs:
• Entity IDs (ULIDs) — these are meaningless without the DB
• Entity types (transaction, budget, goal) — types are not sensitive
• Durations, counts, error codes, status codes
• Screen names, module names, operation names
• Boolean outcomes (success/failure)
• Anonymized aggregates (e.g., "budget has 47 transactions" — count only)

7.5 Correlation ID Strategy

Correlation IDs link all log entries, metrics, and traces that are part of the same logical operation. This is the primary mechanism for incident investigation.

Correlation ID generation rules:
• User-initiated operation (e.g., "Save transaction"): new correlation ID generated at the user action; all DB writes, cache updates, and UI events for that action share the same correlation ID
• Background operations (e.g., "Sync batch"): new correlation ID per sync batch; all operations within the batch share it
• Session-level operations (e.g., "App launch"): correlation ID = session ID for launch-sequence events
• Error events: inherit the correlation ID of the operation that caused them; if no operation context, generate a new correlation ID

11.3 Alert Deduplication & Fatigue Management

  • Cooldown Window: Each alert fires at most once per defined cooldown (configurable per alert, default 5min). Subsequent triggers within the window increment a suppression counter rather than firing a new alert.
  • Aggregation: Multiple triggers of the same alert type within a cooldown window are reported as one alert with a count (e.g., "DB slow query: 7 occurrences in 5 min").
  • Exponential Suppression: Alerts firing repeatedly across multiple windows increase their cooldown period (×2 each occurrence up to 60min) until a sustained healthy period resets the base cooldown.
  • User-Facing Alert Cap: At most 2 in-app banners visible simultaneously. Third alert queues behind existing banners. EMER alerts always preempt lower-severity banners.
  • Developer Overlay vs. User Surface: INFO and some WARN alerts route only to the developer overlay (not shown to end users). User-visible alerts require explicit approval in the alert definition table.

12.2 Memory Lifecycle Enforcement

Memory management is governed by a three-tier priority eviction policy. When memory pressure is detected, caches are evicted in strict priority order before any data loss risk occurs.

Eviction Priority Order (lowest priority evicted first)
  1. Image render cache — Pre-rendered chart images and icon composites. Evicted first; regenerated on demand. Maximum 20MB; target 10MB.
  2. Prefetched report data — Report dataset cached in memory for recent report views. Maximum 15MB; evicted on any memory warning.
  3. AI suggestion cache — Last 10 AI responses cached to avoid re-inference. Maximum 5MB; evicted on memory warning.
  4. L1 Zustand derived state — Computed views cached in Zustand. Recomputed from SQLite on eviction. No absolute maximum; full eviction on critical pressure.
  5. SQLite prepared statement cache — Retained for performance; re-prepared on eviction. 100-statement limit; evicted in LRU order.
  6. Active screen component state — Only evicted if app is in deep background (OS low-memory kill imminent). State persisted to SQLite before eviction.
  • AppState-Driven Eviction: When app transitions to background, L1 cache (image render + report + AI suggestion) is proactively evicted to free memory before OS applies pressure.
  • Warning-Driven Eviction: OS memory warning events trigger immediate eviction of all non-essential caches (tiers 1–3) and a forced GC hint to Hermes.
  • Heap Budget Enforcement: Monitoring checks heap size every 30s during active sessions. If heap exceeds 120MB (WARN) or 150MB (CRIT), cache eviction is triggered programmatically without waiting for OS signal.

12.6 Large Dataset Pagination Strategy

Finance Bag never loads unbounded datasets into memory. All list views and reports use cursor-based or keyset pagination enforced at the query layer.

  • Transaction List: Keyset pagination with (created_at, transaction_id) cursor. Page size: 50 rows. Total count fetched separately (cheap COUNT(*) with index).
  • Report Dataset: Chunked processing in 1,000-row batches for aggregation. Partial results streamed to UI as each chunk completes.
  • Category/Budget List: Always loaded in full (bounded by FHS design: max ~200 nodes); no pagination needed.
  • Archive Restore: Streamed in 500-record chunks; progress reported per chunk; cancellable between chunks.
  • AI Coaching History: Last 50 interactions loaded; older history paginated on explicit user scroll.

12.7 Long-Session Management

Sessions lasting more than 4 hours introduce compounding risks: memory accumulation, stale cache state, and sync queue depth. The following policies apply:

  • At 4-hour session mark: automatic L1 cache (tier 1–3) eviction and GC hint; log "long session" event.
  • At 6-hour mark: full prepared statement cache flush and re-warm of only the most recently used 20 statements.
  • At 8-hour mark: soft suggestion to user to restart the app (non-blocking toast). If heap is below 80MB, no suggestion is made.
  • Navigation state snapshot persisted to SQLite at 1-hour intervals so a restart does not lose context.
  • Zustand store integrity check at 2-hour intervals to catch any state drift.

  • Measurement Window: Rolling 24-hour window; computed per bundle version.
  • Session Definition: A session starts on app foreground and ends on background or after 30min of inactivity. A crashed session is one ending in an unhandled exception or OS kill with no clean lifecycle event.
  • Crash Attribution: Crashes grouped by symbolicated stack frame top-3. New crash signatures (not seen in prior bundle) flagged as regressions. Recurrent crash signatures compared to known backlog.
  • Non-Fatal Error Rate: HANDLED and UNHANDLED non-crash errors tracked separately. Target: <0.1% of sessions with UNHANDLED non-crash errors.

13.6 Hotfix Decision Criteria

A hotfix OTA (or expedited app store update) is triggered when any of the following occur in production with confirmed root cause:

  • Any EMER alert type fires for >0.1% of sessions over a 4-hour window.
  • Data integrity alert (ALT-003, ALT-004, ALT-005, ALT-021) fires for any user.
  • Crash-free rate drops below 99% for >2 consecutive hours.
  • Encryption key access failure (ALT-017) confirmed as app bug (not keychain policy issue).
  • Any sync operation confirmed to produce duplicate financial records (zero tolerance).

Hotfix SLO: root cause confirmed within 2 hours; fix deployed within 8 hours of trigger condition first occurring.

§14 — Privacy & Compliance

Finance Bag handles deeply personal financial data. The monitoring and observability subsystem is designed with privacy as the primary constraint, not an afterthought. This section defines the privacy model, consent architecture, data masking rules, and regulatory readiness.

14.1 Anonymous Diagnostics Design

All telemetry and performance monitoring is designed to be structurally anonymous: no persistent user identifier ties monitoring data to an individual. The privacy model follows three principles:

  1. No Financial Values: Monetary amounts, transaction descriptions, category names, and budget labels never enter the monitoring subsystem. The monitoring layer receives only counts, durations, and boolean outcomes.
  2. No Persistent Identity: Each installation uses a random, non-resettable installation ID (not tied to email, device fingerprint, or account). The installation ID is rotated on app reinstall. It is never transmitted in combination with any personally identifiable information.
  3. Minimal Surface: Only metrics necessary to diagnose performance and reliability are collected. Business analytics require separate explicit opt-in and are analytically independent from technical diagnostics.

§15 — Edge Cases & Resilience

The monitoring subsystem must be resilient to the same failure conditions that affect the rest of the app. A monitoring subsystem that crashes under the conditions it is meant to monitor is counterproductive. This section defines edge case handling for the observability layer itself.

15.1 Offline Monitoring Behavior

  • All monitoring signals (metrics, logs, traces, health indicators) are written to the local log DB regardless of connectivity state.
  • Any monitoring signals configured for remote transmission are held in a bounded outbound queue (max 2,000 events, FIFO with oldest discarded on overflow) and transmitted when connectivity is restored.
  • Business analytics events accumulated while offline are batched and sent on next sync cycle. If the batch exceeds 500 events, the oldest events are discarded to stay within the batch limit.
  • Health dashboard, diagnostic tools, and alert system all operate fully offline.
  • Connectivity state transitions (ONLINE → OFFLINE → ONLINE) are themselves logged as INFO-level events with timestamp and duration.

15.2 Corrupted Log Handling

  • Log DB is opened with PRAGMA integrity_check at app launch. If corruption is detected, the log DB is quarantined (renamed with .corrupt suffix + timestamp).
  • A new clean log DB is initialized immediately; monitoring continues without interruption.
  • The quarantined file is not automatically deleted — it is preserved for up to 7 days for developer diagnostic bundle export if available, then auto-purged.
  • Log corruption events are written first to an in-memory ring buffer (100 entries) before the new DB is ready, ensuring no monitoring gap during recovery.
  • A CRIT alert fires on log DB corruption detection; no user-visible notification (INFO-level health dashboard update only).

15.3 Storage-Full Behavior

  • When storage is full (write fails with ENOSPC or equivalent), the monitoring subsystem immediately switches to in-memory-only mode.
  • In-memory mode: a circular buffer of 500 most recent log entries is maintained; older entries are silently dropped.
  • An EMER alert is generated immediately. If alert persistence fails (also out of storage), the alert is surfaced purely in-memory as a blocking UI modal.
  • No further writes to the log DB are attempted until a storage-free event is detected (file delete, cache prune).
  • The diagnostic bundle export is suspended in storage-full state (cannot write the ZIP).

15.4 Log Overflow Protection

  • The log DB hard limit (25MB) is enforced via a pre-write check. Each write is preceded by a lightweight size check (cached, refreshed every 50 writes) against the 25MB ceiling.
  • If the ceiling would be exceeded, the oldest 20% of log entries (by timestamp) are deleted before the write is accepted.
  • Log entry ingestion rate is capped at 1,000 entries per second per module. If a module emits faster (e.g., a hot loop), entries are sampled (1 in N) and a "N entries suppressed" summary is appended each second.
  • The audit log (90-day retention) is stored in a separate table from the operational log (7-day retention); overflow protection on the operational log never affects the audit log.

15.5 Monitoring-Disabled State

If the monitoring subsystem itself fails to initialize (e.g., log DB cannot be created, monitoring module crash), the app continues to function. The monitoring subsystem follows a "silent failure" principle: a monitoring failure never causes an app-level crash.

  • All monitoring calls are wrapped in a null-object pattern: if the monitoring singleton is unavailable, all calls are no-ops.
  • A degraded-monitoring state is tracked in a simple in-memory boolean; alerts are surfaced on the health dashboard when the monitoring subsystem is in degraded mode.
  • The developer overlay displays "Monitoring DEGRADED" in this state.
  • App data integrity and user-facing functionality are unaffected by monitoring subsystem failures.

15.6 Clock Change Handling

  • All monitoring timestamps use monotonic clock (process uptime) for duration calculations; wall clock time is used only for absolute event timestamps.
  • Clock skew >5min detected via server-response timestamp comparison triggers ALT-020 and switches all sync timestamps to server-provided time.
  • DST transitions are handled by always storing timestamps in UTC; local display conversion is a view concern, not a storage concern.
  • Manual clock changes by the user while the app is running are detected by wall clock delta exceeding 60s in either direction; a log event is emitted and any time-based metric windows are reset.
  • Backward clock jumps (device clock set earlier): monitoring session continues; timestamps on new events may appear earlier than historical events. No corruption — events are timestamped as received.

15.7 App Kill During Logging

  • SQLite WAL mode ensures that any in-progress write at kill time is either committed or rolled back atomically at next open. No partial log entries persist.
  • In-memory log buffer (for pre-DB-init events): on kill, buffer is lost. This is acceptable — these are monitoring events, not financial data. App-level financial writes are committed to their own transactional DB before any monitoring write.
  • Session end event (marking session duration) may not be written if app is force-killed. This is handled by the session reconstruction algorithm at next launch: if a session start event exists without a matching session end, the session duration is inferred as (last_event_timestamp - session_start_timestamp).
  • Background task state is checkpointed every 60s; a kill in between loses at most 60s of background task progress metrics.

15.8 Sync Loop Detection

A sync loop is a condition where the sync engine repeatedly processes and re-enqueues the same operation without progress. This can occur due to conflict resolution cycles or server-side validation rejections.

  • Detection: Any sync operation that has been attempted >5 times is flagged as a potential loop. The operation ID, type, and attempt count are logged.
  • Confirmation: If the same operation_id appears in 3 consecutive sync cycles without successful completion, it is confirmed as a loop.
  • Response: The operation is moved to a "quarantine queue" and excluded from normal sync cycles. ALT-010 fires. User is notified that one operation could not sync and requires review.
  • Metrics: Quarantine queue depth is a monitored metric; persistent non-zero depth triggers WARN-level alert if sustained >1hr.

15.9 Large Diagnostic Datasets

On long-lived installations with high transaction volume (DS-HEAVY: 10,000+ transactions), diagnostic datasets can become large enough to affect diagnostic tool performance.

  • Query log viewer paginates: only last 500 queries shown; older results accessible via "load more."
  • Diagnostic bundle export enforces per-file size limits (see §10.8) and truncates oldest entries if limits are exceeded, with a note in the manifest indicating truncation.
  • Slow query detector retains at most 200 distinct slow queries per session (LRU by recency).
  • Sync timeline view shows last 100 cycles by default; full history accessible via export only.
  • Health dashboard history retained for 30 days; older health state transitions are archived in the audit log table, not the main health history table.

§18 — Future Scalability & Business Rules

18.1 Cloud Observability Integration Path

The monitoring subsystem is designed to remain purely device-local in v1. The data model and API surface are designed to support cloud integration in future versions without architectural refactoring.

Phase 1 (v1 — Current): Local Only
  • All four signal types stored in device-local encrypted log DB
  • Diagnostic bundle exported manually by user/developer
  • Business analytics transmitted in anonymous batches to analytics platform
  • No persistent cross-device telemetry linkage
Phase 2 (Future): Opt-In Cloud Diagnostics
  • Crash reports transmitted to crash analytics service (opt-in)
  • Performance metrics transmitted to a backend metrics store for cross-device aggregation
  • Monitoring signal schemas (§16) serve as the transmission contract with no changes
  • Existing telemetry pipeline gains a "cloud sink" alongside the local DB sink
Phase 3 (Future): Distributed Tracing
  • Trace span schema (§16.3) is already W3C Trace Context-compatible (trace_id + span_id)
  • Adding a propagation layer to sync HTTP requests enables end-to-end distributed tracing across client and sync server
  • No changes to trace model required; only a propagation adapter and a backend trace collector
Phase 4 (Future): AI-Assisted Diagnostics
  • Diagnostic bundle format (§10.8) is machine-readable; AI analysis tooling can ingest it directly
  • Pattern recognition over slow query logs, memory slopes, and sync timelines to suggest root causes
  • Predictive alerting: model trained on historical diagnostic data to surface degradation before it becomes a user-visible issue
  • Privacy constraint maintained: AI sees only the privacy-safe diagnostic bundle, never financial data

18.2 Real-Time Dashboard Readiness

The health dashboard (§8) is designed for a future where monitoring data is streamed rather than polled.

  • Health indicator updates in v1 are pull-based (periodic health checks on a timer). The health check schema (§16.4) is event-driven by design; switching from pull to push requires only changing the check trigger, not the schema.
  • The in-app health dashboard architecture separates data retrieval from display; a remote data source can replace the local SQLite query without UI changes.
  • A future web-based developer dashboard can consume the same monitoring signal schemas via a sync-enabled API layer.

18.3 Remote Diagnostics Architecture

Remote diagnostics (allowing a developer to inspect a user's device with their consent) would use the diagnostic bundle export as its data source. Design requirements for future implementation:

  • User must initiate the remote session explicitly; no passive remote access.
  • Diagnostic bundle is transmitted only after user-confirmed consent with a visible in-app indicator.
  • All privacy constraints from §14 apply to remotely transmitted bundles — financial values structurally excluded.
  • Session-scoped access only; no persistent remote inspection capability.
  • All remote diagnostic sessions logged in the audit log (90-day retention).

18.4 Multi-Device Monitoring Considerations

As Finance Bag adds cross-device sync in future versions, monitoring must extend to cover multi-device state.

  • Each device retains its own monitoring session and installation ID — no cross-device session merging.
  • Sync conflicts (types A–G from SPEC-QA-001) are already instrumented per-device; future cloud aggregation can correlate conflict events across devices using the shared entity IDs (financial data IDs, not user IDs).
  • The SLO for data integrity (SLO-009: zero duplicate records) extends to multi-device sync: a duplicate record created by a sync conflict failure between two devices is a SLO-009 breach regardless of where it originated.
  • Health dashboard could future-show aggregate health across all registered devices for the same account (without linking user identity to device identity in the monitoring backend).

18.5 Monitoring Schema Evolution Policy

  • All monitoring schemas (§16) are versioned via the build_version field. Consumers must handle unknown fields gracefully (ignore-unknown policy).
  • A schema registry (internal documentation, not a runtime component in v1) tracks all schema versions and their differences.
  • Diagnostic bundle exports include a manifest.json listing all schema versions for each file in the bundle.
  • Retired event types are deprecated for 2 major versions before removal, with a deprecation notice in the schema registry.

18.6 Business Rules — SPEC-PMO-001

BR-PMO-01 through BR-PMO-05
  • BR-PMO-01: All monetary values are structurally excluded from every monitoring signal type. Any monitoring code that references a financial amount field is a defect. Enforced by code review and automated static analysis.
  • BR-PMO-02: The monitoring subsystem must never cause a user-visible crash or data integrity failure. Monitoring is observational infrastructure; its failure must be silent and self-healing.
  • BR-PMO-03: Every performance target in §2 (Performance Objectives) must be measured against the defined dataset size (DS-EMPTY, DS-MINIMAL, DS-STANDARD, DS-HEAVY). Measurements taken on DS-EMPTY are not valid SLO evidence for DS-STANDARD workloads.
  • BR-PMO-04: No persistent user identifier may link monitoring data across sessions. Installation IDs are per-install, not per-account. Session IDs are per-session. Correlation across sessions is not supported by design.
  • BR-PMO-05: Business analytics (§9) are operationally independent from technical diagnostics (§§5–8). A user opting out of analytics must not degrade crash reporting, and a user opting out of crash reporting must not affect analytics collection.
BR-PMO-06 through BR-PMO-10
  • BR-PMO-06: All database operations on the main (JS) thread are prohibited. Any DB access that blocks the main thread for more than 8ms is a performance defect regardless of which query it is.
  • BR-PMO-07: Retry logic must implement exponential backoff for all retriable operations. Fixed-interval retries that could cause network storms are prohibited.
  • BR-PMO-08: Alert deduplication (§11.3) is mandatory. An alert that fires more than once per cooldown window without a state change between firings indicates a defect in the alert's trigger condition.
  • BR-PMO-09: The log DB hard limit (25MB for operational logs) is enforced before every write, not after overflow. Write-then-truncate patterns that temporarily exceed the limit are prohibited.
  • BR-PMO-10: All health check durations are themselves monitored. A health check taking longer than 50ms is itself a WARN-level event (a slow health check degrades the monitoring cadence).
BR-PMO-11 through BR-PMO-15
  • BR-PMO-11: Every alert definition in §11.2 must have a corresponding recovery action. Alerts without defined recovery paths are informational at best and alert fatigue at worst — they must be upgraded to actionable or removed.
  • BR-PMO-12: SLO breach (§17.2) triggers a mandatory engineering response. A product team may not override an SLO breach without documented justification and explicit engineering sign-off that the breach is acceptable (i.e., due to a known transient external factor, not a systemic app defect).
  • BR-PMO-13: Pre-release performance baselines (§13.1) are mandatory before any app store submission or OTA rollout. A release without a captured baseline cannot be meaningfully monitored for regression and must not proceed to production.
  • BR-PMO-14: Privacy masking rules (§14.3) are enforced at the monitoring layer boundary, not at the call site. Relying on call sites to self-censor financial values is insufficient; the monitoring API must structurally reject any field that could contain financial content.
  • BR-PMO-15: Diagnostic bundle export privacy scans (§10.8) are not optional. A diagnostic bundle export without a completed privacy scan must be blocked, not warned. The bundle's value to engineering is non-zero; the risk of inadvertent financial data exposure in a shared file is also non-zero. The scan requirement is non-negotiable.
