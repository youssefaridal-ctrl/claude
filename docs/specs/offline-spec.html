01

Overview & Architecture Philosophy

Why offline-first is not a feature but a fundamental design constraint — and the mental model that shapes every decision in this specification.

1.1 The Core Premise

A personal finance app that requires internet access to display your account balance has failed its user. Financial data is maximally private and maximally personal — it should be available unconditionally, in airplane mode, in a basement, on a plane, during a network outage, and after months without opening the app. Synchronization with a cloud service is a convenience that multiplies the value of local data. It is never a prerequisite for using Finance Bag.

The Offline-First Guarantee

Every Finance Bag feature that exists in v1.0 must function identically whether the device has full connectivity, limited connectivity, or no connectivity at all. The words "Requires internet connection" must never appear in v1.0 features.

1.2 Offline-First vs Sync-Enhanced

The distinction between offline-first and "offline fallback" is architectural, not cosmetic:

PropertyOffline Fallback (traditional)Offline-First (Finance Bag)
Source of truthRemote server; local is a cacheLocal database; remote is a replica
Read path (online)Fetch from server, renderRead from local DB (same path as offline)
Read path (offline)Serve stale cache; may show errorRead from local DB (identical to online)
Write path (online)POST to server; update UI on responseWrite to local DB; enqueue sync operation; update UI immediately
Write path (offline)Queue or reject; show "offline" messageWrite to local DB; enqueue sync operation; update UI immediately
User experience offlineDegraded — some features disabledIdentical — no degradation whatsoever
Latency per operationBounded by network (100–3000ms)Bounded by local I/O (1–20ms)
Startup timeNetwork round-trip requiredFirst render from local DB, no network wait

1.3 Six Architectural Principles

PrincipleMeaning in Finance Bag context
Local-Primaryfinance.db on the device is always the authoritative data source. Every read and write targets the local database first and only. The sync engine propagates local changes to other devices — it does not replace the read path.
Optimistic WritesEvery user write is committed to the local DB immediately and reflected in the UI before any sync operation is attempted. The user never waits for a network round-trip to see their own changes take effect.
Eventual ConsistencyMultiple devices may hold divergent states temporarily. The sync engine converges them via the conflict resolution model defined in §7. The divergence window is bounded by the sync interval, not by the user's actions.
Transparent SyncSynchronization is an invisible background process. Users see a sync status indicator but are never blocked by sync. Conflicts, when they occur, are surfaced as gentle notifications — never modal interruptions during active use.
Idempotent OperationsEvery sync operation is designed to be safely replayed. If a sync operation is applied twice (due to retry or interrupted sync), the second application produces the same result as the first. This makes the sync queue resilient to interruption.
Causally OrderedOperations from a single device are applied to other devices in the order they were created on the originating device. ULID ordering ensures causal consistency within a device's operation stream. Cross-device ordering uses vector clocks.

1.4 v1.0 Scope: Fully Local

Finance Bag v1.0 is a single-device, zero-network application. Every principle in this document applies immediately to the local-only architecture. The sync-related sections (§4–§8) describe the architecture for future cloud sync, which is designed now so that the code structure requires no rearchitecting when sync is activated. In v1.0:

  • The sync queue exists but is never drained to a server — operations accumulate locally until cloud sync is enabled.
  • The conflict detection engine exists but only ever detects conflicts within a single device (which can only occur from programmatic bugs, not from concurrency — so conflicts should never arise in v1.0).
  • Network state monitoring exists for future use and to handle captive portal scenarios on WiFi (relevant for future FAQ updates and crash report uploads).

3.2 Cache Strategy

Finance Bag uses two distinct caching mechanisms. Neither uses a TTL (time-to-live) — there is no concept of "stale cache" because all data is local and always fresh. Cache entries are invalidated by events, not by time.

Dashboard Snapshot Cache

Snapshot Cache Invalidation Rules
  • The dashboard_snapshot_json field in app_state is recomputed whenever an EventBus event that affects dashboard values fires. Specifically: EXPENSE_CREATED, EXPENSE_UPDATED, EXPENSE_DELETED, PERIOD_SEALED, PAYMENT_RECORDED, EMF_CONTRIBUTION, GOAL_CONTRIBUTION, BUDGET_ALLOCATION_CHANGED, SALARY_CHANGED.
  • The snapshot is written within the same SQLite transaction as the triggering event, ensuring consistency — the snapshot always reflects the database state at the time of the write.
  • On cold start, the snapshot is read before biometric auth completes — so the dashboard shows the correct pre-auth state (amounts obscured if security.obscure_amounts = true) with zero additional query latency.
  • The snapshot schema version is stored alongside the snapshot. If the app version changes the snapshot schema, the snapshot is treated as invalid and recomputed on first post-auth render.

In-Memory Zustand Cache

  • The Zustand store is the rendering source — React components never query finance.db directly. They subscribe to Zustand slices.
  • Zustand is populated from finance.db on session open (after biometric auth). Selectors map DB rows to UI-ready state shapes.
  • Write operations update Zustand optimistically (immediately, before the SQLite write completes), then the SQLite write confirms or rolls back. If the write fails, Zustand is reverted to the pre-write state and the user sees an error toast.
  • Zustand is never persisted to disk — it is purely in-memory. finance.db is the persistent record.

3.4 Database Maintenance

A nightly maintenance job runs when the app is open (foreground), triggered by a 24-hour timer. If the app is not opened for more than 24 hours, the job runs at next open after the previous scheduled time has passed.

Nightly Maintenance Sequence (runs in background thread)
  1. Retention purge: DELETE from event_log WHERE created_at < NOW() − 90 days. DELETE from audit_log WHERE created_at < NOW() − 365 days. DELETE from click_signal_log WHERE created_at < NOW() − 30 days.
  2. Sync queue cleanup: DELETE from sync_queue WHERE status = 'COMPLETED' AND processed_at < NOW() − 7 days. DELETE from sync_queue WHERE status = 'FAILED' AND created_at < NOW() − 30 days.
  3. WAL checkpoint: PRAGMA wal_checkpoint(PASSIVE) — flushes WAL pages to main DB file without blocking readers. Keeps WAL file size controlled.
  4. FTS5 index optimization: INSERT INTO search_idx(search_idx) VALUES('optimize') — merges FTS5 segment files, improving query performance. Runs only if last_fts_optimize > 7 days ago.
  5. Fragmentation check: Query page_count and freelist_count from sqlite_schema. If freelist_count / page_count > 0.3 (30% fragmentation): schedule VACUUM for next overnight (VACUUM cannot run during active writes — it requires exclusive lock).
  6. Snapshot refresh: Recompute dashboard_snapshot_json to ensure it's consistent with current DB state (catches any edge case where an in-flight crash left it stale).
  7. Integrity check: PRAGMA quick_check (faster than full integrity_check — detects most corruption without full page scan).

Synchronization Architecture

An event-sourced, operation-log synchronization model designed for eventual consistency, crash resilience, and zero data loss — ready to activate when cloud accounts launch.

4.1 Synchronization Model: Operation Log

Finance Bag uses an operation-log synchronization model rather than a state-snapshot model. Instead of comparing database states between devices, the sync engine records every write operation as a discrete, replayable event. Synchronization means exchanging operation logs and replaying them in causal order on each device.

PropertyState-Snapshot SyncOperation-Log Sync (Finance Bag)
Sync payloadFull or delta database snapshotOrdered list of write operations since last sync
Conflict detectionCompare field values between snapshotsDetect operations that targeted the same entity concurrently
Sync after long offlineLarge snapshot diff requiredAll accumulated operations replayed in order
BandwidthProportional to amount of data changedProportional to number of operations (usually smaller)
Audit trailNo inherent historyOperation log is inherently an audit trail
IdempotencyNot naturally idempotentOperations carry idempotency keys; safe to replay

4.2 Synchronization Phases

4.3 Sync Operation Structure

Every local write to finance.db (except audit_log and event_log, which are device-local) generates a corresponding sync operation that is written to the sync_queue table within the same SQLite transaction:

SyncOperation fields
  • id — ULID. Globally unique operation identifier. Used as idempotency key on server.
  • device_id — The device that originated this operation.
  • operation_type — CREATE | UPDATE | SOFT_DELETE | RESTORE | PREFERENCE_CHANGE | ARCHIVE_SEAL
  • entity_type — expense | category | goal | goal_dependency | debt | debt_payment | emf_contribution | emf_withdrawal | period | budget_allocation | preference
  • entity_id — ULID of the affected record.
  • payload_json — For CREATE: full record JSON. For UPDATE: changed fields only (field-level delta). For SOFT_DELETE: {"deleted_at": timestamp}. For PREFERENCE_CHANGE: {"key": "...", "value": ...}.
  • vector_clock_json — The device's vector clock at the time this operation was created (used for conflict detection).
  • created_at — UNIX timestamp (milliseconds) of when this operation was generated locally.
  • status — PENDING | IN_FLIGHT | COMPLETED | FAILED | CANCELLED
  • retry_count — INTEGER, 0 initially.
  • next_retry_at — UNIX timestamp. NULL for PENDING (immediate). Set on FAILED.
  • processed_at — UNIX timestamp. NULL until COMPLETED or FAILED.

4.5 Vector Clock Model

Each device maintains a vector clock — a JSON map of { device_id: lamport_timestamp } stored in app_state.sync_vector_json. The Lamport timestamp is a monotonically increasing integer incremented on every local write operation.

  • When Device A writes an operation, it increments its own slot in the vector clock and records the full clock snapshot in the operation's vector_clock_json.
  • When Device A receives operations from Device B, it advances its own clock to max(local_clock, received_clock) + 1 for the device B slot.
  • Two operations on the same entity from different devices are concurrent (and therefore conflict candidates) if neither operation's vector clock dominates the other — i.e., they are causally unrelated.
  • Clock comparison: clock A "dominates" clock B if A[device] ≥ B[device] for all devices. If A dominates B, A happened after B; no conflict. If neither dominates, they are concurrent; conflict detected.
05

Synchronization Queue

The durable, ordered, idempotent operation queue that mediates between local writes and cloud synchronization — resilient to interruption, crash, and retry.

5.1 Queue Architecture

The sync queue is a table in finance.db rather than a separate queue system. This design choice is critical: it ensures that the enqueue of a sync operation and the write to the operational table (e.g., the expenses table) are atomic. A crash between "write expense" and "enqueue sync operation" is impossible when they share a transaction.

Atomicity Guarantee

Every local write to finance.db executes within a single SQLite transaction that includes both the write to the target table AND the INSERT into sync_queue. The transaction either commits both or rolls back both. There is no state where a financial record exists without a corresponding sync operation, and no state where a sync operation exists without a corresponding financial record.

5.2 Operation Status Lifecycle

Status State Machine

PENDING → IN_FLIGHT → COMPLETED (terminal, success)

PENDING → IN_FLIGHT → FAILED → PENDING (retry via next_retry_at)

PENDING → IN_FLIGHT → FAILED × 5 → DEAD (terminal, requires manual intervention)

PENDING → CANCELLED (terminal, if the operation was superseded — e.g., record hard-deleted before sync)

5.3 Priority Ordering

Operations in the queue are dispatched in priority order. Within the same priority, ULID ordering is used (chronological, monotonically increasing). The SyncOrchestrator reads from the queue using: ORDER BY priority ASC, id ASC.

PriorityOperation typesRationale
P1 — CriticalARCHIVE_SEAL, SOFT_DELETEArchives are immutable state changes; deletions prevent ghost records. Must reach server before other operations on the same entity.
P2 — HighPREFERENCE_CHANGEPreference sync payload is tiny and keeps other devices in the right configuration. Fast to sync, high impact.
P3 — NormalUPDATEUpdates to existing records. Conflict detection applies — ordered processing matters.
P4 — LowCREATENew records. Lower conflict risk than updates. Largest payload type but least time-sensitive.

5.4 Retry Policy

Errors that do NOT trigger retry (terminal failures): 401 Unauthorized (session expired — requires re-auth before retry), 409 Conflict with manual resolution required (routed to conflict resolver, not retry queue), 422 Unprocessable (server rejects payload schema — likely a client bug, not a transient failure).

5.5 Batch Dispatch

The SyncOrchestrator does not dispatch operations one-by-one. It batches them into payloads of up to 100 operations per HTTP request, ordered by priority then ULID. Batching reduces HTTP overhead and allows the server to process a burst of writes (e.g., after a long offline period) atomically.

  • Batch size: maximum 100 operations, or maximum 512KB payload, whichever is reached first.
  • Batch atomicity: the server applies all operations in a batch within a single server-side transaction. If any operation in the batch causes a non-conflict error, the entire batch is rejected and the client retries the batch.
  • Conflict operations: if a batch contains a conflicting operation (server returns 409 for that operation specifically), the server applies all non-conflicting operations and returns a partial-success response listing the conflicting operation IDs. The client routes conflicting operations to the conflict resolution flow, marks others as COMPLETED.

5.6 Queue Cancellation Rules

  • If an expense is soft-deleted locally before its CREATE operation was synced: cancel the CREATE and enqueue a SOFT_DELETE instead. The server never needs to know about the record's intermediate existence.
  • If an UPDATE operation is superseded by a later UPDATE on the same field of the same entity (both still PENDING): cancel the earlier UPDATE, retain only the latest.
  • If an ARCHIVE_SEAL operation is in the queue and the period is subsequently found to have sealing errors (before the operation is dispatched): cancel the ARCHIVE_SEAL, enqueue a corrective RE_OPEN_PERIOD operation (if periods are re-openable in future).
  • Queue compaction: when the queue drains after a long offline period, compact adjacent UPDATE operations on the same entity into a single merged update payload before dispatch. This reduces bandwidth without changing the end state.

Conflict Detection

How Finance Bag identifies that two devices have made incompatible changes to the same data — using vector clocks, operation ordering, and server-side merge validation.

6.1 Conflict Classification

TypeScenarioDetection mechanismFrequency
Type ANo conflict — two devices write to different entitiesServer detects no entity_id overlap in batch; merges all operations. No conflict state created.Very common — most syncs are Type A
Type BSame entity, non-overlapping fields — Device A edits expense.notes; Device B edits expense.category_idServer sees two UPDATE operations on same entity_id with non-overlapping payload_json field keys. Field-level merge applied.Occasional
Type CSame entity, same field, different values — both devices edit expense.amount_centsServer sees two UPDATE operations with the same entity_id AND overlapping payload_json field keys, AND their vector_clock_json values show neither dominates the other (concurrent).Rare — requires concurrent edits on same field on two devices
Type DDelete vs. Update — Device A soft-deletes; Device B updates same recordServer sees a SOFT_DELETE and an UPDATE for the same entity_id with concurrent vector clocks.Very rare
Type EArchive vs. update — Device A seals a period; Device B records an expense in that periodServer sees ARCHIVE_SEAL and CREATE/UPDATE operations for entities in the same period, with overlapping timestamp ranges. ARCHIVE_SEAL has P1 priority and is applied first.Rare
Type FDuplicate creation — Two devices create a record with the same natural key (e.g., same ULID, which should be impossible due to ULID's device-independent uniqueness, or same budget category name)ULID uniqueness prevents true duplicate entity IDs. Natural key duplicates (e.g., category name) detected by server's UNIQUE constraint check on the merge commit.Extremely rare for entity_id; possible for named categories

6.2 Conflict Detection Algorithm

Server-Side Conflict Detection (per operation in a batch)
  1. Extract entity_type + entity_id from the incoming operation.
  2. Look up the server's current state for that entity: last applied operation's vector_clock and payload.
  3. Compare incoming operation's vector_clock with server's last-applied vector_clock:
    • If incoming DOMINATES server: no conflict — incoming is causally after server state. Apply.
    • If server DOMINATES incoming: no conflict — this is a replay of an already-applied operation. Skip (idempotency).
    • If CONCURRENT (neither dominates): conflict detected. Route to conflict resolver.
  4. If conflict detected: check operation_type overlap:
    • Non-overlapping fields (Type B): auto-resolve via field merge. No user notification.
    • Same field (Type C): apply Last-Write-Wins rule. Log to conflict history. Optionally notify user.
    • Delete vs. Update (Type D): Delete wins. Discard update. Log to conflict history.
    • Archive conflict (Type E): Archive wins. Discard update. Notify user of discarded change.
  5. Record conflict in server-side conflict_log. Return conflict metadata to client in sync response.

6.3 Offline Conflict Detection (Local)

In v1.0 (single device), conflicts cannot arise from concurrent multi-device edits. However, the local conflict detection machinery must handle one legitimate scenario: a sync operation fails and is retried after the user has made additional local edits to the same entity. The retry queue compaction (§5.6) handles this by merging superseded UPDATE operations, preventing false conflicts.

Six resolution strategies — applied based on the data type involved, not uniformly — minimizing data loss while keeping resolution transparent to users wherever possible.

8.3 State Transitions

Network State Transition Rules
  • OFFLINE → ONLINE: Publish NETWORK_RESTORED event to EventBus. SyncOrchestrator subscribes and immediately begins queue drain. Status transitions PENDING → SYNCING.
  • ONLINE → OFFLINE: Publish NETWORK_LOST event. SyncOrchestrator pauses dispatch (no retry storm). Any IN_FLIGHT operations are reverted to PENDING status (with retry count preserved).
  • ONLINE → DEGRADED: SyncOrchestrator switches to timeout-reduced mode. No user interruption. If DEGRADED persists more than 5 minutes: status badge shows degraded indicator.
  • DEGRADED → ONLINE: After 3 consecutive successful requests. Full sync resumes immediately.
  • Any → CAPTIVE_PORTAL: SyncOrchestrator halts immediately. One-time user notification. No retry attempts until state changes.
  • CAPTIVE_PORTAL → ONLINE: User authenticated with portal (external action). NetInfo detects internet reachability restored. Normal sync resumes.

8.4 Connectivity Probe

React Native's NetInfo.isInternetReachable is not perfectly reliable on all Android devices. Finance Bag supplements it with a periodic lightweight connectivity probe:

  • Probe: HTTP HEAD request to Finance Bag's health endpoint (future: https://api.financebag.app/health). In v1.0: HTTP HEAD to a public CDN URL for app bundle integrity check.
  • Probe interval: every 60 seconds when NetInfo reports connected but isInternetReachable is uncertain (null or false with isConnected = true).
  • Probe success (200 from expected origin): transition to ONLINE.
  • Probe failure (non-200 or unexpected origin): CAPTIVE_PORTAL state.
  • Probe timeout (5s): DEGRADED state.
  • Probe cost: HEAD request is ~200 bytes. Probing once per 60 seconds costs ~288KB/day — negligible.

Each module's nav item can display a small numeric badge indicating pending (not-yet-synced) writes for data owned by that module. This is supplementary — the user can still read and write normally. The badge communicates "your data is not yet in the cloud."

  • Badge is suppressed if the app is ONLINE and currently syncing (so it doesn't flicker during fast syncs).
  • Badge is suppressed entirely in v1.0 (deferred to cloud sync rollout) to avoid confusion when cloud sync doesn't yet exist.
  • Maximum display: "99+" for counts above 99.

9.4 In-App Conflict Notification

When a conflict is detected and requires user resolution (Type F: User Choice strategy), an in-app notification card appears. It does not use a system push notification — conflicts are resolved in-app, not via background alert.

  • Card location: Inline card on the affected entity's detail screen (e.g., expense detail, goal detail). The card replaces the normal view of the field(s) in conflict.
  • Card content: Side-by-side comparison of local value vs. server value, with "This device" / "Cloud" labels and formatted timestamps.
  • Actions: "Keep mine" / "Use theirs" / "View history" (last 3 values in conflict_log). The chosen value is written immediately as a new operation — no partial states.
  • Dismissal: Cannot be dismissed without making a choice. Swiping away is disabled. This prevents silent data loss.
  • Unresolved conflicts badge: The Settings tab nav item shows a red dot badge if unresolved User Choice conflicts exist.

The last successful sync timestamp is stored in app_state.last_sync_at (ISO-8601 UTC). It is displayed in:

  • Sync status drawer (primary location).

9.6 Data Freshness Indicator

Reports and dashboards display a subtle freshness indicator when the user is viewing data that has not been confirmed synced to the cloud:

  • Trigger: User is on a reports or dashboard screen AND PENDING count > 0 AND more than 15 minutes have elapsed since last_sync_at.
  • Indicator: A small "Local data only" chip below the report header. Not a blocking banner — reports remain fully usable.
  • Suppressed in v1.0 (same as badges — deferred to cloud sync rollout).

9.7 Offline Write Confirmation

When a user saves a financial record while OFFLINE, the save succeeds immediately (optimistic write) and a brief toast confirms it:

  • Toast text: "Saved · Will sync when online" (max 2 seconds, non-intrusive).
  • Toast is shown only when network state is OFFLINE or CELLULAR_CONSTRAINED.
  • Toast is suppressed if the user has dismissed it more than 3 times in the last 7 days (preference: ofl.show_offline_save_toast).

10.2 Stale IN_FLIGHT Detection

On every app foreground event and every cold launch, SyncManager runs a stale-operation check:

  1. Query sync_queue WHERE status = 'IN_FLIGHT'.
  2. For each row: if (now − created_at) > 10 minutes AND processed_at IS NULL: reset status to PENDING, increment retry_count by 1.
  3. If retry_count after increment ≥ 5: set status = DEAD, set error_detail = 'Stale IN_FLIGHT timeout'.
  4. This runs within a SQLite transaction so the check-and-update is atomic.

10.3 Queue Consistency Invariants

The following invariants must hold at all times. Violation triggers a full sync_queue rebuild (drop + re-enqueue from local DB):

  • INV-OFL-01: Every sync_queue row has a valid JSON payload_json parseable to the SyncOperation type.
  • INV-OFL-02: Every sync_queue row with status = IN_FLIGHT has a corresponding in-progress network request OR was created more than 10 minutes ago (stale detection applies).
  • INV-OFL-03: No two sync_queue rows share the same id (ULID primary key enforced by SQLite UNIQUE constraint).
  • INV-OFL-04: For every entity_type + entity_id combination, there is at most one PENDING CREATE row (duplicates are compacted on insert).
  • INV-OFL-05: A SOFT_DELETE row for entity_type + entity_id cancels all prior PENDING rows for the same entity (queue compaction on insert).

10.4 Manual Recovery Tools

Available under Settings → Developer Options (hidden in production builds; exposed in debug/staging):

  • Reset sync queue: Clears all PENDING, FAILED, DEAD rows. Triggers Phase 4 full re-sync. Irreversible — pre-operation backup created automatically before clearing.
  • Force full re-sync: Keeps sync_queue intact but enqueues a Phase 4 trigger on next foreground.
  • Export sync queue: Exports all sync_queue rows as JSON for diagnostic submission. Sanitized (no payload_json content) in release builds.
  • Reset vector clock: Resets app_state.sync_vector_json to {}. Use when persistent clock skew errors are detected.

11.2 WAL Mode Optimization

SQLite WAL (Write-Ahead Log) mode is the foundation of Finance Bag's read/write concurrency:

  • Readers never block writers; writers never block readers. Local UI writes and sync reads can interleave without lock contention.
  • WAL file is checkpointed via PRAGMA wal_checkpoint(PASSIVE) during nightly maintenance — passive mode does not block active readers.
  • WAL file is also checkpointed on app backgrounding (via AppState listener) to prevent unbounded WAL growth between maintenance windows.
  • WAL file maximum size: 10MB before automatic checkpoint is triggered regardless of schedule (PRAGMA wal_autocheckpoint = 2560 pages at 4096 bytes each).
  • finance.db and search.db each have their own WAL file. They are checkpointed independently.

11.3 Large Import Batching

Importing large CSV files (e.g., 500 bank transactions) is a common user workflow. This must not freeze the UI or overwhelm the sync queue:

  • Batch size: 50 records per SQLite transaction. Larger batches risk exceeding WAL page limits and cause perceptible UI lag.
  • Inter-batch yield: After each 50-record transaction commits, the import job yields execution for 16ms (one animation frame) before the next batch. This keeps the UI responsive at 60fps.
  • Sync queue de-duplication during import: All 500 CREATE operations are enqueued in the sync_queue, but the queue dispatch does not start until import completes. A single sync dispatch then batches them in groups of 100.
  • Progress reporting: Import UI shows "Saving 50 of 500 expenses…" with a progress bar updated per batch. Cancel is allowed between batches (already-committed batches remain; partial import is valid).
  • Duplicate detection during import: Before inserting each record, check (amount_cents, date, description_hash) tuple. Existing matches are skipped (not duplicated). A final "3 duplicates skipped" summary is shown.

11.4 Storage Monitoring

Storage is monitored proactively to prevent the SQLITE_FULL failure scenario:

  • Total storage used is computed during nightly maintenance (sum of file sizes for finance.db, finance.db-wal, search.db, attachments directory, backups directory).
  • Result is stored in app_state.storage_used_bytes.
  • Warning threshold: 500MB. When exceeded, a non-intrusive banner appears on next app open: "Storage at 500MB — review attachments and old backups."
  • Critical threshold: 900MB. When exceeded, a modal appears blocking navigation: "Storage almost full. Finance Bag needs space to save your data." with actions: "Manage attachments", "Delete old backups", "Export and clear data".
  • Free space check: Before any file write (attachment save, backup creation), check that device free space > (file size × 2) + 50MB safety margin. If not, abort the operation with a user-facing error.

11.5 Background Sync Constraints

Background sync (when app is backgrounded or device is locked) is subject to OS restrictions:

  • iOS (Expo Background Task): Background execution limited to ~30 seconds per OS grant. SyncManager prioritizes the highest-priority PENDING operations first (P1, then P2, etc.). If time runs out, IN_FLIGHT operations are reset to PENDING on next foreground.
  • Android (Expo Background Fetch): Background fetch interval is OS-managed (minimum ~15 minutes). Finance Bag registers a background fetch task to drain sync_queue when granted time.
  • Network state in background: Sync is only attempted in BACKGROUND network state if queue has P1 (ARCHIVE_SEAL or SOFT_DELETE) operations. Lower-priority operations wait for foreground.
  • Battery saver mode: Both platforms restrict background tasks in battery saver mode. Finance Bag does not attempt to circumvent this — local-primary architecture means data is safe even without background sync.
  • Background sync is best-effort: The architecture makes no guarantees about background sync frequency. Users are informed that sync is faster when the app is open.

12. Security Considerations

Offline-first architecture introduces unique security considerations around key availability, sync payload integrity, and the security of the local operation log. These are addressed as first-class concerns, not afterthoughts.

12.1 Encrypted Local Database

The sync_queue table resides in finance.db, which is encrypted with SQLCipher (AES-256-CBC, 256,000 PBKDF2 iterations, HMAC-SHA512 per page). The sync payload (payload_json) is encrypted at rest as part of the database encryption — it is never stored in plaintext outside the encrypted DB. This means:

  • An attacker with physical access to the device cannot read pending sync operations without the DB_KEY.
  • A forensic image of the device storage yields only encrypted bytes for the sync_queue.
  • The sync_queue is excluded from iOS iCloud backup (NSURLIsExcludedFromBackupKey = true on the DB file). Only the .fbk encrypted backup includes sync state, and only indirectly (via WAL checkpoint state).

12.2 Authentication Persistence Across Sync

Sync operations require authentication context (future: JWT or equivalent). The authentication lifecycle interacts with sync as follows:

  • In v1.0 (offline-only): No authentication token is needed for sync. Sync queue is local-only.
  • In cloud sync phase: A valid session token is required for every HTTP request. Token expiry during a multi-batch sync cycle triggers an AUTH_EXPIRED event. SyncManager pauses, AuthService attempts silent refresh, then resumes. If refresh fails, the sync cycle pauses completely and an in-app prompt notifies the user.
  • Sync does not "borrow" auth from the UI session. SyncManager holds its own token reference, obtained from AuthService, not from Zustand UI state.
  • A force-logout (including app-initiated logout on suspicious activity) cancels all in-flight sync operations before the session is invalidated.

12.3 Sync Payload Security

Zero-knowledge design: the sync payload is structured so the server processes operation logs without needing to decrypt field-level financial data:

  • All amount_cents, balance values, and user-entered text are field-encrypted within payload_json using AES-256-GCM before the payload is serialized. The server receives an opaque blob for these fields.
  • Entity metadata (entity_type, entity_id, operation_type, timestamps, vector_clock) is transmitted in plaintext — this is the minimum necessary for the server to order operations and detect conflicts.
  • The server cannot reconstruct a user's financial picture from sync payloads alone, even if the transport layer is compromised.
  • Future: End-to-end encryption (E2EE) for the full payload. This requires client-side conflict resolution only (server cannot resolve conflicts it cannot read). The conflict detection algorithm must run client-side in this model.

12.4 Tamper Resistance of Sync Queue

The sync_queue is the authoritative log of what the local device intends to commit. Tampering with it would allow an attacker to submit unauthorized financial operations to the cloud.

  • SQLite integrity: quick_check runs nightly to detect DB-level corruption. Corruption triggers queue rebuild, not silent use of corrupted data.
  • Payload signature (future): Each SyncOperation payload will include an HMAC-SHA256 signature computed using a device-specific signing key stored in the hardware Keystore. The server verifies the signature before accepting any operation. This prevents an attacker who extracts payload_json from the DB from modifying and replaying operations.
  • Sequence integrity: ULID-ordered operations in the sync_queue cannot be reordered by the server without detection — the vector clock would be inconsistent with the ULID ordering.
  • Rate limiting: The sync server enforces per-device rate limits (max 1,000 operations per minute). A compromised device cannot flood the server with fabricated operations.

12.5 Offline Key Management

The DB_KEY must be available before the sync_queue can be read or written, since both operations require the decrypted database. Key availability offline is handled as follows:

  • DB_KEY is stored in expo-secure-store (iOS Keychain / Android Keystore). It is available offline — neither platform requires network access to retrieve hardware-backed secrets.
  • Biometric authentication (required to unlock DB_KEY access) works offline — both Face ID and fingerprint are local sensor operations with no network dependency.
  • PIN fallback (Argon2id hash comparison) also works fully offline.
  • There is no online key escrow in v1.0. Loss of device + loss of backup means data cannot be recovered. This is a deliberate privacy trade-off documented in the user-facing privacy notice.
  • Future key escrow option: an encrypted key shard can be stored in the cloud, recoverable only with a recovery passphrase. This never sends the plaintext key to the server.

13. Future Compatibility

The offline-first architecture is designed to accommodate significant feature expansion without requiring a rebuild. The following capabilities are planned and the current architecture specifically leaves room for them.

13.1 Real-Time Sync

When cloud sync reaches Phase 3 (incremental delta sync), the architecture supports a real-time upgrade path:

  • Replace the polling-based sync trigger with a persistent WebSocket connection to the sync server.
  • The operation-log model (SyncOperation rows) maps cleanly to WebSocket event streams — each event is a SyncOperation pushed from the server.
  • The existing ConflictResolver can be reused without modification — real-time sync changes the delivery mechanism, not the conflict model.
  • The vector clock model is specifically designed for multi-device concurrent editing — real-time sync is the operational mode where vector clocks provide the most value.
  • Fallback: if the WebSocket connection drops, the queue-based polling sync automatically takes over. The user never notices the switch.

13.2 Multi-Device Editing

The current architecture supports up to 5 registered devices. Enabling simultaneous edits from multiple devices requires:

  • Each device already has a device_id in expo-secure-store and a lane in the vector clock JSON.
  • The 7-type conflict classification already handles all multi-device scenarios (Type B through F cover concurrent edits from different devices).
  • The only addition required is cloud sync Phase 3 (incremental delta pull from server to local) — currently planned but not yet active in v1.0.
  • No schema changes are required. The sync_queue, conflict_log, and vector clock tables are already designed for multi-device.

13.3 Shared Family / Business Accounts

Multiple users sharing a Finance Bag account requires a profile_id scoping layer:

  • All entity tables receive a profile_id foreign key column (migration-safe: defaults to the existing user's implicit single profile).
  • SyncOperation gains a profile_id field in the payload — the server routes operations to the correct profile's sync log.
  • Conflict resolution must consider profile ownership: edits to another profile's data require elevated permission (future P3 or P4 level).
  • The preference scope enum (device | user | family | org) defined in SPEC-SET-001 §17 maps directly to profile types.
  • Each profile gets its own sync_vector_json clock — clocks across profiles are not compared (profiles are not causally ordered).

13.4 Business Workspaces

Business accounts introduce org-level data that multiple users contribute to simultaneously:

  • A workspace_id replaces or extends profile_id. Each workspace has its own sync log stream on the server.
  • Workspace data may require server-side conflict resolution for shared budgets (e.g., two team members update the same budget allocation simultaneously).
  • The field-merge conflict resolution strategy (already defined) is the correct model for concurrent budget allocation edits.
  • Access control lists (ACLs) per entity type: some users have read-only access to certain modules. The permission level system (P0–P3) maps to workspace roles (viewer / editor / admin / owner).

13.5 AI Sync

AI-powered features (categorization suggestions, anomaly detection, spending forecasts) require embedding vectors that must be synced:

  • SyncOperation payload gains an optional embeddings field (float32 array). The server stores embeddings in a vector database separate from the relational sync store.
  • Embeddings are computed on-device (future: Core ML / TFLite model) and included in CREATE/UPDATE operations for expense and goal entities.
  • The sync queue already supports arbitrary JSON in payload_json — embeddings are added as a versioned field with backward-compatible schema evolution.
  • Vector clock ordering applies to embeddings as to any other field — concurrent embedding updates use Last-Write-Wins (embeddings are not mergeable).

13.6 Cloud Provider Portability

The sync architecture is designed to be cloud-provider agnostic:

  • SyncManager communicates with an abstract SyncAdapter interface (v1.0: LocalSyncAdapter that no-ops; v2: RestSyncAdapter for Finance Bag cloud; future: S3SyncAdapter, iCloudSyncAdapter for user-owned storage).
  • The SyncAdapter interface requires only four operations: pushOperations(ops[]), pullOperations(since: vector_clock), resolveConflict(local, remote), uploadBackup(file).
  • Users can choose their own cloud storage provider (S3 bucket, iCloud Drive, Google Drive) for backup sync in particular. Phase 2 backup sync is the first target for this flexibility.

13.7 Wearable Companion

Apple Watch / Wear OS companions would receive a minimal sync vector subset:

  • Only dashboard snapshot and quick-expense-create capability are synced to the wearable.
  • The wearable device gets its own device_id and vector clock lane, but only for the entity types it can write (expense CREATE).
  • A WearSyncAdapter proxies through the paired phone's SyncManager — the wearable never establishes a direct cloud connection.
  • Sync priority for wearable-originated expenses: P4 (CREATE) — same as any other CREATE operation. No special priority.

13.8 Desktop Companion

A future desktop app (Electron or Tauri) would participate in the same sync network as mobile devices:

  • Desktop counts as a registered device (increments toward the 5-device max).
  • Desktop uses the same SyncAdapter interface (RestSyncAdapter) and the same operation-log model.
  • Desktop has no hardware Keystore equivalent — DB_KEY is derived from a user-supplied passphrase via Argon2id on desktop (no biometric option in v1.0).
  • Desktop sync queue is a SQLite table in the desktop app's local database — identical schema to the mobile sync_queue.

14. Edge Cases

14.1 Device Change (EC-OFL-01)

Scenario: User buys a new phone. Old device data needs to transfer to the new device.

  • v1.0 path: User creates a manual backup on old device (.fbk file), transfers via AirDrop/Files/cable, restores on new device via Settings → Backup → Restore. New device gets all financial data as a point-in-time snapshot. Sync queue from old device is not transferred (PENDING/FAILED ops are abandoned — old device should drain queue before creating backup).
  • Cloud sync path: New device registers with account, downloads Phase 4 full sync from cloud. Local state is rebuilt from operation log. No manual file transfer required.
  • Constraint: Old device should be deregistered after transfer to keep device count ≤ 5. If old device count exceeds 5, new registration requires deregistering an existing device via Settings → Sync → Registered Devices.

14.2 App Reinstall (EC-OFL-02)

Scenario: User deletes and reinstalls the app.

  • iOS: expo-secure-store survives app uninstall by default (Keychain is app-scoped but persists across installs). DB_KEY and device_id are still available after reinstall. However, finance.db is deleted with the app. Result: keys exist but database does not — DB must be restored from .fbk backup. User is prompted to restore on first launch if keys are present but DB is absent.
  • Android: expo-secure-store (Keystore) data is deleted with app uninstall on most Android versions. DB_KEY and device_id are lost. User must restore from .fbk backup and will need to re-authenticate (PIN setup, biometric re-enrollment). This is clearly communicated in the onboarding flow.
  • No data loss occurs if the user has a current backup. This is why the backup frequency and auto-backup UX are critical.

14.3 Sync After Extended Offline Period (EC-OFL-03)

Scenario: User has been offline (airplane travel, rural area) for 6 weeks. Device has 10,000+ PENDING sync operations.

  • The sync_queue has no TTL on PENDING operations. All 10,000 operations are preserved.
  • On reconnect: SyncManager detects ONLINE state and begins batch dispatch. 10,000 ops ÷ 100 per batch = 100 HTTP requests. At 2 seconds per batch: ~3.3 minutes to drain the queue.
  • User is informed: "Syncing 10,000 changes — this may take a few minutes."
  • Sync proceeds in the background while the user continues using the app (local reads/writes are not blocked).
  • If the user backgrounds the app before sync completes, the queue is preserved. Sync resumes on next foreground.
  • Vector clock skew: 6 weeks offline means the server's clock has advanced significantly. All local operations will appear "old" by server clock standards. The vector clock comparison treats this as a causally-ordered batch — no false conflicts if only one device was writing during the offline period.

14.4 Clock Manipulation (EC-OFL-04)

Scenario: User manually changes device clock (or travels across time zones while offline).

  • ULID-based entity IDs include a millisecond timestamp prefix. Backward clock adjustment causes new ULIDs to have lower timestamps than recent ones — breaking the monotonic ordering guarantee.
  • Mitigation: SyncManager maintains a monotonic clock (last_known_timestamp in app_state). If device clock moves backward, the monotonic clock prevents ULID timestamp regression. New ULIDs are issued with monotonic_clock + random suffix, not device clock directly.
  • Vector clock Lamport timestamps are logical (integer counters), not wall-clock. Time zone changes and clock adjustments do not affect vector clock correctness.
  • Conflict Type G (clock skew) is defined for cases where the server detects an operation timestamp that is implausibly far in the past or future (defined as > 30 days divergence from server time). Server-side resolution applies.

14.5 Multiple Simultaneous Devices (EC-OFL-05)

Scenario: User edits the same expense on phone and tablet simultaneously (both offline, then both reconnect).

  • Both devices enqueue UPDATE operations for the same expense entity_id. Both operations are dispatched to the server when each device reconnects.
  • Vector clock comparison: Device A's clock and Device B's clock are concurrent — neither dominates. Server detects Type B conflict (concurrent field edits).
  • ConflictResolver applies Field Merge strategy: non-conflicting fields (category_id changed on device A only) are merged. Truly conflicting fields (both devices changed amount_cents) trigger User Choice resolution on the device that synced second.
  • The user who synced second sees the in-app conflict card and makes the final decision.

14.6 Cloud Rollback (EC-OFL-06)

Scenario: Finance Bag cloud service has a bug and rolls back their database to a prior state. Local devices have operations that the server no longer knows about.

  • On next sync: server returns a lower last_processed_clock than the local vector clock. This indicates the server has lost operations the local device thought were COMPLETED.
  • SyncManager detects this condition (server clock regression) and transitions to Phase 4 (full re-sync). Local COMPLETED operations that are "newer" than the server's rolled-back state are re-queued as PENDING.
  • This is a cloud-side disaster recovery scenario — local data is the authoritative source for re-populating the cloud.
  • User notification: "Cloud sync issue detected — re-uploading your data." No data loss on the user's side.

14.7 Corrupted Sync State (EC-OFL-07)

Scenario: A bug in a previous version corrupted the sync_queue or vector clock. User upgrades to a fixed version.

  • Migration scripts (run on DB open, within a transaction) detect and repair known corruption patterns from prior versions.
  • If migration cannot repair: wipe sync_queue, reset vector clock, enqueue Phase 4 full re-sync.
  • All financial data (expenses, goals, budgets) is in the main tables — untouched by sync_queue corruption. Only the sync history is lost, not the data.
  • User sees: "Sync history was reset after an update. Your data is safe — re-syncing now."

14.8 Large Import (EC-OFL-08)

Scenario: User imports 500 bank transactions via CSV while offline.

  • 500 PENDING CREATE operations are enqueued in sync_queue.
  • Each batch of 50 records takes <200ms (nightly maintenance shows average is ~80ms per 50-record batch on a mid-range device).
  • Total import time: ~2 seconds for the full 500 records (10 batches × 200ms average).
  • Sync queue grows by 500 rows. Each row is ~500 bytes in payload_json (expense entity). Total queue growth: ~250KB — well within storage budget.
  • When reconnected: 500 ops are dispatched in 5 HTTP batches (100 ops each). Total upload time: ~10 seconds on a typical connection.
  • Duplicate detection: The server deduplicates on idempotency key (ULID). If the import is run twice (user error), the second run's ULIDs differ — but the duplicate detection at the application layer (amount_cents + date + description_hash tuple) prevents the second import from creating rows locally.

14.9 Large Export While Syncing (EC-OFL-09)

Scenario: User exports all data to CSV while a large sync cycle is in progress.

  • Export reads from finance.db using a read transaction. WAL mode allows this to proceed concurrently with the sync write transaction (no blocking).
  • Export reads a consistent snapshot as of the moment the read transaction starts. Operations that commit to finance.db after the read transaction starts are not included in the export (correct — the export is a point-in-time snapshot).
  • Export and sync can proceed simultaneously without coordination. The WAL isolation model guarantees consistency without explicit locking from the application layer.

14.10 Backup Restoration Mid-Sync (EC-OFL-10)

Scenario: User restores a .fbk backup while a sync cycle is in progress.

  • Backup restoration is a pre-operation-backup → close-DB → delete-DB → decrypt-and-restore-DB → reopen-DB sequence. This is incompatible with an active sync cycle.
  • Before beginning restore: SyncManager is signaled to stop immediately. All IN_FLIGHT operations are reset to PENDING (they will be superseded by the restored state anyway).
  • After restore: sync_queue is cleared (it contains operations for the pre-restore state, which is now gone). Vector clock is reset. Phase 4 full re-sync is triggered to reconcile the restored state with the cloud.
  • The user is warned: "Restoring a backup will stop the current sync and restart. Your cloud data will be updated to match the backup. Continue?" — explicit confirmation required.

15. Business Rules

15.1 Core Offline Guarantees

Rule IDRuleRationale
BR-OFL-01 Local-Primary Guarantee: Every user-initiated write is committed to the local SQLite database before any UI confirmation is shown. The app never shows "saved" before the local transaction commits. Offline-first means local is authoritative. Users must be able to trust that "saved" means durably saved on this device.
BR-OFL-02 Optimistic Write Requirement: All writes are optimistic — the sync queue entry is created in the same transaction as the local DB write. No write is blocked on cloud confirmation. Blocking on network connectivity would break the offline-first guarantee. Every write is local; cloud sync is an eventual background process.
BR-OFL-03 Sync Queue Atomicity: A financial data write and its corresponding sync_queue INSERT must occur within a single SQLite transaction. If either fails, both are rolled back. A data row without a sync_queue entry would silently not sync to cloud. A sync_queue entry without a data row would corrupt the server state. Atomicity prevents both.
BR-OFL-04 No Sync Without Account: Cloud sync only activates when a cloud account is linked. The sync_queue is populated regardless of account state, but dispatch only occurs with valid credentials. New users who have not yet created an account benefit from the queue architecture from day one. Their queue drains automatically when they sign up.
BR-OFL-05 ULID Monotonicity: All entity IDs are ULIDs. New ULIDs are never issued with a timestamp earlier than the most recently issued ULID on this device (monotonic clock enforcement). Non-monotonic ULIDs break B-tree index ordering and cause false "old operation" detection at the server. Monotonicity must be enforced even when device clock moves backward.
BR-OFL-06 Soft Delete Only: No hard DELETE SQL statement is ever issued for user data (expenses, goals, budgets, debts, etc.). Soft delete sets deleted_at timestamp. Hard delete only occurs on factory reset or account deletion. Soft delete enables sync queue cancellation (a SOFT_DELETE operation can be sent to cloud to propagate the delete), conflict recovery (deleted item can be restored), and audit trail.
BR-OFL-07 Idempotent Operations: Every SyncOperation has a unique ULID (id field) used as an idempotency key at the server. Re-submitting the same operation always produces the same result with no side effects. Network retries are guaranteed in the retry policy. Without idempotency, retries would create duplicate records. The ULID ensures the server can recognize and deduplicate re-submitted operations.
BR-OFL-08 Causal Ordering: Operations in the sync_queue are dispatched to the server in ULID order within each entity. A CREATE must be processed before any UPDATE for the same entity. Out-of-order operations would cause server-side failures (UPDATE for a non-existent entity). The ULID timestamp prefix guarantees causal ordering within a device.
BR-OFL-09 5-Attempt Retry Maximum: No sync operation is retried more than 5 times. After 5 failures, status is set to DEAD. DEAD operations are preserved in the queue for diagnostic purposes. Unlimited retries on a malformed operation would block the queue indefinitely. The 5-attempt cap with exponential backoff balances persistence with eventual degradation.
BR-OFL-10 Batch Size Limits: Sync dispatch batches are capped at 100 operations OR 512KB payload, whichever comes first. A single operation cannot exceed 512KB payload. Unbounded batch sizes risk server timeout and mobile memory pressure. The 512KB limit accommodates the largest expected expense payloads (including field-encrypted blobs) with headroom.
BR-OFL-11 DEAD Operations Preserved: DEAD sync_queue rows are never automatically deleted. They are retained until the user explicitly clears them or performs a factory reset. DEAD operations represent failed data sync that the user may want to investigate. Automatic deletion would hide data loss from the user. Manual review is the correct resolution path.
BR-OFL-12 Conflict Log Retention: conflict_log rows are retained for 30 days after resolution. After 30 days, they are purged by nightly maintenance. 30 days gives users time to notice unexpected data changes and trace them to a resolved conflict. Indefinite retention would grow the conflict_log unboundedly.
BR-OFL-13 No Sync on Metered Network by Default: When network state is CELLULAR_CONSTRAINED, sync is paused by default. Users can override this in Settings → Sync → Sync on Cellular. Unexpected data charges damage user trust. Sync over cellular is opt-in. The local-primary guarantee means no data is lost while cellular sync is disabled.
BR-OFL-14 Backup Before Destructive Sync Operations: Before executing a Phase 4 (full re-sync) or queue reset, SyncManager automatically triggers a pre-operation backup. The reset cannot proceed if the backup fails. Full re-sync and queue resets are destructive to sync state. A backup checkpoint before proceeding ensures the user can recover if the re-sync introduces unexpected data changes.
BR-OFL-15 Transparency Over Silence: Sync errors that result in DEAD operations must be surfaced to the user within 24 hours (via sync drawer, not push notification). The user must never be silently losing cloud sync coverage. Silent sync failures erode trust. Users who believe their data is synced but it is not face a data loss risk on device change. Proactive surfacing of sync errors is a trust requirement, not optional UX.
