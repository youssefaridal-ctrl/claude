Overview & Philosophy

The Settings & Personalization Center (module: SET) is the user's control panel for every aspect of Finance Bag's behavior, appearance, and data management. It is designed to be immediately approachable for first-time users who never touch it, while offering the depth that power users expect from a premium financial application.

Core Design Principle: Sensible Defaults First. Every setting has a carefully chosen default that works well for the majority of users without any configuration. The Settings screen is optional — a user who never opens it should still have a great experience. Advanced options exist for those who seek them, but are never in the way of those who don't.

1.1 Five UX Principles

#PrincipleWhat It Means in Practice
IPurpose Before OptionEvery setting must have a documented reason for existing. Settings that can't be justified are removed. The user should never wonder "what does this do?"
IIInstant FeedbackNon-destructive settings apply immediately — theme changes, font size, obscure amounts. The user sees the effect before leaving the settings screen. No "Apply" button is needed for these.
IIIProgressive DisclosureCommon settings are immediately visible. Advanced options are grouped under "Advanced" sub-sections. Developer options are hidden by default and require a deliberate unlock gesture (7 taps on the version number).
IVSafe by DefaultDestructive operations (delete data, factory reset, account deletion) require: (1) explicit authentication, (2) a confirmation dialog that describes exactly what will be lost, (3) a typed confirmation string for irreversible operations.
VSearchable AlwaysEvery setting is discoverable via the SCH module's search system. Users who know what they want but don't know where it lives can type it in the search bar and navigate directly.

1.2 Relationship to Other Modules

The SET module is the owner of user preferences. Other modules consume preferences but do not write to them directly. The consumption pattern is read-only: a module reads a preference value at runtime but never updates it except through the SET module's public API. This ensures consistent change tracking and audit logging for all preference changes.

  • DSH reads dashboard.widget_order, dashboard.startup_screen, and appearance.theme.
  • EVT reads all notifications.* preferences to enforce quiet hours and channel preferences.
  • SCH reads search.save_history and is responsible for indexing all settings as searchable entities.
  • BUD / DBT / GOL read locale.* preferences for date/number formatting.
  • SYS reads security.* preferences for biometric lock behavior.

Architecture & Preference Model

The preference model is a typed key-value store with a schema registry. It extends the existing settings singleton from SPEC-DB-001 by moving to a purpose-built preferences table that supports richer types, default management, and future sync.

2.1 Preference Storage Architecture

Three storage layers serve different preference needs:

LayerTable / StoreContentsOwned By
Structured Preferencespreferences (new)All typed user-configurable settings. Key-value with schema. The canonical preference store.SET
Operational Stateapp_state (existing)Non-user-configurable runtime state: dashboard_snapshot, db_schema_version, onboarding_complete. Not shown in Settings UI.SYS
Legacy Singletonsettings (existing)Deprecated in favor of preferences. Migrated to preferences table at upgrade time. Retained for schema migration backward compatibility.SET

2.2 preferences Table Schema

FieldTypeDescription
keyTEXT PKNamespaced preference key (e.g. appearance.theme, security.biometric_lock). Dot-notation, category prefix required.
value_jsonTEXT NOT NULLJSON-serialized current value. Type determined by schema.
updated_atINTEGER NOT NULLUnix ms of last user-initiated change.
sync_eligibleINTEGER DEFAULT 10 = device-specific (do not sync across devices). e.g. biometric_lock is device-specific; theme preference is sync-eligible.

2.3 Preference Schema Registry (In-Memory)

The schema registry is a static in-memory definition of every preference key. It is not stored in SQLite — it is bundled in the app. Each entry defines:

FieldTypeDescription
keystringPreference key (must match preferences.key)
labelLocalizedStringDisplay label shown in Settings UI (localized)
descriptionLocalizedString | nullHelp text shown below the setting (localized)
typeenum'boolean' | 'string' | 'integer' | 'enum' | 'json'
defaultanyDefault value used on first launch or after factory reset
allowed_valuesany[] | nullFor enum type: the valid values. Null for other types.
validationValidationRule | nullFor integer: min/max. For string: maxLength, pattern. Null for boolean/enum.
requires_authbooleanIf true, biometric/PIN re-authentication is required before the change is written.
requires_restartbooleanIf true, app must restart for the change to take effect (rare — language change is the main case).
categorystringCategory key for grouping in the Settings UI (e.g. 'appearance', 'security')
sync_eligiblebooleanWhether this preference should sync across devices in future cloud sync.
visible_in_uibooleanFalse for preferences that exist but are managed programmatically, not shown to the user.

2.4 Preference Read / Write Flow

  • Read. Modules call PreferenceService.get(key). The service reads from an in-memory cache (populated at startup). On cache miss, reads from preferences table. If no row exists for the key, returns the schema default.
  • Write. Modules call PreferenceService.set(key, value). The service (a) validates the value against the schema, (b) checks requires_auth and triggers re-auth if needed, (c) writes to preferences table, (d) updates the in-memory cache, (e) publishes a PREFERENCE_CHANGED event to the EVT bus with the key and new value so subscribing modules can react.
  • Reset to default. PreferenceService.reset(key) deletes the row from preferences table. Subsequent reads return the schema default.
  • Reset all. Deletes all rows from preferences table. All reads return defaults. Used by Factory Reset.

2.5 Change Propagation via Events

When a preference changes, the EVT module broadcasts a PREFERENCE_CHANGED event with payload { key, oldValue, newValue, changedAt }. Subscribing modules react without polling:

  • DSH subscribes to appearance.theme, dashboard.* changes.
  • EVT subscribes to notifications.* changes to rebuild reminder schedules.
  • SCH subscribes to search.save_history changes.
  • All modules subscribe to locale.* changes to re-format displayed values.

3.1 Category Navigation Pattern

The Settings root screen is a flat list of category rows. Each row shows the category icon, name, and a brief descriptor (e.g. "Appearance — Dark mode, accent color, font size"). Tapping a category pushes a sub-screen with the category's individual settings. No accordion / expand-in-place on the root screen — navigation is always push.

The root screen has a persistent search bar at the top (delegates to SCH module). The search bar is always visible, not hidden behind scroll.

4.2 Account Deletion Flow

This is the most consequential action in the app. Account deletion must be designed to be impossible to trigger accidentally.
  • User taps "Delete Account". A full-screen warning screen replaces the settings screen (not a modal sheet).
  • Warning screen clearly lists everything that will be deleted: all salary records, all expenses, all debts, all goals, all archives, all settings.
  • User must re-authenticate with biometric or PIN.
  • User must type the phrase "DELETE MY DATA" exactly (localized equivalent in French/Arabic).
  • A final "I understand, delete everything" destructive button becomes enabled only after steps 3 and 4 are complete.
  • On confirmation: all rows in all financial tables are hard-deleted (an exception to the soft-delete rule — this is an explicit user-initiated wipe). The preferences, app_state, search.db, and the main finance.db files are deleted. The app resets to first-launch state.

Localization is not an afterthought — it affects date formatting, number formatting, RTL layout, currency display, and the order of settings groups themselves. All locale-dependent values are formatted at render time using the user's locale preference, never stored as formatted strings.

5.2 RTL (Right-to-Left) Support

When language = Arabic, the entire layout mirrors horizontally. Specific RTL rules:

  • Navigation arrows point left instead of right (back arrows point right).
  • Sidebar (if shown) appears on the right edge.
  • Text alignment flips to right-align for body text.
  • Icon positions mirror (left-icon rows become right-icon rows).
  • Charts and progress bars fill from right-to-left.
  • Number formatting stays LTR within RTL text (numbers are always displayed in the reading direction of the numeral system, not the surrounding text).
  • The locale.direction preference (computed, not user-set) is derived from the language selection and consumed by all UI components.

6.3 Theme Application Rules

10.3 Delete All My Data Flow

"Delete All My Data" is distinct from "Delete Account" (§4.2): it wipes all financial records but leaves the app in a configured state (profile, preferences, settings are retained). Use case: a user wants a clean slate without re-configuring appearance, language, or security settings.

  • Re-authentication required.
  • Warning dialog lists what will be deleted: all salary records, expenses, debts, goals, EMF records, archives, and search history. Settings, profile, and preferences are retained.
  • User must type "SUPPRIMER" (French) / "DELETE" (English) / "حذف" (Arabic) to confirm.
  • On confirmation: all financial transaction tables are hard-deleted. The salary_periods table is reset to a single new ACTIVE period. The search index is rebuilt (empty). Preferences are untouched.

10.4 Consent Management (Future)

When analytics or cloud features are introduced, a consent management layer is added. Consent is: explicit (requires affirmative action, not pre-checked), granular (per feature type), revocable (can be withdrawn at any time), and versioned (re-consent required when data use changes). The privacy.consent_version key tracks which consent version the user has accepted.

Settings Search

How preferences are indexed, surfaced, and navigated via the SCH module — making every setting findable in under two keystrokes.

15.1 Philosophy

Settings search is not a filter on a list — it is a first-class retrieval experience. Every preference, toggle, and action in the Settings module is indexed as a settings_entry entity in the global search index (search.db). Users never need to recall where a setting lives; they only need to recall what it does. The search bar is permanently visible at the top of the Settings root screen, not tucked behind an icon.

15.2 Integration with the SCH Module

Settings entries are owned by SET but served by SCH. SET registers all settings entries into the global search index on first launch and whenever the PreferenceSchemaRegistry is updated. The entity type is settings_entry.

15.4 Settings-Specific Search UX

The Settings module has its own embedded search entry point in addition to the global search overlay. Both use the same SCH infrastructure but the embedded bar is scoped to module:SET by default.

Settings Search Bar Behavior
  • Position: Pinned at the very top of the Settings root screen, above all category groups, below the screen title.
  • Scope: Searches settings_entry entities only by default. A "Search all of Finance Bag" chip appears below results to expand scope to the global SCH index.
  • Debounce: 100ms (tighter than global 150ms — settings index is small and results should feel instant).
  • Minimum query length: 1 character.
  • Behavior on match: The Settings category list is replaced by a flat result list. Each result shows the setting label, its category path (as breadcrumb), and its current value (if displayable).
  • Behavior on empty query: The full category list is restored immediately.
  • Navigation on tap: Deep links directly to the setting's screen and scrolls to anchor it in view with a 1.5s highlight pulse.

15.5 Recent & Frequently-Used Settings

Settings navigation patterns are tracked locally (never synced) to surface the settings a user changes most often.

Tracking rules
  • Every write to a preference key via PreferenceService.set() increments a usage counter for that key stored in app_state.
  • Recent: The 5 most recently modified settings keys, in reverse-chronological order. Shown as a "Recently Changed" section at the top of the Settings root screen when the search bar is empty and the user has at least one prior setting change.
  • Frequent: The top 3 settings by usage count over the past 30 days. Shown only if usage count ≥ 3. Displayed as quick-access chips below the search bar.
  • Exclusions: Developer options, internal state keys, and read-only entries are never tracked or surfaced.

15.6 Favorites

Users can long-press any setting row in search results or any settings screen to mark it as a Favorite. Favorites are stored as a JSON array at preference key set.favorites (a list of preference keys).

  • Favorites appear as a dedicated "Pinned Settings" section at the top of the Settings root screen, below the quick-access chips and above the category list.
  • Maximum 8 favorites. Attempting to add a 9th triggers an inline error: "You've reached the 8-favourite limit. Remove one to add another."
  • Favorites are sync_eligible = true — they travel with the user across devices if cloud sync is enabled.
  • Favorites are excluded from the required-reauth gate — revealing the existence of a preference as a favorite is not sensitive.

15.7 Search Within Global SCH

When a user types in the global search overlay (SCH module), settings entries are included in results under a "Settings" result group. The group respects the standard per-group default limit of 3 results, expandable. Each settings result shows the category breadcrumb as subtitle and the current value where safe to display (amounts are obscured if security.obscure_amounts = true).

Business Rules

Invariants that must hold true in every state of the system — these are non-negotiable constraints, not implementation suggestions.

IDRuleEnforcement layer
BR-SET-01 Default always exists. PreferenceService.get(key) must never throw or return null. If the key is absent from the preferences table, the value defined in PreferenceSchemaRegistry.default is returned immediately and the row is not written until an explicit set() call. PreferenceService
BR-SET-02 Unknown keys are rejected. PreferenceService.set(key, value) throws a PreferenceKeyError if the key does not exist in PreferenceSchemaRegistry. No freeform keys may be persisted outside the registry. PreferenceService
BR-SET-03 Type and range validation is mandatory. Every set() call runs the validation function defined in PreferenceSchemaRegistry before persisting. A value that fails validation is rejected with a PreferenceValidationError; the existing value is unchanged. PreferenceService
BR-SET-04 Destructive actions require explicit user confirmation. Any action marked destructive: true in the schema (factory reset, delete account, clear search history) must present a confirmation dialog or a typed confirmation before execution. No destructive action may be triggered programmatically without user initiation on the same app session. SET UI layer
BR-SET-05 Re-authentication gates are not bypassable. Any preference whose schema sets requires_auth: true must re-authenticate the user before displaying the current value or accepting a new value. A valid biometric or passcode session that is older than 60 seconds does not count as "just authenticated" — a fresh challenge is required. SET UI layer + PreferenceService
BR-SET-06 Device-specific preferences are never cloud-synced. Any preference with sync_eligible: false in the schema must not be included in any backup export, cloud sync payload, or cross-device preference propagation. This includes: security.biometric_lock, security.auto_lock_timeout, a11y.haptic_feedback, and all developer options keys. Backup service, sync service
BR-SET-07 PREFERENCE_CHANGED must always fire. Every successful set() call must publish a PREFERENCE_CHANGED event to the EventBus containing the key, old value, and new value. Modules that depend on a preference must react to this event, not poll. Firing the event is not optional even if old value === new value (allows forced re-applies). PreferenceService
BR-SET-08 Salary day is capped at 28. profile.salary_day accepts only integers 1–28. Any attempt to set a value of 29, 30, or 31 is rejected with a PreferenceValidationError. The UI must not present options above 28 in the salary day picker. PreferenceSchemaRegistry validation + SET UI
BR-SET-09 Quick actions list has a hard cap of 4. dashboard.quick_actions stores a JSON array of action IDs. Any array with more than 4 elements is rejected. If the user attempts to add a 5th quick action, the UI must present an inline message: "You can pin up to 4 quick actions. Remove one to add another." PreferenceSchemaRegistry validation + SET UI
BR-SET-10 Favorites cap is 8. set.favorites stores a JSON array of preference keys. Maximum 8. Any array with more than 8 elements is rejected. UI enforces this inline before writing. PreferenceSchemaRegistry validation + SET UI
BR-SET-11 Language change is immediate on restart only. Changing locale.language must not attempt a hot-reload or partial UI update. The change is written to the preferences table immediately, a toast informs the user "Language will apply after restart", and the app does not restart programmatically. The user chooses when to restart. SET UI, PreferenceService
BR-SET-12 Currency change is isolated to new entries. Changing currency.code does not retroactively convert historical amounts. All amounts in the database remain in their original centimes value. The currency symbol and formatting applied at render time changes immediately. A persistent banner must be shown for 72 hours after a currency change: "Currency display changed to [X]. Historical amounts have not been converted." SET UI, render layer
BR-SET-13 Settings index is always consistent with the registry. The SCH index for settings_entry entities must be rebuilt whenever the PreferenceSchemaRegistry changes (e.g., on app update). This rebuild is triggered by a REBUILD_SEARCH_INDEX event published by the SET module post-update. Index lag for settings entries must not exceed 5 seconds from app launch (BR-SCH-01 applies). SCH IndexManager, SET module init
BR-SET-14 Developer options are read-as-production in release builds without unlock. In production builds where the 7-tap unlock has not been performed in the current session, all developer option keys must return their production-safe defaults (e.g., dev.debug_logging = false). The 7-tap state is never persisted — it resets on every app launch. PreferenceService, SET UI
BR-SET-15 Factory reset is truly total. Factory reset must: (1) close all DB connections, (2) delete finance.db and search.db, (3) delete all backup files in the app's sandbox, (4) clear all entries from the preferences table, (5) clear app_state, (6) navigate the user to the Onboarding flow. The app must not retain any user-generated data after a factory reset completes successfully. SET UI, DB service

Edge Cases & Future Compatibility

Behaviors that must be explicitly defined to prevent undefined states — and forward-compatibility slots that keep the architecture open without requiring a redesign.

17.1 Edge Cases

IDScenarioRequired behavior
EC-SET-01 App is updated and a new preference key appears in PreferenceSchemaRegistry that has no row in the preferences table. PreferenceService.get() returns the registry default. No migration is required. The row is written lazily on first explicit set() call. The settings index is rebuilt at app launch to include the new entry.
EC-SET-02 App is updated and an existing preference key is removed from PreferenceSchemaRegistry (deprecated). The orphan row remains in the preferences table but is invisible to PreferenceService.get() (which consults the registry first). The orphan is purged by the next schema migration that explicitly lists the key for deletion. No runtime errors are raised on the orphan's presence.
EC-SET-03 The user changes the language to Arabic (RTL) while the app is open. The new locale is written immediately. A toast confirms: "Arabic will apply after you restart Finance Bag." The current session continues in the previous language. No partial RTL flip occurs mid-session. On next launch the full RTL layout is applied.
EC-SET-04 The user initiates a factory reset, but the app is backgrounded and killed by the OS mid-reset (after DB deletion but before clearing preferences). On next launch, the DB files are absent. The launch sequence detects missing finance.db and treats this as a first-time setup state. It proceeds through the Onboarding flow. The leftover preferences table rows will be overwritten or ignored during onboarding. A SPEC-DB-001 §16 EC-DB-10 (First Launch) applies.
EC-SET-05 The user changes security.obscure_amounts while the Dashboard is actively visible in the background stack. The PREFERENCE_CHANGED event fires immediately. The Dashboard listens for this event and re-renders all amount fields using the new setting. No navigation away-and-back is needed. The transition is instantaneous.
EC-SET-06 The user sets a quiet hours window where end time is before start time (e.g., start 22:00, end 06:00 — a cross-midnight window). The notification system interprets this correctly as a cross-midnight range. The quiet hours window spans 22:00 on day N to 06:00 on day N+1. The UI displays "10:00 PM → 6:00 AM (next day)" to make this explicit. No validation error is raised for end < start.
EC-SET-07 The user taps "Delete All Search History" while a search query is in progress. The deletion is deferred until the active query completes (the search_history write from the current query is committed first, then the full deletion runs). If the user taps Delete while no query is in flight, the deletion is immediate. The result set of the current query is not affected by the deletion.
EC-SET-08 The user changes appearance.font_size to 1.4× while viewing a data table with many columns. The PREFERENCE_CHANGED event fires. Screens that use the font size token re-render immediately. Tables that cannot fit all columns at 1.4× must respond by enabling horizontal scroll on their overflow container (already required by SPEC-DB-001 §12 and SPEC-SCH-001 §11). No content is truncated without a scroll affordance.
EC-SET-09 A backup restore overwrites the preferences table with a backup that contains deprecated keys or keys from a newer schema version than the current app. The restore process runs a preference migration pass after restoring. Keys not in the current registry are orphaned (EC-SET-02 handling). Keys in the registry but absent from the backup receive their current defaults. A post-restore settings audit event (SETTINGS_RESTORED) is published so modules can re-initialize if needed.
EC-SET-10 The user enables biometric lock on a device that has no enrolled biometrics. The SET UI queries the biometric availability API before presenting the toggle as enabled. If no biometrics are enrolled, the toggle is shown but tapping it presents a system-level prompt directing the user to enroll a biometric in device Settings. The preference value is not written to true until successful enrollment is confirmed. The toggle visually remains in its previous state.

17.2 Future Compatibility Slots

The following capabilities are intentionally not implemented in v1.0 but the architecture preserves slots for them. No redesign of the preference model, schema, or service layer should be needed to activate any of the following.

AI Personalization & Smart Recommendations
  • The usage_counter data in app_state for frequently-used settings is the foundation for an AI personalization layer that proactively suggests settings changes. Example: "You've dismissed the budget alert 12 times — would you like to increase your dining threshold?"
  • The PreferenceSchemaRegistry's category field allows a recommendation engine to group related settings and present them in context without knowing their individual keys.
  • AI recommendations must always be presented as suggestions, never applied silently. A suggestion that the user dismisses 3 times must never re-surface.
Cloud Preferences & Cross-Device Sync
  • All preferences with sync_eligible: true are ready for cloud sync. The preferences table schema (key, value_json, updated_at) maps naturally to a cloud document store keyed by user ID + preference key.
  • Conflict resolution strategy: last-write-wins on updated_at. For preferences that are sensitive to device context (e.g., dashboard.widget_order), a future per-preference conflict_strategy field can override the default.
  • Device-specific preferences (sync_eligible: false) are stored in a separate device profile document identified by device_id. They are synced per-device, never merged across devices.
Shared Family Settings & Business Profiles
  • The settings singleton model currently assumes one user per app installation. A future multi-profile architecture would introduce a profile_id scope on the preferences table (key + profile_id as composite PK).
  • Family profiles would share some preference keys (currency, locale) while keeping others independent (security, notifications). The sync_eligible field would be extended with a scope enum: device | user | family | org.
  • Business profiles require an additional preference tier for organization-level mandates (e.g., "force biometric lock = ON" for all users in an org). Org-level preferences would be read-only and displayed as "Set by your organization."
Wearables & Desktop Companion
  • Wearable companions (Apple Watch, Wear OS) require a subset of preferences — specifically security.obscure_amounts, appearance.theme, and notification preferences — to be mirrored to the watch. A future WearPreferenceAdapter subscribes to PREFERENCE_CHANGED and pushes sync_eligible watch-relevant keys via the companion API.
  • A desktop companion (macOS menu bar, Windows widget) would consume the same exported preferences JSON as the backup format uses, with an additional desktop-only preference namespace (desktop.*) handled identically to the existing model.
Contextual & Scheduled Preferences
  • A future "Scheduled Settings" feature would allow preferences to change on a schedule (e.g., "Enable hide amounts when away from home WiFi"). The preferences table would gain a schedule_rule_json column. PreferenceService would evaluate rules at access time, returning the schedule-overridden value without writing to the main value.
  • Context-aware preferences (e.g., auto-enable hide amounts when screen sharing is detected) would be driven by OS events forwarded to a ContextPreferenceEvaluator that sits between PreferenceService.get() and the preferences table.
Preference Audit & Compliance Export
  • For future regulatory compliance (GDPR, DPDP, etc.), the preferences change history must be auditable. The audit_log table already captures preference changes (action type SETTING_CHANGED). A compliance export would filter this table for all SETTING_CHANGED rows and produce a human-readable preference change history.
  • Consent preferences (privacy.consent_version, privacy.analytics_consent) must be included in any consent audit export with exact timestamps, the consent version presented at the time of acceptance, and the user action taken.
