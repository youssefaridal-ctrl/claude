SPEC-DBT-001 — Debt Management

Debt Management & Repayment Planner

Complete functional specification for the Debt Management module of Finance Bag. Defines debt types, data model, repayment strategies, planning engine with amortization formulas, payment tracking, analytics, and future scalability — no implementation code.

01 Core Philosophy

The Debt Management module is not a passive debt register — it is an active financial coach. Its purpose is to transform the anxiety of debt into a structured, motivating plan with a clear finish line.

🎯
Founding Principle Debt is not a permanent condition — it is a temporary obligation with a calculable end date. The application's job is to make that end date visible, credible, and achievable.

Design Tenets

TenetMeaningProduct Consequence
Radical TransparencyUsers must see the full cost of their debt — principal, interest, timeDashboard shows total interest to be paid, not just monthly payment
Motivating ProgressSmall wins matter psychologicallyVisual progress bars, milestone celebrations, "months saved" on extra payments
Strategy FlexibilityNo single repayment method works for everyone6 strategies supported; comparison view; user chooses
Coaching, Not JudgingMissed payments happen; shame makes it worseMissed payment handling is empathetic; focus on recovery, not penalty
Budget IntegrationDebt payments are a budget category (DEBT_PAYMENT, see SPEC-BUD-001)Monthly payment amounts auto-sync to budget; no double entry

Integration with the Broader App

  • Budget Engine (SPEC-BUD-001): Each debt's monthly payment appears as a DEBT_PAYMENT category in the budget. Updating a debt's monthly payment auto-updates the budget category.
  • Salary Module (SPEC-SAL-001): Debt-to-income ratio is calculated using the user's salary figure. The repayment planner factors in salary-day-aligned budget periods.
  • Financial Health Score: Total debt load and repayment regularity contribute 25 points to the health score defined in SPEC-SAL-001.

PAID Transition

When currentBalance reaches 0 (via payment entry or manual update), the app:

  1. Sets status = PAID and paidAt = today.
  2. Triggers a milestone celebration notification: "🎉 You paid off [name]! You saved X MAD in interest."
  3. Removes the linked budget category for the next period.
  4. Adds a "Debt-Free" entry to the financial history timeline.
  5. Recalculates the Financial Health Score (debt component improves).
  6. After 30 days in PAID status, prompts user to archive.

Strategy Recommendation Logic

The app recommends a strategy based on the user's profile:

  • Recommend Snowball if: user has 3+ debts AND the smallest balance debt will be paid off within 6 months at current payments.
  • Recommend Avalanche if: interest rate spread >5% between debts (highest vs. lowest rate).
  • Recommend Highest Payment if: DTI >40% and user wants to reduce monthly obligations quickly.
  • Show comparison view if: no clear winner — display "Strategy Comparison" with estimated savings for each approach.

07 Planning Engine & Formulas

The Planning Engine computes amortization schedules, payoff projections, and interest calculations. All computations are performed in centimes (integer arithmetic) and converted to display currency only at the presentation layer.

Standard Amortization

-- Monthly Payment (fixed-rate amortizing loan) P = currentBalance r = annualInterestRate / 100 / 12 (monthly rate) n = remainingMonths If r = 0 (interest-free): monthlyPayment = P / n If r > 0: monthlyPayment = P × [r × (1 + r)^n] / [(1 + r)^n - 1] -- Per-period interest and principal split: interestPortion(payment_k) = remainingBalance(k-1) × r principalPortion(payment_k) = monthlyPayment - interestPortion(payment_k) remainingBalance(k) = remainingBalance(k-1) - principalPortion(payment_k)

Months to Payoff (with extra payment)

totalMonthly = monthlyPayment + extraPayment If r = 0: monthsToPayoff = CEIL(currentBalance / totalMonthly) If r > 0: monthsToPayoff = -ln(1 - (currentBalance × r) / totalMonthly) / ln(1 + r) -- Result rounded up to nearest integer (CEIL) -- Guard: if totalMonthly ≤ currentBalance × r → impossible (interest accumulates faster than payments) -- Show warning: "Your payment does not cover monthly interest. Increase by X MAD."

Total Interest Cost

totalInterestPaid = (monthlyPayment × monthsToPayoff) - currentBalance interestSaved(extraPayment) = totalInterestPaid(0 extra) - totalInterestPaid(extraPayment) timeSaved(extraPayment) = monthsToPayoff(0 extra) - monthsToPayoff(extraPayment) -- months

Debt-to-Income Ratio Thresholds

DTI = totalMonthlyDebtPayments / monthlyGrossIncome × 100 DTI < 20% → 🟢 Excellent — healthy debt load 20% ≤ DTI < 36% → 🟡 Acceptable — monitor 36% ≤ DTI < 50% → 🟠 Concerning — reduce debt DTI ≥ 50% → 🔴 Critical — debt restructuring recommended

Strategy Payoff Sequencing Algorithm

Inputs: debts[] = all active debts (ordered by strategy priority) budget = totalMonthlyPayments (sum of all minimums + extra budget) extraBudget = budget - Σ(minimumPayments) (available to accelerate) Algorithm (monthly loop): 1. Apply minimumPayment to each debt → reduces each balance 2. Apply extraBudget entirely to debts[0] (highest priority) 3. If debts[0] is now paid: a. Mark debts[0] as PAID b. Roll debts[0].monthlyPayment + debts[0].extraBudget → extraBudget c. Remove debts[0] from queue d. Repeat from step 1 (snowball effect) 4. Advance month counter 5. Repeat until debts[] is empty Output: { payoffSchedule[], totalMonths, totalInterestPaid, payoffDate }

Recording a Payment

  1. User opens a debt and taps "Record Payment."
  2. App pre-fills: scheduled amount, due date, standard split (interest/principal).
  3. User confirms amount (or edits for partial/extra payment).
  4. App computes: principalPortion = paidAmount - interestPortion; new remainingBalance.
  5. Payment entry created; currentBalance updated on the Credit record.
  6. If LUMP_SUM: amortization schedule is recalculated (new monthly payment or new term, user chooses).
  7. Budget module notified: the DEBT_PAYMENT category marks this month's payment as "spent."

Payment History View

  • Chronological list, newest first.
  • Each entry shows: date, amount, principal portion, interest portion, remaining balance.
  • Color-coded status: green (PAID), orange (PARTIAL), red (MISSED), gray (REVERSED).
  • Running balance column (shows balance after each payment).
  • Cumulative interest paid to date shown at top of history.
  • Export to CSV (v1.0), PDF (v2.0).

14 Edge Cases

EC-01 Missed Payment
Payment due date passes without a recorded payment. System marks the Payment record as MISSED after midnight on the due date. Sends missed payment notification. Balance unchanged; interest continues to accrue daily. User is prompted to record the missed payment when they open the app. Recovery: user records late payment; history preserved including the MISSED entry.
EC-02 Early Payoff
User records a payment that reduces currentBalance to exactly 0 (or makes a lump sum ≥ remaining balance). System marks status = PAID, sets paidAt, triggers celebration notification, removes from budget. If paidAmount > currentBalance, the excess is refunded as a note: "You overpaid by X MAD — contact your lender for refund."
EC-03 Loan Refinancing
User refinances an existing loan: new interest rate, new term, possibly new lender. Flow: user opens the debt → "Refinance" action → enters new rate, new term, new lender. System closes the old debt (marks it ARCHIVED with a "Refinanced" note), creates a new debt with originalAmount = current balance of the old one and links them via a refinanceOf field. History of the old debt is preserved.
EC-04 Interest Rate Change (Variable Rate)
For variable-rate debts (interestRateType = 'variable'), the user can update the interest rate at any time. System recalculates: new monthly payment required to maintain the same end date; OR maintains the same payment and shows the new payoff date. User chooses which to recalculate. All future amortization projections use the new rate; past payments are unaffected.
EC-05 Partial Payoff
User applies a lump sum that doesn't pay off the debt but significantly reduces the balance. Two modes offered: (A) Keep same monthly payment → end date moves earlier. (B) Recalculate lower monthly payment → same end date, less per month. User selects preferred mode. Amortization schedule regenerated from current balance and chosen parameters.
EC-06 Payment Reversal
User recorded a payment in error (wrong amount, wrong debt). Reversal action available within 30 days of payment. Creates a REVERSED payment entry. Restores currentBalance to pre-payment value. Restores principalPortion to remaining balance. Budget category marks the reversal. Note: if the reversal crosses a salary period boundary, a warning is shown that it will affect a closed period's snapshot.
EC-07 Duplicate Debt
User adds a debt with the same name and lender as an existing active debt. System warns: "A debt named '[name]' from '[lender]' already exists. Is this a duplicate?" User can confirm it is a different debt (proceeds), merge with existing, or cancel. No auto-deduplication — user intent is required.
EC-08 Payment Exceeds Monthly Interest (Interest-Only Risk)
For variable-rate debts where the balance has grown, if monthlyPayment ≤ balance × monthlyRate, no principal is ever reduced (negative amortization). System detects this immediately on rate change or balance update and shows a critical warning: "Your current payment of X MAD only covers interest. Increase to Y MAD to make progress on principal." The debt is flagged with a ⚠️ icon in all lists.
EC-09 Archived / Deleted Debt
Archiving: debt is hidden from dashboard; payments can no longer be recorded; budget category is removed. Historical data and payment history are preserved. Soft-delete: same as archive but marks deletedAt; not recoverable via UI (admin recovery only). Neither operation removes historical payment records — they remain for analytics and lifetime interest calculations.
EC-10 Currency Change
User changes the app's primary currency (e.g. MAD → EUR). All debt amounts are displayed in the new currency using the stored exchange rate at the time of change. Historical amounts are frozen in their original currency and displayed with a footnote: "Original: 127,400 MAD." New payments recorded after the currency change use the new currency. Exchange rate stored on conversion event.
EC-11 Zero-Interest Debt
Family loans or BNPL at 0% APR. Amortization formula uses the r=0 branch: monthly payment = balance / remaining months. No interest portion on any payment. Total cost = original amount. All projections and reports remain accurate. Interest savings simulations are not available (always show 0 interest saved by extra payments, but months saved is still computed).
EC-12 No End Date (Credit Card / Open-Ended)
Credit cards have no fixed end date. endDate field is optional for CREDIT_CARD type. Payoff projection is computed dynamically based on currentBalance, monthlyPayment, and rate: payoffDate = today + monthsToPayoff(currentBalance, monthlyPayment, rate). The "end date" field in the UI is relabeled "Estimated Payoff Date" for credit cards and updates automatically as balance changes.

15 Automation

Automatic Repayment Projections

Every time a payment is recorded, the full amortization schedule for that debt is recalculated and stored as a projection cache. The cache is invalidated and rebuilt when: any payment is recorded, the interest rate changes, extraPayment is updated, or the strategy changes.

Monthly Payment Auto-Generation

On each salary day (from SPEC-SAL-001), the system auto-generates pending Payment records for all active debts due in the upcoming period. These appear in the payment calendar as "Scheduled" and transition to PAID, PARTIAL, or MISSED based on user action.

Automatic Status Updates

Smart Repayment Recommendations

  • Strategy Switch Suggestion: If Avalanche would save >5,000 MAD vs. current strategy, the app shows a one-time banner: "Switching to Avalanche could save you 5,200 MAD in interest."
  • Extra Payment Prompt: If the budget module shows unassigned balance ≥ 100 MAD and the user has active debts, a suggestion card appears in the dashboard.
  • Refinancing Alert: If the market interest rate (user-entered) drops >2% below the rate of the highest-interest debt, the app suggests: "You may save X MAD by refinancing [debt name] at [lower rate]."
  • Debt Consolidation Check: If the user has 3+ debts with rates above 10%, the planner surfaces a "Consolidation Scenario" showing the break-even analysis.

Future: AI Repayment Advisor (v2.0)

A conversational interface will answer questions like "How much will I save if I put this month's bonus toward my credit card?" or "Which debt should I focus on if I only have 500 extra MAD?" The AI calls the Planning Engine API (§7) directly and formats the result as a natural-language explanation with the underlying numbers.

Business Rules

Rule IDStatement
BR-DBT-01All monetary values are stored as integer centimes (×100). Display conversion to MAD (or other currency) occurs only at the presentation layer.
BR-DBT-02A debt's currentBalance may never be set to a negative value. If a payment would cause balance < 0, the excess is noted but balance is floored at 0 and the debt is marked PAID.
BR-DBT-03Deleting a debt is a soft delete only (deletedAt is set). Payment history is preserved permanently for audit purposes.
BR-DBT-04The monthly payment for a fixed-rate amortizing loan must always be ≥ the interest portion for that month. If the user enters a payment below this threshold, the system warns and suggests the minimum viable payment.
BR-DBT-05Extra payments (LUMP_SUM, EXTRA) are applied 100% to principal — never to interest. This is standard amortization behavior and is non-configurable.
BR-DBT-06The Planning Engine uses the current date's remaining balance as the starting point for all projections. It does not retroactively recompute past periods.
BR-DBT-07A debt linked to a budget category (isLinkedToBudget = true) automatically updates the budget DEBT_PAYMENT category when monthlyPayment changes. The user is notified of the budget impact.
BR-DBT-08Payment reversal is available for up to 30 days after the payment date. After 30 days, a reversal requires creating a manual adjustment note rather than undoing the original record.
BR-DBT-09The Debt-to-Income ratio uses gross monthly income (before tax) from the salary module. If multiple income sources exist, all are included in the income figure.
BR-DBT-10When a repayment strategy changes, all pending payment records are re-prioritized. Already-PAID records are never modified. The change takes effect from the next payment due date.
BR-DBT-11Credit cards with no fixed end date use dynamic payoff projection. The projected payoff date is recalculated every time a payment is recorded or the balance changes.
BR-DBT-12A payment due day is capped at 28 to ensure validity in all months (February alignment). If the user's actual due date is the 29th, 30th, or 31st, it is stored as 28 with a note.
