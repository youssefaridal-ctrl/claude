01 Core Philosophy

The Budget Engine is the financial brain of Finance Bag. It is the layer that transforms raw income into a purposeful, structured financial plan — turning a salary figure into a living budget that guides every spending decision throughout the month.

💡
Founding Principle Every amount of money entering the application must have a purpose. No income should remain unexplained. Every budget category must contribute to one of the user's financial objectives.

Five Design Tenets

TenetMeaningConsequence
Purposeful AllocationEvery dirham is assigned before the month beginsThe engine warns when income is unassigned
Simplicity FirstA first-time user can build a budget in under 3 minutesDefaults, templates, and auto-suggestions do the heavy lifting
Absolute FlexibilityPower users can define any structure they needCustom types, subcategories, custom rules, custom templates
Historical IntegrityPast months are immutable records of what was plannedSnapshot system; edits to past months require explicit intent
Forward CompatibilityThe engine must absorb future features without redesignExtensible data model; behavior flags not hard-coded types

Relationship to SPEC-SAL-001

The Salary module (SPEC-SAL-001) defines when income arrives and how much is available. This Budget Engine spec defines where that income goes. The two are tightly coupled: the allocation engine reads the total income figure from the salary module and distributes it across categories.

Budget periods are salary-day-aligned (not calendar-month aligned) as defined in BR-01 of SPEC-SAL-001. This spec inherits that constraint.

02 Category Data Model

Each budget category is a rich entity with identity, visual, behavioral, and rule attributes.

Full Schema

BudgetCategory { -- Identity id UUID (primary key) name string (1–60 chars, required) description string (0–200 chars, optional) parentId UUID | null (null = top-level category) -- Visual icon string (single emoji, required) color HexColor (#RRGGBB, required) -- Classification type CategoryType (enum, required) tags string[] (max 10 tags, each 1–30 chars) -- Allocation allocationMethod 'percentage' | 'fixed' | 'hybrid' percentage number 0–100 (used when method ≠ 'fixed') fixedAmount number ≥ 0 (centimes; used when method ≠ 'percentage') -- Behavior flags isDefault boolean (shipped with the app; cannot be deleted) isLocked boolean (locked by user; cannot be deleted/hidden) isHidden boolean (excluded from dashboard view) isArchived boolean (inactive; not shown in active budget) isFavorite boolean (pinned at top of category picker) isTemplate boolean (saved as reusable template) isReusable boolean (can be duplicated across periods) -- Ordering sortOrder integer (0-indexed, ascending) -- Budget rules (optional) rules BudgetRule[] (see §8) -- Audit createdAt ISO-8601 datetime updatedAt ISO-8601 datetime archivedAt ISO-8601 datetime | null deletedAt ISO-8601 datetime | null (soft delete) }

Monthly Budget Allocation (period-specific)

The above schema defines a category template — the reusable definition. Each budget period stores its own snapshot of allocation values:

PeriodCategoryAllocation { id UUID periodId string (YYYY-MM format, aligns to salary day) categoryId UUID (references BudgetCategory) -- Computed from category template at period start, then overrideable: allocatedAmount number (centimes; computed = income × percentage OR fixedAmount) spentAmount number (centimes; sum of transactions in this category + period) -- Override flags (user manually edited this period's allocation) isOverridden boolean overrideNote string | null }
⚠️
Amounts vs. Percentages Percentages and fixed amounts live on the category template and define the default behavior. Actual money amounts for a specific period are always stored in PeriodCategoryAllocation, computed at period creation and then optionally overridden by the user.

03 Category Hierarchy

Categories support a two-level hierarchy: top-level parent categories and subcategories. This is intentionally shallow — deeper nesting produces complexity that defeats the purpose of a personal budgeting app.

Hierarchy Rules

  • Maximum depth: 2 levels. A parent can have subcategories. A subcategory cannot have its own subcategories.
  • A category can be one of three things: standalone (no parent, no children), parent (has at least one child), or child/subcategory (belongs to exactly one parent).
  • A parent cannot have a parentId — promoting/demoting categories adjusts this relationship.
  • Deleting a parent requires the user to choose: delete all children, promote children to top-level, or cancel.
  • Budget rollup: A parent category's allocated and spent amounts equal the sum of its children (when it has children). The parent row itself holds no direct transactions.

Example Hierarchies

🏠 Housing Essential • 30% ├── 🔑 Rent/Mortgage 25% ├── 💡 Electricity 2% ├── 💧 Water/Gas 1% └── 📡 Internet 2% 🛒 Food Variable • 15% ├── 🥑 Groceries 10% └── 🍽️ Restaurants 5% 💰 Savings Savings • 20% ├── 🛡️ Emergency Fund 10% └── 🎯 Financial Goals 10% ✈️ Vacation Standalone • 5%

Visual Representation in UI

  • Parent categories are displayed with a collapse/expand toggle.
  • Subcategories are indented under their parent with a connector line.
  • Progress bars on parent categories show aggregate spent vs. allocated.
  • Tapping a parent shows the breakdown of children.
  • A parent with no children is displayed as a standalone category.

State Rules

  • Default categories (isDefault = true) cannot be permanently deleted — only archived.
  • Locked categories cannot be renamed, recolored, reordered, or archived without unlocking first.
  • Hidden categories still participate in the budget calculation but do not appear on the main dashboard.
  • Archived categories are excluded from new budget periods. Historical snapshots retain their data.
  • Deleted categories are soft-deleted (deletedAt is set). Historical snapshot data is preserved via foreign key to the snapshot record, not the live category.

Merge Operation Detail

Merging is a destructive but reversible operation (within 7 days, via Undo). The flow:

  1. User selects 2+ categories of the same type.
  2. User selects the target category (the surviving one).
  3. App shows a summary: X transactions from A + B → target name.
  4. User confirms → source categories are soft-deleted; all their transactions get the target categoryId.
  5. Historical snapshot data is repointed to target for reporting continuity.

Split Operation Detail

Splitting creates new subcategories from an existing category:

  1. User selects a category to split.
  2. User defines 2–5 new subcategories (name, icon, color, % share of original).
  3. App proposes auto-categorization of existing transactions by keyword matching.
  4. User reviews and confirms. Original becomes the parent.

08 Budget Rules Engine

Each category may have zero or more budget rules that govern its behavior. Rules are enforced by the Validation Engine (§11) and drive alert generation.

Rule TypeDefinitionBehavior
MAX_AMOUNT Cannot spend more than X MAD in this category per period Enforced at transaction entry; shows remaining budget; triggers CRITICAL alert at 90% consumed
MIN_ALLOCATION Must allocate at least X% of income to this category Budget editor warns when allocation drops below threshold; cannot close period if below minimum
TARGET_PERCENTAGE Ideal percentage of income (non-enforced guide) Shown as a target line on allocation editor; health score bonus when within ±5% of target
FIXED_AMOUNT Always allocate exactly X MAD to this category Allocation engine treats this as a fixed commitment; subtracted from distributable income before percentage categories
WARNING_THRESHOLD Alert when X% of allocated budget is spent Default 75%; push notification sent; category turns yellow in UI
CRITICAL_THRESHOLD Alert when X% of allocated budget is spent Default 90%; push notification; category turns red; transaction entry shows warning banner
OVERFLOW_BEHAVIOR What happens when spending exceeds allocated amount Three modes: WARN (allow + warn), BLOCK (reject transaction), SILENT (allow silently for fixed costs)
UNUSED_BALANCE What happens to unspent budget at period close ZERO (disappears), CARRY_OVER (added to next period's allocation), REDISTRIBUTE (split to other categories)
CARRY_OVER_LIMIT Maximum carry-over amount (used with CARRY_OVER unused balance) Caps carry-over; excess goes to REDISTRIBUTE bucket
RECOMMEND_ALLOCATION Suggested allocation shown in the editor Shown as hint text; auto-fills on template application

Carry-Over Calculation

-- At period close for each category with CARRY_OVER: unspent = allocatedAmount - spentAmount carry = MIN(unspent, carryOverLimit ?? unspent) -- Next period: nextAllocation = baseAllocation + carry

Applying a Template

  1. User opens the budget editor and selects "Use Template."
  2. App shows a preview of the template's category structure and allocations.
  3. User confirms: "Apply template — this will replace current allocations."

10 Allocation Engine

The Allocation Engine is the computational core of the Budget Engine. It transforms income + category rules into concrete per-category amounts for a budget period. It recalculates instantly on every change.

Allocation Methods

MethodDescriptionFormula
PERCENTAGE Allocated amount = percentage of total income amount = totalIncome × (pct / 100)
FIXED Allocated amount = constant value regardless of income amount = fixedAmount
HYBRID Percentage applied to remainder after all fixed commitments are deducted amount = distributable × (pct / 100)

Complete Calculation Sequence

Step 1: Compute Total Income ──────────────────────────────────────────── totalIncome = salary + Σ(otherIncomeSources.amount) Step 2: Compute Fixed Commitments ──────────────────────────────────────────── fixedCommitment = Σ(categories where allocationMethod = 'fixed', fixedAmount) Step 3: Compute Distributable Income ──────────────────────────────────────────── distributable = totalIncome - fixedCommitment Constraint: distributable ≥ 0 → If distributable < 0: VALIDATION_ERROR "Fixed commitments exceed income" Step 4: Compute PERCENTAGE Category Amounts ──────────────────────────────────────────── For each category c where method = 'percentage': c.allocatedAmount = totalIncome × (c.percentage / 100) Step 5: Compute HYBRID Category Amounts ──────────────────────────────────────────── For each category c where method = 'hybrid': c.allocatedAmount = distributable × (c.percentage / 100) Step 6: Compute Carry-Over Additions ──────────────────────────────────────────── For each category c with CARRY_OVER rule from prior period: c.allocatedAmount += priorPeriod.carryOverAmount(c) Step 7: Compute Remainder ──────────────────────────────────────────── remainder = totalIncome - Σ(allCategories.allocatedAmount) Step 8: Handle Remainder ──────────────────────────────────────────── If remainder > 0 → Show "Unassigned: X MAD" warning If remainder = 0 → Budget is complete ✅ If remainder < 0 → VALIDATION_ERROR "Over-allocated by X MAD" Step 9: Rounding Correction ──────────────────────────────────────────── roundingDiff = totalIncome - Σ(round(allocatedAmount)) Add roundingDiff to the highest-priority PERCENTAGE category

Priority Order

When the allocation engine processes categories for rounding adjustments or distribution of a remainder, it follows this priority order:

  1. ESSENTIAL_EXPENSE (locked categories first)
  2. DEBT_PAYMENT
  3. TAX
  4. EMERGENCY_FUND
  5. FINANCIAL_GOAL
  6. SAVINGS
  7. VARIABLE_EXPENSE
  8. CUSTOM (sorted by user sort order)

11 Validation Engine

The Validation Engine runs on every allocation change, template application, category creation/edit, and period close. Errors block saving; warnings allow saving with confirmation.

VAL-001 · OVER_ALLOCATION
Trigger: Σ(percentage allocations) > 100%
Message: "Budget over-allocated by X%. Remove X MAD from your categories."
Action: Block save; highlight offending categories in red
VAL-002 · FIXED_EXCEEDS_INCOME
Trigger: Σ(fixed allocations) > totalIncome
Message: "Your fixed expenses (X MAD) exceed your income (Y MAD)."
Action: Block save; highlight fixed categories
VAL-003 · NEGATIVE_VALUE
Trigger: Any allocation, percentage, or fixedAmount < 0
Message: "Allocation cannot be negative."
Action: Block save; auto-reset to 0
VAL-004 · DUPLICATE_NAME
Trigger: Two active categories with the same name under the same parent
Message: "A category named '{name}' already exists."
Action: Block save; suggest auto-suffix "(2)"
VAL-005 · CIRCULAR_REFERENCE
Trigger: Category's parentId chain contains its own id
Message: "This would create a circular category hierarchy."
Action: Block; prevented at the data layer
VAL-006 · DELETE_MANDATORY
Trigger: User attempts to delete a default or locked category
Message: "This category cannot be deleted. You can archive it instead."
Action: Block delete; offer archive
VAL-007 · INVALID_PERCENTAGE
Trigger: Percentage value is NaN, Infinity, or outside [0, 100]
Message: "Percentage must be between 0 and 100."
Action: Block; clamp to valid range with warning
VAL-008 · UNDER_ALLOCATION
Trigger: Σ(all allocations) < totalIncome — some income unassigned
Message: "X MAD is unassigned. Consider adding it to Savings."
Action: Warn; allow save; show remainder in editor
VAL-009 · MIN_ALLOCATION_BREACH
Trigger: Category with MIN_ALLOCATION rule is allocated below its minimum
Message: "'{name}' requires at least X% allocation."
Action: Warn; block period close (not save)
VAL-010 · EMPTY_REQUIRED_FIELD
Trigger: Category name is blank or whitespace only
Message: "Category name is required."
Action: Block save; focus name input
VAL-011 · DEEP_HIERARCHY
Trigger: Attempt to nest a subcategory under another subcategory
Message: "Subcategories cannot be nested. Maximum depth is 2 levels."
Action: Block; show hierarchy rule
VAL-012 · MAX_CATEGORIES
Trigger: User has 200 active categories and attempts to create another
Message: "Maximum 200 active categories reached. Archive unused categories."
Action: Block create; guide to archive

12 Automation

The budget engine supports smart automation to reduce friction and help users build sustainable financial habits with minimal manual work each month.

Copy Previous Month

When a new budget period starts, the app offers a one-tap "Use Last Month's Budget" action that:

  • Copies all categories and their allocations (percentage or fixed) from the most recent period.
  • Recalculates fixed amounts against the new income (if income changed).
  • Preserves carry-over amounts from the previous period per the CARRY_OVER rule.
  • Excludes archived categories.
  • User reviews and confirms before the plan is activated.

Auto-Suggestion Engine

After 3 completed budget periods, the engine generates personalized allocation suggestions:

SignalAlgorithmOutput
Historical spending3-month rolling average per categorySuggested allocation ≈ average spend + 5% buffer
Consistent overspendCategory exceeded budget ≥ 2 of last 3 months"Consider increasing {name} by X MAD"
Consistent underspendCategory unused ≥ 50% for 3 months"Consider reducing {name} — you've used only X% on average"
Income changeSalary changed >5% vs last periodProportional reallocation of all PERCENTAGE categories

Auto-Create Monthly Plan

If enabled in settings, the app automatically creates a draft budget plan on salary day using the previous month's structure and auto-suggestions. The user receives a notification: "Your budget draft for this month is ready — review it." The plan remains a draft until the user confirms it.

Smart Round

The editor shows a "Balance to 100%" button that automatically distributes the remaining unassigned percentage across categories proportionally, or assigns it all to the highest-priority SAVINGS category.

Auto-Fill Recurring Fixed Costs

Categories with FIXED_AMOUNT rules and a history of identical monthly amounts are auto-filled each period without user input. The user sees them pre-populated and can override.

Category Prediction (Transaction Entry)

When the user adds a transaction, the engine predicts the most likely category based on:

  • Description keyword matching against historical transactions.
  • Merchant name pattern matching (e.g., "Marjane" → Groceries).
  • Recency weighting: categories used in the last 7 days rank higher.
  • Time of day / day of week patterns (e.g., Friday evening → Restaurants).

Prediction confidence threshold: show suggestion only if confidence ≥ 60%. Never auto-assign without user confirmation.

Future: AI Budgeting Assistant (v2.0)

A conversational assistant will accept natural-language budget instructions: "Move 5% from Entertainment to Savings" or "What's my highest spending category this month?" The allocation engine exposes a programmatic API that the AI assistant calls; the engine handles all calculation and validation.

13 Monthly Budget Snapshots

Every completed budget period produces an immutable snapshot — a frozen record of what was planned and what actually happened.

🔒
Immutability Guarantee Editing a previous month's budget must never modify another month. Every snapshot stands alone. This is a non-negotiable product invariant.

Snapshot Schema

BudgetSnapshot { id UUID periodId string (YYYY-MM, salary-day-aligned) version integer (increments on explicit edit) -- Period metadata startDate ISO-8601 date endDate ISO-8601 date totalIncome number (centimes) -- Frozen allocation state (JSON blob) categories SnapshotCategory[] -- Aggregate outcomes totalAllocated number (centimes) totalSpent number (centimes) totalSaved number (centimes) totalCarryOver number (centimes) -- Audit trail createdAt ISO-8601 archivedAt ISO-8601 | null editedAt ISO-8601 | null (set if user edits after archive) editNote string | null -- Health score at period close healthScore HealthScoreSnapshot } SnapshotCategory { categoryId UUID (reference; denormalized for history) name string (captured at archive time) icon string color HexColor type CategoryType allocationMethod string allocatedAmount number spentAmount number carryOverAmount number }

Snapshot Lifecycle

  1. Period Created: Draft snapshot created when salary day arrives; allocation plan loaded.
  2. Period Active: Snapshot is mutable (draft). Transactions accumulate. Allocations can be adjusted.
  3. Period Closed: On the next salary day (or manual close), the snapshot is sealed. archivedAt is set. The snapshot becomes immutable.
  4. Explicit Edit: If the user explicitly opens and edits an archived period, a new snapshot version is created. editedAt and editNote are set. The prior version is preserved for audit purposes.

Editing an Archived Month

The only valid reason to edit a past month is to correct a data entry error. The flow:

  1. User navigates to the archived month.
  2. User taps "Edit this month" — a prominent warning appears: "You are editing a closed period. This will not affect your current budget."
  3. User makes corrections and saves with a mandatory edit note.
  4. Snapshot version increments. Health score is recalculated. All derived reports are invalidated and recalculated.
📐
Storage Efficiency Each snapshot's categories array is stored as a compressed JSON blob (not normalized rows). This avoids table bloat for users with 60+ months of history while keeping reads fast (single-row fetch per period).

Report Generation Rules

Lazy Loading Strategy

  • Active period: loaded into memory at app start.
  • Last 3 periods: pre-fetched for fast report rendering.
  • Older periods: fetched on demand when user scrolls history.
  • Archived categories: excluded from initial load; fetched only when user opens archive view.

Business Rules Summary

Rule IDStatement
BR-BUD-01Total allocation across all active categories must not exceed 100% of total income. This is enforced by the validation engine at save time.
BR-BUD-02Default categories cannot be permanently deleted. They may be archived or hidden.
BR-BUD-03Every budget period is salary-day-aligned (inherits BR-01 from SPEC-SAL-001). Calendar months are never used as period boundaries.
BR-BUD-04A closed budget period's snapshot is immutable. Explicit edits create a new snapshot version; the original is preserved.
BR-BUD-05All monetary amounts are stored as integer centimes (×100). Display conversion happens at the presentation layer only.
BR-BUD-06Category hierarchy is limited to 2 levels. Subcategories of subcategories are not permitted.
BR-BUD-07Fixed allocations are subtracted from total income first. Percentage allocations apply to the remainder (hybrid mode) or to total income (percentage mode).
BR-BUD-08Unspent budget at period close follows the UNUSED_BALANCE rule of each category. Default is ZERO (no carry-over) unless explicitly configured.
BR-BUD-09Category prediction at transaction entry is a suggestion only. The engine never auto-assigns a category without user confirmation.
BR-BUD-10A parent category with subcategories holds no direct transactions. Transactions belong to leaf categories only.
