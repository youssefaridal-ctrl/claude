01

Overview & Architecture Mandate

Serves all modules SAL BUD DBT EMF GOL RMP DSH RPT

Every module specification written to date defines notifications, reminders, and automation triggers independently. This creates eight separate notification systems that duplicate logic, produce inconsistent behaviour, compete for the user's attention without coordination, and cannot be governed by a single preference model. This specification eliminates that fragmentation.

The Smart Event Engine (EVT) is the single notification, reminder, and automation layer for the entire application. Every user-facing alert, reminder, and background workflow is owned and executed by this engine. No other module delivers notifications directly.

🔔
Architecture mandate: After this specification is adopted, all notification-related sections in SPEC-BUD-001, SPEC-DBT-001, SPEC-EMF-001, SPEC-GOL-001, SPEC-RMP-001, SPEC-DSH-001, and SPEC-RPT-001 are superseded by SPEC-EVT-001. Those sections define what events exist; this spec defines how they are processed and delivered.

Three Core Concerns

EventsFacts that happened — immutable, timestamped records published by modules to the EventBus (e.g. BUDGET_THRESHOLD_REACHED, DEBT_PAYMENT_OVERDUE)
NotificationsMessages delivered to the user in response to events — push, in-app banner, in-app toast, badge update, or silent
AutomationsBackground workflows triggered by events or time conditions — snapshot rebuild, carry-over computation, dashboard refresh, analytics update

What the Engine Provides to Every Module

  • A single EventBus.publish(event) call — the module's entire notification responsibility
  • Global frequency caps, quiet hours, and DND enforcement — no module implements these independently
  • Deduplication — the same event published twice within 5 minutes is processed only once
  • User preference awareness — a user who disabled goal notifications never receives them, regardless of which module published the event
  • Delivery channel selection — the engine decides push vs. in-app vs. silent based on app state and user preferences
  • Audit trail — every event, notification delivery, and automation execution is logged

04

Publishing Protocol

Every module publishes events by calling EventBus.publish(payload). This is the only interface between a module and the notification system. The module is responsible for constructing the payload with correct fields; the engine is responsible for everything that happens after.

4.1 EventBus Interface

interface EventBus { // Primary publish method — fire-and-forget from the module's perspective publish(payload: EventPayload): void // Subscribe to event types (used internally by the engine's handlers) subscribe(types: EventType[], handler: EventHandler): Unsubscribe // Query the event log (for audit and deduplication lookups) getRecentEvents(type: EventType, entityId: string, withinMs: number): EventLogRow[] } type EventHandler = (event: EventPayload, logRow: EventLogRow) => Promise<void>

4.2 idempotencyKey Convention

The idempotencyKey field in EventPayload is the deduplication anchor. It must be deterministic — the same logical event always produces the same key. The engine uses this to detect and discard duplicates within a 5-minute window.

// Convention: 'MODULE-EVENTTYPE-ENTITYID-DATE' Examples: BUDGET_THRESHOLD_80 → 'BUD-BUDGET_THRESHOLD_80-period-2026-07-01' DEBT_PAYMENT_DUE_3D → 'DBT-DEBT_PAYMENT_DUE_3D-creditId123-2026-07-11' EMF_MILESTONE_REACHED → 'EMF-EMF_MILESTONE_REACHED-emf-1-LEVEL_2' GOAL_COMPLETED → 'GOL-GOAL_COMPLETED-goalId456-2026-07-11' FHS_SIGNIFICANT_CHANGE → 'DSH-FHS_SIGNIFICANT_CHANGE-2026-07-11' // Milestones that should only notify once ever use a permanent key (no date suffix): // GOAL_MILESTONE_PCT 100% → 'GOL-GOAL_COMPLETED-goalId456' (no date — fires once)

4.3 Module Publishing Examples

// Budget module — threshold reached EventBus.publish({ type: 'BUDGET_THRESHOLD_80', sourceModule: 'BUD', sourceEntityId: periodId, priority: 3, data: { categoryName: 'Food', utilizedPct: 83, allocatedAmount: 150000 }, idempotencyKey: `BUD-BUDGET_THRESHOLD_80-${periodId}`, occurredAt: Date.now() }) // Debt module — payment overdue EventBus.publish({ type: 'DEBT_PAYMENT_OVERDUE', sourceModule: 'DBT', sourceEntityId: creditId, priority: 1, data: { creditName: 'Visa', overdueAmount: 80000, daysOverdue: 2 }, idempotencyKey: `DBT-DEBT_PAYMENT_OVERDUE-${creditId}-${today}`, occurredAt: Date.now() }) // Goal module — contribution reminder (no entity action, just a due date) EventBus.publish({ type: 'GOAL_CONTRIBUTION_REMINDER', sourceModule: 'GOL', sourceEntityId: goalId, priority: 3, data: { goalName: 'House Down Payment', requiredAmount: 285000, daysUntilContributionDay: 2 }, idempotencyKey: `GOL-GOAL_CONTRIBUTION_REMINDER-${goalId}-${today}`, occurredAt: Date.now() })
05

Processing Pipeline

Every event published to the EventBus passes through a 6-step synchronous pipeline before reaching the delivery layer. If any step rejects the event, processing stops and the reason is recorded in event_log.skipped_reason.

5.1 Pipeline Steps

  1. Validation: Verify all required fields are present and type is a recognized EventType. Malformed payloads are discarded with an error log entry — they never reach the database.
  2. Persistence: Write the event to event_log with processed_at = null. This is the source of truth; all subsequent steps read from this row.
  3. Deduplication: Query event_log for any row with the same event_key within the last 5 minutes (or "ever" for lifetime-milestone keys). If found: set skipped_reason = 'DUPLICATE', mark as processed, stop.
  4. User Preference Filter: Load NotificationPreferences. If the user has disabled notifications for this module or event category: set skipped_reason = 'USER_PREF', allow automation handlers to still run, stop notification delivery.
  5. Frequency Cap Check: Count notifications sent in the last 24 hours (Section 10). If over the cap and event priority > 1: set skipped_reason = 'THROTTLED', stop notification delivery only — automations still run.
  6. Route: Send to Notification Engine (Section 6) and Automation Engine (Section 8) in parallel. Update processed_at = now.

5.2 Deduplication Window

// Standard events: deduplicate within 5 minutes isDuplicate = event_log.exists WHERE event_key = payload.idempotencyKey AND created_at >= now - 5_MINUTES_IN_MS // Lifetime milestone events (GOAL_COMPLETED, DEBT_FULLY_PAID, EMF_FULLY_FUNDED, // FHS_EXCELLENT_ACHIEVED): deduplicate forever isDuplicate = event_log.exists WHERE event_key = payload.idempotencyKey // no time window // Due-date events (DUE_DATE category): deduplicate within 24 hours // Prevents re-alerting after a quiet-hours deferral fires on the same day isDuplicate = event_log.exists WHERE event_key = payload.idempotencyKey AND created_at >= now - 24_HOURS_IN_MS AND skipped_reason IS NULL // prior delivery must have succeeded

5.3 Pipeline Execution Context

The pipeline runs synchronously on the calling thread for events published while the app is in the foreground. For background events (Expo BackgroundTask, scheduled checks), the pipeline runs on a background thread. The event_log write in Step 2 uses a WAL-mode SQLite transaction to prevent data loss if the app is killed mid-pipeline.

Notification Engine

The Notification Engine is responsible for constructing the NotificationDelivery record, selecting the appropriate delivery channel, and executing the delivery. It is invoked by the pipeline after all filters have passed.

6.1 Channel Selection Logic

selectChannel(event: EventPayload, appState: AppState): DeliveryChannel IF appState == 'FOREGROUND': priority == 1 CRITICAL → IN_APP_BANNER // interrupts the user priority == 2 HIGH → IN_APP_BANNER priority == 3 MEDIUM → IN_APP_TOAST // non-interrupting priority == 4 LOW → IN_APP_TOAST priority == 5 INFO → SILENT IF appState == 'BACKGROUND' OR 'KILLED': priority == 1 CRITICAL → PUSH // always push priority == 2 HIGH → PUSH // if push permission granted priority == 3 MEDIUM → PUSH // subject to quiet hours priority == 4 LOW → BADGE_ONLY // increment badge, no banner priority == 5 INFO → SILENT // no user-visible delivery // If push permission NOT granted: downgrade PUSH → BADGE_ONLY for priority 2–3 // CRITICAL push is attempted regardless — system may show it as critical alert

7.2 Reminder Lifecycle

  1. Creation: Reminders are created by module operations (e.g., adding a new debt creates DEBT_PAYMENT_REMINDER rows for that debt). Creation is idempotent — creating a reminder for an entity+type that already exists updates the existing row rather than inserting a duplicate.
  2. Scheduling: scheduled_for is set to the next fire time. next_fire_at mirrors this for recurring reminders.
  3. Firing: On fire: the engine publishes the corresponding EventType into the EventBus (e.g. GOAL_CONTRIBUTION_REMINDER event), then advances next_fire_at to the next recurrence. The reminder itself is not a notification — it becomes an event that flows through the pipeline.
  4. Snoozing: User snoozes → snoozed_until = now + snoozeDuration. Next check: if now < snoozed_until, skip. Snooze duration options: 1 hour, 3 hours, 24 hours, 3 days.
  5. Dismissal: User permanently dismisses → dismissed_at = now. Recurring reminders with dismissed_at set are never fired again (soft-disabled). The row is never hard-deleted.
  6. Cleanup: When a source entity is soft-deleted (goal cancelled, debt archived): all its associated reminders are dismissed automatically (dismissed_at = now).

7.3 Reminder Check Algorithm

ON app_foreground OR timer_tick: now = Date.now() dueReminders = SELECT * FROM scheduled_reminders WHERE scheduled_for <= now AND dismissed_at IS NULL AND (snoozed_until IS NULL OR snoozed_until < now) AND deleted_at IS NULL ORDER BY scheduled_for ASC FOR each reminder IN dueReminders: EventBus.publish({ type: reminder.reminder_type_as_event, ... }) IF reminder.recurrence IS NOT NULL: reminder.next_fire_at = computeNextFire(reminder) reminder.scheduled_for = reminder.next_fire_at reminder.snoozed_until = null ELSE: reminder.dismissed_at = now // one-shot: auto-dismiss after firing

8.2 Automation Failure Handling

  • Automation failures are logged to automation_log with status = 'FAILED' and the error message
  • Failed automations are retried once, 30 seconds later, before being marked permanent failures
  • A failed automation never prevents notification delivery or other automations — they are independent
  • Critical automations (ADVANCE_PERIOD, PROPAGATE_ROADMAP_IMPACT) surface a silent in-app warning in the developer debug panel if they fail twice

10.1 Global Frequency Caps

10.2 Cap Check Algorithm

checkFrequencyCap(event: EventPayload): 'ALLOW' | 'THROTTLE' window24h = now - 24_HOURS_IN_MS sent24h = COUNT(event_log WHERE processed_at >= window24h AND notifications_sent > 0 AND skipped_reason IS NULL) IF event.priority == 1: RETURN 'ALLOW' // CRITICAL: never throttle IF sent24h >= 5: RETURN 'THROTTLE' // Global daily cap sentByModule24h = COUNT(... AND source_module = event.sourceModule) IF sentByModule24h >= 2: RETURN 'THROTTLE' // Per-module cap RETURN 'ALLOW'
⚠️
Throttling ≠ silent drop. A throttled notification is not lost. It is queued in the event_log with skipped_reason = 'THROTTLED'. The engine re-evaluates throttled events on the next app open; if the cap window has reset, the event is re-processed. This ensures no DEBT_PAYMENT_DUE notification is permanently missed due to an earlier notification burst.

10.3 Notification Batching

When multiple events fire in quick succession (e.g., period rollover triggering both BUDGET_PERIOD_ENDED and BUDGET_PERIOD_STARTED), the engine batches deliveries within a 500 ms window into a single notification where appropriate:

  • Multiple goal milestone events for different goals → batch into "3 goals reached new milestones"
  • Multiple budget threshold events for different categories → batch into "3 categories near budget limit"
  • BUDGET_PERIOD_ENDED and BUDGET_PERIOD_STARTED → single "New period started" notification with prior period summary
  • CRITICAL events are never batched — each must be individually actionable

13.2 Background Task Architecture

  • The reminder check runs as an Expo TaskManager background task, registered at app start, scheduled to run every 15 minutes when the app is backgrounded
  • The background task is allowed a maximum 30-second execution window by iOS — all operations must complete within this budget
  • Android: Expo BackgroundFetch API, minimum 15-minute interval

Edge Cases

EC-EVT-01
Push Permission Denied
If the user denies OS push notification permission: pushEnabled is set to false automatically. All push notifications downgrade to BADGE_ONLY (priority 2–3) or SILENT (priority 4–5). CRITICAL events are still attempted as push — iOS Critical Alert permission (separate from standard push) can be requested for overdue debt payments. The preferences screen shows a "Enable push notifications" prompt linking to OS settings.
EC-EVT-02
App Never Opened on a Due Date
If a DEBT_PAYMENT_DUE_1D reminder was scheduled but the app is never opened that day: iOS/Android push delivers the notification directly (if push permission granted and OS has the scheduled notification queued). If the reminder was engine-managed and not yet scheduled to the OS: on next app open, the engine finds it overdue and immediately publishes DEBT_PAYMENT_OVERDUE. No reminder is silently missed.
EC-EVT-03
Notification Burst from Period Rollover
At the start of a new budget period, multiple events may fire in rapid succession: BUDGET_PERIOD_ENDED, ADVANCE_PERIOD automation, BUDGET_PERIOD_STARTED, SALARY_RECORD_REMINDER, GOAL_CONTRIBUTION_REMINDER (if contributionDay = period start). The batching logic (Section 10.3) collapses these into at most 2 notifications: one for the period transition and one aggregated reminder. Frequency caps apply after batching.
EC-EVT-04
Duplicate Events from Concurrent Module Writes
If two rapid writes to the same entity (e.g., two goal contributions within 30 seconds) both publish GOAL_CONTRIBUTION_MADE: the deduplication check in Step 3 catches the second event within the 5-minute window. The first succeeds; the second is marked DUPLICATE. If the two events have different idempotencyKeys (different contribution IDs), both are processed — this is intentional, as they are genuinely distinct user actions.
EC-EVT-05
Entity Deleted After Reminder Scheduled
If a goal is cancelled after its GOAL_CONTRIBUTION_REMINDER rows exist: the DISMISS_GOAL_REMINDERS automation fires immediately on goal cancellation and sets dismissed_at on all associated reminders. If the reminder fires between cancellation and automation execution (race condition): the engine checks the source entity's status before delivery — if the entity is soft-deleted, the notification is suppressed and the reminder is dismissed.
EC-EVT-06
Quiet Hours Span Midnight
The standard default (22:00–08:00) spans midnight. The isQuietHours() function correctly handles this as an overnight window (Section 12.1 — the start > end branch). Deferred events are delivered at 08:00 the following morning, not at 22:00 on the same day. The deferredUntil timestamp is computed in device local time, not UTC.
EC-EVT-07
Automation Failure Cascade
If ADVANCE_PERIOD automation fails: the new period is not created. The engine retries once after 30 seconds. On second failure: logs FAILED status and publishes a SYSTEM-level anomaly event that surfaces as a "Finance Bag needs attention" in-app banner. The user is prompted to manually trigger the period advance from the budget screen. No downstream automations (GOAL_CONTRIBUTION_REMINDER creation, etc.) run until ADVANCE_PERIOD succeeds.
EC-EVT-08
All Notifications Disabled
If the user disables both pushEnabled and inAppEnabled: SILENT becomes the channel for all events. Automations continue to run — snapshot rebuilds, roadmap propagation, FHS history writes, and reminder checks all execute normally. The event_log still records all events for audit purposes. CRITICAL events (overdue payments) will surface the next time the user opens the app via the Dashboard Alert Center, which reads from event_log directly.
EC-EVT-09
contributionDay = 29, 30, or 31
Any reminder scheduled for a day-of-month that doesn't exist in the current month (e.g., contributionDay = 31 in February) is rescheduled to the last valid day of that month. The engine uses MIN(contributionDay, lastDayOfMonth) for all monthly reminder scheduling — consistent with BR-EVT-07 and the contributionDay cap-at-28 rule established in prior module specs.
EC-EVT-10
Throttled High-Priority Event Queue Grows Large
If a user receives 5 notifications in hour 1, and then 10 HIGH-priority events are throttled, and then the cap window resets: the engine processes the throttled queue in priority order, applying a fresh cap check. It will deliver up to 5 more notifications in the new 24-hour window. Events older than 24 hours in the throttled queue are discarded (they are stale) except for DEBT_PAYMENT_OVERDUE which is re-evaluated regardless of age.

Business Rules

BR-EVT-01
Modules Never Deliver Notifications Directly
No module other than EVT may call Expo Notifications APIs, schedule OS-level reminders, or show in-app banners. All notification-adjacent UX from other modules is limited to: (a) publishing events to EventBus, and (b) displaying module-screen-level inline status messages (e.g., "Payment overdue" label on a debt card). The centralized architecture is a hard constraint, not a recommendation.
BR-EVT-02
Events Are Immutable Facts
Once written to event_log, an event row may not be updated (except for processed_at, notifications_sent, automations_run, and skipped_reason which are set by the engine). Event rows are never hard-deleted within their 90-day retention window. This ensures a complete audit trail for debugging notification issues.
BR-EVT-03
CRITICAL Events Cannot Be Silenced by User Preferences
Priority 1 (CRITICAL) events always result in user-visible delivery, regardless of module preferences, category preferences, or in-app notification settings. The only mechanism that affects CRITICAL delivery is push permission (OS-level). CRITICAL events bypass quiet hours, frequency caps, and all throttling. This rule exists because DEBT_PAYMENT_OVERDUE and AVAILABLE_MONEY_NEGATIVE represent situations where user awareness has direct financial consequences.
BR-EVT-04
Idempotency Key Must Be Deterministic
The idempotencyKey in EventPayload must produce the same value for the same logical event, regardless of how many times the publishing code runs. Using UUID v4 or random values as idempotency keys is prohibited — they defeat deduplication. Keys must be built from stable identifiers: entityId, eventType, and a time boundary (date for daily events, periodId for period events, "forever" for lifetime milestones).
BR-EVT-05
Automation Runs Regardless of Notification Suppression
When an event's notification is skipped (THROTTLED, USER_PREF, QUIET_HOURS), automations registered for that event type still execute. A user who turns off budget notifications still gets their dashboard snapshot rebuilt when a budget event fires. Notification suppression only affects user-visible delivery — the underlying system state is always kept consistent.
BR-EVT-06
Notification Copy Is Engine-Owned
Notification titles and bodies are defined in the engine's copy template table (Section 6.2), not in module code. Modules provide structured data fields in EventPayload.data; the engine interpolates them. This ensures consistent tone, correct frequency of emoji usage, and centralised copywriting without module-level divergence.
BR-EVT-07
contributionDay and paymentDueDay Cap at 28
Any reminder scheduled on a day-of-month derived from a contributionDay or paymentDueDay uses MIN(day, 28) as the scheduling anchor, consistent with BR-GOL-08, BR-DBT-12, and BR-EMF rules established in prior module specs. This prevents reminders from being silently skipped in months shorter than the scheduled day.
BR-EVT-08
Reminder-to-Event Mapping
Every ReminderType maps to exactly one EventType when it fires. The reminder system is a scheduling mechanism; it does not define delivery logic. When a reminder fires, it publishes its mapped EventType into the EventBus — from that point, all standard pipeline logic (deduplication, preferences, caps, quiet hours) applies. A reminder firing is not a direct notification delivery.
BR-EVT-09
No Circular Automation Chains
An automation execution may publish new events to the EventBus (e.g., ADVANCE_PERIOD publishes BUDGET_PERIOD_STARTED). However, no event type may ultimately trigger an automation that publishes the same event type — this would create an infinite loop. The engine detects circular chains by checking if the event being published is already in the current execution call stack. Circular events are discarded and logged as ANOMALY.
BR-EVT-10
90-Day Event Log Is the Source of Truth for Audit
The event_log table is the authoritative record of all significant financial events that occurred in the application. If a user reports "I didn't receive a notification about my payment," the event_log is the first diagnostic source: was the event published? Was it deduplicated, throttled, or suppressed by quiet hours? The skipped_reason field answers each of these questions without requiring code instrumentation.

Future AI Scalability & Extensibility

16.1 AI Event Handler

The EventBus's subscribe() interface is designed for extensibility. An AI module can register a handler that receives every event and produces additional actions without modifying existing handlers:

  • An AI handler receives all events (or a filtered subset by type/priority) and can publish new events, schedule reminders, or trigger automations based on pattern recognition across the event history
  • AI-generated events use sourceModule: 'AI' (a new module added to the SourceModule enum) and are subject to the same pipeline processing as any other event
  • The event_log's 90-day history provides the training signal for on-device behavioral models

16.2 Intelligent Notification Timing

The engine is designed to accept a bestTimeToDeliver field on notifications in a future version. Current pipeline delivers at the moment the cap check passes; a future AI timing model would optimize delivery time based on historical engagement patterns (when the user typically opens the app, when they have historically taken action on similar notifications).

16.3 Adaptive Frequency Caps

Current frequency caps are static (Section 10.1). A future version replaces static caps with user-adaptive caps: if a user consistently dismisses GOAL_CONTRIBUTION_REMINDER notifications without acting, the engine automatically increases the suppression window for that reminder type. If a user acts immediately on BUDGET_THRESHOLD_80, the engine increases urgency for that type.

16.4 Cross-Module Event Correlation

The event_log stores all events with their sourceEntityId. A future correlation engine can detect patterns like "every month when the EXPENSE_LOG_REMINDER fires, a BUDGET_THRESHOLD_100 follows 3 days later" — and proactively notify the user earlier. The data structure already supports this; only the pattern-matching logic needs to be added.

16.5 Webhooks & External Integrations

The EventBus can be extended with an external delivery adapter layer. CRITICAL events could be routed to SMS or WhatsApp for users who prefer those channels. The EventPayload type is already channel-agnostic — the routing layer decides delivery, not the event itself. This separation ensures external integrations can be added without modifying any module's publishing logic.

16.6 Event Sourcing Upgrade Path

The current architecture stores events as audit logs (append-only, cleaned after 90 days). A future upgrade path leads toward full event sourcing: if event retention is extended to lifetime and all module state is rebuilt from events rather than stored directly, the application gains complete financial history replay, time-travel debugging, and crash recovery. The event schema (Section 2.1) is intentionally compatible with this future direction — no breaking changes are needed to move toward full event sourcing.
