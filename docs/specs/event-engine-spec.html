Overview & Core Philosophy

The Smart Event Engine (EVT) is the central nervous system of Finance Bag. Rather than allowing each feature module to independently manage its own reminders, notifications, and side-effects, all significant actions across the application are expressed as events that flow through a single, unified engine. The engine owns all delivery, scheduling, deduplication, automation, and audit logic.

Architectural Mandate: No module other than EVT may call Expo Notifications APIs, schedule OS-level reminders, or display in-app banners directly. All cross-module communication must flow through the EventBus. This is a hard constraint, not a recommendation.

1.1 Core Philosophy

Event-First Design. Every user action, system transition, and financial milestone generates an event. Events are the canonical record of what happened in the application. Notifications, automations, and analytics are consequences of events — not primary outputs of module code.

📡
Single Source of Truth
The event log is the authoritative record of all significant application activity. Any question about "what happened when" is answered by querying events, not module tables.
🔒
Modules Stay Pure
Feature modules (SAL, BUD, DBT, EMF, GOL, RMP, DSH, RPT) contain only business logic for their domain. They publish events; they never know what consumes them.
⚡
Consistent Processing
Deduplication, frequency caps, quiet hours, preference filtering, and retry logic apply uniformly to all events — not duplicated inside each module.
🔮
AI-Ready Architecture
The event stream is the training signal for future on-device behavioral models. The schema is designed to support AI handlers, predictive alerts, and adaptive workflows without breaking changes.
🌐
Offline-First
Events are persisted locally before processing begins. The engine operates entirely on-device. No network call is required for any event to be published, queued, or delivered.
🔁
Idempotent by Default
Every event carries a deterministic idempotency key. Publishing the same event twice has exactly the same effect as publishing it once. Duplicate processing is structurally impossible.

1.2 What the Engine Owns

  • All push notification scheduling and delivery
  • All in-app banner and toast delivery
  • All scheduled and recurring reminders
  • All automated side-effects (snapshot rebuilds, period advances, report generation)
  • The global event log and 90-day audit history
  • All frequency caps, quiet-hour enforcement, and preference filtering
  • All retry and failure recovery logic
  • The event rules engine (IF/THEN workflows)

1.3 What the Engine Does Not Own

  • Business logic for any feature domain (salary calculations, debt amortization, etc.)
  • UI rendering of any module screen
  • In-module inline status indicators (e.g., "Payment overdue" badge on a debt card — those are module UI)
  • User-facing financial data displayed in notification payloads — modules provide this data via EventPayload.data; the engine interpolates it into copy templates

Architecture Overview

The Event Engine is composed of nine distinct components. Each component has a single responsibility. Together they form the complete event-processing pipeline.

📤
1 — Event Producers
The 8 feature modules (SAL, BUD, DBT, EMF, GOL, RMP, DSH, RPT) plus the Scheduler and Rules Engine. Each producer calls EventBus.publish(payload) and returns immediately. Producers are fire-and-forget; they never await processing results.
🚌
2 — EventBus
The pub/sub message broker. Accepts EventPayload from producers, assigns it to the Event Queue, and notifies all registered subscribers. Operates synchronously for the publish() call (<5ms target); processing is asynchronous. The EventBus is a singleton initialized at app start.
📋
3 — Event Queue
An ordered, in-memory FIFO queue with SQLite persistence as overflow. Buffers events when the processing pipeline is busy. Priority 1 events skip to the front. The queue is drained by the Event Dispatcher. Maximum in-memory depth: 500 events before SQLite overflow.
🔀
4 — Event Dispatcher
Pulls events from the queue and routes them through the 6-step processing pipeline. Handles concurrency: at most 3 events process in parallel; CRITICAL events preempt processing slots. The Dispatcher calls the Notification Engine and Automation Engine in parallel after routing.
📖
5 — Event Registry
The schema catalog for all known EventTypes. Defines required fields, allowed data keys, valid sourceModules, and default priority for each type. Used by the Dispatcher for validation and by developers as a contract. New event types must be registered here before use.
📥
6 — Event Consumers
Three built-in consumer groups: Notification Engine (delivers to user), Automation Engine (executes side-effects), and Analytics Consumer (records behavioral data for RPT). Future consumers (AI Handler, Webhook Adapter) register via the same EventBus.subscribe() interface.
🗄️
7 — Event History Store
The event_log SQLite table. Append-only within the 90-day retention window. Stores full EventPayload, processing state, delivery counts, skipped reasons, and retry metadata. The primary diagnostic and audit tool for the entire application.
🏷️
8 — Event Priorities
A 5-level urgency system (1=CRITICAL → 5=INFO) that governs queue position, channel selection, frequency cap bypass, and quiet-hour behavior. Priority is set by the Event Registry default and can be elevated by the Rules Engine, never lowered by a producer.
🔄
9 — Retry & Recovery
Failed processing steps are retried with exponential backoff (1s → 2s → 4s → 8s → 16s, max 5 attempts). Events that exhaust retries move to the Dead Letter Queue (DLQ). CRITICAL events in the DLQ surface an in-app anomaly banner on next app open.

2.1 Data Flow

A
Module Action → EventBus.publish(payload)
A module completes an action (e.g., salary recorded) and calls EventBus.publish() with a fully-formed EventPayload. This call returns in <5ms. The module continues execution immediately.
B
EventBus → Queue Insertion
The EventBus validates the payload schema against the Event Registry, assigns a queue position (CRITICAL events jump to front), and enqueues. A lightweight event record is written to SQLite immediately for crash durability.
C
Dispatcher → 6-Step Pipeline
The Dispatcher pulls the next event, runs it through: Validation → Persistence → Deduplication → Preference Filter → Frequency Cap → Route. Each step can mark the event SKIPPED with a reason.
D
Parallel Consumer Execution
Notification Engine and Automation Engine execute in parallel. Notification Engine delivers to the appropriate channel; Automation Engine executes all registered automations for this event type.
E
Event Log Update → DELIVERED / SKIPPED / FAILED
The event record is updated with final state, delivery counts, automation counts, and skipped reason. The event is now available in Event History. Failed events enter the Retry & Recovery path.

4.2 The 6-Step Processing Pipeline

1
Validation
State: VALIDATING. The Dispatcher checks the EventPayload against the Event Registry schema: required fields present, EventType known, sourceModule valid for this type, priority within range, idempotencyKey non-empty and deterministic-format. Failure → DEAD_LETTERED immediately (schema errors are programming bugs, not transient failures).
2
Persistence
State: PERSISTED. Full event record written to event_log with processed_at = null. This write is synchronous and must succeed before any further processing. If the SQLite write fails (disk full, corruption), the event is held in memory queue and retried before entering the pipeline proper.
3
Deduplication
State: DEDUPLICATING. The engine queries event_log for any row with the same event_key (idempotencyKey) within the applicable deduplication window: 5 minutes (standard), 24 hours (DUE_DATE reminder types), indefinite (lifetime milestones: GOAL_COMPLETED, EMF_TARGET_REACHED, DEBT_FULLY_REPAID). If a match is found, the current event is marked SKIPPED with reason DUPLICATE. No further processing occurs.
4
Preference Filter
State: FILTERING. The engine reads NotificationPreferences (singleton row). If the event's module or category is disabled by the user, the notification delivery is suppressed (skippedReason = USER_PREF). Automations are not affected — they run regardless of preference settings. CRITICAL events (priority 1) bypass this filter entirely.
5
Frequency Cap Check
State: FILTERING (continued). Counts push notifications delivered in the last 24 hours (global cap: 5; per-module cap: 2). If caps are exceeded, the notification is throttled (skippedReason = THROTTLED). CRITICAL events bypass all caps. Throttled events are placed in the retry queue to be re-evaluated when cap window resets.
6
Route to Consumers
State: ROUTING. The Dispatcher calls Notification Engine and Automation Engine in parallel. The Notification Engine selects the delivery channel based on priority and app foreground/background state. The Automation Engine executes all registered automations for this EventType. Both consumers update the event record when complete.

4.3 Idempotency Key Convention

The idempotencyKey must be constructed deterministically. The standard pattern is:

// Format: MODULE-EVENTTYPE-ENTITYID-TIMEBOUNDARY // Daily events (fire once per calendar date) `${sourceModule}-${eventType}-${entityId}-${dateISO}` // Example: 'DBT-DEBT_PAYMENT_REMINDER_1D-debt_abc123-2026-07-15' // Period events (fire once per salary period) `${sourceModule}-${eventType}-${entityId}-${periodId}` // Example: 'SAL-SALARY_PERIOD_STARTED-period_xyz789-2026-07' // Threshold events (fire once per threshold crossing, per entity) `${sourceModule}-${eventType}-${entityId}-${thresholdLabel}` // Example: 'BUD-BUDGET_THRESHOLD_80-cat_food-80pct' // Lifetime milestones (fire exactly once per entity, ever) `${sourceModule}-${eventType}-${entityId}-lifetime` // Example: 'GOL-GOAL_COMPLETED-goal_holiday2026-lifetime' // PROHIBITED: UUID v4 or Math.random() as idempotency keys // These defeat deduplication and must never be used

EventBus & Event Registry

5.1 EventBus Specification

The EventBus is a singleton in-process pub/sub broker. It does not require a network or external message broker. All modules access it via the same module reference.

// EventBus API contract (no implementation) interface IEventBus { // Publish an event — returns in <5ms, processing is async publish(payload: EventPayload): void // Register a consumer handler for one or more event types subscribe( types: EventType[] | '*', handler: (EventRecord) => Promise<void>, options?: { priority?: number; moduleLabel?: string } ): UnsubscribeFn // Remove a consumer handler unsubscribe(fn: UnsubscribeFn): void // Replay unprocessed events from event_log after a crash replayPending(): Promise<void> // Drain the in-memory queue to SQLite (called on app background) flush(): Promise<void> }

5.2 Subscription Model

  • Consumers register with one or more specific EventTypes, or '*' to receive all events
  • Multiple consumers can subscribe to the same EventType (fan-out)
  • Subscription handlers receive the persisted EventRecord, not the raw EventPayload
  • Handlers are invoked asynchronously and must not throw — uncaught rejections are caught by the Dispatcher and logged
  • Handler execution order within the same EventType is not guaranteed unless an explicit priority is set in the subscription options

5.3 Event Registry

The Event Registry is a compile-time map of every known EventType to its schema definition. It serves as the canonical contract between producers and consumers.

type EventRegistryEntry = { type: EventType category: EventCategory // FIN | USR | REM | SYS | ANA | SEC | SYNC | AI | CUSTOM defaultPriority: EventPriority // 1–5 allowedSources: SourceModule[] requiredData: string[] // keys that must be present in EventPayload.data optionalData: string[] // keys that may optionally be present dedupWindow: '5min' | '24h' | 'lifetime' notificationTemplate: string | null // copy template ID; null = SILENT only automations: AutomationType[] // automations triggered by this event rulesTrigger: boolean // whether this event is evaluated against event_rules }

5.4 Queue Management

  • In-memory queue: ring buffer, max 500 slots. CRITICAL events always placed at front (head-insertion).
  • SQLite overflow: when in-memory queue depth ≥ 500, new events spill to event_log with state = QUEUED and are picked up by the Dispatcher on its next sweep.
  • Dispatcher sweep: runs every 250ms when events are pending; sleeps when queue is empty.
  • Crash recovery: on app start, EventBus.replayPending() queries event_log for all rows with state IN ('QUEUED','PERSISTED','RETRYING') and re-enqueues them.

6.4 Grouped Notifications

When multiple notifications are delivered within a short window (e.g., period rollover triggers salary reminder + budget setup reminder + goal reminder), the engine groups them into a single OS notification with a count badge.

  • Grouping window: events processed within the same 10-second window are candidates for grouping
  • Minimum group size: 3 notifications must accumulate before grouping activates
  • Group title: "Finance Bag — {{n}} updates"
  • Group body: highest-priority item's body text
  • CRITICAL events are never grouped — they are always delivered individually
  • Group summary: tapping the group notification opens the Dashboard, where each item is listed in the Alert Center

6.5 Notification History

All delivered notifications are recorded in event_log via the notifications_sent counter and the full event record. A notification inbox is derived from event_log queries — it is a view, not a separate table.

  • Notification inbox: events where notifications_sent ≥ 1 and priority ≤ 3, ordered by created_at DESC
  • Unread count: events in the inbox where created_at > last_session_started_at
  • Mark as read: setting a read_at timestamp on the event record (soft-read, not deletion)
  • Retention: follows event_log retention (90 days)

The Reminder Engine manages all time-based user alerts. Reminders are stored in scheduled_reminders, evaluated by the Scheduler, and fire by publishing their mapped ReminderEventType into the EventBus — from that point, all standard pipeline processing applies.

Key Principle: Reminders are scheduling mechanisms, not notification mechanisms. A reminder firing is not a direct notification delivery. It publishes an event, which then flows through the full pipeline (deduplication, preference filtering, frequency caps, quiet hours).

7.3 Snooze & Dismiss Behavior

  • Snooze options: 1 hour, 3 hours, "remind me tonight" (20:00), "remind me tomorrow" (same time +24h)
  • Max snooze count: 3 per reminder instance. After 3 snoozes, the reminder escalates priority by 1 level
  • Dismiss: sets dismissed_at on the reminder row. The reminder will not fire again in the current period. Recurring reminders reset at the next period/month cycle (dismissed_at is cleared during period advance)
  • Auto-dismiss: when the triggering condition is resolved (e.g., salary recorded → salary reminder auto-dismissed), the Automation Engine calls dismissRemindersByType(type, entityId)
  • CRITICAL reminders cannot be dismissed — only resolved by the underlying financial action

7.4 Smart Reminder Logic

The Reminder Engine adapts behavior based on user history (evaluated at fire time, not schedule time):

  • If the user has dismissed a GOAL_CONTRIBUTION_REMINDER 3 consecutive times without making a contribution, the next instance is escalated from MEDIUM to HIGH priority and the body copy adds "{{monthsSkipped}} months since your last contribution"
  • If EXPENSE_LOG_REMINDER fires but the user has already logged an expense today, the reminder is silently suppressed without counting against frequency caps
  • If DEBT_PAYMENT_REMINDER_7D fires and the payment is already marked as made, it is immediately dismissed
  • Location-aware reminders (future): schema supports a locationTrigger field in RecurrenceRule for geofence-based firing. Not implemented in V1.
  • Calendar integration (future): events in scheduled_reminders can be exported to device calendar via a future CalendarAdapter. The reminder engine fires its own notification independently of calendar.

Automation Engine

The Automation Engine executes automatic side-effects in response to events. Automations keep application state consistent without requiring the user to manually trigger recalculations. Every automation is registered in the Event Registry and runs in response to specific EventTypes.

Key Rule (BR-EVT-05): Automations always execute regardless of whether the event's notification was suppressed by user preferences, quiet hours, or frequency caps. Notification suppression only affects user-visible delivery — system state is always kept consistent.

8.2 Automation Execution Rules

  • Atomicity: each automation is a single logical operation. If an automation involves multiple SQLite writes, they are wrapped in a transaction. A partial write that fails rolls back completely.
  • Idempotency: automations must be safe to re-run. Before executing, each automation checks whether the work has already been done (e.g., RECORD_FHS_HISTORY checks for an existing row with today's date before inserting).
  • No circular chains: an automation may publish new events, but the engine detects and rejects any chain that would republish the same event type that triggered the current chain. Circular events are discarded and logged as SYSTEM_ANOMALY.
  • Retry on failure: failed automations are retried with exponential backoff (1s, 2s, 4s, 8s, 16s — max 5 attempts). Retry state is tracked in automation_log.
  • Result logging: every automation execution (success, failure, or skip) is written to automation_log with a summary.

8.3 Configurable Automation Hooks

Automations are registered in a configuration map rather than hard-coded in the Dispatcher. Adding a new automation requires only a new entry in the registry — no Dispatcher code changes. Future AI automations register via the same interface.

type AutomationRegistryEntry = { type: AutomationType triggers: EventType[] // EventTypes that activate this automation condition?: (event: EventRecord) => boolean // optional guard handler: (event: EventRecord) => Promise<AutomationResult> retryable: boolean timeout: number // ms; exceeded = treat as failure }

9.3 Rule Evaluation

  • Rules are evaluated after the ROUTING step for each event that has rulesTrigger: true in the Event Registry
  • Rules are evaluated in ascending priority order (RULE-001 before RULE-002, etc.)
  • Multiple rules can fire for the same event; all matching rules execute unless a prior rule's action was SUPPRESS_NOTIFICATION (which halts further rule evaluation for that event's notification path)
  • Rule actions that publish new events use the standard EventBus.publish() path — they do not bypass any pipeline step
  • Rule evaluation must complete within 10ms total; rules that exceed their budget are skipped and logged
  • Disabled rules (enabled = 0) are never evaluated

9.4 Custom Rules (Future)

V1 ships with the 15 built-in rules above as read-only entries in the event_rules table. A future user-facing Rules Builder will allow users to create additional rules with a constrained condition/action vocabulary. Custom rules use priority ≥ 100 to ensure built-in rules always evaluate first. Maximum 10 custom rules per user.

Scheduling Engine

The Scheduling Engine manages all time-based event firing. It is the only component allowed to create entries in scheduled_reminders. All reminder scheduling (including reminders created by automations) flows through this engine.

10.2 next_fire_at Computation

After each firing (or on initial schedule creation), the engine computes next_fire_at for recurring reminders:

  • Daily: next_fire_at = today + interval days, at timeOfDay in device timezone
  • Weekly: next_fire_at = next occurrence of dayOfWeek, at timeOfDay in device timezone
  • Monthly: next_fire_at = first day of next month + MIN(dayOfMonth,28)−1 days, at timeOfDay. If that day doesn't exist (Feb 30 → Feb 28), use last valid day.
  • Period-Based: next_fire_at = nextPeriodStart + offsetDays, at timeOfDay
  • After maxFires reached: sets deleted_at (soft-delete); reminder will never fire again
  • After endDate reached: same as maxFires — soft-delete after last firing

10.3 Timezone & DST Handling

  • All next_fire_at values are stored as UTC Unix milliseconds but computed from wall-clock time in the device's IANA timezone
  • On DST transitions, next_fire_at is recomputed using wall-clock time, not UTC offset arithmetic. A reminder set for 08:00 remains at 08:00 local time after DST — it is not shifted by one hour
  • The Scheduler reads the device's current timezone at each computation, not at schedule creation time. If the user travels to a different timezone, reminders will fire at the local equivalent of the stored wall-clock time
  • A future fixedTimezone flag on RecurrenceRule will allow pinning to a specific IANA zone regardless of device location

10.4 Missed Event Recovery

Events scheduled for a time when the app was terminated or the device was off are considered "missed." The Scheduler handles these on app start:

1
Boot Query
On app start, the Scheduler queries scheduled_reminders for rows where next_fire_at ≤ NOW() and dismissed_at IS NULL and deleted_at IS NULL.
2
Staleness Check
If next_fire_at is more than 48 hours in the past: the reminder is considered stale and is silently skipped (not fired). next_fire_at is advanced to the next valid recurrence. Exception: DEBT_PAYMENT_OVERDUE reminders are never stale — they always fire regardless of age.
3
Condition Re-evaluation
Before firing a missed reminder, the condition is re-evaluated (e.g., a missed DEBT_PAYMENT_REMINDER_1D that fires on app open: if the payment has since been made, the reminder is auto-dismissed instead of fired).
4
Batch Firing with Grouping
If more than 3 missed reminders are recovered simultaneously, they are published to the EventBus in priority order and subject to the grouping logic (Section 6.4). No more than 5 missed reminders are delivered as notifications in a single boot cycle.

10.5 Background Execution

The Scheduler relies on Expo TaskManager / BackgroundFetch for periodic evaluation when the app is not in the foreground. OS-scheduled local notifications (via Expo Notifications scheduleNotificationAsync) handle the most time-critical reminders (DEBT_PAYMENT_REMINDER_1D, SALARY_RECORD_REMINDER) — these fire at the OS level without requiring the app to be running.

  • OS-scheduled (most reliable): DEBT_PAYMENT reminders, SALARY_RECORD_REMINDER, PERIOD_END_REMINDER
  • BackgroundFetch-evaluated (best-effort): EXPENSE_LOG_REMINDER, WEEKLY_REVIEW_REMINDER, INACTIVE_USER checks
  • On-open only: analytics reminders (MONTHLY_REPORT_REMINDER) — acceptable to delay until next app open
  • Maximum 64 OS-scheduled local notifications (iOS limit). The engine tracks scheduled slots and prioritizes by urgency when approaching the limit.

11.2 Quiet Hours Logic

Quiet hours define a window during which non-critical notifications are suppressed:

  • CRITICAL (P1): always delivers, bypasses quiet hours entirely
  • HIGH/MEDIUM (P2–P3): notification is deferred — stored with a deferredUntil timestamp equal to quiet-hours end time, then delivered when quiet hours end. The event record is still written immediately.
  • LOW (P4): notification is discarded during quiet hours — badge and automations still run
  • INFO (P5): always SILENT; quiet hours not applicable
// isQuietHours() — handles overnight spans correctly function isQuietHours(prefs, nowLocalTime): start = HHMMtoMinutes(prefs.quietHours.startTime) // e.g. 22:00 = 1320 end = HHMMtoMinutes(prefs.quietHours.endTime) // e.g. 08:00 = 480 now = HHMMtoMinutes(nowLocalTime) // e.g. 23:30 = 1410 if start > end: // overnight span (22:00–08:00) return now >= start || now < end else: // same-day span (09:00–17:00) return now >= start && now < end // deferredUntil = today (or tomorrow if now >= start and overnight) // at endTime, in device local timezone

11.3 Weekend & Working Hours

  • Weekend suppression (future V2): a weekendBehavior preference will allow downgrading all P3/P4 notifications on weekends to SILENT
  • Working hours (future V2): a workingHours range will suppress non-critical notifications during work hours (e.g., 09:00–18:00), deferring them to end of working hours
  • V1 behavior: only quiet hours. All other hours are treated uniformly.

12.2 Retention Policy

  • Standard events: 90 days from created_at. Hard-deleted by the CLEANUP_OLD_EVENTS automation.
  • Lifetime milestones (GOAL_COMPLETED, DEBT_FULLY_REPAID, EMF_TARGET_REACHED): exempt from 90-day cleanup. Retained indefinitely in a milestone_log view (subset of event_log with extended retention flag).
  • Security events: 365 days retention.
  • Dead-letter queue entries: retained until manually resolved + 30 days.

12.3 Diagnostic Use

The primary diagnostic flow for "I didn't receive a notification about X":

  • Query event_log for the expected EventType + approximate date
  • If no row: the event was never published — module code issue
  • If state = SKIPPED, reason = DUPLICATE: the idempotency key matched a prior event — deduplicated correctly
  • If state = SKIPPED, reason = USER_PREF: user had that module's notifications disabled
  • If state = SKIPPED, reason = THROTTLED: frequency cap was active
  • If state = SKIPPED, reason = QUIET_HOURS: event fell inside quiet window and was LOW priority (discarded)
  • If state = FAILED: check automation_log for the error message
  • If state = DEAD_LETTERED: check dead_letter_queue for the failure chain

12.4 User-Facing Event Timeline

A future "Activity" screen derives its content from event_log. It is a read-only view — users cannot modify events. Grouping: events on the same calendar day are grouped under a date header. Privacy: payloadJson is not displayed raw — only the interpolated notification copy template (title + body) is shown. Events with priority = 5 (INFO / automations-only) are excluded from the user-facing timeline.

Retry applies to: notification delivery failures, automation execution failures, SQLite write failures. Schema validation failures (Step 1) are not retried — they indicate a programming error and go directly to DLQ.

13.2 Failure Scenarios

ERR-001
Push Notification Delivery Failure
Expo push delivery fails (network error, token expired, OS rejection). The engine retries with exponential backoff. After 3 failed push attempts, the notification downgrades to IN_APP_BANNER (delivered on next app open). Token expiry triggers a silent token-refresh event; the notification is re-queued with the new token.
ERR-002
Device Offline
All push scheduling is performed locally (Expo local notifications). The app does not require a network connection to schedule, fire, or process events. Push notifications that require the Expo Push Service are queued locally and sent when connectivity resumes. In-app notifications are unaffected by offline state.
ERR-003
Push Permission Denied
If the user denies OS notification permission: pushEnabled is set to false automatically. All PUSH deliveries downgrade to BADGE_ONLY (P2–P3) or SILENT (P4–P5). CRITICAL (P1) events attempt OS Critical Alert permission (separate from standard push on iOS). The Settings screen shows a "Enable push notifications" prompt linking to OS settings.
ERR-004
Duplicate Events from Concurrent Writes
If two module actions generate the same logical event within milliseconds (e.g., two rapid goal contributions): the deduplication step catches the second event if it shares the idempotencyKey within the 5-minute window. If the two events have genuinely different idempotencyKeys (different entity IDs or different time boundaries), both are processed — this is correct behavior, as they represent distinct actions.
ERR-005
Automation Failure Cascade
If ADVANCE_PERIOD automation fails after all retries: the new period is not created. The engine publishes SYSTEM_ANOMALY, which surfaces as a "Finance Bag needs attention" in-app banner on next open. No downstream automations (CREATE_DEBT_REMINDERS, CREATE_GOAL_REMINDER, etc.) run until ADVANCE_PERIOD succeeds. The user sees a manual "Retry period advance" option.
ERR-006
Entity Deleted After Reminder Scheduled
If a goal is cancelled after its GOAL_CONTRIBUTION_REMINDER rows exist: the DISMISS_GOAL_REMINDERS automation fires immediately on goal cancellation and sets dismissed_at. Race condition (reminder fires between cancellation and automation): the engine re-checks source entity status at fire time — if soft-deleted, the notification is suppressed and the reminder is auto-dismissed.
ERR-007
Event Queue Overflow
If the in-memory queue reaches 500 events (exceptional condition): all new events spill directly to SQLite. The Dispatcher switches from queue-drain mode to SQLite-sweep mode, processing events from the database in priority order. Once the backlog clears, the engine returns to normal in-memory queue operation.
ERR-008
Corrupted Event Queue
If the SQLite event_log table is unreadable on app start: the engine logs a catastrophic error and initializes a fresh event_log table. The corrupted table is renamed to event_log_backup_{timestamp} for potential recovery. All pending OS-scheduled notifications remain active (they are independent of the event_log). The user sees a "Some activity history was lost" in-app message.
ERR-009
Circular Automation Chain Detected
The engine detects circular automation chains by maintaining a call-stack set for the current processing chain. If an automation attempts to publish an event type already present in the current chain, the publish call is rejected and logged as SYSTEM_ANOMALY. No infinite loop can occur — the check is O(n) where n is chain depth, which is always small.
ERR-010
All Notifications Disabled by User
If both pushEnabled and inAppEnabled are false: delivery channel for all events is SILENT. Automations still execute normally — snapshot rebuilds, period advances, FHS history writes all run. CRITICAL events (DEBT_PAYMENT_OVERDUE, AVAILABLE_MONEY_NEGATIVE) surface on next app open via the Dashboard Alert Center, which reads from event_log directly rather than relying on notification delivery.

Security

14.1 Event Data Security

  • Sensitive payload fields (salary amounts, debt balances, account numbers) stored in payloadJson are subject to the same encryption-at-rest as all other SQLite data. If the app uses SQLCipher or Expo's SecureStore-backed encryption, the event_log is encrypted at the same level.
  • Notification copy displayed in the OS notification tray may contain financial amounts (e.g., "{{amount}} overdue"). Users who are concerned about financial data visible in the notification shade can enable obscureNotificationAmounts: true in preferences — amounts will be shown as "an amount" in notification copy while the full detail appears in-app.
  • Export of event history requires the same biometric/PIN authentication as accessing salary and debt data.

14.2 Permission Validation

  • All EventBus.publish() calls are validated against the Event Registry's allowedSources list. An event published with a sourceModule not in the allowed list is rejected with a schema validation failure (Step 1 of the pipeline).
  • Automation actions that write to module tables must go through that module's own write functions — automations cannot bypass module-level business rules (e.g., ADVANCE_PERIOD calls the SAL module's period advance function, not a raw SQLite write).
  • The Rules Engine cannot produce RuleActions that elevate priority above CRITICAL (priority 1) or that publish events outside the Event Registry.

14.3 Audit Logging

  • All authentication events (AUTH_SUCCESS, AUTH_FAILED) are written to event_log with 365-day retention regardless of global 90-day policy.
  • All DATA_EXPORT_REQUESTED events are logged with the export format and timestamp. This provides a complete record of when financial data left the device.
  • SENSITIVE_DATA_ACCESSED events are INFO-level (no notification) but always written to event_log for audit purposes.
  • Dead-letter queue entries are never automatically purged — they require explicit resolution by the system, preserving the complete failure audit trail.

14.4 Data Integrity

  • Event records are append-only within their retention window. The payloadJson, eventType, createdAt, and eventKey fields are immutable after the Persistence step. Only processing metadata fields (state, processedAt, notificationsSent, automationsRun, skippedReason) are updated post-write.
  • The idempotency key system ensures that even in the presence of app crashes, network retries, or backgroundFetch re-executions, no financial event is processed more than once. The deduplication window is the last line of defense against duplicate side-effects.

14.5 Rate Limiting

  • The EventBus.publish() interface does not enforce rate limits (it is an internal in-process call). Rate limiting at the notification level is handled by frequency caps (Section 6.6).
  • The Rules Engine enforces a per-event evaluation timeout of 10ms to prevent rule processing from becoming a DoS vector if rule conditions are complex.
  • Custom Events (future) are limited to 20 types per user and 100 custom events per day to prevent runaway custom automation chains.

15.2 Battery Optimization

  • Event batching: INFO-level (P5) events are batched and processed together in a single SQLite transaction rather than individually. Batch window: 2 seconds or 20 events, whichever comes first.
  • BackgroundFetch cadence: minimum 15-minute intervals (OS enforced on iOS). The engine avoids redundant work by checking the last-sweep timestamp before running reminder evaluations.
  • SQLite write coalescing: multiple automation writes that affect the same table within a single event processing chain are wrapped in a single transaction.
  • Dispatcher sleep: when the event queue is empty, the Dispatcher's polling loop backs off exponentially from 250ms to 5s idle sleep, reducing CPU wakeups.
  • OS notification slots: the engine pre-schedules OS local notifications for time-critical reminders during app-active sessions, eliminating the need for background wakeups to fire those reminders.

15.3 Throughput Capacity

  • The engine is designed for a personal finance app with typical event volumes of 10–50 events per day. The architecture supports up to 1,000 events per hour without degradation.
  • SQLite with WAL mode supports concurrent reads during event_log writes, ensuring Event History queries remain responsive during active event processing.
  • The dead-letter queue is expected to be empty in steady-state operation. An accumulating DLQ is a signal of a systemic issue requiring developer investigation.

15.4 Offline-First Guarantees

  • 100% of event processing occurs on-device. No event is ever lost due to network unavailability.
  • The event_log SQLite table is the crash-recovery source. If the app is force-killed mid-processing, events with state IN ('QUEUED','PERSISTED','RETRYING') are replayed on next launch via EventBus.replayPending().
  • OS-scheduled local notifications fire regardless of app state, ensuring time-critical reminders (debt payment, salary reminder) are delivered even when the app is never opened.
16

AI Readiness & Future Scalability

16.1 AI Event Handler

The EventBus's subscribe() interface is designed for extensibility. An AI module registers a handler that receives all events (or a filtered subset) and produces additional events, reminders, or automation triggers without modifying any existing pipeline logic:

  • AI handlers use sourceModule: 'AI' and publish events through the standard EventBus.publish() path
  • AI-generated events are subject to the full 6-step pipeline including deduplication, preference filtering, and frequency caps
  • The 90-day event_log provides the behavioral training signal for on-device models
  • AI handlers register with lower consumer priority than built-in handlers, ensuring they do not interfere with standard processing

16.2 Behavior Prediction Interface

The event history supports a future BehaviorPredictor service. The predictor reads from event_log to answer questions like "Is this user likely to miss their debt payment this month?" based on historical patterns. Predictions are expressed as AI Events published to the EventBus — the engine handles delivery and timing through its standard pipeline.

// Future BehaviorPredictor interface (no implementation in V1) interface IBehaviorPredictor { predictPaymentRisk(debtId: string, lookaheadDays: number): RiskScore predictSavingsRate(periodCount: number): Trend detectSpendingAnomaly(categoryId: string, currentAmount: number): AnomalyResult generateRecommendation(context: FinancialContext): Recommendation }

16.3 Intelligent Notification Timing

V1 delivers notifications at the moment the frequency cap check passes. A future AI timing model adds a bestTimeToDeliver field to the notification record. Rather than delivering immediately, the engine holds P3/P4 notifications in a "pending delivery" queue and releases them at the predicted optimal time (based on historical app-open patterns and past notification engagement). CRITICAL and HIGH priority notifications are never delayed by this mechanism.

16.4 Adaptive Frequency Caps

V1 uses static frequency caps (5 push/day total, 2 push/module/day). A future adaptive cap system personalizes these limits per user:

  • If a user consistently dismisses a notification type without acting, the suppression window for that type automatically increases (up to 72h)
  • If a user acts immediately on a notification type, the cap for that type is relaxed (up to 2× the default)
  • Adaptive caps are stored as per-type overrides in the notification_preferences table, added alongside the V1 fields without breaking changes

16.5 Cross-Module Event Correlation

The event_log's combination of sourceModule, sourceEntityId, and timestamps enables future cross-module pattern detection. Example: "every time EXPENSE_LOGGED fires on days 1–3 of a period, BUDGET_THRESHOLD_100 follows 5 days later in 80% of months." A future Correlation Engine publishes AI_SPENDING_ANOMALY_DETECTED proactively, before the threshold is crossed. No schema changes are required — the data is already there.

16.6 Personalized Financial Coaching

The AI_RECOMMENDATION_GENERATED event type (Section 3.8) carries a structured recommendation payload. In V1, this event type is defined but never published (reserved). In a future version, the BehaviorPredictor publishes coaching recommendations triggered by combinations of financial events (e.g., FHS_SIGNIFICANT_CHANGE + BUDGET_OVERSPENT + USER_INACTIVE_7D → coaching prompt about budget review habits). The notification copy template for this event type is designed to accept variable coaching content.

16.7 Webhooks & External Integrations

The EventBus can be extended with an external delivery adapter. CRITICAL events could route to SMS or WhatsApp for users who prefer those channels. The EventPayload schema is channel-agnostic — the routing layer decides delivery, not the event itself. External adapters register as EventBus subscribers, just like internal consumers, with no changes to the pipeline.

16.8 Event Sourcing Upgrade Path

The current architecture stores events as an audit log (append-only, pruned after 90 days). The upgrade path to full event sourcing requires only two changes:

  • Extend retention from 90 days to lifetime (or selectively for financial domain events)
  • Replace module state tables with a projection layer that rebuilds state from events on demand

The event schema (Section 2.2) is intentionally compatible with this direction. No breaking changes to EventPayload, EventRecord, or EventBus interfaces are required to move toward full event sourcing. The idempotency key system already guarantees that replaying events produces identical state.

16.9 Business Rules

BR-EVT-01
Modules Never Deliver Notifications Directly
No module other than EVT may call Expo Notifications APIs, schedule OS-level reminders, or show in-app banners. All notification-adjacent UX from other modules is limited to: (a) publishing events to EventBus, and (b) displaying module-screen-level inline status messages. This is a hard constraint, not a recommendation.
BR-EVT-02
Events Are Immutable Facts
Once written to event_log, an event row's core fields (eventType, sourceModule, sourceEntityId, eventKey, payloadJson, createdAt) may not be updated. Only processing metadata fields are mutable. Events within their retention window are never hard-deleted. This ensures a complete audit trail for debugging notification issues.
BR-EVT-03
CRITICAL Events Cannot Be Silenced by User Preferences
Priority 1 (CRITICAL) events always result in user-visible delivery, regardless of module preferences, category preferences, in-app notification settings, or quiet hours. The only mechanism that affects CRITICAL delivery is OS-level push permission denial. CRITICAL events bypass all frequency caps and throttling. This rule exists because DEBT_PAYMENT_OVERDUE and AVAILABLE_MONEY_NEGATIVE represent situations where user awareness has direct financial consequences.
BR-EVT-04
Idempotency Keys Must Be Deterministic
The idempotencyKey must produce the same value for the same logical event regardless of how many times the publishing code runs. Using UUID v4 or random values as idempotency keys is prohibited. Keys must be built from stable identifiers: entityId, eventType, and a time boundary (date for daily events, periodId for period events, 'lifetime' for lifetime milestones).
BR-EVT-05
Automations Run Regardless of Notification Suppression
When an event's notification is skipped (THROTTLED, USER_PREF, QUIET_HOURS), automations registered for that event type still execute. A user who turns off budget notifications still gets their dashboard snapshot rebuilt when a budget event fires. Notification suppression affects only user-visible delivery — the underlying system state is always kept consistent.
BR-EVT-06
Notification Copy Is Engine-Owned
Notification titles and bodies are defined in the engine's copy template table (Section 6.3), not in module code. Modules provide structured data fields in EventPayload.data; the engine interpolates them. This ensures consistent tone, controlled emoji usage, and centralized copywriting without per-module divergence.
BR-EVT-07
contributionDay and paymentDueDay Cap at 28
Any reminder scheduled on a day-of-month derived from contributionDay or paymentDueDay uses MIN(day, 28) as the scheduling anchor, consistent with BR-GOL-08, BR-DBT-12, and BR-EMF rules established in prior module specs. This prevents reminders from being silently skipped in months shorter than the scheduled day.
BR-EVT-08
No Circular Automation Chains
No event type may ultimately trigger an automation that publishes the same event type — this creates an infinite loop. The engine detects circular chains by checking if the event being published is already in the current execution call stack. Circular events are discarded and logged as SYSTEM_ANOMALY. Chain depth is always small (≤5 levels in the built-in system).
BR-EVT-09
Reminder Firing ≠ Notification Delivery
A reminder firing publishes its mapped EventType into the EventBus — from that point, all standard pipeline logic applies (deduplication, preferences, caps, quiet hours). A reminder firing is not a direct notification delivery. The reminder engine is a scheduling mechanism; the notification engine is the delivery mechanism. These responsibilities must not be conflated in implementation.
BR-EVT-10
event_log Is the Source of Truth for Audit
The event_log table is the authoritative record of all significant financial events. If a user reports a missing notification, event_log is the first diagnostic source: was the event published? Was it deduplicated, throttled, or suppressed by quiet hours? The skippedReason field answers each question without requiring code instrumentation. The 90-day retention window is the minimum acceptable audit window for this application.
